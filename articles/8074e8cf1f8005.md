## 開発したもの

### 管理者向け動画管理機能（PR #167）

資料側で先に実装した登録・編集・削除のパターンを、そのまま動画一覧に横展開しました。Admin ロールを持つユーザーにだけ「新規登録」「編集」「削除」のボタンを表示し、削除は確認モーダルを挟んだうえで論理削除（`is_deleted` を `true` に更新）します。

ポイントは、**登録と編集を 1 つのモーダル `VideoFormModal` で兼用**したことと、**Supabase クライアントをサーバー用／クライアント用に明確に分離**したことです。従来 `videos.ts` にまとめていたサーバー側処理を `videos-server.ts` にリネームし、ブラウザから呼ぶ CRUD は `videos-client.ts` に新設しました。

まず、登録／更新フォーム用の型は DB のテーブル定義から `Omit` で派生させています。

```typescript
// app/types/index.ts（抜粋）
type VideosTable = Database["public"]["Tables"]["videos"];

export type VideoInsertFormType = Omit<
  VideosTable["Row"],
  "id" | "created_at" | "updated_at" | "updated_by" | "is_deleted"
>;
export type VideoUpdateFormType = Omit<
  VideosTable["Row"],
  "created_at" | "updated_at" | "created_by" | "is_deleted"
>;
```

実際の DB 操作は `videos-client.ts` に集約し、登録・更新・削除を薄い関数として保ちました。スプレッド構文で受け取ったフォーム値をそのまま流し込み、更新時は `id` だけ分離して `update` 対象から外しています。

```typescript
// app/services/api/videos-client.ts
import { createClientSupabaseClient } from "./supabase-client";
import type { VideoInsertFormType, VideoUpdateFormType } from "@/app/types";

export async function registerVideo(params: VideoInsertFormType) {
  const supabase = await createClientSupabaseClient();
  const { error } = await supabase.from("videos").insert([
    { ...params, is_deleted: false, updated_by: params.created_by },
  ]);
  if (error) {
    console.error("動画の登録に失敗:", error);
    return { success: false, error };
  }
  return { success: true, error: null };
}

export async function updateVideo(params: VideoUpdateFormType) {
  const supabase = await createClientSupabaseClient();
  // idだけ分離し、残りをupdate対象に
  const { id, ...updateFields } = params;
  const { error } = await supabase.from("videos").update(updateFields).eq("id", id);
  if (error) {
    console.error("動画の更新に失敗:", error);
    return { success: false, error };
  }
  return { success: true, error: null };
}

export async function deleteVideo(id: number, userId: number) {
  const supabase = await createClientSupabaseClient();
  const { error } = await supabase
    .from("videos")
    .update({ is_deleted: true, updated_by: userId })
    .eq("id", id);
  if (error) {
    console.error("動画の削除に失敗:", error);
    return { success: false, error };
  }
  return { success: true, error: null };
}
```

`VideoFormModal` は `initialData` の有無で登録／編集を切り替えます。同じフォーム UI を使い回せるため、登録と編集で画面を二重に持たずに済みます。

```typescript
// app/(authenticated)/videos/components/VideoFormModal.tsx（抜粋）
const handleSubmit = async () => {
  if (!form.name || !form.url?.trim() || form.category_id === 0) {
    notifications.show({ title: '入力エラー', message: '動画名とURL及びカテゴリーは必須です', color: 'red' });
    return;
  }
  // URL形式チェック
  const urlValidation = /^https?:\/\/.+/.test(form.url);
  if (!urlValidation) {
    notifications.show({ title: '入力エラー', message: '正しいURLを入力してください', color: 'red' });
    return;
  }

  // 初期値あり：編集（更新）／初期値なし：新規登録
  const result = initialData
    ? await updateVideo({ ...form, id: initialData.id, updated_by: userId })
    : await registerVideo({ ...form, created_by: userId });

  if (result?.success) {
    notifications.show({
      title: initialData ? '更新完了' : '登録完了',
      message: initialData ? '動画が正常に更新されました。' : '動画が正常に登録されました。',
      color: 'green',
    });
    router.refresh();
  } else {
    notifications.show({ title: initialData ? '更新失敗' : '登録失敗', message: String(result?.error?.hint) || '不明なエラー', color: 'red' });
    return;
  }
  onClose();
};
```

### カテゴリーリンクとTOPへ戻る導線の改善（PR #165）

### GitHub Actions による型チェック・Lint・ビルドテスト（PR #168 / #162）

`.github/workflows` 配下に YAML を置くだけで動く GitHub Actions を使い、CI を整備し始めました。今回は型チェック（`tsc --noEmit`）と ESLint、そして別途ビルドテストを追加しています。**`app/**` 配下が更新されたときだけ走る**ように `paths` フィルタをかけており、ドキュメント修正などでは無駄に起動しません。

```yaml
# .github/workflows/typecheck.yml
name: TypeScript Type Check

on:
  push:
    paths:
      - "app/**"
      - "*.ts"
      - "*.tsx"
      - "tsconfig.json"
      - "package.json"
      - "package-lock.json"
  pull_request:
    paths:
      - "app/**"
      - "*.ts"
      - "*.tsx"
      - "tsconfig.json"
      - "package.json"
      - "package-lock.json"
  workflow_dispatch:

jobs:
  typecheck:
    runs-on: ubuntu-latest
    name: TypeScript Type Check
    strategy:
      matrix:
        node-version: [22.x]
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Setup Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: "npm"
      - name: Install dependencies
        run: npm ci
      - name: Run TypeScript type check
        run: npx tsc --noEmit
      - name: Run ESLint type-aware rules
        run: npm run lint
```

## 会議の様子

### 動画管理機能のコードレビュー

担当メンバーから、登録・編集・削除の 3 関数についての解説がありました。登録は一覧右上の「新規登録」ボタンからモーダルを開き、バリデーションとプルダウン選択を行います。編集・削除ボタンは管理者ユーザーにだけ表示され、削除は誤操作を防ぐために 2 段階の確認を挟みます。コード面では、Supabase にアクセスする API をクライアント用とサーバー用で区別して定義する方針が共有されました。

司会からは、Supabase クライアント側の実装でスプレッド構文を使ってプロパティを簡潔に組み立てている点や、`isAdmin` の真偽値でボタンの表示を出し分けている点について補足がありました。最初は不自然に感じる書き方でも、Web 系では定番のパターンであることをメンバー間で確認しました。あわせて、GitHub Copilot のエージェントパネルを使ったレビュー・修正の進め方も共有し、チーム全体で活用していく方針となりました。

### GitHub Actions によるテスト基盤の構築

テスト用の CI 整備は司会が主導して順次進めています。フレームワークのテストから、モックテスト、データベーステスト、静的解析、コンパイルチェック、未使用コードや `console.log` の検知、ユニット／コンポーネント／ビルド／E2E テストまで、段階的に追加していく計画です。要件定義として `testing.md` というテストドキュメントも用意しています。今回はビルドテストと型チェック、Lint を追加しました。

議論では以下のような論点が共有されました。

- **`console.log` の検知**：開発中に入れたログは基本的に不要なため、検知してワーニングを出す仕組みを検討。`error` や `warn` は別扱いで、`warn` は本番でも残す場合があるため対象外とする
- **実行トリガーの絞り込み**：`app` ディレクトリ配下が更新されたときに限定し、ドキュメント更新などでは起動しないようにする
- **作業分担**：未着手のテストが複数あるため手分けして進め、進捗はこの定例で調整する
- **失敗時の記録**：実行ログは GitHub の Actions タブに残るが、無料枠では古いものが消えていくため、テストが落ちたときだけ Webhook で Slack 通知して記録に残す案が挙がった

### 今後追加したい機能・権限

- **メンテナー権限の追加**：現状は「メンバー」と「管理者（Admin）」の 2 種類のみ。管理者はユーザー承認まで含む強い権限なので、資料・動画の追加／編集／削除だけができる **Maintainer ロール**を別途用意したい。ユーザーの承認・拒否は引き続き管理者限定とする。実現には Supabase の RLS で `insert` / `update` / `delete` 権限の設定追加が必要
- **記事ページ構想**：会員限定記事を掲載するブログ的なページの案。ヘッドレス CMS（microCMS など）の導入を検討
- **開発アプリの紹介ページ構想**：AI で作った簡易アプリやボードゲームアプリなどを、URL 付きで紹介する場としての活用案
- **ナビバーの領域重複バグ**：横幅を固定値で指定しているために画面サイズによってサイドバーとメインエリアが重なる問題、ボタンの反応範囲が広すぎる問題、カテゴリーリンクがポインターとして認識されない不具合を修正する

### ブランチ命名ルールの整備

ブランチ名の接頭辞を内容に応じて `bug/`・`docs/`・`refactor/` のように使い分けるルールを整備することになりました。「バグ修正なのに `feature/` だと気持ち悪い」という感覚を共有し、Wiki に明文化してチームへ周知します。

## 活用した技術

### Next.js App Router の Server / Client API 分離

データ取得や認証情報の参照はサーバーコンポーネント側で完結させ、必要な値だけを `props` でクライアントへ渡す構成です。今回の動画機能では、サーバー専用処理を `videos-server.ts`、ブラウザから呼ぶ CRUD を `videos-client.ts` に分け、サーバー用クライアントとクライアント用クライアントを別ファイルで管理することで、両者を取り違えるリスクを減らしました。

### 登録・編集を 1 つのモーダルで兼ねる設計

`VideoFormModal` は `initialData` を受け取るかどうかで「新規登録」と「編集（更新）」を切り替えます。`useEffect` でモーダルの開閉や `initialData` の変化を監視してフォームを初期化するため、同じ UI コンポーネントを両用途で使い回せます。

### TypeScript の `Omit` による派生型

登録・更新フォーム用の型は、テーブル定義の `Row` 型から自動採番カラムなどを `Omit` して作っています。登録時は `id` や `created_at` 等を除外し、更新時は `id` を残して `created_by` を除外する、といった具合に用途別の型を安全に導出できます。スキーマが変わってもフォーム側の型が自動で追従するのが利点です。

### GitHub Actions（CI）

`.github/workflows` に YAML を置くと、`push` や `pull_request` に応じて自動でジョブが走ります。`paths` フィルタで対象を `app/**` などに絞れば、関係のない変更でワークフローが無駄に起動するのを防げます。今回は `tsc --noEmit` による型チェックと ESLint を組み合わせ、マージ前に静的な品質チェックが走るようにしました。

### スプレッド構文によるオブジェクト合成

`{ ...params, is_deleted: false }` や `{ ...form, id: initialData.id, updated_by: userId }` のように、既存オブジェクトを展開しつつ一部のプロパティだけ上書き・追加する書き方です。フォーム値に DB 用の付加情報を足して登録・更新関数へ渡す場面で重宝します。更新時は `const { id, ...updateFields } = params;` のように分割代入で `id` を切り出し、残りをまとめて更新対象にしています。

## 総括

ver3.0 リリース後の開発は、「動くものを作る」から「設計を再利用して横展開する」段階に入ってきました。資料側で確立した登録・編集・削除のパターンを動画にそのまま展開できたこと、そして前回レビューで挙がった「役割判定は上位層で `boolean` にして渡す」という指針がさっそく実装に反映されたことは、レビューが積み上がってきた手応えです。

加えて GitHub Actions による CI の整備が始まり、型チェックや Lint が自動で回るようになりました。メンテナー権限の設計やブランチ命名ルールの整備など、開発プロセスそのものを整える動きも出てきています。
