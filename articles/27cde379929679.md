## 概要

本記事は、[チーム開発記録30：ローディングページの追加](https://zenn.dev/singularitylabs/articles/e8e1418847bec8)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回の定例では、ver5の目玉機能である**管理画面のメンバー承認機能**の実装が完了し、レビューを通過した状態でマージ前の最終確認が行われました。機能としては問題なく動く一方で、**権限チェックがブラウザ側で実行される実装になっている**というセキュリティ上の懸念が見つかり、「このままマージするか、直してからマージするか」をチーム全員で議論しました。

また、Googleカレンダー連携が「権限の壁」で行き詰まった経緯の共有、プロフィールへのSNSアカウント登録に向けた設計書更新とER図（Mermaid）の書き方レクチャー、そして「GitHub上のコメントだけでコミュニケーションが完結する状態を目指すべきでは」というレビュー運用をめぐる率直な意見交換など、開発プロセスそのものを見つめ直す回となりました。

## 開発したもの

### 管理画面のメンバー承認機能

このポータルサイトでは、Googleアカウントでログインした新規ユーザーは `status = 'pending'`（承認待ち）として登録され、管理者の承認を経て正式メンバーになります。これまでデータベースを直接操作していた承認作業を、管理画面（ダッシュボード）から行えるようにしました。

サーバーサイドでは、承認待ちユーザーの一覧をSupabaseから取得する関数を追加しています。

```typescript
// app/services/api/users-server.ts（抜粋）
/**
 * 承認待ちユーザー一覧を取得する
 */
export async function fetchApprovalUsers(): Promise<{
  data: PendingUserType[] | null;
  error: PostgrestError | null;
}> {
  const supabase = await createServerSupabaseClient();

  const { data, error } = await supabase
    .from("users")
    .select("id, display_name, email")
    .eq("is_deleted", false)
    .eq("status", USER_STATUS.PENDING);

  if (error) {
    console.error("Supabase 承認待ちユーザー一覧取得エラー:", error.message);
    return { data: null, error };
  }

  return { data, error: null };
}
```

一覧に表示された承認待ちユーザーはカード形式で並び、「承認」「否認」ボタンから確認モーダルを経てステータスを更新します。承認処理は `status` を `active` に更新するシンプルな実装です。

```typescript
// app/services/api/users-client.ts（抜粋）
export async function approveUser({
  userId,
}: {
  userId: number;
}): Promise<{ error: PostgrestError | null }> {
  const supabase = createClientSupabaseClient();

  const { error } = await supabase
    .from("users")
    .update({ status: "active", updated_at: new Date().toISOString() })
    .eq("id", userId)
    .eq("is_deleted", false);

  if (error) {
    console.error("Supabase ユーザー承認エラー:", error.message);
    return { error };
  }

  return { error: null };
}
```

会議では、当初サイドバー（クライアントコンポーネント）内で行っていた管理者権限のチェックがセキュリティ・パフォーマンスの両面で問題になると指摘されました（詳細は「会議の様子」参照）。最終的には、**サーバーコンポーネントであるレイアウト側で権限を判定し、結果だけを `isAdmin` としてサイドバーに渡す**形に修正されたうえでマージされています。

```tsx
// app/(authenticated)/layout.tsx（抜粋・修正後、エラーハンドリング省略）
export default async function AuthLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
  let isAdmin = false;

  const { authId, error: currentUserError } = await getServerCurrentUser();
  if (!currentUserError && authId) {
    const { role, error: roleError } = await fetchUserInfoByAuthId({ authId });
    if (!roleError && role) {
      isAdmin = checkAdminPermissions(role);
    }
  }

  return (
    <AuthGuard>
      <div className="sm:flex min-h-screen">
        <SideNav isAdmin={isAdmin} />
        <div className="flex-1 sm:ml-64 p-4">{children}</div>
      </div>
    </AuthGuard>
  );
}
```

なお、ダッシュボードには前回導入したスケルトンスクリーン方式の `loading.tsx` も用意されており、承認待ちカードの形をしたプレースホルダーが表示されます。前回の学びが早速新機能に活かされた形です。

### SNSアカウント登録に向けた設計書の更新

プロフィール画面にSNSアカウントのURLを登録できるようにする機能では、実装に先立ってデータベース仕様書と画面仕様書の修正が進みました。当初はSNS用の入力欄を1つだけ設ける案でしたが、レビューを経て**X（旧Twitter）・Facebook・Instagram・GitHub・ポートフォリオサイトの5項目を個別のカラムとして持つ**設計に固まりました。

```text
%% docs/database.md のER図（抜粋）: usersテーブルに追加されたカラム
erDiagram
    users {
        TEXT x_url "X（旧Twitter）アカウントURL"
        TEXT facebook_url "FacebookアカウントURL"
        TEXT instagram_url "InstagramアカウントURL"
        TEXT github_url "GitHubアカウントURL"
        TEXT portfolio_url "ポートフォリオサイトURL"
    }
```

会議では、データベース設計書の下部にあるER図もあわせて更新が必要なことが共有され、リードが画面を見せながらMermaid記法の仕組みをレクチャーしました。「他のカラムの書き方を真似て追加し、プッシュ後にGitHub上で図としてレンダリングされることを確認すればよい」という具体的な進め方まで確認しています。

## 会議の様子

### 「動く」だけでは終わらない — 承認機能へのセキュリティ指摘

メンバー承認機能はレビュアーの承認（Approve）まで完了していましたが、マージ直前にリードが確認したところ、**サイドバー内の権限チェックがクライアントサイドで実行される実装**になっていることが分かりました。サイドバーは全ページ共通のコンポーネントのため、「ポータルサイトにアクセスするたびに全ユーザーのブラウザ側で権限確認が走る」ことになり、セキュリティ上好ましくないうえに読み込みも遅くなります。

対応方針としては「一旦マージして追加修正する」「直してからマージする」の2択が議論され、レビュアーからは「Approveのステータスを一度戻し、リードが同じブランチに修正を積んでから反映するのが良いのでは」という提案がありました。リードは「担当メンバー自身が直したい気持ちもあるのでは」と気遣いましたが、担当メンバーの答えは明快でした。**「チームのプロダクトなので、全部自分で最後までやることにこだわりはない。設計はすでにマージ済みなので、自分で直すことよりver5に入れることを優先したい」**。リリース予定日を過ぎて再調整中という状況も踏まえ、リードが同一ブランチに修正をプッシュし、元のレビュアーが再レビューする進め方に決まりました。

レビュアーからも「機能的に動くことを優先して見てしまい、クライアント側で動かすべきでない処理を見逃した」という率直な振り返りがあり、**「動くこと」と「あるべき実装」は別物**という学びをチーム全体で共有する場になりました。

### 「GitHubだけで完結する」コミュニケーションを目指して

今回の定例で最も熱を帯びたのは、レビューコメントの残し方をめぐる議論です。発端は「気になる点があるので会議で話します」とだけ伝えてマージを保留したケースで、メンバーから「**何が要検討事項なのかを言語化して、必要な箇所にコメントを書くべきではないか**」という指摘がありました。会議に毎回出られないメンバーもいる中で、理由の見えない保留が続くと属人的になり、参加しづらくなるという問題提起です。

別のメンバーからも「せっかくGitHubを使っているので、**Slackや会議を見なくてもGitHub上だけでコミュニケーションが完結している状態が理想**。止まってしまう要因があるなら、分かった時点で明示されるべき」という意見が出ました。一方でリードからは「コメントへの要求水準が上がりすぎると、『面倒だからコメントしない』という萎縮につながるのが一番怖い」という懸念も示され、単純にルールを厳しくすればよい話ではないことも確認されました。

着地点として、**会議で口頭共有した指摘はその場でPRコメントに残す**（実際にこの会議中も、アロー関数の書き方やテンプレート重複の指摘をその場でコメント化しました）、**細かく書けない事情があるときは「なぜ今書けないか」だけでも一言添える**という運用が共有されました。コメントとして残すことが次の担当者のナレッジになる、という点でも意見が一致しています。

### カレンダー連携を阻んだ権限の壁

シンラボカレンダーの表示機能は、前回までメンバーが実装を進めていましたが、今回リードがタスクを引き取った理由が共有されました。実装自体は正しく、ローカルのビルドも通っていたのに、**画面に埋め込んだGoogleカレンダーが真っ白になる**という現象が発生。調査の結果、非公開カレンダーの表示には「Google Cloud側で認証情報（サービスアカウント）を発行し、それをGoogleカレンダーに登録し、APIで呼び出す」という一連の設定が必要で、これは**システム管理者権限を持つメンバーにしかできない作業**だったことが判明しました。

リードは「スキルの問題ではなく権限の問題。自分も知識不足だった」と振り返り、元の担当メンバーの実装は間違っていなかったことを明言しました。あわせて、コードレビューとして「関数宣言はアロー関数ではなく `function` で書く（チームの統一ルール）」「`import React` は現在のNext.jsでは不要なので削除する」という2点がその場でコメントとして残されました。

### サイドバー再構成と「集約ブランチ」談義

新しいタスクのアサインでは、まず「カテゴリー編集機能」が候補に挙がりましたが、「設計の選択肢が多く、既存実装の真似だけでは作れない。ガイド役が必要な難易度のタスクを、慣れていないうちに振るべきではない」という判断で見送りました。代わりに採用されたのが**サイドバーの構成見直し**です。プロフィールをホーム直下に移動し、「アプリ紹介一覧」「会員一覧」といった項目名を簡潔にする、という並び替えを新メンバーが担当し、提案者のメンバーがレビューを務めることになりました。

議論の途中では、「プロフィールをサイドバーから外す」タスクと「右上にプロフィールボタンを配置する」タスクを別々に進めた場合、**外す作業だけが完了した状態で本番リリースのタイミングが来たらどうするか**という問題が持ち上がりました。経験豊富なメンバーからは「複数の対応をまとめてリリースする必要があるときは、中間の**集約ブランチ**を作り、各作業ブランチはそこから切ってそこへマージする方法がある」という実務ノウハウが共有されましたが、今回は「そこまで複雑にせず、外す作業と追加する作業を1つの案件として別途まとめて管理する」というシンプルな解決策を選びました。

このほか、ブランチ名は `feature/`（機能追加）、`bug/`（バグ修正）、`refactor/`（リファクタリング）で始めるという命名規約や、PRタイトルは日本語で書くという運用も新メンバー向けに再確認されました。週末のもくもく会でver5リリースを行う予定も共有され、本番環境へのリリース承認は別のメンバーが担当します。

## 活用した技術

### Next.jsにおける権限チェックの「置き場所」

Next.js App Routerでは、コンポーネントは**サーバーコンポーネント**（サーバー側でレンダリング）と**クライアントコンポーネント**（`"use client"` を宣言しブラウザで動作）に分かれます。今回問題になったのは、管理者かどうかの判定をクライアントコンポーネント内で行っていた点です。ブラウザ側のコードはユーザーが自由に覗いたり改変したりできるため、権限に関わる判定をクライアントに置くのはセキュリティ上のリスクになります。また、全ページ共通のサイドバーで毎回データベースへの問い合わせが走るため、表示速度にも悪影響がありました。

修正後は、サーバーコンポーネントである `layout.tsx` で認証情報とロールを取得・判定し、`isAdmin` という真偽値だけをpropsとしてサイドバーに渡す構成になりました。**判定ロジックと機密情報はサーバーに置き、UIに必要な結果だけをクライアントに渡す**——App Router時代の権限管理の基本形といえる修正です。なお、管理画面ページ自体もサーバー側で `checkAdminPermissions` による二重のチェックを行っており、URLを直接叩かれても管理者以外は閲覧できません。

### Googleサービスアカウントによる非公開カレンダーの取得

Googleカレンダーを外部サイトに表示する場合、公開カレンダーなら埋め込みタグだけで済みますが、組織内の非公開カレンダーはそうはいきません。**サービスアカウント**という「人間ではなくプログラム用のGoogleアカウント」をGoogle Cloudで発行し、その認証情報（JSONキー）を使ってCalendar APIにアクセスする方式が必要になります。カレンダー側でもサービスアカウントに閲覧権限を共有する設定が必要で、アプリのコードだけでは完結しない点が今回のつまずきの原因でした。

実装では、認証スコープを `calendar.readonly`（読み取り専用）に絞り、本番環境ではJSONキーを環境変数から読み込む構成になっています。**権限は必要最小限に、秘密情報はコードに埋め込まない**というクラウド連携の定石を押さえた作りです。

### MermaidでER図を「コードとして」管理する

データベース設計書のER図（テーブル同士の関係を表す図）は、**Mermaid**というテキスト記法で書かれています。Markdownファイル内に `erDiagram` から始まるコードブロックを書くだけで、GitHubがブラウザ上で自動的に図としてレンダリングしてくれます。

作図ツールで描いた画像と違い、テキストなので**Gitの差分として変更履歴が残り、レビューもコードと同じ流れでできる**のが最大の利点です。今回のSNSカラム追加でも、「他のカラムの書き方を真似て数行追加し、プッシュしてGitHub上で図を確認する」という手順で、設計初心者のメンバーでも無理なくER図を更新できることが確認されました。ドキュメントとコードを同じリポジトリ・同じワークフローで管理する実践例です。

## 総括

今回は、メンバー承認機能という「管理者の運用を楽にする」機能の完成に加えて、その最終レビューで見つかったクライアントサイド権限チェックの問題を通じて、「動くこと」と「あるべき実装」の違いをチーム全体で学ぶ回となりました。Approve済みのPRに対しても懸念があれば立ち止まり、担当者・レビュアー・リードで役割を組み替えて最短でver5に載せる——チームとしての柔軟な判断が光りました。

また、レビューコメントの残し方をめぐる議論では、耳の痛い指摘も含めて率直な意見がぶつかりました。「GitHub上で完結するコミュニケーション」という理想と、「要求を上げすぎて発言が萎縮する」リスクの間でバランスを探る議論は、リモート中心のチーム開発ならどこでも起こりうるテーマです。結論を急がず「手探りでやりながら考える」と締めたのも、このチームらしい着地でした。週末のもくもく会でのver5リリースに向けて、開発は大詰めです。
