## 開発したもの

### データ取得処理の並列化（Promise.all）

資料・動画の一覧ページでは、表示にあたって「資料（動画）データ」「カテゴリーデータ」「ユーザー情報（権限確認用）」という複数のデータを取得しています。これまではそれぞれを順番に `await` していたため、前の取得が終わるまで次の取得を開始できず、無駄な待ち時間が発生していました。

```tsx
// 変更前：逐次に await しているため、前の取得が完了するまで次に進めない
const { data: documents } = await fetchDocuments();
const { data: categories } = await fetchCategoriesByType("documents");
const { id: userId, role } = await fetchUserInfoByAuthId({ authId });
```

これら3つの取得は互いに依存していないため、同時に走らせても問題ありません。そこで `Promise.all` を使い、3つの取得処理を並列化しました。

```tsx
// app/(authenticated)/documents/page.tsx（抜粋・変更後）
// 資料データ・カテゴリーデータ・ユーザー情報を並列取得して権限を確認
const [documentsResult, categoriesResult, userResult] = await Promise.all([
  fetchDocuments(),
  fetchCategoriesByType("documents"),
  fetchUserInfoByAuthId({ authId: authId }),
]);

const { data: documents, error: documentError } = documentsResult;
const { data: categories, error: categoryError } = categoriesResult;
const { id: userId, role, error: roleError } = userResult;
```

取得した結果は分割代入で取り出し、それぞれに対してこれまでどおりエラーハンドリングを行います。同じ修正を資料ページ・動画ページの両方に適用しました。独立した取得処理を同時に走らせるだけのシンプルな変更ですが、ページの初期表示が速くなるパフォーマンス改善です。

なおリリースに向けては、ヘッダーに表示されているアイコン（デプロイ先であるVercelのデフォルトアイコンのままになっていた箇所）を、シンラボのアイコンへ差し替える対応も予定しています。原因の見当はついており、リリース前に反映させる方針です。

## 会議の様子

### リリースに含める範囲をどう決めるか

ver4のリリース作業日を10月5日（日曜）に設定しているため、「どこまでをこのリリースに含めるか」が大きな論点になりました。

特に議論になったのが「設計だけが先に完成し、実装がまだのもの」の扱いです。レビューやアプルーブ自体は進めてよいものの、**承認済み（アプルーブ済み）であってもリリース日まではmainブランチへのマージを避ける**という方針で合意しました。「設計だけがマージされて、実装が本番に反映されない中途半端な状態は避けたい」「リリース直前に未確定の要素を増やすのはリスクになる」という考えからです。締め切りが決まっているときほど、未承認・未確定のものは次回に回すという判断は、前回のスコープ管理の議論とも一貫しています。

### レビュアーをどう決めるか

レビュー依頼のたびに「誰にレビューを頼むか」で悩む、という運用面の課題も話題になりました。

まず前提として、「レビュアーがその対象について十分な知見を持っているか（レビュアーの適正）」が重要で、適正が不十分だとレビュー内容も不十分になりやすい、という指摘がありました。そのうえで、設計レビューについては「実装ほど専門的な知識を要するわけではなく、メンバーであれば誰でも担当できそう」という整理に。

決め方については「指名制」「持ち回り制」「Slackのメンション機能で抽選」「ルーレット」など複数のアイデアが出ましたが、毎回悩むこと自体が無駄なので、**まずは順番を決めた持ち回り制で運用し、忙しいときはその回をスキップする**というシンプルな運用で試すことになりました。レビューは品質を担保する重要な工程である一方、運用の手間をいかに減らすかも継続には欠かせない、という気づきがありました。

### 承認機能は小さく分割する

管理者によるユーザー承認機能については、「一般ユーザーの承認／拒否を行う機能」だけにスコープを絞り、メンバーの退会時にデータを削除するといった処理は別のIssueとして切り出すことにしました。機能を1つに詰め込みすぎると要件がどんどん発散してしまうため、小さく分割して進めるという方針です。これも前回までに繰り返し共有されてきた、レビュー負荷とスコープを意識したチーム開発の進め方です。

このほか、テスト用のGitHub Actionsについては、出力されるログの日本語化や、既存の `console.log` を検出から除外する対応が進められており、引き続きレビューを経てマージしていく予定です。

## 活用した技術

### Promise.all による非同期処理の並列化

`Promise.all` は、複数の非同期処理（Promise）をまとめて受け取り、**すべてが完了するのを待ってから結果を配列で返す**JavaScript標準の機能です。互いに依存しない処理を `await` で逐次実行すると「直列」になり、各処理の待ち時間が積み上がってしまいます。`Promise.all` でまとめると処理が「並列」に走るため、全体の待ち時間を最も時間のかかる処理1つ分に近づけられます。

注意点として、`Promise.all` は渡したPromiseのうち**1つでも失敗（reject）すると全体が失敗扱い**になります。「一部が失敗しても他の結果は受け取りたい」という場合には `Promise.allSettled` を使うなど、状況に応じた使い分けが必要です。今回はまず標準的でわかりやすい `Promise.all` を採用し、より新しい書き方の導入は今後の課題としています。

### リリースマネジメントとスコープ管理

ソフトウェアのリリースでは、「リリース日を決めたら、それ以降は未確定の変更を新たに取り込まない」という考え方（いわゆるフィーチャーフリーズ）が品質の安定に役立ちます。今回の「アプルーブ済みでもリリース日まではmainにマージしない」という判断は、まさにこの考え方の実践です。リリース直前に不確定要素を持ち込まないことで、想定外の不具合やスケジュールの遅延を防ぎます。

### コードレビューの運用

レビュアーの選定は、コード品質に直結する一方で、チーム運用の負担にもなりがちです。「対象に対する知見（適正）」を踏まえつつ、持ち回り制のように**意思決定のコストを下げる仕組み**を用意することで、レビューを継続しやすくなります。誰がレビューしたかをPR上で明示できるよう、担当者を記録する運用も合わせて検討しました。

## 総括

ver4リリースを目前に控えた今回は、開発面では `Promise.all` によるデータ取得の並列化でパフォーマンス改善を仕上げつつ、会議ではリリースのスコープ管理・レビュアーの決め方・機能分割といった「進め方」の合意形成に多くの時間を使いました。

機能を作ることと同じくらい、「何を今回に含め、何を次回に回すか」「どうレビューを回すか」といった運用上の判断が、チーム開発の成否を左右します。こうした意思決定の過程をメンバー全員で共有しながら進められるのは、チームで開発する大きな価値だと感じます。次回はいよいよver4のリリースをお届けする予定です。
