## 開発したもの

### アプリ紹介ページのデータベース設計 — appsテーブルの追加

シンラボメンバーが開発したアプリ（AIアプリ、Next.js製のWebアプリ、GASによる自動化ツールなど）を紹介するページを新設するため、まずは設計書2点（`docs/database.md` と `docs/specification.md`）を更新するプルリクエストがマージされました。このチームでは、新しい機能を追加するときはフロントエンドのコードを書く前に設計書を更新するのが決まりごとになっています。

データベース設計書には、新たに `apps` テーブルが追加されました。アプリ名・詳細説明・カード表示用の短い紹介文・カテゴリー・アプリへのリンク・サムネイル画像に加えて、開発者ID（`users` テーブルと紐付け）や監査用の作成者・更新者カラム、論理削除フラグを持つ構成です。既存の `categories` テーブルも、カテゴリー種別に `apps` を受け入れられるよう拡張されています。ER図には次のようなリレーションが追加されました。

```text
（docs/database.md のER図より抜粋）
users ||--o{ apps : "1:N (developer_id)"
users ||--o{ apps : "1:N (created_by)"
categories ||--o{ apps : "1:N"
```

RLSポリシーは既存テーブルの方針を踏襲し、**閲覧は承認済みのログインユーザー全員、作成・更新は管理者またはメンテナーのみ、物理削除は禁止（論理削除のみ）**という設計です。閲覧ポリシーの条件は以下のように定義されています。

```sql
-- docs/database.md より抜粋：appsテーブルの閲覧ポリシー（SELECT）条件
EXISTS (
  SELECT 1 FROM users
  WHERE auth_id = auth.uid()
  AND status = 'active'
  AND is_deleted = false
)
AND is_deleted = FALSE
```

### アプリ紹介ページの機能設計

機能設計書（`specification.md`）には、画面の構成が定義されました。サイドバーに「アプリ紹介」メニューを追加し、`/apps` ページではアプリを**カード形式・1行4カードのグリッドレイアウト**で一覧表示します。カードは「ゲーム」「作業効率化」「学習」といった分類ごとにまとまり、ページ上部には各分類へのショートカットを配置（モバイルではプルダウン形式）。カードの「詳細」ボタンを押すとモーダルが開き、そこから「アプリを開く」ボタンで新しいタブでアプリに遷移する流れです。

```text
（docs/specification.md のカードデザインより抜粋）
+--------------------------+
|  アプリ名            [ ⋮ ] |
|                          |
|  短い紹介文（2行程度）      |
|                          |
|  カテゴリー: [ゲーム]       |
|     [    詳細    ]        |
+--------------------------+
```

管理者・メンテナー権限を持つユーザーには、カード右上に編集・削除用の3点リーダーメニューを表示します。なお、作業が大きくなりすぎるのを防ぐため、ポータルサイト上からアプリを登録する機能は今回のスコープには含めず、まずは表示機能から作る方針です。設計レビューは完了しており、現在は実装コードに着手中。近日中に実装のプルリクエストが出される予定です。

## 会議の様子

### Issue確認 — 「なくても進める」タスクの優先度をどう扱うか

冒頭のIssue確認では、各タスクの進捗と優先度が話し合われました。ユーザー承認画面は設計まで完了しており、担当メンバーが来週から実装を再開する予定です。会員の役割別表示は、担当メンバーが週末のモクモク会で設計から着手することになりました。

議論になったのは、停滞している「テスト用GitHub Actionsの構築」の扱いです。担当メンバーからは「**これがなくても開発は進められる。他のタスクへの影響はない**」という認識が示され、リードも「ないと作れないものではない」と同意。急かして中途半端に進めるのではなく、担当者が時間を確保できるタイミングを待つ「長い目で見る」判断となりました。なお、Jestのセットアップ自体はすでに完了しており、残っているのはテストをどう設計して書くかというフェーズです。

また、カンバン運用の整理も行われました。自己紹介欄の拡張やカードの横幅調整のように設計書の変更が不要なタスクは、設計カードを外してシンプルに管理することに。一方でテスト工程のカードについては「GitHub Actionsが自動でやってくれるから消してもよいのでは」という案に対し、「これから参加する人の理解のためには残しておいてもよいのでは」という意見があり、残す方向に落ち着きました。

### 設計書レビュー — 「半分はAIが書いている」

アプリ紹介ページの設計書について、リードが内容を解説しました。レビューでは、テーブル名をめぐる指摘が印象的でした。レビュー担当メンバーから「**`apps` ではなく `applications` にしませんか？ `documents`、`videos` と来ているのに略語なのは気持ち悪い**」という命名の一貫性に関する指摘があり、実装時に合わせて修正することになりました。既存の命名規則との整合性は、レビューだからこそ拾える観点です。

さらに、新メンバーから「この設計書はゼロから書いたのか、ひな形があるのか」という質問が出ると、リードは「**ぶっちゃけて言えば、半分はAIが書いています**」と制作の裏側を公開。「こういう機能を作りたい」と伝えて既存の設計書を参照させ、テーブル定義やポリシーの案を生成させたうえで、人間が手直ししてプルリクエストに出しているそうです。設計書の原型自体もAIに必要な要素を挙げさせて精査したもので、「2年前までは人間が全部考えていたが、今はAIが経験値をもとに使いやすい形式を提案してくれる」という時代の変化も共有されました。

### Git・プルリクエスト講座 — 「壊れることはないのでビビらずに」

今回、複数の新メンバーが「コーディングは終わったが、プルリクエストの出し方が分からない」という同じ壁に当たっていました。AIに聞きながら操作していたら意図しないリクエストになってしまった、最初にmainブランチを直接触ってしまった、といった初心者ならではのつまずきです。そこでリードが、VS Codeの画面を使ってGitの基本フローを一通り解説しました。

* **ブランチを切る**: mainから自分用のブランチを作る（VS Code左下の `main` 表示から作成可能）
* **ステージ**: 修正したファイルの差分を確認し「＋」で変更をステージに載せる
* **コミット**: 修正内容のメッセージを添えてローカルに記録する
* **プッシュ**: 「ブランチの発行」でGitHubのリモートサーバーに反映する
* **プルリクエスト**: GitHub上でmainへの反映を依頼する「指示書」を作り、レビュアーを指定する

解説の中では、「コミットは引っ越しのときに段ボールに詰める感じ。まだ送っていない手元の状態」というメンバーの例えも飛び出し、概念の理解が深まりました。「コミット後でも `git reset` で戻せる」「コミット先はmainではなく自分のブランチ」「作業前に**プル（Pull）でローカルのmainを最新化してからブランチを切る**」といった質疑も交わされています。

そして何より強調されたのは、**mainブランチには直接プッシュできないよう保護設定がされているので、壊れることはない。ビビらずにやってほしい**というメッセージでした。新メンバーがAIにコードやエラーを投げて質問しながら進めているという話にも「それで全然いい」と背中を押し、詰まったらガンガン質問する文化を確認して締めくくられました。

## 活用した技術

### Row Level Security（RLS）によるロールベースのアクセス制御

Supabase（PostgreSQL）のRow Level Securityは、テーブルの行単位でアクセス条件を定義できる仕組みです。今回の `apps` テーブルでは、「閲覧は承認済み（`status = 'active'`）のログインユーザー」「作成・更新は `role` が管理者かメンテナーのユーザーのみ」「DELETEは常に拒否して論理削除のみ許可」という3層のポリシーを設計しました。

アプリケーション側のコードで権限チェックを書く方法もありますが、RLSならデータベース自体がアクセスを拒否するため、実装漏れによる情報流出を防げます。既存の `documents` や `videos` テーブルと同じパターンを踏襲することで、レビューもしやすくなっています。

### Gitのブランチモデルとプルリクエスト

Gitでは、mainブランチ（本流）から作業用のブランチを分岐させ、そこで変更を積み重ねてから本流に合流（マージ）させるのが基本の開発スタイルです。変更は「ステージ→コミット」でローカルに記録され、「プッシュ」で初めてリモート（GitHub）に共有されます。プルリクエストは「この変更をmainに取り込んでください」という依頼と、レビューの場を兼ねた仕組みです。

このチームではmainブランチへの直接プッシュを制限しているため、初心者が操作を間違えても本体が壊れることはありません。「最悪クローンし直せば解消する」という安全網があるからこそ、新メンバーが失敗を恐れず手を動かせる環境になっています。

### 生成AIを活用した設計書ドラフト作成

今回の設計書のように、生成AIに既存ドキュメントを参照させて新機能のテーブル定義やセキュリティポリシーの草案を作らせ、人間がレビュー・手直しして仕上げる進め方は、実務でも広がりつつあるワークフローです。AIは過去の膨大な設計パターンをもとに「よくある構成」を素早く提案できるため、たたき台作りの時間を大幅に短縮できます。

一方で、`apps` か `applications` かといったプロジェクト固有の命名規則や、そのチームならではの運用事情はAIだけでは判断しきれません。**AIがたたき台を作り、人間のレビューで文脈を整える**という役割分担が、品質とスピードを両立させるポイントになっています。

## 総括

今回は、アプリ紹介ページという新機能の設計書がマージされ、データベース設計からRLSポリシー、画面レイアウトまでの全体像がチームに共有されました。テーブル命名の指摘のように、レビューを通じて設計の一貫性を高めていくプロセスも機能しています。「設計書の半分はAIが書いている」という共有は、AI時代のドキュメント作成のリアルな実践例といえるでしょう。

後半のGit・プルリクエスト講座は、新メンバーが実際につまずいたポイントから始まった、まさに実践的な学びの時間でした。ブランチ保護という安全網を用意したうえで「壊れないからビビらずに」と送り出す——初心者が安心して挑戦できる環境づくりは、このチーム開発が大切にしている文化です。技術スキルの差を前提に、質問しやすい雰囲気とその場での解説で埋めていく様子が伝わる回となりました。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
