## 開発したもの

### 説明文のマークダウン対応 — 共通コンポーネントMarkdownText

これまでポータルサイトの説明欄はプレーンテキスト表示だったため、「アプリ紹介の詳細説明でマークダウン風に書いても、見出しや箇条書きとして表示されない」という課題がありました。今回、`react-markdown` と `remark-gfm` を使った共通コンポーネント `MarkdownText` を新設し、アプリ紹介・動画・資料・会員の自己紹介など長文を扱う画面すべてに適用しました。

セキュリティ面では、`javascript:` などの危険なスキームを持つリンクを無効化する処理を組み込んでいます。

```tsx
// app/components/MarkdownText.tsx（抜粋）
export const MarkdownText = memo(
  ({ children, enableGfm = true, className, ...textProps }: MarkdownTextProps) => {
    return (
      <Text
        component="div"
        className={`prose prose-sm max-w-none ${className || ""}`}
        {...textProps}
      >
        <ReactMarkdown
          remarkPlugins={enableGfm ? [remarkGfm] : []}
          components={{
            // リンクの安全性チェック
            a: ({ ...props }) => {
              const href = props.href || "";

              // 危険なスキームまたは空のhrefをブロック
              const isDangerous =
                !href ||
                href.startsWith("javascript:") ||
                href.startsWith("data:") ||
                href.startsWith("vbscript:") ||
                href.startsWith("file:") ||
                href.trim() === "" ||
                href === "#";
              // ...（危険なリンクは無効化したテキストとして表示）

              // 安全なリンクのみ有効化
              return <a {...props} target="_blank" rel="noopener noreferrer" />;
            },
          }}
        >
          {children}
        </ReactMarkdown>
      </Text>
    );
  }
);
```

効果が分かりやすいのが動画詳細ページです。これまでは「各行がURLかどうかを判定してリンク化する」処理を自前で実装していましたが、マークダウン対応によりこのロジックごと置き換えられ、コードが大幅にシンプルになりました。

```tsx
// app/(authenticated)/videos/[id]/components/Template.tsx（抜粋・変更前）
<Text component="div">
  {String(video.description)
    .split("\n")
    .map((item, index) => {
      return (
        <div key={"description_" + index}>
          {
            // 概要欄の各行がURL形式かを判定する
            URL.canParse(item) ? (
              <Link href={item} rel="noopener noreferrer" target="_blank">
                {item}
              </Link>
            ) : (
              item
            )
          }
          <br />
        </div>
      );
    })}
</Text>
```

```tsx
// app/(authenticated)/videos/[id]/components/Template.tsx（抜粋・変更後）
<Text component="div" className="prose prose-sm max-w-none">
  <MarkdownText>{video.description}</MarkdownText>
</Text>
```

### Claude Codeのチーム共有設定

AI駆動開発をチームで進めるための土台として、Claude Code用の設定ファイル一式をリポジトリに追加しました。プロジェクト指示書となる `CLAUDE.md`（技術スタック・ディレクトリ構成・開発コマンドを記載し、コーディング規約はGitHub Wikiを参照する形式）、チーム共通の許可設定 `.claude/settings.json`、初心者向けの導入ガイド `docs/claude-code-guide.md` の構成です。

```json
// .claude/settings.json（抜粋）
{
  "permissions": {
    "allow": [
      "Bash(npm run:*)",
      "Bash(npm run build:*)",
      "Bash(npm run lint:*)",
      "Bash(git log:*)",
      "Bash(git diff:*)",
      "Bash(git status:*)",
      "mcp__serena__find_symbol",
      "mcp__context7__query-docs",
      "mcp__github__get_pull_request",
      "mcp__supabase__list_tables"
    ],
    "deny": []
  }
}
```

チーム共通の許可は**読み取り系の操作を中心**に絞り、ファイル編集やコミットなどの書き込み系は各メンバーがGit管理外の `.claude/settings.local.json` に追加する運用としています。

## 会議の様子

### サイドバー改修の「スコープ」を合わせる

サイドバー見直しの進捗確認では、担当メンバーから「資料や動画など各コンテンツの中身をカテゴリーに分類するところまで含めると、かなり大掛かりな作業になる。作業のやり方よりも、どう分類するかの相談が先ではないか」という問題提起がありました。

これに対してリードメンバーは、「このissueで想定しているのは、サイドバーの表題の文言と並び順を修正するだけ。各コンテンツの分類までは想定していない」と説明。認識のズレが解消され、担当メンバーからは「それならすぐできる」との回答がありました。カテゴリー分けなどの追加アイデアは、**別のissueとして起票し、定例ミーティングで「本当にやるべきか」をすり合わせてから着手する**という、チームの基本フローも改めて確認されました。作業を始める前にスコープを合わせることの大切さがよく分かるやり取りでした。

### issueテンプレートに「背景」を追加

issueの起票方法についても改善提案がありました。あるメンバーから「今のテンプレートの『概要』欄は書きにくい。**背景と修正箇所に分けたほうが書きやすい**のではないか」という提案です。一方で同じメンバーから「埋めるのが義務になると、issueを作ること自体が億劫になる」という懸念も示され、書きやすさと負担のバランスが論点になりました。

別のメンバーからは「背景や目的が書いてあると、**その目的に対して実装内容が合っているかを他の人が確認しやすい**」という賛成意見が出ました。チームで開発している以上、「なぜ変えたいのか」をある程度クリアにしておくべきだという点で合意し、最終的に「概要」という大きな項目はやめて、**「背景」と「更新箇所」の2項目に分ける**ことが決まりました。一言でもよいので背景を書く、という運用です。テンプレート修正はその場でissue化され、担当メンバーがすぐに対応することになりました。

### Dependabot導入の検討 — 依存関係を学ぶ

あるメンバーから、**Dependabot**の導入が提案されました。依存しているフレームワークやパッケージに更新があると、対応するプルリクエストを自動で作ってくれるGitHubの機能です。「PRを勝手に作ってくれるのは便利だが、マージの承認は人間が行う」という仕組みで、実際にリポジトリのスター数を確認しながら「企業でも広く使われている実績あるツール」であることを確かめ、導入する方向で合意しました。一方で提案したメンバーからは「PRが自動で増えても誰も対応せず溜まっていくパターンもある」という実務経験に基づく注意点や、「リリースのたびにチェックが必要になるのでは」という運用面の指摘もあり、導入後に運用ルールを考えていくことになりました。

この議論に合わせて、リードメンバーが初学者向けに`package.json`と依存関係の解説を行いました。アプリは先人が作ったパッケージを組み合わせて作られており、あるパッケージの更新が依存する他のパッケージに影響し得ること、ESLintのようなツールを1つ入れると関連パッケージが自動的に複数追加されること、`package.json`にはバージョン番号まで記録されることなど、実際のファイルを見ながらの説明で、チーム内の知識の底上げが図られました。

### AI駆動開発をチームの共通基盤に

リードメンバーから、**AI駆動開発をチーム開発にもっと取り入れていく**方針が共有されました。現状は各メンバーが思い思いのAIツールを使っている状態のため、Claude Codeを軸に共通の開発環境を整え、`CLAUDE.md` のような**チーム開発用のルールファイル**を管理していく構想です。この構想が、前述のChrome共有設定のPR……ではなく、前述のClaude Codeチーム共有設定のPRとして実装されました。

有料プラン（月20ドル程度のサブスクリプション）については「契約を強制するものではない」ことが明確にされました。メンバーからは「チームでAIのクレジットを共有できないか」という質問もありましたが、1つのアカウントの共有は規約面でも難しく、クレジットもすぐに尽きてしまうため見送りに。まずは**他のメンバーがAIでどう開発しているかを見て学ぶだけでも得るものがある**、興味が湧いたら無料枠や単月契約で試せばよい、という段階的な方針です。リードメンバーからはClaude Code・GitHub Copilot・Cursorを併用した自身の開発スタイルも紹介され、無料枠でGitHub Copilotを試し始めたメンバーも現れるなど、早速動きが出ています。ラボ内の勉強会の時間枠もAI寄りの内容にシフトしていく予定です。

このほか、アプリ紹介や動画の**サムネイル画像をアプリ上からアップロードできる機能**も新たにissue化されました。現状はSupabaseのダッシュボードから直接画像を登録するしかないため、Supabaseのストレージ（バケット）への画像アップロード機能を実装する計画です。

## 活用した技術

### react-markdownによる安全なマークダウン表示

**react-markdown**は、マークダウン文字列をReactコンポーネントとして描画するライブラリです。`dangerouslySetInnerHTML` を使わずに仮想DOMを直接構築するため、デフォルトで生のHTMLタグがエスケープされ、XSS（クロスサイトスクリプティング）に強いのが特徴です。**remark-gfm**プラグインを足すと、表やタスクリストなどGitHub Flavored Markdownの記法にも対応できます。

実装では2つのハマりどころがありました。1つは、react-markdownがバージョン8以降「余計なDOM propsを受け取らない」設計に変わったこと。`className` を直接渡せないため、Tailwind Typographyの `prose` クラスは外側の要素に付与し、リンクの `target` 指定は `components` プロパティで行う必要があります。もう1つは、Mantineの `<Text>` がデフォルトで `<p>` タグを出力すること。その中でマークダウンの段落がさらに `<p>` を生成すると、HTMLとして禁止されている「pタグの入れ子」となりhydrationエラーが発生します。`<Text component="div">` と出力タグを変更することで回避しました。

### Dependabotによる依存関係の自動更新

**Dependabot**は、GitHubが公式に提供する依存関係管理ツールです。リポジトリ内の `package.json` などの依存定義を監視し、パッケージに新しいバージョンが出ると、更新内容を反映したプルリクエストを自動で作成してくれます。セキュリティ脆弱性が見つかったパッケージへの警告・更新にも対応しており、依存パッケージを手動で追いかける手間を大きく減らせます。

ただし会議でも指摘があったとおり、自動で作られたPRを放置すれば溜まっていく一方です。「誰がいつレビュー・マージするか」という運用ルールとセットで導入してこそ効果を発揮するツールといえます。

### CLAUDE.mdとチーム共有のAI開発環境

Claude Codeは、リポジトリ直下の `CLAUDE.md` を**プロジェクトの指示書**として自動で読み込みます。技術スタックや設計ドキュメントの場所をここに書いておくことで、どのメンバーがAIに指示しても同じ前提知識で開発を進められます。今回の実装では、コーディング規約などの詳細はGitHub Wikiへのリンク参照とし、**同じ情報を二重管理しない**構成にした点がポイントです。Wiki側を更新すれば、Claude Codeが参照する情報も自動的に最新になります。

また `.claude/settings.json` にはチーム共通で許可するコマンドを定義できます。ビルドやlintなどの読み取り系操作だけをチーム標準として許可し、書き込み系の許可は各自の `settings.local.json`（Git管理外）に委ねるという設計は、安全性と利便性のバランスを取った運用の好例です。

## 総括

今回は、説明文のマークダウン対応という「見た目と表現力」の改善が完成した回でした。共通コンポーネントとして実装したことで、アプリ紹介・動画・資料・会員プロフィールと横断的に適用でき、動画詳細ページでは自前のURL判定ロジックを丸ごと置き換えてコードもシンプルになりました。ライブラリのバージョンによる仕様変更やhydrationエラーへの対処など、実践ならではの学びも詰まっています。

会議では、サイドバー改修でのスコープのすり合わせ、issueテンプレートの「背景」欄追加、Dependabotの導入検討と、開発プロセスを改善する議論が続きました。そしてClaude Codeのチーム共有設定が導入されたことで、AI駆動開発をチームの共通基盤にしていく取り組みが本格的に動き出しています。個人のスキルに閉じず、設定ファイルとノウハウ共有でチーム全体を底上げしていく今後の展開が楽しみです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
