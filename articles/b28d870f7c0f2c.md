## 開発したもの

### プロフィールボタンを右上のアバターメニューへ移動

これまでサイドバーに並んでいた「プロフィール」「ログアウト」のボタンを、画面右上のアバターアイコンから開くドロップダウンメニューに移動しました。新しく「トップヘッダー」というコンポーネントを作り、モバイルではハンバーガーメニューとアバターを含むヘッダーバー、デスクトップではアバターのみを右上に固定表示する構成です。

### ホーム画面に「本日のイベント」ウィジェットを追加

ホーム画面に、Googleカレンダーから取得した**当日のイベント一覧**を表示するウィジェットを追加しました。担当メンバーがこだわったのは、日付を跨ぐイベントの表示です。開始・終了が今日の範囲に収まるかどうかで表示を切り替えています。

```tsx
// app/(authenticated)/components/TodayEventsWidget.tsx（抜粋）
function formatEventTime(event: CalendarEvent, todayStart: Date, todayEnd: Date): string {
  if (!event.start?.dateTime) return "終日";

  const start = new Date(event.start.dateTime);
  const end = new Date(event.end?.dateTime ?? event.start.dateTime);

  const startIsToday = start >= todayStart && start < todayEnd;
  const endIsToday = end > todayStart && end < todayEnd;

  if (startIsToday && endIsToday) {
    return `${toHHmm(start)}〜${toHHmm(end)}`;
  } else if (startIsToday && !endIsToday) {
    return `${toHHmm(start)}〜`;
  } else if (!startIsToday && endIsToday) {
    return `〜${toHHmm(end)}`;
  } else {
    return "終日";
  }
}
```

もうひとつのポイントがエラーの明示です。カレンダー情報が取得できなかったとき、単に空のリストを出すと「今日はイベントがない」と勘違いさせてしまいます。そこで、すべてのカレンダーの取得に失敗した場合はエラーを返し、画面に失敗した旨を表示するようにしました。

```typescript
// app/api/calendar/calendar-server.ts（抜粋・変更後）
// 全カレンダーが失敗した場合はエラーを返す
const allFailed = results.length > 0 && results.every(r => r.failed);
if (allFailed) {
  return { data: null, error: "カレンダーイベントの取得に失敗しました" };
}

const allEvents = results.flatMap(r => r.events);
```

このほか、イベントに設定されたZoomなどのURLを直接クリックして開けるようにする改善も入っています。

### コード品質と一貫性の改善

細かな品質改善をまとめたリファクタリングPRもマージされました。担当メンバーからは4点の修正内容が共有されました。

1. プロフィール入力画面のURLバリデーションで、エラーメッセージの改行が表示されない問題の修正
2. ドキュメント詳細モーダルにあった重複したチェックコードの削除
3. SQLのURLチェック制約を各テーブルで統一
4. 共通化したバリデーション関数を、APIディレクトリから適切なディレクトリ（`app/utils/`）へ移動

SQLの制約は、テーブルごとに書き方がばらついていた「httpsのみ許可するCHECK制約」を、**NULLを許容しつつhttpsのみ許可する**形にそろえました。

```sql
-- supabase/migrations/01_tables/applications/02_add_url_check_constraint_to_applications.sql（変更後）
-- 1. 古い制約を削除
ALTER TABLE applications DROP CONSTRAINT IF EXISTS applications_url_https_check;

-- 2. 新しい制約（IS NULL OR あり）を追加
-- applicationsテーブルのurlカラムにhttpsのみ許可するCHECK制約を追加
-- NULLは許容（未入力可）、入力がある場合はhttps://から始まること
ALTER TABLE applications
  ADD CONSTRAINT applications_url_https_check
  CHECK (url IS NULL OR url ~ '^https://');
```

## 会議の様子

### 設計書の図をDraw.ioで描くか — まず1枚試作して判断

今回の中心的な検討テーマは、設計書のワイヤーフレームを**Draw.io**で作るかどうかです。Draw.ioは無料で使える作図サービスで、「設計書のレイアウトをタイピングで表現するより、綺麗な画像にした方が見やすい」という問題意識から候補に挙がりました。SVGファイルとして保存でき、ある程度の編集も可能で、マークダウンから呼び出して表示する運用が想定されます。

一方で、慎重な意見も出ました。提案したメンバー自身が「SVGファイルを作ってマークダウンから呼び出す運用は、地味に面倒かもしれない」と認めたほか、リードからは「全員が使えないと導入には抵抗がある。スキル面とメリットのバランスが大事」「今はAIがほぼレイアウトを書いてくれるので、HTMLのモックを書いた方がメンテナンス性がいい気もする」という指摘もありました。

結論は、**既存の画面を1枚だけDraw.ioでワイヤーフレーム化してみて、全員で見て判断する**というもの。別のメンバーからも「イメージが湧かないので一度見てみたい」という声があり、机上の議論を続けるより試作で判断する進め方に落ち着きました。ツール導入の是非を「小さく試して決める」のは、このチームらしい意思決定です。

### SQLスニペットは消すべき？ —「RUNした瞬間だけ動く」を共有

コード品質改善の作業報告の中で、SupabaseのSQLエディターに残っている過去のスニペット（SQLファイル）の扱いが話題になりました。担当メンバーは「古い制約を定義したファイルが残っていると、その制約が毎回働いてぐるぐるループしてしまうのでは」と考え、古いファイルを削除して新しいファイルを作り直していました。

これに対してリードから、**スニペットは「RUN」を押した瞬間だけ実行されるもので、ルールが常に適用され続けるわけではない**という説明がありました。実行後のファイルはただのドキュメント（実行記録）であり、データベースの状態は後から実行された処理で上書きされていくため、過去のファイルが残っていても悪さをすることはありません。VS Code上のマイグレーションSQLファイルも同様に「コマンドの記録」です。

「古い制約を消して新しい制約を入れる」という処理自体は必要だが、実行し終わった後のファイルは消さなくてよい——この整理によって誤解が解け、**スニペットは今までの作業記録として残し続ける**方針が確認されました。疑問をその場で口に出し、全員の理解に変えていくやりとりは、初心者を含むチームならではの光景です。

### 次の担当決め — RLS共通化・画像アップロード・リリース自動化

手が空いたメンバーへの次のIssue割り当ても行われました。「セキュリティやデータのリクエスト・レスポンスについて勉強したい」というメンバーには、**RLS（行レベルセキュリティ）ポリシーの共通化**をアサイン。現状、アプリケーション・ドキュメント・ビデオの3つで同じようなアクセスルールを独立に実装しているため、Supabaseの**ファンクション（関数）機能**で共通関数化してメンテナンス性と安全性を高めます。いきなり実装するのではなく、**まず設計書を修正して概念を整理してから**進める方針です。

別のメンバーには、プロフィール画像を自分の好きな画像に差し替えられる**画像アップロード機能**を割り当てました。Supabaseの**ストレージ**機能を初めて使う挑戦的なテーマで、無料プランのため容量に制限（トータル500MB程度）があり、画像サイズを1MB以下に抑えるなどの制約設計も必要になります。チーム内でストレージ機能の経験があるメンバーがレビューを担当することになりました。

リード自身は、**本番リリース操作のGitHub Actionsによる自動化**に取り組みます。ここでは「完全自動化よりも、承認ステップを設けたりジョブを分けたりする方がよい」という助言があり、失敗時にSlackへ通知を飛ばす構想も語られました。また、近くリリース予定のWebスキルアップ系の新サービスを今後このチームでメンテナンスしていく方針も共有されました。Next.jsとSupabaseという同じ構成ながら、新しいランタイムやBiomeといった最新のコード品質管理ツールを試しており、新しい学びが期待できそうです。

### AIとの距離感とセキュリティニュース

品質改善を担当したメンバーからは「URLバリデーションの修正はClaudeに相談したら一気に終わってしまったので、後から何をやったのか目視でしっかりチェックした。AIが凄すぎてついていくのが大変」という感想がありました。リードも「AIに一気に任せると自分の知識が追いつかなくなる。ステップバイステップで確認しながら進めるのはすごく大事な習慣」と応じ、AI活用と理解の両立が改めて確認されました。

また、メンバーから「Claude Codeの開発コードが漏れたというニュースを見たが影響はあるか」という質問があり、リードが「すぐに何か対応が必要なものではなさそうだが確認する」と引き取りました。別のメンバーからは、**npmパッケージのAxiosを狙ったサプライチェーン攻撃**への注意喚起も共有されました。こうしたセキュリティ情報を日常的にウォッチし、チームで共有し合う習慣も開発文化の一部になっています。

## 活用した技術

### Draw.ioとSVG — 「コードで表せる図」の強み

Draw.io（diagrams.net）は、ブラウザ上でフローチャートやワイヤーフレームを描ける無料の作図ツールです。特徴は、図を**SVG（Scalable Vector Graphics）**として保存できること。SVGはベクトルデータなので拡大しても滑らかに表示され、実体はXMLベースのテキストのため、Gitで差分管理でき、**コードで図を表現できる分AIとの相性もよい**と言われています。

一方、今回の議論で出たように「AIにHTMLモックを書かせる」という選択肢もあります。HTMLなら実装にそのまま近づけられ、修正もテキスト編集で完結します。作図ツールの学習コストと運用の手間、成果物のメンテナンス性——導入判断に必要な材料を、まず1枚の試作で集めるのが今回のチームの答えでした。

### PostgreSQLのCHECK制約と「DROP → ADD」パターン

テーブルのカラムに条件を課す**CHECK制約**は、`CHECK (url IS NULL OR url ~ '^https://')` のように書くことで「未入力は許容しつつ、入力があればhttpsで始まること」を強制できます。アプリ側のバリデーションをすり抜けたデータも、データベースの層で確実に弾けるのが利点です。

既存の制約を変更するときは、今回のPRのように `DROP CONSTRAINT IF EXISTS` で古い制約を消してから `ADD CONSTRAINT` し直すのが定石です。`IF EXISTS` を付けておけば、制約がまだ存在しない環境で実行してもエラーにならず、**同じSQLを何度実行しても結果が変わらない（冪等な）**マイグレーションになります。会議で話題になった「実行後のスニペットはただの記録」という理解とも地続きの話で、SQLファイルは「実行した操作の履歴」、データベースの現在の状態は「最後に実行された定義」で決まります。

### タイムゾーンを意識した「今日」の算出

「本日のイベント」ウィジェットでは、サーバー側で当日の開始・終了時刻を計算しています。ここで注意が必要なのがタイムゾーンです。サーバーは必ずしも日本時間で動いているとは限らないため、単純に `new Date()` から日付を取り出すと、UTC基準で「今日」がずれる可能性があります。

今回の実装では `Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を指定して年月日を取り出し、`T00:00:00+09:00` を付けて日本時間の0時を確定させています。さらに、日付を跨ぐイベントは「開始だけ今日」「終了だけ今日」「どちらも今日ではない（終日扱い）」の3パターンに分けて表示を切り替えており、カレンダー連携で起こりがちな境界条件を丁寧に処理した実装になっています。
