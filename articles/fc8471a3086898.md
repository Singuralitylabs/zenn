## 概要

本記事は、[チーム開発記録36：説明文のマークダウン対応](https://zenn.dev/singularitylabs/articles/b051d15d0c44e6)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回の定例までに、**プロフィールにSNSやポートフォリオのURLを登録して会員一覧から参照できる機能**と、**セキュリティ関連パッケージの一括更新**がマージされました。また、ポータルサイトのテスト方針をまとめた**テスト設計書**の作成が進み、レビューと並行してJestによるユニットテストの実装も始まっています。

会議では、マスターテーブルの編集画面を共通化するかどうか、イシューに「背景」を書くルール、ラベルとプライオリティの運用と、開発プロセスに関する議論が数多く行われました。意見が割れたテーマをどう着地させたのか、議論の過程も含めてご紹介します。

## 開発したもの

### プロフィールにSNSリンクを登録できる機能

プロフィール編集画面に、X・Facebook・Instagram・GitHub・ポートフォリオサイトのURLを入力できる欄を追加しました。登録したURLは、会員一覧の詳細モーダルにリンクとして表示されます。データベース側では、Supabaseの `users` テーブルに各SNSのURL用カラムを追加しています。

実装のポイントは**バリデーション（入力値の検証）**です。URLが `http://` または `https://` で始まる形式かをチェックする関数を用意しました。

```tsx
// app/(authenticated)/profile/components/Template.tsx（抜粋）
// URL形式チェック関数
const validateUrl = (url: string | null) => {
  if (!url) return true;
  return /^https?:\/\//.test(url);
};
```

保存時には各URL欄をチェックし、形式が不正な場合は入力欄ごとのエラーメッセージと画面右上の通知を表示して送信を中断します。

```tsx
// app/(authenticated)/profile/components/Template.tsx（抜粋）
// URL入力にエラーがあれば表示して中断
if (Object.keys(newErrors).length > 0) {
  setErrors(newErrors);
  notifications.show({
    title: "入力エラー",
    message: "URLの形式を確認してください",
    color: "red",
  });
  return;
}
```

会員詳細モーダル側では、いずれかのURLが登録されている場合のみリンク欄を表示するようにしています。

```tsx
// app/(authenticated)/members/components/MemberDetailModal.tsx（抜粋）
const hasLinks =
  memberInfo.x_url ||
  memberInfo.facebook_url ||
  memberInfo.instagram_url ||
  memberInfo.github_url ||
  memberInfo.portfolio_url;
```

なお、今回実装したバリデーションは**フロントエンド（クライアントサイド）のみ**です。サーバーサイドのバリデーションは、既存のURL入力欄も含めて別イシューでまとめて対応することになりました。この判断の背景は「活用した技術」で解説します。

### テスト設計書の作成とユニットテストの実装（レビュー中）

テスト用GitHub Actionsの構築タスクとして、担当メンバーが**テスト設計書**を作成し、現在レビュー中です。もともとリードが書いていた設計書に大幅な加筆をしたもので、テストピラミッド（ユニット・インテグレーション・E2E）に基づくテスト戦略、現状のCI/CDで動いているチェック内容、今後導入すべきテスト項目の優先度付き一覧などがまとめられています。

あわせて、設計書の内容の一部をJestのユニットテストとして実装するプルリクエストも出ています。大量の新規テストファイル（`xxx.test.ts`）はほぼAIが生成したもので、「人が手で書いたら大変なことになっていた」規模です。レビューは設計書を優先し、設計書のマージ後にテストコードを確認する順序で進めることになりました。レビューの中では「サービス層のテストのうち、コンポーネントのテストとAPIのテストでタスクを分けた方がよいのでは」という整理も出ています。

## 会議の様子

### マスター編集画面は共通化するか — まず設計書を作ってから議論する

役割タグの編集機能の進捗確認から、設計方針の議論に発展しました。担当メンバーから「役割マスタの編集は、開発予定のカテゴリーマスタの編集機能に相乗りする形で、**テーブルを選んで編集できる共通のマスター管理画面**としてまとめた方が使いやすいのでは。今後も◯◯マスタの編集画面が欲しくなるはずなので、共通設計の方がよい」という提案が出ました。これに対しカテゴリー機能の担当メンバーは「カテゴリー単体で編集できる機能を想定していたので、総合的なマスター管理画面となると設計を考え直す必要がある」と応じ、リードも「マスター管理画面と聞いて頭に思い浮かべるものが人によってバラバラで、このまま議論してもすり合わせが難しい」と指摘しました。

結論は、**ベースとなる設計書を1つ作ってから統合の是非を議論する**というものです。マスター管理画面は別タスクとして起票し（プライオリティはMedium）、役割タグの担当メンバーはもう1つの論点である「役割の紐付け」の設計から着手することになりました。

また、「役割とカテゴリーは表示順を管理する仕組みが似ているので、裏側の処理を共通化できるのでは」という提案も出ましたが、「役割はカテゴリーと違って1人に複数紐付けられるので毛色が違う」との反論があり、提案したメンバーも考慮不足を認めて、**表示順（ディスプレイオーダー）の仕組みだけ共通化し、実装自体は分ける**方向に落ち着きました。提案と反論が短いやり取りで噛み合い、すぐに方針修正できたのは良い議論だったと言えます。

### イシューに「背景」を書くか — 原則記載のルールに

機能を共通化しなかった理由のような**意思決定の背景をどこに残すか**も議題になりました。あるメンバーは「背景を書くのはマストだと思っている。書いて普通」と主張し、要件定義書や課題管理表など新しいドキュメントを作る案も出ました。一方リードは「イシューとの二重管理になる」「人が一生懸命書く運用は現実には続かない。過去のイシューを見ても丁寧に書かれていた印象がない」と慎重な立場です。

他のメンバーからも「なくても作れるので必須ではないが、ナレッジとして残すならWikiという手もある」「背景の項目があれば書く、書くことがなければ書かなくてよい、くらいがいい」「後からチーム開発に加わる初心者にも分かるように残っていると嬉しい」と意見が出ました。最終的には、**イシューの背景欄に原則書く。書かない場合はその理由を残す**というルールに決定。「◯◯という理由で作ります」と1行書くだけでも十分で、深刻になりすぎず軽い気持ちで始めて、機能しなければその時に対策を考える——ただしチームで決めた以上ルールは守る、という着地になりました。

### ラベルとプライオリティの運用

イシューにラベルが付いているものと付いていないものが混在している問題も話し合われました。「機能分類のラベルより難易度（Easy/Normal/Difficult）の方が便利では」という案も出ましたが、「ラベルでフィルタリングする使い方ができるので既存ラベルにも意味がある」「イシュー作成時のテンプレートで自動的に付くものもある」という整理から、**今あるラベルを活用し、今後作るイシューにはラベルを付ける**方針になりました。

さらに「難易度以上にプライオリティを付けるべき。プライオリティの高いものが放置されるのはまずい」「こういう会議こそプライオリティを付ける場では」という意見を受けて、**新しいイシューには作成者がその場の判断でプライオリティを設定し、定例で必要に応じて上げ下げを調整する**運用も決まりました。

このほか、資料詳細モーダルの実装を担当するメンバーからは「Claude Codeに細かく指示しながら実装し、コーディングは完了。AIに色々教えてもらっている」という共有があり、リードからも「AIに教わるのはスキルアップにとても良いやり方」というコメントがありました。また、プルリクエストのチェックリストは**更新が不要な項目を行ごと削除する**（残しておくと単なる未対応に見えてしまうため）という運用も確認されています。資料管理アプリの登録・編集モーダルの説明欄を広げる修正も完了し、レビュー待ちの状態です。

## 活用した技術

### テストピラミッドとCI/CD

テスト設計書の中心にあるのが**テストピラミッド**という考え方です。関数など1つ1つの部品が正しく動くかを検証する**ユニットテスト（単体テスト）**を土台に、部品を組み合わせた時の動きを確認する**インテグレーションテスト（結合テスト）**、実際の画面操作を通して全体を確認する**E2Eテスト**を積み上げる構造で、下の層ほど数を多く、上の層ほど絞って作るのが定石とされています。

現状のポータルサイトのCI（GitHub Actionsによる自動チェック）では、ビルドが通るか・型エラーがないかといった最低限の確認しか行っていません。今回の設計書では、Jestによるユニットテストを軸に、データベースからデータを正しく取得できるか、ログイン機能が動くかといったテストを優先度付きで整理しました。ただし「テストはやればやるほど良いわけではなく、細かいバグ対応だけで時間を取られることもある。どこまでやるかはチームのスキルが問われる」というのがリードの補足で、優先度の高い項目から段階的に導入していきます。AIが登場する前は「コードより先にテストを書く」テスト駆動開発が当たり前の時代もありましたが、今回はテストコードの大部分をAIが生成しており、時代の変化を感じる場面でもありました。

### 二段構えのバリデーションとSQLインジェクション対策

SNSリンク機能のレビューでは、「バリデーションはフロントエンドとサーバーサイドのどちらで実装しているか」という質問が出ました。今回はフロントエンドのみの形式チェックですが、クライアント側のチェックは意図的に回避できるため、おかしなデータがそのままサーバーに届く可能性があります。**不正な文字列を送り込んで本来見えないデータを表示させたり、勝手にデータを書き換えたりするSQLインジェクションのような攻撃を防ぐには、サーバーサイドのチェックが不可欠**という指摘です。

実はこれまでの実装でも、アプリや資料のURL入力などでサーバーサイドのバリデーションは入っていませんでした。そこで今回のプルリクエストでは個別に対応せず、既存のURL入力全般をまとめて別イシュー化し、バックエンド側のバリデーションを統一的に実装する方針を取っています。担当メンバーは一度バックエンド側の処理も作ったものの、実装がバラバラになるのを避けるためにあえて削除してイシュー化に切り替えた、という経緯も共有されました。

### セマンティックバージョニングとパッケージ更新

`package.json` に並ぶ依存パッケージのバージョンは `2.48.1` のようにドット区切りの3つの数字で表され、左から**メジャー・マイナー・パッチ**と呼ばれます（セマンティックバージョニング）。パッケージは別の会社やチームが継続的に管理しており、バグ修正やセキュリティホールの修正が随時リリースされるため、基本的にはアップデートに追従した方がよいとされています。

ただしメジャーアップデートは互換性が壊れて「今まで動いていたシステムが動かなくなる」ことがあるため、慎重な対応が必要です。今回の更新でもメジャーアップデートは見送り、動作確認をした上でマイナー・パッチ中心に適用しました。こうした更新を定期的に続けることが、セキュリティを保つ地道で確実な方法です。

## 総括

今回は、SNSリンク機能とパッケージ更新という目に見える成果に加えて、テスト設計書のレビューが進み、ビルドと型チェックだけだったCIに本格的なテスト体制を組み込む準備が整ってきました。フロントエンドだけでなくサーバーサイドのバリデーションを統一的に整備する動きも始まり、品質とセキュリティの土台を固める回になったと言えます。

会議では、マスター管理画面・イシューの背景・ラベルとプライオリティと、コードそのものよりも「チームとしてどう開発を進めるか」に多くの時間が割かれました。イメージが揃わないならまず設計書を作ってから議論する、ルールは軽く始めて機能しなければ見直す、といった進め方は、規模を問わずチーム開発の参考になるはずです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
