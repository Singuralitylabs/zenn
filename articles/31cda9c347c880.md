## 開発したもの

### AI駆動開発時代の環境変数管理 — dotenvxによる暗号化

ポータルサイトはSupabaseの接続情報やGoogleサービスアカウントキー、Slackの Webhook URL など、外部に出せない秘密情報を多数扱います。これまでは各自がローカルの `.env.local` に実値を持ち、新規メンバーは共有された値を手作業で配置する運用でした。今回、[dotenvx](https://dotenvx.com) を導入し、**暗号化した状態の `.env.development` をリポジトリにコミットする**方針へ切り替えました。

仕組みはシンプルで、公開鍵で暗号化した値をコミットし、対になる復号鍵（`.env.keys`）だけを Git 管理外で各自が保管します。実行時は `dotenvx run` が復号してプロセスに環境変数を渡すため、開発コマンドは dotenvx 経由に置き換えられています。

```json
// package.json（抜粋・変更後）
{
  "scripts": {
    "dev": "dotenvx run --strict -f .env.development -- next dev --turbopack",
    "build:local": "dotenvx run --strict -f .env.development -- next build",
    "start:local": "dotenvx run --strict -f .env.development -- next start",
    "db:types:local": "dotenvx run --strict -f .env.development -- node scripts/db-types.cjs",
    "lint:env": "node scripts/check-env-encrypted.cjs"
  },
  "devDependencies": {
    "@dotenvx/dotenvx": "^2.3.4"
  }
}
```

暗号化済みファイルをコミット対象にするため、`.gitignore` では `.env.development` だけを除外解除しています。復号鍵は引き続き除外したままです。

```bash
# .gitignore（抜粋・変更後）
# .env.development は dotenvx で暗号化済みのためコミット対象（復号鍵 .env.keys は除外のまま）
!.env.development
```

この運用の肝は、**暗号化し忘れた平文がうっかりコミットされるのを防ぐ**ことです。そのために、`.env.development` の各値が確実に `encrypted:` で始まっているかを検証する Node スクリプトを用意し、CIで走らせています。

```javascript
// scripts/check-env-encrypted.cjs（抜粋）
// 平文で保持してよいキー。dotenvx の公開鍵は仕様上、平文で書き込まれる（秘密情報ではない）
const PLAINTEXT_ALLOW_KEYS = new Set(["DOTENV_PUBLIC_KEY_DEVELOPMENT"]);

const violations = [];
lines.forEach((line, index) => {
  const trimmed = line.trim();
  if (trimmed === "" || trimmed.startsWith("#")) return;

  const match = line.match(assignment);
  if (!match) return; // 代入行でなければ対象外

  const [, key, rawValue] = match;
  if (PLAINTEXT_ALLOW_KEYS.has(key)) return;

  const value = stripQuotes(rawValue);
  if (!value.startsWith("encrypted:")) {
    violations.push({ line: index + 1, key });
  }
});

if (violations.length > 0) {
  console.error(
    `NG! ${rel} に暗号化されていない値があります。\n` +
      `\`npx dotenvx encrypt -f .env.development\` で暗号化してからコミットしてください。`
  );
  process.exit(1);
}
```

このチェックは、`.env.development` などの変更があったときにだけ GitHub Actions で自動実行されます。依存パッケージ不要（Node標準モジュールのみ）で動くため、`npm ci` を省いて軽量に回しています。

```yaml
# .github/workflows/check_env_encryption.yml（抜粋）
name: Check env encryption
on:
  pull_request:
    paths:
      - ".env.development"
      - "scripts/check-env-encrypted.cjs"
      - "package.json"
jobs:
  check-env-encryption:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22.x
      # 依存不要（Node 標準モジュールのみ）のため npm ci は行わない
      - name: Check .env.development is fully encrypted
        run: npm run lint:env
```

あわせて、AIコーディングエージェント（Claude Code）が秘密情報ファイルを読み取れないよう、設定側でも明示的に読み取りを拒否しています。人的ミスとツール由来の漏洩の両面を塞ぐ狙いです。

```json
// .claude/settings.json（抜粋・変更後）
"deny": [
  "Bash(rm -rf:*)",
  "Read(./.env.keys)",
  "Read(./.env)",
  "Read(./.env.production)",
  "Read(./google-service-account.json)",
  "Read(**/*.pem)"
]
```

## 会議の様子

### 役職タグをどう表示するか — 二重管理をめぐる設計議論

この日いちばん議論が盛り上がったのが、メンバー一覧ページの先頭に「代表・副代表」を特別枠で固定表示する機能でした。担当者が AI（Claude Code）に実装を依頼したところ、`LEADERSHIP_POSITIONS` のような**役職の「ID」と「名前」を持つ定数**をコード側に新しく作り、テンプレートから参照する形になっていました。担当者からは「わざわざファイルを作って役職名を持たせる必要があるのか」という相談が上がりました。

リードエンジニアの見立ては明快でした。役職の情報はすでにデータベース（`positions`）側にも「ID」と「名前」で入っているため、**コードにも同じ情報を持たせると二重管理になる**。たとえば「代表」を「理事」に変えたいとき、データベースとコードの両方を直さないと表示が食い違い、それ自体が潜在的なバグになる、という指摘です。一方で、AIがこの設計を選んだ意図（メンバー一覧のトップに特別枠を作るため、対象の役職を明示できる変数を用意した）も理解できる、という整理でした。

ここから、代替案が次々に出ました。

- **int配列でIDだけを持つ**：役職名の文字列は持たず、対象のIDだけをフロントに配列で持たせる。3件程度ならハードコーディングでも許容できるのでは、という現実的な案。
- **テーブルにフラグ列を足す**：メンバーズテーブルに「トップに出す用のTrue/Falseカラム」を1つ追加すれば、コード側に余計な定数を持たなくて済むという、一番きれいなゴール案。
- **SQL/APIで絞り込む**：クエリ側で対象IDを絞る案。ただしDBアクセスにIDをハードコーディングするのはリスキー、という慎重論も出ました。

議論の途中で、もう一段深い落とし穴が共有されます。**役職のIDはデータベースが自動採番しているため、開発環境と本番環境で番号がズレる可能性がある**というものです。本番は手動投入の比重が大きく、「開発では 8, 9, 10 でも本番では別番号」という事態が起こり得ます。決め打ちのIDをコードに埋めると、環境差分でそのまま表示が壊れてしまいます。

最終的な結論は、「まずは動くものを最小の手間で」でした。役職名の文字列はコードに持たず**IDのみ**を保持し、`ID 8 はこれ` といった対応をコメントで明示しておく。そのうえで、環境差分やより良い設計への対応は**別イシューとして起票し、追って検討する**方針に決めました。「まだ役職は10件程度で力技でも対応できる」という現状認識と、「役割は増えることはあっても消えたり変わったりはそうそうない」という見通しが、この割り切りを後押ししています。

### マスター管理画面のスコープを詰める

冒頭のissue確認では、マスター管理画面の**対象範囲の絞り込み**が話題になりました。当初案にあった「ユーザーテーブルの参照」については、権限管理の動線が複雑になるうえ、いま実際に必要とされているわけではないため、思い切って外す判断に。「あっても使わない機能のために手間を増やすより、参照対象から落とす方へ倒す」という、YAGNI寄りの意思決定です。

設計面では、この画面が**`database.types.ts`（Supabaseの型定義）を参照する**構造にしている点も確認されました。テーブルが増えても管理画面の修正を最小化する狙いですが、「更新・追加機能まで踏み込むと、選択肢のような制約情報が型定義だけでは足りず、補足情報を持たせる必要が出てくる」という保守コストの論点も共有されました。今回は**参照のみ**に絞ることで、この難しさは後々の課題として残す形にしています。

### 環境構築でのつまずきと、ゴミ箱機能の完了確認

新しく導入した dotenvx について、一部のメンバーがローカルでうまく動かせず、会議で相談が挙がりました。「メインブランチを取得し、復号鍵を受け取って `npm run dev` すれば動くはず」という基本手順を確認しつつ、レビュー用にブランチを分けた際に暗号化ファイルがうまく引き継がれていなかった可能性など、環境依存の要因を一つずつ切り分けました。Linux・他メンバーの環境では問題なく動作していることも確認され、「どうしても解決しなければ復号鍵の保管を諦めてローカルに鍵ファイルを置く運用に切り替える」というフォールバックも用意して、無理なく進める方針にしています。

また、前回マージ済みの**ゴミ箱機能**（削除したコンテンツの復活）について、担当者が実際にテスト環境でコンテンツを復活させるデモを行い、正しく動くことを全員で確認しました。あわせて、テスト用のダミーデータ（`ZZ` など）は積極的に消していった方が、何をテストしているか分かりやすいという運用上のちょっとした合意も生まれています。

このほか、AIによるセキュリティ点検で見つかっていた**ユーザーテーブルの権限露出**が「重要なバグ」として改めて取り上げられ、リードエンジニア自身が対応に着手することになりました。Jest実行時のエラー表示については、特定メンバーの環境依存の可能性が高いと見て、まずは環境側の確認から進める切り分けを行っています。

## 活用した技術

### dotenvxの公開鍵暗号方式

dotenvx は、`.env` ファイルの値を**公開鍵で暗号化**し、対になる秘密鍵（復号鍵）で実行時に復号する仕組みを提供します。公開鍵はファイル冒頭に平文で書かれますが、これは暗号化する側の情報であり秘密ではありません。逆に、値の暗号文（`encrypted:...`）と平文を復元できる `.env.keys` を分離することで、**暗号化済みファイルそのものはリポジトリに置いても安全**になります。これにより「秘密情報をどう安全に共有するか」という積年の課題を、Gitの仕組みに乗せて解けるのがポイントです。

チームでは、この安全性を「仕組みだけ」に頼らず、CIで**平文混入を機械的に検出**する層を重ねました。人はいつか暗号化を忘れますが、`encrypted:` で始まらない値をPRの段階で弾けば、公開リポジトリへの平文流出を未然に防げます。「安全な設計 × 自動チェック × ツール権限の制限」という多層防御の考え方が、そのまま実装に落ちています。

### データの単一情報源（Single Source of Truth）

役職タグの議論の根っこにあったのは、**同じ意味を持つ情報を1か所でしか管理しない**という原則です。データベースとコードの両方に役職名を持つと、片方の更新漏れがそのまま表示バグになります。今回、フロント側はIDだけを持ち、名前や表示制御の判断はできるだけデータ側に寄せる、という方向で合意しました。理想は「トップ表示用のフラグ列をテーブルに持つ」ことですが、実装コストとのトレードオフを踏まえ、**いったんIDのみ＋コメントで意味を補い、改善は別イシューで追う**という段階的アプローチを取っています。

### 自動採番IDを環境をまたいで扱うリスク

もう一つの学びは、**DBが自動採番する連番は「環境間で一致する保証がない」**という点です。開発環境で `8, 9, 10` だからといって本番環境で同じ番号になるとは限りません。こうした番号をアプリのコードやクエリに決め打ちで埋め込むと、環境差分で静かに壊れます。今回はこのリスクを認識したうえで、「まだ件数が少なく力技で追随できる」現実を踏まえて割り切りつつ、恒久対応（フラグ列の追加や、意味のある値でのマッピングなど）はイシュー化して切り離す、という判断を下しました。

## 総括

今回は、**秘密情報の暗号化管理（dotenvx）というインフラ面の前進**と、**役職タグ表示をめぐる設計議論**が両輪の回でした。特に後者は、「AIが書いたコードをそのまま採用するか」ではなく、「二重管理を避けるにはどこに情報を持たせるべきか」「環境差分に強い設計は何か」といった、**AI駆動開発だからこそ人間が担うべき設計判断**が凝縮された議論だったと思います。最小の手間で動かしつつ、難しい部分はイシューとして未来の自分たちに手渡す——その割り切りの付け方こそ、継続的にプロダクトを育てるチームの実力かもしれません。
