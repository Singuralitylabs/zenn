本記事は、[チーム開発記録21：データ取得の並列化とリリース準備](https://zenn.dev/singularitylabs/articles/2c94f33d694d82)に続く最新の活動記録です。

## 開発したもの

### スクロール時のヘッダー固定表示

資料一覧・動画一覧のページは、ページ上部にタイトルと「事務局資料」「広報用資料」といった分類（カテゴリー）へのショートカットリンクを表示しています。これまでは画面をスクロールするとこれらが上に隠れてしまい、別の分類へ移動したいときに毎回ページの先頭まで戻る必要がありました。

そこで、タイトルとカテゴリーリンクの部分を `sticky` なレイヤーで包み、スクロールしても画面上部に固定表示されるように修正しました。

```tsx
// app/(authenticated)/documents/components/Template.tsx（抜粋・変更後）
<div className="sticky top-0 z-10 bg-white">
  <PageTitle>資料一覧</PageTitle>
  {isContentMgr && (
    <div className="mt-4 flex justify-end">
      <ContentMgrNewButton type={CONTENT_TYPE.DOCUMENT} categories={categories} userId={userId}>
        新規登録
      </ContentMgrNewButton>
    </div>
  )}

  <div className="mb-4 py-4 flex flex-wrap items-center">
    <CategoryLink
      categories={existingCategories.map(category => ({
        id: category.id,
        name: category.name,
      }))}
    />
  </div>
</div>
```

あわせて、カテゴリーリンクをクリックしてページ内の見出しへジャンプしたとき、固定ヘッダーの分だけ見出しが隠れてしまわないように、ジャンプ先の見出しにはスクロール位置の余白を指定しています。

```tsx
// ジャンプ先の見出しに scroll-mt-40 を指定して、固定ヘッダー分の位置ずれを補正
<h2 id={`category-${category.id}`} className="scroll-mt-40">{category.name}</h2>
```

同じ修正を資料一覧・動画一覧・会員一覧の3ページに適用し、仕様書にも「スクロール時も固定表示」の記述を追記しました。

### ブラウザタブに表示されるアイコン（ファビコン）の修正

ver4になる前まで、ブラウザのタブにはシンラボのマークではなく別のアイコンが表示されてしまっていました。原因は、プロジェクト内にNext.jsのテンプレート由来のアイコンファイル（`app/favicon.ico` や `apple-icon.png` など）が残っており、こちらが優先して表示されていたことでした。

対応としては、使っていないアイコン画像ファイルを削除し、メタデータで参照するアイコンをシンラボのアイコン（`/icon.png`）に統一しました。

```tsx
// app/layout.tsx（抜粋・変更後）
export const metadata: Metadata = {
  icons: {
    icon: "/icon.png",
    shortcut: "/icon.png",
    apple: "/icon.png",
    other: {
      rel: "apple-touch-icon",
      url: "/icon.png",
    },
  },
};
```

「不要なファイルを消す」だけのシンプルな修正ですが、Next.jsのファイル規約によるアイコンの優先順位を理解していないと原因にたどり着きにくい、学びのある修正でした。

### console.log / debugger を検出するGitHub Actions

テスト用GitHub Actionsの第一弾として、コード中に消し忘れた `console.log` や `debugger` が残っていないかを自動チェックするワークフローを追加しました。`app/` 配下のJavaScript / TypeScriptファイルを対象に、pushやプルリクエストのタイミングで自動実行されます。

```yaml
# .github/workflows/check_console_log.yml（抜粋・一部省略）
name: Check console.log and debugger

on:
  push:
    paths:
      - "app/**"
  pull_request:
    paths:
      - "app/**"

jobs:
  check-console-log:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Search for console.log or debugger
        run: |
          OUTPUT=$(find app -type f \( -name "*.js" -o -name "*.ts" -o -name "*.jsx" -o -name "*.tsx" \) \
            ! -path "*/node_modules/*" \
            -print0 | xargs -0 grep -nE "console\.(log|info)|debugger" || true)
          if [ -n "$OUTPUT" ]; then
            echo "NG! console.log または console.info または debugger が見つかりました。削除してください。"
            echo "$OUTPUT" >> $GITHUB_STEP_SUMMARY
            exit 1
          else
            echo "OK! console.log または console.info または debugger は見つかりませんでした。"
          fi
```

意図的に残している認証まわりのログは除外リストで許可する形にしており、検出された場合はワークフローが失敗（`exit 1`）してマージ前に気づける仕組みです。このほか、Jestを使ったテスト実行のワークフローも現在レビュー中で、順次追加していく予定です。

## 会議の様子

### ver4リリースの振り返り — リリースで見つかった2つのバグ

冒頭で、ver4のリリース完了が報告されました。会員一覧ページ・プロフィール機能・コンテンツ管理権限・Slack通知機能などを含む大きなアップデートで、課題管理ボードもver5へ移行しています。

一方で、リリース作業中に2つのバグが発覚しました。1つは**まったく同じSQLファイルが2箇所に重複して存在していた**こと、もう1つは**資料・動画テーブルのポリシーを定義するSQLなのに、対象テーブルが誤ってユーザーテーブルを指していた**ことです。

このSQLの誤りをめぐっては、「なぜテスト環境で気づけなかったのか」という視点で議論が交わされました。今回のクエリはどのテーブルに対しても通ってしまうシンプルなものだったため、実行してもエラーにならず発見が遅れた、というのが実態です。テストケースを整備してデータベースの機能確認を行う案も出ましたが、このチーム開発は「バグをゼロにする完璧さよりもスピードを重視する」スタンスで運営しているため、当面はレビュー時の注意喚起にとどめる判断となりました。品質保証のコストとリリース速度のトレードオフを、チームの目的に照らして意思決定する良い事例になりました。

### プルリクエストのテンプレートを強化する

マージ済みプルリクエストの確認では、ファビコン修正のように「画面の差分だけでは変更内容が分かりにくい」ケースをきっかけに、**レビュアーへの情報提供をどう標準化するか**が議論になりました。

メンバーからは次のような意見が出ました。

* 差分から変更内容が読み取りにくい場合に備えて、**確認方法**をプルリクエストに書いてほしい
* UIの変更なら、変更後の画面の**スクリーンショットを添付**してもらえるとレビュアーの負担が大きく減る
* 変更が大きくなりそうなら、ファイル数や行数の目安で**プルリクエスト自体を分割**する工夫も有効
* レビューは「作った人の視点」ではなく**ユーザー視点**で行えるように、どこがどう変わるのかを明示する

議論の結果、プルリクエストのテンプレートに「技術的な変更点」「レビューしてほしい観点（確認方法）」「UI変更時のスクリーンショット」といった項目を追加する方針でIssue化しました。運用してみて書く負担が大きすぎれば適宜見直す、というスモールスタートの進め方です。

### リリース手順のドキュメント化と2名体制

今回のリリース作業を踏まえて、リリース手順をチームのWikiに文書化したことも共有されました。手順は大きく、①Supabaseのデータベース更新（カラムやポリシーの追加）→ ②初期データの投入 → ③環境変数の設定 → ④リリースブランチへのマージ（レビューとGitHub Actionsのテストを通す）→ ⑤フォーク先リポジトリへの同期 → ⑥Vercelでのデプロイ、という流れです。

さらにメンバーから「承認者を事前に決めてスケジュールを確保する」「リリース作業時だけ権限を昇格し、終わったら戻す」といった運用改善の提案があり、**次回からはリリース作業を2名体制で行う**ことになりました。属人化しがちなリリース作業を、ドキュメントと体制の両面で改善していきます。

### 新しいメンバーの見学と、発言しやすい会議づくり

今回から新しいメンバー2名が見学として参加しました。「まずはポータルサイトを実際に触って気づいたことを共有してもらう」「環境構築の手順書を整備して、動かせる環境づくりから始めてもらう」といったオンボーディングの進め方も話し合われました。オープンソースのリポジトリなので、生成AIにリポジトリを読み込ませて理解を深める方法も紹介されています。

早速、新メンバーから「Googleログインの画面に `supabase.co` というドメインが表示されて戸惑った」という指摘があり、認証画面の表示ドメイン改善がToDoに追加されました。新しい視点が入ることで、開発メンバーだけでは気づけない改善点が見つかった好例です。

また、「質問がある方はいますか？と聞かれても発言しづらい」という率直なフィードバックから、名指しで意見を聞く、質問しやすい聞き方に変えるなど、**会議の進行そのものを改善する議論**も行われました。技術だけでなくコミュニケーションの取り方も継続的に見直していくのが、このチームらしいところです。

## 活用した技術

### CSSの position: sticky による固定表示

`position: sticky` は、要素を「通常はコンテンツの流れの中に置きつつ、スクロールで画面外に出そうになったら指定位置に貼り付ける」CSSの定番テクニックです。Tailwind CSSでは `sticky top-0` と書くことで「画面上端に固定」を表現できます。

あわせて指定している `z-10`（`z-index: 10`）は要素の重なり順の指定で、スクロールしてきたコンテンツが固定ヘッダーの**下に潜り込む**ようにするために必要です。また、ページ内リンクのジャンプ先には `scroll-mt-40`（`scroll-margin-top`）を指定し、固定ヘッダーの高さの分だけスクロール位置をずらすことで、見出しがヘッダーに隠れる問題を防いでいます。固定表示と組み合わせるときに忘れがちなポイントです。

### Next.js App Routerのファイル規約とメタデータ

Next.jsのApp Routerでは、`app/favicon.ico` や `app/apple-icon.png` といった**特定のファイル名を置くだけでアイコンとして自動認識される**ファイル規約があります。便利な反面、`metadata.icons` で明示的に指定した設定よりもファイル規約が優先されるため、テンプレート由来のファイルが残っていると「設定したはずのアイコンが表示されない」という今回のような事象が起こります。使わない規約ファイルは削除し、アイコンの参照先を一本化することで解決しました。

### GitHub Actionsによる静的チェックの自動化

GitHub Actionsは、GitHubへのpushやプルリクエスト作成をトリガーに任意の処理を自動実行できるCI/CDの仕組みです。今回追加したワークフローは、`find` と `grep` を組み合わせて対象ファイルから `console.log` / `console.info` / `debugger` を検索し、見つかった場合はジョブを失敗させることで、デバッグコードの消し忘れがmainブランチに混入するのを防ぎます。検出結果は `$GITHUB_STEP_SUMMARY` に出力しており、実行結果のサマリー画面から該当箇所をすぐ確認できます。人間のレビューで見落としやすい機械的なチェックこそ、自動化の効果が高い領域です。

## 総括

ver4のリリースを無事に終え、ver5に向けた新しいサイクルが始まりました。今回は、ヘッダー固定表示やファビコン修正といったUI改善に加えて、`console.log` 検出のGitHub Actions、プルリクエストのテンプレート強化、リリース手順のドキュメント化と2名体制化など、**開発を支える仕組みへの投資**が目立つ回となりました。

リリースで見つかったバグを「完璧を目指すか、スピードを取るか」という軸で率直に振り返り、新しいメンバーの指摘から改善点を拾い、会議の進め方そのものも見直す──機能開発だけでなく、チームとして成長していく過程を感じられる定例でした。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
