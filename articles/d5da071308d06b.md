## 概要

本記事は、[チーム開発記録55：AIレビューのトークン削減](https://zenn.dev/singularitylabs/articles/ac86a17c7a4375)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回の定例までに、**バージョン8.0.0の本番リリース**が完了しました。前回までに整備したGitHub Actionsによる半自動リリース手順を初めて本番で運用した回であり、途中「スカッシュ＆マージ」に起因する履歴同期のトラブルに見舞われながらも、無事リリースまでたどり着きました。あわせて、Slackや共有ドライブなどへの入口をまとめた**クイックリンクページ**も新機能としてリリースに含まれています。

会議では、リリーストラブルの原因と再発防止策の共有に加えて、設計書にUIモック画像を自動生成して載せる仕組みの検討結果（結論は見送り）、Dependabotで検出された64件の脆弱性への対応方針、完了イシューの運用改善など、開発プロセスをめぐる議論が中心となりました。イシューボードはすでにバージョン9の開発へと移行しています。

## 開発したもの

### バージョン8.0.0の本番リリース

GitHub Actionsで半自動化した手順による、初めての本番リリースを実施しました。流れは次のとおりです。

1. **リリースPR作成**のワークフローを実行すると、mainブランチをreleaseブランチへマージするプルリクエストが、バージョン番号などのパラメーター込みで自動作成される
2. プルリクエストの内容確認は人間が行い、データベースのマイグレーションや初期データ投入が必要であればあわせて実施する
3. プルリクエストをマージすると、本番環境へのデプロイが自動的に行われる
4. **フォーク同期**のワークフローで、本番環境を管理するフォーク先リポジトリへ変更を反映する（フォークはリポジトリをまるごとコピーするGitHubの機能です）
5. 本番環境での動作確認後、**リリース作成**のワークフローでタグとリリースノートを自動生成する

途中でトラブルはあったものの（詳細は「会議の様子」で紹介します）、履歴を再接続するback-mergeのプルリクエストで復旧し、リリースは成功しました。

### クイックリンクページの実装

Slack・共有ドライブ・SNSなど、シンラボ関連の外部サービスへの入口を一覧できる「クイックリンク」ページを実装しました。サイドバーとトップページからアクセスできます。

リンク情報はデータベースではなく定数ファイルで管理し、カテゴリーごとに「直リンク方式」か「詳細モーダル方式」かの表示モードを切り替えられる設計です。

```typescript
// app/constants/links.ts（抜粋）
export const QUICK_LINK_CATEGORIES: QuickLinkCategoryType[] = [
  {
    id: "tools",
    name: "ツール",
    displayMode: "direct",
    links: [
      {
        name: "シンラボSlack",
        url: "https://sinlab-community.slack.com/archives/CCU85HMHA",
        description:
          "シンラボメンバーの日々のコミュニケーションツールです。プロジェクトの連絡やイベント告知などが行われています（リンク先は「00-ガイドライン」チャンネル）。",
        logoPath: "/links/slack.svg",
      },
      // ...
    ],
  },
  // ...
];
```

カードコンポーネントは表示モードに応じて挙動を変えます。ツール類はワンクリックで新しいタブで開き、自作サービスは「詳細」ボタンから説明モーダルを開く構成です。

```tsx
// app/(authenticated)/links/components/LinkCard.tsx（抜粋）
// 直リンク方式：カード全体をリンクとして新タブで開く
if (displayMode === "direct") {
  return (
    <Card
      component="a"
      href={link.url}
      target="_blank"
      rel="noopener noreferrer"
      shadow="sm"
      padding="0"
      radius="md"
      withBorder
      className="w-full h-full min-h-[14rem] flex flex-col transition-shadow hover:shadow-md"
    >
      {cardContent}
    </Card>
  );
}
```

### AI向けドキュメントへのフォーマットチェック手順の追記

AIにコード変更をさせた際、フォーマット崩れがビルド段階まで見過ごされる問題に対応するため、GitHub CopilotやClaude向けの指示ファイルに、フォーマットチェックの手順を追記しました。

```markdown
- 変更後は `npm run lint` → `npm run type-check` → `npm run format:check` → `npm run build` を順に実行する（ビルド前に整形差分を検知する）
- `npm run format:check` で整形差分が検出された場合は、`npm run format` を実行して整形を適用し、整形差分を含めてコミットする
```

AIが自律的に品質チェックを回せるように、チェックの順序と差分検出時のリカバリー手順まで明文化しているのがポイントです。環境ドキュメントであるWikiへの反映も含め、担当メンバーが引き続き対応を進めています。

### GitHub Actionsのアクションをv5系へ更新

CIで利用している `actions/checkout` と `actions/setup-node` を、Node.js 20の非推奨化に対応したv5系へ一括更新しました。ビルド・テスト・型チェック・リリース関連など、すべてのワークフローファイルが対象です。

```diff
       - name: Checkout repository
-        uses: actions/checkout@v4
+        uses: actions/checkout@v5

       - name: Setup Node.js ${{ matrix.node-version }}
-        uses: actions/setup-node@v4
+        uses: actions/setup-node@v5
```

## 会議の様子

### スカッシュ＆マージが招いた履歴トラブルと再発防止

リリース報告の中心は、途中で発生したトラブルの共有でした。原因は、releaseブランチへのマージに使っていた**スカッシュ＆マージ**です。スカッシュは複数のコミットを1つに圧縮してから反映する機能で、コミット数が膨大にならない利点から採用していましたが、圧縮されたコミットは元の履歴を持たないため、mainブランチとreleaseブランチの**履歴が同期されなくなる**という弊害が発覚。リリース処理がうまく進まなくなってしまいました。

復旧は、バージョン6の時点からブランチを切り直し、バージョン7に履歴をきちんと追加するステップを挟むことで対応しました。再発防止策として、**今後releaseブランチへのマージはスカッシュを使わず通常のマージコミットで行う**ことを決定し、経緯はWikiのトラブルシューティングに記録しました。

また、リリース手順で使うワークフローが複数あることを受けて、「ワークフロー名に01、02のような番号を振れば、実行順が一目で分かるのでは」という改善案が出ました。テスト系のワークフローも同様に番号を振る方向で、イシューに追記して対応することになりました。

### 設計書のモック画像自動生成 — 検討の末に「見送り」

数週にわたって調査してきた、機能設計書にUIモック画像を載せる仕組みについて、担当メンバーから検討結果が共有されました。当初候補だったdraw.ioは使わず、**HTMLとCSSでモックを書き、ブラウザ表示をPlaywrightで撮影してPNG化する**方式に落ち着いたとのこと。コマンド一発で全画像を生成でき、生成された画像を機能設計書へ読み込む形です。以前SVGでの生成も試したものの、AIではHTMLの見た目どおりのSVGを作れず断念した経緯も共有されました。

議論の焦点は「そもそも何のためのモックか」でした。リードからは「今の実装に寄せて画像を作るなら、それは設計図を綺麗にするだけで本末転倒。**設計からモックを起こす方向でこそ価値がある**」という指摘があり、担当メンバーも「その方向も可能なことは確認済み」と応じます。一方で、設計のたびにモックの作成・修正・レビューのやり取りが発生して設計プロセスが重くなること、AI利用によるトークン消費、画像ファイルの増加（1枚あたり約20KBとはいえ塵も積もれば）、指示の出し方への習熟が必要なことなど、コストも具体的に挙がりました。

最終的に、**見栄えの向上というメリットに対して工数と手間がアンバランス**という判断で、今回の導入は見送りに。ただし画像生成のコード自体は別ブランチとして残すことにしました。mainとコンフリクトしにくい構成のため、必要になればリベースで追従して復活できます。「ポータルサイト以外でも、ガイド作成などに使えそう」という前向きな声もあり、調査の成果は無駄にしない形で決着しました。

### Dependabotの脆弱性64件への対応

リードが今週から着手したのが、**Dependabotで検出された64件の脆弱性への対応**です。アラートにはクリティカル1件も含まれており、放置されていた依存パッケージの更新を一括で進めています。

レビューを依頼された担当メンバーからは「基本的に受け入れでよいと思うが、**1つ1つのバージョンアップの妥当性は情報収集して確認したい**」「急ぎなのは分かるが、確実に対応できる運用方法であることも含めて確認させてほしい」と、スピードと確実性のバランスを取る姿勢が示されました。今後のアップデート運用についても、「自動更新ではなく、必ず人がチェックしてOKなら更新する手動更新にしたい」という方針で一致し、運用方法の検討は別イシューとして残すことになりました。

また、セキュリティに関わる修正であることから、「バージョン9のリリースを待たず、**バージョン8.1のようなパッチリリースで先に反映してもよいのでは**」という案も出ています。こちらはマージ完了後に改めて相談する予定です。

### 完了イシューは「In Review」を経由する運用へ

イシュー運用にも改善が入りました。きっかけは「完了したイシューは、一度この会議で共有してからクローズしたい。**情報共有なしにタスクがクローズされない仕組みにしたい**」という提案です。議論の結果、完了したイシューはすぐにクローズせず「In Review」列に置き、会議で共有してからクローズする運用をまず試してみて、やりにくければ戻すことになりました。

このほか、レコード復活機能のテストをめぐって、担当者間で「ボールがどちらにあるか」の認識がずれていたことが会議中に発覚し、その場で整理して解消する一幕もありました。ちょっとした認識ずれを定例で拾って正せるのも、こうした進捗共有の場の価値といえそうです。

## 活用した技術

### スカッシュ＆マージとGitの履歴

GitHubのマージ方法には、通常のマージコミット・スカッシュ＆マージ・リベースの3種類があります。スカッシュ＆マージは、プルリクエストの複数コミットを1つに圧縮してから取り込むため、履歴がシンプルになる反面、**圧縮後のコミットは元のコミットとの親子関係を持ちません**。

mainとreleaseのように2つのブランチを行き来させる運用では、この「履歴の断絶」が命取りになります。Gitは共通の祖先コミットを基準に差分を判定するため、履歴を持たないコミットができると、ブランチ同士の同期が正しく行えなくなるのです。今回のように**長期のブランチ間マージにはマージコミットを使う**のが定石であり、それをトラブルから学べたのは貴重な経験でした。

### Dependabotによる依存関係の脆弱性管理

Dependabotは、GitHubに組み込まれた依存パッケージの監視機能です。プロジェクトが利用しているライブラリに既知の脆弱性が見つかると、深刻度（クリティカル〜低）付きでアラートを発行し、更新のプルリクエストを自動作成することもできます。

便利な一方で、依存パッケージの更新は「アプリが動かなくなるリスク」と隣り合わせです。メジャーバージョンアップには破壊的変更が含まれることも多く、今回チームが選んだ「自動マージはせず、更新の妥当性を人間が確認してから取り込む」運用は、小規模チームにおける現実的な落とし所といえます。64件を放置せず一括で棚卸しし、以降は都度対応に切り替えるという進め方も参考になるはずです。

### PlaywrightによるHTMLモックの画像化

今回は導入見送りとなったものの、検討されたモック画像生成の仕組みは技術的に興味深いものでした。Playwrightはブラウザ操作を自動化するツールで、E2Eテストでの利用が有名ですが、**HTMLをブラウザで実際にレンダリングした結果をスクリーンショットとして保存する**用途にも使えます。

AIに直接SVGを描かせると実際の見た目とかけ離れた画像になりがちですが、「AIにはHTML+CSSを書かせ、レンダリングと撮影はブラウザに任せる」構成なら、CSSフレームワークの表現力をそのまま活かした忠実なモック画像が得られます。設計ドキュメントへの組み込みは見送られましたが、操作ガイドの挿絵作成など、応用が利きそうなアプローチです。

## 総括

今回は、半自動化されたリリース手順による初のバージョン8.0.0本番リリースを達成した回でした。スカッシュ＆マージ起因の履歴トラブルという想定外の壁にぶつかりながらも、原因を特定して復旧し、再発防止策とWikiへの記録まで一気通貫で対応できたのは、リリース手順を仕組み化してきた積み重ねの成果といえます。

会議では、モック画像生成の「導入見送り」という判断も印象的でした。数週間かけた調査であっても、目的とコストを天秤にかけて冷静に見送る。一方でコードはブランチに残して将来の再利用に備える。機能を作ることと同じくらい、「作らない・今はやらない」判断を丁寧に行うのがこのチームの持ち味です。バージョン9の開発は、Dependabotの脆弱性対応という足元の守りから始まります。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
