## 概要

本記事は、[チーム開発記録59：役職タグ表示と環境変数の暗号化](https://zenn.dev/singularitylabs/articles/31cda9c347c880)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、ポータルサイトと学習支援アプリ「sinlab-study」を隔週交互で開発しています。今回はsinlab-studyの回で、**承認前のユーザーを「お試し（trial）ユーザー」と定義し直す設計**がマージされました。

これまでsinlab-studyは、Googleログインした直後のユーザー（`status = 'pending'`）を承認待ち画面に隔離し、管理者が承認するまでアプリの中身を一切見せない仕様でした。今回の設計では**承認待ち画面そのものを廃止**し、承認前でもそのままログインできるようにしたうえで、「お試し公開」と指定されたコンテンツだけを閲覧・提出できるようにします。入会前に中身を体験してもらい、入会の動機につなげる狙いです。

一見すると「フラグを1つ足すだけ」に見える変更ですが、実際には**Row Level Security（RLS）ポリシーの再設計**、**upsertとRLSの相性という落とし穴**、**RLSをバイパスするservice_roleをどこまで許すか**といった論点が芋づる式に出てきました。今回マージされたのはコードではなく設計書のみで、実装はこの設計に沿って現在進行中です。

* 技術スタックは[こちら](https://github.com/Singuralitylabs/portal-site/wiki)をご参考ください

## 開発したもの

### 承認待ち画面の廃止 — 「お試しユーザー」という再定義

今回マージされたPRは、要件定義書・機能設計書・データベース設計書・テスト設計書、そしてAI向けのプロジェクト指示書（`CLAUDE.md`）を横断して更新するものでした。中心にあるのは、ユーザーステータスの意味づけの変更です。

要件定義書のユーザーステータス表は、次のように書き換えられました。

| ステータス | 説明 |
|:--|:--|
| `pending` | 承認待ち = **お試し（trial）ユーザー**。ログインしてサービスを利用できるが、閲覧・提出できるのはお試し公開コンテンツ（`is_open_to_trial = true`）のみ。承認待ちであることはアプリ内バナーで通知する |
| `active` | 承認済み（学習サービスに制限なくアクセス可能） |
| `rejected` | 却下済み（`/rejected` 却下画面へリダイレクト） |

これに伴い、認証フローの分岐も変わります。従来は「`pending` は `/pending` へリダイレクト」「ステータス取得に失敗したら `/pending`」という扱いでしたが、新しい設計では次のようになりました。

- 未認証・**ステータス取得不能（null）** → `/login` にリダイレクト（フェイルクローズ）
- `rejected` → `/rejected` にリダイレクト
- `active` と `pending`（お試し）→ アプリへのアクセスを許可

ステータスが取れなかったときの行き先が `/pending` から `/login` に変わっている点が地味に重要です。「よく分からない状態のユーザーは、いちばん権限の低いところへ落とす」というフェイルクローズの原則が、承認待ち画面の廃止によってあらためて徹底された形です。

`/pending` については、旧URLをブックマークしている人がいる可能性を考えて404にはせず、`/` へリダイレクトする方針が明記されました。設計書には、その実装をどこに置くかまで書き込まれています。

> 1. `shouldSkipMiddleware()` の対象から `/pending` を外す（対象に残したままだとプロキシが判定せず素通りさせ、ページ削除後は404になる）
> 2. ステータス判定を通過した `active` / `pending` ユーザーについて、パスが `/pending` の場合は `/` へリダイレクトする

リダイレクト判定をプロキシ（`proxy.ts`、Next.js 16におけるMiddlewareの後継）1箇所に集約することで、`rejected` は既存のステータス判定で `/rejected` に、ステータス取得不能時は `/login` に流れ、**旧URLでも各ステータスの行き先が通常パスと一致する**ようになります。

### お試し公開フラグ `is_open_to_trial`

データベース側の変更は、学習コンテンツテーブルへのフラグ1列の追加です。

| カラム | 型 | NULL | デフォルト | 制約 | 説明 |
|:--|:--|:--|:--|:--|:--|
| `is_open_to_trial` | BOOLEAN | NO | false | NOT NULL | お試し公開フラグ。true の場合、お試しユーザー（`status = 'pending'`）にも公開する |

ポイントは、既存の公開フラグ `is_published` との関係を設計書で明示したことです。

> `learning_contents` はさらに `is_open_to_trial` フラグを持ち、お試しユーザー（`status = 'pending'`）に見えるのは `is_published = true AND is_open_to_trial = true` の行のみ。2つのフラグは AND で効き、`is_open_to_trial = true` でも `is_published = false` なら誰にも公開されない

「お試し公開にチェックを入れたのに未公開のコンテンツが表に出てしまった」という事故を防ぐため、**通常の公開制御が常に優先される**ことをルールとして固定しています。設定はコンテンツ管理画面（`/manage/contents`）のチェックボックス「お試しユーザーにも公開する」から行い、デフォルトは未チェックです。

### RLSにステータス判定を持ち込む

sinlab-studyはアクセス制御をRLSで担保しています。今回、そのポリシーに**ステータス判定**という3つ目の軸が加わりました。従来からあるロール判定・本人判定に続く追加です。

判定用のヘルパー関数も1つ増えました。

| 関数 | 返り値 | 説明 |
|:--|:--|:--|
| `get_user_role()` | TEXT | 認証ユーザー（`auth.uid()`）の `role` を返す（`is_deleted = false` が対象） |
| `get_user_id()` | INTEGER | 認証ユーザーの `users.id` を返す（`is_deleted = false` が対象） |
| `get_user_status()` | TEXT | 認証ユーザーの `status`（`pending` / `active` / `rejected`）を返す（`is_deleted = false` が対象）。お試しユーザーのコンテンツ制限に使用する |

これらは `users` テーブル自身のRLSと無限再帰を起こさないよう `SECURITY DEFINER` で定義され、未認証（`anon`）からREST RPC経由で呼ばれないようEXECUTE権限を絞る、という既存のパターンをそのまま踏襲しています。設計書には「新たにヘルパー関数を追加する際も、同じパターンを踏襲する」という一文が追記されました。

そのうえで、学習コンテンツのSELECTポリシーが次の条件に差し替えられます。

```sql
-- learning_contents の SELECT ポリシー条件
(
  is_published = true
  AND is_deleted = false
  AND (
    (select get_user_status()) = 'active'
    OR ((select get_user_status()) = 'pending' AND is_open_to_trial = true)
  )
)
OR (select get_user_role()) IN ('admin', 'maintainer')
```

`(select get_user_xxx())` と副問い合わせで包んでいるのは、行ごとに関数が再評価されるのを防いでInitPlan化させるためです（Supabaseの `auth_rls_initplan` 対策）。

興味深いのは、**ステータスによる絞り込みを追加するのは `learning_contents` の1テーブルだけ**に閉じた点です。親階層にあたるテーマ・フェーズ・週のテーブルは、従来どおりステータス不問で公開分を全員に見せます。

> 親階層（`learning_themes` / `learning_phases` / `learning_weeks`）はステータスによる絞り込みを行わず、従来どおり公開分を認証済み全ユーザーが参照できる。お試しユーザーにもコースツリーの骨格（テーマ・フェーズ・週）を見せてロック表示するための設計であり、これによりステータス判定の対象は `learning_contents` の1テーブルに閉じる。

「何が学べるかは見せる、中身は見せない」という体験設計と、「変更するテーブルを最小限にする」という実装上の都合が、きれいに同じ結論に着地しています。お試し非公開のコンテンツはツリー上に鍵アイコンで表示され、直リンクで開いた場合もロック画面が出ます。

### upsertの落とし穴 — INSERTだけに条件を課すと素通りする

今回の設計でいちばん技術的に面白いのが、進捗・提出物の**書き込み制限**の部分です。

お試しユーザーがブラウザの開発者ツールなどからAPIを直接叩き、お試し非公開コンテンツの進捗を記録してしまわないよう、RLSの書き込みポリシーにも「対象コンテンツが自分に可視であること」という条件を足します。

```sql
-- user_progress / submissions の INSERT・UPDATE に課す EXISTS 条件
EXISTS (SELECT 1 FROM learning_contents WHERE id = content_id)
```

シンプルに見えますが、これは `learning_contents` のSELECTポリシーが適用されることを利用したものです。お試しユーザーの場合、この EXISTS はお試し公開コンテンツに対してのみ真になります。ステータス別の分岐をアプリ側に書かなくても、RLSがすでに織り込んだ可視性をそのまま再利用できるわけです。

そして落とし穴が、この条件を**UPDATEにも課す**必要があるという点でした。

> 進捗API（`/api/progress`）は upsert（`onConflict: user_id,content_id`）で、既存行がある場合は UPDATE 経路を通る。INSERT のみに条件を課すと2回目以降の更新がすり抜けるため、UPDATE にも同じ条件が必要。

sinlab-studyの進捗は「完了／未完了」のトグルで、`(user_id, content_id)` のユニーク制約に対する upsert で実装されています。つまり初回はINSERT、2回目以降はUPDATEです。INSERTだけを守っても、**1回でも進捗を付けたことがあるコンテンツは以降フリーパス**になってしまいます。設計書には、この気づきがデータベース設計書のupsertパターンの節にも注意書きとして残されました。

> **RLSポリシー設計上の注意**: 上記のとおり2回目以降の操作は UPDATE 経路を通るため、書き込み制限を追加する際は INSERT だけでなく UPDATE ポリシーにも同じ条件を課す必要がある

一方、提出物（`submissions`）は作成後に受講生が更新・削除することがないためUPDATE/DELETEのポリシー自体が存在せず、EXISTS条件はINSERTだけでよい、という非対称も明記されています。

なお、この条件はステータスを問わず適用されるため、`active` ユーザーも未公開コンテンツや存在しないIDには書き込めなくなります。従来は未公開コンテンツへの書き込みが素通りし、存在しないIDはFK違反で500になっていたものが、いずれも403に統一されるという副次的な改善です。

### service_role をどこまで許すか

RLSを強化すると、今度は**アプリ側が必要な情報を取れなくなる**という副作用が出ます。お試し非公開コンテンツは、タイトルすら通常クライアントから取得できなくなるためです。しかしツリーにロック項目を並べるには、少なくともタイトルと並び順が要ります。

ここで登場するのがRLSをバイパスできる `service_role` クライアントですが、便利な分だけ危険でもあります。そこで設計書は、**使ってよい箇所を2つに限定**しました。

| 用途 | 理由 |
|:--|:--|
| ツリー表示の一覧サマリー取得 | ロック済みコンテンツのタイトル・並び順を表示するため |
| コンテンツ詳細ページの存在チェック | 直リンク時に「存在しない（404）」と「ロックされている」を区別するため。通常クライアントでは両者とも0行になり判別できない |

さらに、この2箇所のクエリに課す条件まで具体的に決めています。

| 項目 | 内容 |
|:--|:--|
| WHERE 条件 | **`is_published = true AND is_deleted = false` で必ず絞る**（RLSが効かないため、通常の公開制御をアプリ側で再現する） |
| カラム許可リスト | `id, title, content_type, display_order, is_open_to_trial` のみ。本文カラム（`text_content` / `video_url` / `pdf_url` / `exercise_instructions` / `reference_answer` / `hint`）は select しない |
| 0行だった場合 | 未公開・論理削除済み・存在しないコンテンツのいずれかであり、**404 として扱う**（ロック画面は表示しない） |

条件を省くと「`active` ユーザーにすら見えない未公開コンテンツのタイトルが、お試しユーザーには見える」という逆転が起きる、という危険まで設計書に書き残されています。RLSを外す判断をするなら、**外した分の防御をアプリ側で明示的に再現する**というルールです。

### 設計に残された「既知の制約」

今回の設計書で好感が持てるのは、解決していない部分を隠さず書いている点です。

- **お試し公開フラグの取り下げ**：提出済みコンテンツの `is_open_to_trial` を後から `false` に戻すと、提出履歴画面でコンテンツのタイトルが取得できず表示が欠ける。提出レコード自体は残り、承認後は再表示される。運用上まれなケースのため、タイトル欠落時のフォールバック表示に留める
- **スライドPDF**：スライドは公開バケット配信でオブジェクトキーが連番のため、ロック済みコンテンツのPDFもURL推測で取得できる。これは本機能以前からの既存の性質であり、署名付きURL化は別issueで対応する
- **`pending` という名前**：DB上のstatus値 `'pending'` 自体のリネームは別issueで対応予定のため、新設するフラグ名・UI文言にのみ trial 系の名称を用いる

「今回のスコープではない」ものを別issueに切り出しつつ、**なぜ今やらないのか**を設計書に残しておく。この積み重ねが、後から入ったメンバーやAIが設計を読んだときの判断材料になります。

## 会議の様子

### 進捗は足踏み、それでも優先順位は動かす

この日の定例は、正直なところ進捗が芳しくない回でした。AIトークン使用量のモニタリング・アラート機能は担当者の手が回らず継続中、トークン消費削減のPRはレビュー結果の確認待ち。「レビューでヒントを生成する機能」と「講座資料を渡す機能」については、**トークン削減のPRがマージされないと着手できない**という依存関係があり、そちらの完了を待っている状態でした。

司会からは「優先順位をつけてやるのは正しい」「手が回らないとなったら誰かに投げるのも大事」という声かけがありつつ、依存関係のあるタスクについては「そもそも講座資料を渡す必要があるのか、というところから検討したほうがいい」という、**着手前にスコープ自体を疑う**姿勢も共有されました。待っている間に前提を見直しておけば、いざ着手できるようになったときに無駄な実装をせずに済みます。

リードエンジニア自身も「サムネイル画像の管理画面からのアップロード機能」に着手できておらず、優先度を下げていることを率直に共有しました。代わりに着手しているのが、今回の記事の主題であるお試し機能です。**やることを増やさず、優先的にやると決めたものから順に片付ける**という判断が、そのまま共有されています。

### 設計だけ先にマージする、という進め方

会議のハイライトは、マージ済みの設計PRの共有でした。「具体的に何を変えたか」として、承認待ちのユーザーを一旦お試しユーザーと定義したこと、承認待ち画面へ飛ばす仕様をやめてログインできるようにしたこと、コンテンツテーブルにお試し公開フラグを追加したこと、そしてRLSポリシーにロール判定・本人判定に加えて**ステータス判定**が入ることが説明されました。ステータスを確認するための関数を1つ追加した、という点も共有されています。

注目したいのは、この時点でマージされたのが**設計書だけ**だという点です。実装はこの設計に基づいて現在進行中で、コードのPRはまだ出ていません。細かいSQLポリシーの中身については「見てみたい方はプルリクを見てください」と会議では深追いせず、設計の意図と全体像の共有に留めました。

AI駆動開発を前提にしているチームにとって、設計書を先に固めてマージしておくことは実利があります。設計書は人間の合意形成の場であると同時に、**AIに渡すコンテキストそのもの**でもあるからです。今回のPRが `CLAUDE.md`（AI向けのプロジェクト指示書）を含む4つのドキュメントを横断的に更新しているのは、その表れといえます。

### リリーススケジュールの相談

sinlab-study・ポータルサイトともに、次のリリースは8月のお盆休み期間あたりを目標に置く方針が共有されました。sinlab-studyについては8月9日あたりを希望しつつ、「遅れる可能性はあるし、間に合わなくても構わない」という現実的なスタンスです。ポータルサイト側は「今回はユーザーにとって何かが大きく変わるアップデートではないので、8月中に急ぐ理由は特にない」という判断でした。

日程調整では、メンバーから「9日は終日PCを見られないかもしれない」という申告があり、承認のタイミングは黙々会にこだわらず別日でも構わない、という形で柔軟に調整することになりました。**リリース日を固定してから人を合わせるのではなく、人の都合に合わせて日を動かす**。ボランティアベースのチーム開発では、このくらいの緩さが継続の条件だと感じます。

### レビュアーの割り当てと、ToDoが増え続ける問題

会議の終盤、前回割り振れていなかったメンバーへのイシューアサインが行われました。欠席していたメンバーの分も含めて、その場で担当を決めていく形です。1つは「自分で指摘したバグが直っていなかったので、自分でやろうかな」という本人の申し出、残り2つはその場で挙手と指名で決着。「今パッと決めてしまってもいいかな」という司会の判断で、持ち帰らずに確定させました。着手順は担当者の判断に任せる、という余白も添えられています。

一方で、ToDoが増える一方であることには危機感も共有されました。「消化の必要はある。どうするかというと消化するしかないんだけど、ぼちぼちやっていきましょう」という、身も蓋もないけれど正直な結論です。

関連して、**プルリクエストをGitHub Projectに紐付けない運用**の再確認もありました。AIがPRを作成すると自動でプロジェクトに紐付いてしまうため、ToDo列が実態以上に膨らんで見える、という現象が起きていたのです。気づいた人が外す、という運用でカバーすることになりました。AI駆動開発の副作用が、こういう地味なところにも出てくるのは興味深い発見です。

## 活用した技術

### RLSにステータスを織り込む二層防御

今回の設計の骨格は、**アプリ層とデータベース層の二層で同じ制限をかける**というものです。Server Componentsでステータスとお試し公開フラグを見てロック判定を行い（第一層）、RLSでも `learning_contents` のSELECTをお試し公開分に絞る（第二層）。どちらか一方が抜けても、もう一方が守ります。

さらに設計として洗練されているのは、**アプリ層がRLSの結果を再利用している**点です。進捗API・提出APIの可視性チェックは「通常クライアントで対象 `contentId` をSELECTし、0行なら403」という一行の判定に集約されました。

> `learning_contents` のRLSがステータスを織り込むため、アプリ層でステータス別の分岐を書く必要はない。この方式は「存在しない contentId」「未公開コンテンツ」も同時に弾ける。

アプリ層で `if (status === 'pending') { ... }` のような分岐を書き始めると、ステータスが増えたときや条件が変わったときに修正箇所が散らばります。「可視かどうか」の判断をRLSに一本化し、アプリ層は**その結果を問い合わせるだけ**にしておけば、ルールの変更はポリシー1箇所で済みます。認可ロジックの単一情報源（Single Source of Truth）をどこに置くか、という設計判断です。

### upsertとRLS — 書き込み経路を数え上げる

「INSERTだけに条件を課すと2回目からすり抜ける」という今回の発見は、RLSを使うすべてのプロジェクトに効く教訓です。

RLSのポリシーは操作（SELECT / INSERT / UPDATE / DELETE）ごとに定義します。一方、アプリケーションコードから見ると `upsert()` は**1つのメソッド呼び出し**にしか見えません。この抽象度のギャップが穴を生みます。ORMやクライアントライブラリが提供する便利なメソッドが、データベースレベルでどの操作に展開されるのかを把握していないと、「書き込みを制限したつもり」が実際には半分しか塞げていない、ということが起こります。

今回のチームは、この点を単に修正するだけでなく、「upsertは2回目以降UPDATE経路を通る」という一般則としてデータベース設計書に書き残しました。次に誰かが（あるいはAIが）別のテーブルに書き込み制限を追加するとき、同じ穴を掘らずに済みます。

### service_role とRLSバイパスの扱い

Supabaseの `service_role` キーはRLSを完全にバイパスします。強力な反面、一度使い始めると「RLSで守っているつもりの経路が実はバイパスされていた」という状況を招きやすい仕組みでもあります。

今回の設計は、この危険に対して**ホワイトリスト方式**で臨みました。受講生向けのコンテンツ配信経路でRLSをバイパスしてよいのは2箇所だけ、と明示的に列挙し、それ以外は対象外であることまで書いています。加えて、バイパスする以上は失われた防御をアプリ側で再現する義務（`is_published = true AND is_deleted = false` の明示、本文カラムを含めないカラム許可リスト、0行なら404）も条件として固定しました。

「便利な抜け道は、使ってよい場所と守るべき条件をセットで文書化する」——RLSに限らず、管理者権限やデバッグ用フラグなど、あらゆる「特権ルート」に応用できる考え方です。

### 体験設計としての「ロック表示」

技術的な話から少し離れますが、今回の設計には**プロダクトとしての意図**もはっきり現れています。

お試しユーザーに対して、コースツリー（テーマ・フェーズ・週・コンテンツ一覧）は全件表示したうえで、お試し非公開のものだけを鍵アイコンでロックする。「そもそも存在を隠す」のではなく「あることは見せて、中身は見せない」という選択です。何が学べるのかを提示することが入会動機につながる、という判断が背景にあります。

一方でダッシュボードの進捗率は、お試しユーザーではお試し公開コンテンツのみを分母とします。ツリーは全件表示なのに進捗率の分母は限定的、という一見ちぐはぐな仕様ですが、設計書はこれを「体験範囲内の進捗を示す意図的なもの」と明記しています。**進捗率を見て「まだ数％しか進んでいない」と落ち込ませない**ための配慮であり、意図せぬ不整合と区別できるよう文章で残されているのが重要な点です。

## 総括

今回は、**「フラグを1つ足す」で済みそうな機能が、認可の設計をどこまで揺さぶるか**がよく見える回でした。承認待ち画面をやめてお試し利用を許すという一見シンプルな方針転換が、RLSポリシーの再設計、upsertとポリシー適用範囲のズレ、service_roleの取り扱いルールにまで波及していきました。

そして今回マージされたのが**設計書だけ**だったことにも意味があります。AIに実装を任せる前提なら、人間が握るべきは「何を作るか」と「なぜそう作るか」であり、それを文書として先に固めておけば、AIも人も同じ設計図を見て動けます。既知の制約や「今回やらない理由」まで書き残しているのは、未来の実装者への申し送りとして効いてくるはずです。

進捗という意味では足踏みの多い週でしたが、依存関係で止まっているタスクのスコープを問い直したり、増え続けるToDoの原因（AIが作るPRの自動紐付け）に手を打ったりと、**止まっている時間を使って前提を整える**動きが取れていた回でもありました。

シンギュラリティ・ラボでは、こうしたチーム開発に一緒に取り組む仲間を募集しています。設計の議論に加わりたい方も、まずは手を動かしてみたい方も、興味があればぜひのぞいてみてください。
