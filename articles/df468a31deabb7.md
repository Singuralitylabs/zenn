## 開発したもの

### メンバー一覧・モーダルへの役職タグ表示

以前の定例で設計した役職タグ機能の実装が完了しました。データベースに役職マスターの `positions` テーブルと、ユーザーと役職を紐づける中間テーブル `position_tags` を追加し、メンバー一覧画面のカードと詳細モーダルに「チームリーダー」などの役職バッジを表示します。

メンバー取得処理では、Supabaseのリレーション指定を使って、ユーザー情報と一緒に役職も取得するようにしました。

```typescript
// app/services/api/users-server.ts（抜粋・変更後）
const { data, error } = await supabase
  .from("users")
  .select(`id, display_name, bio, avatar_url, position_tags(positions(id, name, is_deleted))`)
  .eq("status", "active")
  .eq("is_deleted", false)
  .eq("position_tags.positions.is_deleted", false)
  .order("created_at", { ascending: true });
```

担当メンバーによると、ネストしたリレーションを取得する際のSupabaseの型推論がうまく効かないケースがあったため、明示的に型を変換してから使う処理を挟んでいます。

```typescript
// app/services/api/users-server.ts（抜粋）
// Supabaseの型推論では positions が配列になるため、MemberType[] 型に変換
const transformedData: MemberType[] = data.map((user) => ({
  id: user.id,
  display_name: user.display_name,
  bio: user.bio,
  avatar_url: user.avatar_url,
  position_tags: user.position_tags
    .filter((tag) => {
      const positions = Array.isArray(tag.positions) ? tag.positions[0] : tag.positions;
      return positions?.is_deleted === false;
    })
    .map((tag) => ({
      positions: Array.isArray(tag.positions) ? tag.positions[0] : tag.positions,
    })),
}));
```

UI側は、Mantineの `Badge` コンポーネントをカードとモーダルにそれぞれ追加し、名前の横に役職を並べる形です。

```tsx
// app/(authenticated)/members/components/MemberDetailModal.tsx（抜粋）
{memberInfo.position_tags && memberInfo.position_tags.length > 0 && (
  <Group gap="xs">
    {memberInfo.position_tags.map((tag) => (
      tag.positions && (
        <Badge key={tag.positions.id} variant="light" size="sm">
          {tag.positions.name}
        </Badge>
      )
    ))}
  </Group>
)}
```

この機能は並行して開発中だったSNSアカウント編集機能とファイルが重なっており、担当メンバー同士でコンフリクトを解消しながらのマージとなりました。お互いの変更を消さずに統合する、チーム開発らしい調整も経験できた実装です。

### コンテンツの新規登録・編集画面に表示順の設定欄を追加

動画・資料・アプリのコンテンツを登録するとき、ポータルサイト上に表示される順番を指定する手段がこれまでなく、**データベースを直接編集する以外に方法がない**状態でした。そこで、新規登録・編集モーダルに「表示順」の選択欄を追加しました。

表示順の計算やカテゴリー変更時の再取得といったロジックは `useDisplayOrderForm` という共通のカスタムフックにまとめ、3つの画面（動画・資料・アプリ）から同じように使えるようにしています。

```tsx
// app/(authenticated)/documents/components/DocumentFormModal.tsx（抜粋）
// 表示順操作フック
const { position, setPosition, positionOptions, parsePosition, handleCategoryChange } =
  useDisplayOrderForm("documents", form.category_id, initialData?.id, !!initialData);

// （中略）
<Select
  label="表示順"
  data={positionOptions}
  value={position}
  onChange={value => setPosition(value || "last")}
  placeholder="配置位置を選択"
  mb="sm"
/>
```

設計書のレビューとコードレビューを経て、定例後にマージされました。このほか、機能仕様書にカレンダー機能の概要を追記するドキュメント更新も行われています。

## 会議の様子

### GitHub Actions入門 — プルリクエストを守る自動チェック

進捗確認の中で、新しいメンバーから「そもそもGitHub Actionsって何なんですか？」という率直な質問が出ました。リードメンバーはこの機会に、と画面を共有しながら解説します。

GitHub Actionsは、**プッシュやプルリクエスト作成などをトリガーに、GitHub上で自動的に動くプログラム**のことです。このチームでは主にテスト用途で使っており、チェック項目は大きく4つあります。

* **ビルドチェック**：アプリが正常にビルドできるか
* **コンソールログチェック**：本番では不要な `console.log` が残っていないか（チームでは削除する方針）
* **ユニットテスト（Jest）**：現状はサンプルコードの実行確認のみで、実質的なテストはまだ動いていないため一旦無視してよい
* **TypeScriptの型チェック**：型指定に間違いがないか

プルリクエストの下部に「All checks have passed」と表示されていれば全チェックを通過しています。**プルリクを作ったら、まず自分でこの結果を確認し、エラーが出ていれば直してからレビュー依頼する**という運用も改めて確認されました。あわせて、これらの処理がリポジトリ直下の `.github/workflows` ディレクトリ内のYAMLファイルで定義されていること、「Merging blocked」の表示は最低1人のApproveがないとマージできない保護設定によるもので正常であること、「Update branch」ボタンでベースブランチを最新化できる（ただしコンフリクトが起きる可能性もある）ことなど、プルリク画面の見方を一通り共有しました。

### 「担当者」はプルダウン選択＋フリー入力の併用へ

新しく追加されたイシューの1つ、「資料・動画の担当者をユーザーテーブルから選択できるようにする」をめぐって議論が起こりました。現在は担当者名を直接手入力しており、アプリの開発者欄がすでにプルダウン選択になっているのに合わせよう、という提案です。

これに対してあるメンバーから、「**ポータルサイトにアカウントがない人を担当者にできなくなる**のではないか」という指摘が出ました。たとえば講演した本人がサイトに登録していない場合、動画をアップした別の人を担当者にするしかなくなります。さらに「担当者が退会するとユーザーテーブルから取れず表示が空になってしまうのでは」という運用面の懸念も挙がりました。

一方でリードメンバーからは、「担当者は講師である必要はなく、連絡を取りたいときの窓口という位置づけ。**サイトに載せる以上、担当者はアカウント登録くらいはしてほしい**という思いもある」という考えも示されました。ただし、厳密さを求めすぎると使いにくいサービスになるという意見にも一理あるため、最終的には**プルダウン選択とフリー入力の両方を可能にする**という無難な着地になりました。

このほか、使用パッケージのサポート切れ・メモリリーク警告への対応と、マークダウン対応を見据えた説明欄の入力枠の拡大も、新しいイシューとして追加されました。また、開発中のマークダウン対応については、レビューで**クロスサイトスクリプティング（XSS）のリスクが見つかり修正対応中**であることが共有され、マージ後に改めて解説されることになっています。

### ブランチの切り方ミスから学ぶ、cherry-pick実演講座

Wikiへのナレッジ移行のプルリクエストで、「ファイルの削除だけのはずなのに変更ファイルがやたら多い」ことにレビュアーが気づきました。原因を探ると、担当メンバーが**作業中の別ブランチ（SNS編集機能）から新しいブランチを切ってしまった**ことが判明。ブランチを切ると元のブランチの内容がそのまま引き継がれるため、無関係の修正がプルリクに混ざってしまったのです。「まずメインブランチに戻ってから新しいブランチを切る」という基本手順を、実例を通して全員で確認できました。

ここで経験豊富なメンバーから「せっかくなのでチェリーピックをデモしましょうか」という提案があり、急遽ミニ講座が始まりました。`git cherry-pick` は、**特定のコミットの変更内容だけを、今いるブランチに単独で取り込める**コマンドです。ごちゃついたブランチから必要な修正だけを新しいブランチに移す「お掃除」や、複数ブランチの成果を1つにまとめる用途で使われ、コミット履歴の綺麗さに厳しい現場では必須級のテクニックとのこと。今回のような「余計な変更が混ざったプルリク」も、ゼロからやり直さずに救済できます。

話題はコンフリクト解消のノウハウにも広がり、VS Codeのマージエディターの使い方や、`git diff` でブランチ間の差分を抽出してAIに評価させる方法などが共有されました。「コンフリクト解消はいずれAIがやってくれる時代になる」「いや、まだ任せるのは不安」といった本音の意見交換も交わされています。

### Claude Codeのチーム導入に向けて

リードメンバーから、かねてより話していた**Claude Codeをチームで共有して使う体制づくり**に着手するという宣言がありました。進め方としては、まずAIへの指示を集約した共通ドキュメントを作って共有し、慣れてきたらSupabaseやGitHubをプロンプトから操作できるMCPサーバーの設定、さらにレビュー・コーディング・セキュリティなど専門特化したサブエージェントの整備へと段階的に進める構想です。「チーム開発でAIを使うノウハウはまだどこにも転がっていない。手探りだが、開発効率はかなり上がるはず」と、みんなで学びながら進めることになりました。

## 活用した技術

### GitHub ActionsによるCI（継続的インテグレーション）

GitHub Actionsは、GitHubが提供する自動化基盤です。プッシュやプルリクエスト作成をトリガーに、ビルド・テスト・静的チェックなどを自動実行する使い方は**CI（継続的インテグレーション）**と呼ばれ、「壊れたコードがメインブランチに入るのを水際で防ぐ」役割を担います。

設定はリポジトリ直下の `.github/workflows` ディレクトリにYAMLファイルを置くだけで、GitHubが自動的に読み取って実行してくれます。本プロジェクトでもビルド・不要ログ・型チェックなどのワークフローが動いており、「最低1人のApproveがないとマージできない」ブランチ保護と組み合わせることで、レビューと機械チェックの二段構えで品質を守っています。

### Supabaseのリレーション取得と型の自動生成

Supabaseのクライアントでは、`select()` に `position_tags(positions(id, name, is_deleted))` のようにネストした指定を書くことで、外部キーでつながったテーブルの情報をJOINのように一度に取得できます。今回の役職タグ表示は、ユーザー→中間テーブル→役職マスターと2段階たどる取得の実例です。

また、本プロジェクトでは `npm run db-types` というコマンドでSupabaseのデータベースから型情報を自動生成し、`database.types.ts` に出力しています。**テーブルを追加・変更したらこのコマンドを実行して型を最新化する**のが基本ルールです。一方で、ネストしたリレーションの型推論には限界があり、今回のように明示的な型変換を挟む工夫が必要になる場合もあります。

### git cherry-pick — コミット単位の「いいとこ取り」

`git cherry-pick <コミットID>` は、指定したコミットの変更内容だけを現在のブランチに適用するコマンドです。ブランチ全体を統合するマージと違い、**欲しい修正だけをつまみ食いできる**のが特徴です。

今回の実演のように「誤って別ブランチから切ってしまい、無関係の変更が混ざったブランチ」を立て直す場面では、メインブランチから新しいブランチを切り直し、必要なコミットだけをチェリーピックすれば、作業をゼロからやり直さずに綺麗なプルリクエストを作り直せます。コンフリクトが発生することもありますが、解消すればそのまま使えます。コミット履歴の綺麗さが求められる現場で多用される、覚えておいて損のないコマンドです。
