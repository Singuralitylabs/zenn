## 概要

本記事は、[チーム開発記録26：プルリク作成方法の共有](https://zenn.dev/singularitylabs/articles/6df5cd9019a90c)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回の定例では、シンラボ会員が開発した便利なアプリを紹介する**「アプリ紹介ページ」の実装が完了**し、mainブランチにマージされました。あわせて、プロフィールページの自己紹介欄を使いやすくする改善もマージ済みです。

会議では、完成したアプリ紹介ページのコードをリードが1ファイルずつ解説するコードリーディングが行われたほか、進行中の役職タグ設計をめぐるレビュー論点の共有、そして `package-lock.json` の大量コンフリクトに全員でライブで挑む一幕もありました。うまくいった実装と、一筋縄ではいかなかったGit操作の両方から学びの多い回です。

## 開発したもの

### アプリ紹介ページの実装

シンラボ会員が作った便利なアプリ——スプレッドシートでもWebアプリでもAI製のツールでもOK——をカード形式で紹介する新ページを実装しました。トップページとサイドナビゲーションに「アプリ紹介」へのリンクが追加され、カードの「詳細」ボタンを押すとモーダル（ポップアップ）が開いて、説明文・カテゴリー・開発者名が表示されます。「アプリを開く」ボタンからそのアプリのURLへ移動できる構成です。

ディレクトリ構成は既存の資料・動画ページを踏襲しており、`app/(authenticated)/applications/` 配下に `page.tsx` と `components/` ディレクトリ（テンプレート・カード・モーダル）を新設しました。まず入り口となる `page.tsx` では、Supabaseからアプリとカテゴリーのデータを取得し、エラーチェックをしたうえでテンプレートに引き渡します。

```tsx
// app/(authenticated)/applications/page.tsx
import { fetchApplications } from "@/app/services/api/applications-server";
import { fetchCategoriesByType } from "@/app/services/api/categories-server";
import { ApplicationsPageTemplate } from "./components/Template";

export default async function ApplicationsPage() {
  // アプリデータ・カテゴリーデータを並列取得
  const [applicationsResult, categoriesResult] = await Promise.all([
    fetchApplications(),
    fetchCategoriesByType("applications"),
  ]);

  const { data: applications, error: applicationError } = applicationsResult;
  if (applicationError || !applications) {
    console.error("アプリデータの取得に失敗:", applicationError);
    return (
      <div className="text-center py-8">
        <p className="text-red-600 text-xl">アプリデータを取得できませんでした。</p>
      </div>
    );
  }

  const { data: categories, error: categoryError } = categoriesResult;
  if (categoryError || !categories) {
    console.error("カテゴリーデータの取得に失敗:", categoryError);
    return (
      <div className="text-center py-8">
        <p className="text-red-600 text-xl">カテゴリーデータを取得できませんでした。</p>
      </div>
    );
  }

  return <ApplicationsPageTemplate applications={applications} categories={categories} />;
}
```

データ取得を担う関数も新規に作成しました。Supabaseの `applications` テーブルから、カテゴリー名と開発者の表示名をまとめて1回のクエリで取ってきます。

```typescript
// app/services/api/applications-server.ts（抜粋）
export async function fetchApplications(): Promise<{
  data: ApplicationWithCategoryAndDeveloperType[] | null;
  error: PostgrestError | null;
}> {
  const supabase = await createServerSupabaseClient();
  const { data, error } = await supabase
    .from("applications")
    .select(
      `*, category:categories (name), developer:users!applications_developer_id_fkey (display_name)`
    )
    .eq("is_deleted", false)
    .order("display_order");

  if (error) {
    console.error("Supabase アプリ一覧データ取得エラー:", error.message);
    return { data: null, error };
  }

  return { data, error: null };
}
```

レイアウトの本体はテンプレートコンポーネントです。カテゴリーを `map`（配列のループ処理）で回してカテゴリーごとのブロックを作り、その中に1件ずつ `ApplicationCard` を並べます。詳細モーダルの表示・非表示は `useState` で管理しており、「詳細」ボタンのクリックで `opened` が `true` に切り替わる設計です。

```tsx
// app/(authenticated)/applications/components/Template.tsx（抜粋）
export function ApplicationsPageTemplate({
  applications,
  categories,
}: ApplicationsPageTemplateProps) {
  const [selectedApplication, setSelectedApplication] =
    useState<ApplicationWithCategoryAndDeveloperType | null>(null);
  const [modalOpened, setModalOpened] = useState(false);

  const handleDetailClick = (application: ApplicationWithCategoryAndDeveloperType) => {
    setSelectedApplication(application);
    setModalOpened(true);
  };

  const handleModalClose = () => {
    setModalOpened(false);
    setSelectedApplication(null);
  };

  // ...カテゴリーごとにApplicationCardを一覧表示...

  return (
    <>
      {/* ...省略... */}
      <ApplicationDetailModal
        application={selectedApplication}
        opened={modalOpened}
        onClose={handleModalClose}
      />
    </>
  );
}
```

なお、このPRでは資料・動画のフォームコンポーネントにも修正が入っています。これは1ヶ月ほど前に追加した表示順制御用の `display_order` カラムが型定義ファイル `database.types.ts` に反映されておらず、反映してビルドしたところエラーが発生したための付随修正です（詳細は「会議の様子」で後述します）。

また、資料・動画ページにはあるコンテンツの追加・編集・削除機能がアプリ紹介ページにはまだないため、これを追加するissueを新たに起票しました。マージ後にテスト環境へ反映されていない事象も見つかっており、こちらは原因を調査中です。

プロフィールページの自己紹介欄が狭く書きづらいという課題に対し、入力量に応じてテキストエリアが自動で伸びるよう改善しました。担当メンバーにとって初めてのプルリクエストで、無事マージまで完了しています。


### 会員・資料・動画ページのカード幅調整

会員・資料・動画の3ページで、カードブロックの横幅を縮めて調整するプルリクエストも提出されました。レビューでは修正内容自体に問題なしと判断されたものの、`package-lock.json` の大量コンフリクトが発生してマージできない状態に。会議内での解消は断念し、最終的にリードがブランチを引き取ってコンフリクトを解消し、マージまで完了しています。

## 会議の様子

### 役職タグ設計 — 「代表」の正式名称からRLSポリシーまで

前回から続く会員の役職タグ機能は、設計レビューの指摘反映が進行中です。初期データに「代表」「副代表」を入れるかという論点では、「そもそも代表の正式名称は何か」という話に。正式には「代表理事」ですが、体制表にも明示されておらず、コミュニティ内では「代表」で通っているのが実情です。肩書きの確認は持ち帰りとし、**まずは確定しているチーム名だけを初期データに入れる**ことにしました。将来的にはユーザー自身や管理画面からタグを追加できるようにする構想も共有されています。

物理削除の扱いも議題になりました。Supabaseには**ポリシー（RLS）というデータベースのアクセス制御機能**があり、現状はDELETEを `USING (false)` とすることで全テーブルの物理削除を禁止しています。管理者のみ物理削除を許可するポリシーも書けますが、ポリシーの記法全体を見直す話が別途あるため、**設計書には「削除ポリシーは物理削除を許可する」と日本語で書くにとどめ、実装は見直しのタイミングでまとめて対応**することになりました。

メンバー詳細モーダルの表示項目では、従来のロール（メンテナ等）と今回追加する役職（ポジション）を両方表示するかが議論に。両者は管理の仕方が異なり、別々に取得して並べる必要があるため実装が複雑になります。検討の結果、**一覧・詳細とも新しい役職表示に置き換える**方針に決定。あわせて「仕様設計書の会員一覧にはロール表示が書かれているが、実装では表示されていない」という設計と実装の差分も見つかり、設計書側を修正することになりました。

### ライブで挑むGitコンフリクト解消 — package-lock.jsonとの格闘

カード幅調整のプルリクエストには「branch has conflicts that must be resolved（解決必須のコンフリクトがあります）」という表示が出ていました。コンフリクトとは、**自分のブランチとmainブランチの両方で同じ箇所が更新され、Gitがどちらを正とすべきか判断できなくなった状態**です。今回は `package-lock.json` の中に競合箇所が130個もあり、GitHub上のボタン操作では解決できません。

そこで担当メンバーの画面を共有しながら、全員でライブ解消に挑みました。方針は「`package-lock.json` を削除してmainをリベースする」。ところが `git rebase main` は失敗し（削除をコミットしてから再実行しても大量のコンフリクトが発生）、`git rebase --abort` で中断。別のメンバーの提案で `git merge main` に切り替えるも、やはりコンフリクトが出ます。「差分が出ないよう、mainと同じ内容にまるっと揃えてしまう」という案に方針転換し、直前のコミットを取り消す `git reset --hard HEAD^` を実行したところ——今度は「More?」という見慣れないプロンプトが表示され、コマンドが通らないという謎の現象に遭遇しました。

時間も押してきたため、この日は**リードがブランチを自分の環境に再現してコンフリクトを解消し、マージする**ことで決着。担当メンバーには、マージ完了後にリポジトリをクローンし直してもらうことになりました。「Gitのいいところは、困ったらローカルを全部消してリモートから取り直せば必ず復旧できること」というリードの言葉どおり、壊すことを恐れずに再スタートできるのがGitの強みです。議論の中では「開発環境（Mac/Windows/Linux）が違うと `package-lock.json` に差分が出やすい」という指摘や、「いっそ `.gitignore` で管理対象から外せないか」という案も出ましたが、**依存パッケージの細かいバージョンを固定するために通常はリポジトリに含めるべきファイル**という整理になりました。

### 型定義の更新漏れと「package.jsonを読む癖」

アプリ紹介ページのPRで資料・動画のフォームまで修正が及んだ原因は、以前追加した `display_order` カラムがSupabaseの型定義ファイル `database.types.ts` に反映されていなかったことでした。ここから運用ルールの確認に発展します。型定義ファイルは手で直すのではなく、`package.json` に定義済みの `npm run db:types` コマンドを実行すれば、**Supabaseのテーブル構成を読み取って自動更新される**仕組みになっています。「テーブル構成を変更したら必ずこのコマンドを実行する」ことをチームで確認し、将来的にはGitHub Actionsで毎回 `db:types` を走らせて差分の有無をチェックする案も出ました（現状のActionsはビルドと `console.log` の残存チェックのみ）。

この流れで、リードによる `package.json` のミニ講座も行われました。普段実行している `npm run dev` の正体はこのファイルの `scripts` に書かれたコマンドであること、`dependencies` を見ればプロジェクトで使われているパッケージとバージョンが一覧できること、そして `npm install` は `package.json` を読み取ってネット上からパッケージを集め、Git管理外の `node_modules` フォルダに展開する処理であること。「新しい開発チームに参加したら、まずpackage.jsonを見る癖をつけるといい」という実践的なアドバイスで締めくくられました。

### タスク運用の小さな改善と次の一手

初めてプルリクエストをマージまで完了したメンバーへ、issueカードのクローズ手順もレクチャーされました。単にクローズするのではなく、**「マージ完了」と一言コメントを添えてからクローズする**のがポイント。中止によるクローズなのか完了によるクローズなのかが後から分かるようにするための、小さいけれど効く運用です。普段ステータス変更だけで済ませていたメンバーからも「初めて知った」という声が上がりました。

次のタスクのアサインでは、タスクを終えたメンバーが**Googleカレンダー埋め込み機能**に挑戦することに。認証機能のあるサイトへの埋め込みはチームとしても未経験の領域ですが、「まず仕様設計書を更新してレビュアーとすり合わせてから実装する」という流れを確認し、「難しく考えすぎず、できなかったらできなかったで経験値になる」と背中を押してのスタートです。このほか、Supabase有料プランの使い勝手の調査もリードが継続することになりました。

## 活用した技術

### Next.js App Routerの「page.tsx＋Template＋部品」構成

今回のアプリ紹介ページは、`page.tsx`（サーバー側でのデータ取得とエラーチェック）→ `Template.tsx`（ページ全体のレイアウトと状態管理）→ `ApplicationCard` / `ApplicationDetailModal`（個々のUI部品）という3層の構成になっています。資料・動画ページと同じパターンを踏襲しているため、既存ページを読んだことがあれば新ページも同じ地図で読める、というのがこの構成の利点です。

一方で会議では「カテゴリーを取得してループ表示する部分はどのページもほぼ同じ」という点が話題になり、**Templateの共通化を検討するissueを立てる**ことになりました。ページが増えるほど同じ修正を全ページに入れる手間が増えるため、共通化は早い時期にやるのが得策です。共通化しても、特定ページだけ独自のTemplateを作って `page.tsx` から差し替えることは難しくありません。

### Mantineのモーダル — openedプロパティによる表示制御

詳細表示に使ったUIライブラリMantineの `Modal` コンポーネントは、`opened` という真偽値のプロパティが `false` の間は画面に表示されないという特徴があります。このため「モーダルを開く」処理は、DOMを直接操作するのではなく、`useState` で管理する `modalOpened` を `true` に切り替えるだけで済みます。**「見た目の変化を状態の変化として書く」**というReactの基本的な考え方が、そのまま表れている実装です。

### package-lock.jsonはなぜコンフリクトしやすいのか

`package-lock.json` は、`npm install` 時に解決された全依存パッケージの正確なバージョンを記録するファイルです。チーム全員が同じバージョンのパッケージで開発するために重要な役割を果たしますが、**依存関係が少し変わるだけで機械的に何百行も書き換わる**ため、複数人が別々のブランチで `npm install` を実行すると、人間の編集していない箇所同士でコンフリクトが多発します。手作業で1箇所ずつ解消するのは現実的でないため、今回のように「ロックファイルを一度削除してmainの内容から作り直す」方針が定石のひとつです。

ちなみに、会議中に遭遇した「More?」という謎のプロンプトは、Windowsのコマンドプロンプトでは `^` が特別な意味（エスケープ文字）を持つことが原因です。`git reset --hard HEAD^` の `^`（1つ前のコミットを指す記号）が行の継続として解釈され、続きの入力を促す「More?」が表示されてしまいます。MacやLinuxでは起きない、OS差ならではの落とし穴でした。

## 総括

今回は、アプリ紹介ページという目に見える新機能が完成した回でした。既存ページの構成パターンを踏襲することでスムーズに実装が進んだ一方、型定義の更新漏れという運用面の課題も見つかり、`npm run db:types` の実行ルールやGitHub Actionsへの組み込み案という改善につながりました。実装して終わりではなく、そこから運用ルールを磨いていく流れができています。

そして今回の白眉は、`package-lock.json` のコンフリクトにライブで挑んだ時間です。リベース、マージ、リセットと定石を試しても解決せず、最後は「リードが引き取ってクローンし直す」という判断に落ち着きましたが、コンフリクトとは何か・なぜ起きるのか・詰まったらどうリカバリするのかを全員で体感できたのは、教材では得がたい経験だったはずです。初めてのプルリクエストをマージまで完了したメンバー、未経験のカレンダー機能に手を挙げたメンバーと、チーム全体の挑戦も続いています。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
