## 開発したもの

### 管理画面設計のモーダル表示への変更（PR #149）

資料・動画の新規作成・編集・削除の画面遷移方式を、別ページ遷移からモーダル表示に変更する設計書の更新が行われました。

主な変更点：
- 新規作成・編集：別ページへの遷移 → **モーダルで表示**
- 削除：確認画面への遷移 → **確認モーダルを表示**
- 削除の動作：物理削除 → **論理削除（`is_deleted` を `true` に変更）**

この変更により、資料一覧・動画一覧ページを離れることなく、すべての管理操作をその場で完結できるようになります。

### Clerk 関連コードの削除と RLS ポリシー簡素化（PR #150）

Supabase Auth への移行が完了したことで、Clerk の設定・コードを完全に削除しました。また、RLS ポリシーを Supabase Auth に合わせてシンプルな記述に改めました。

```sql
-- 変更前（Clerk を前提とした独自関数）
CREATE POLICY "is_registered_user" ON documents
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE clerk_id = get_clerk_user_id()
      AND is_deleted = FALSE
    )
  );

-- 変更後（Supabase Auth の組み込み関数を使用）
CREATE POLICY "authenticated_users_can_read" ON documents
  FOR SELECT USING (
    auth.uid() IS NOT NULL
  );
```

`auth.uid()` はSupabase Auth が提供する組み込み関数で、ログイン中のユーザーの UUID を直接返します。Clerk との同期のために作成していたカスタム関数（`get_clerk_user_id()` 等）が不要になり、ポリシーが大幅にシンプルになりました。

また、`middleware.ts` でのユーザーデータ取得のために、サーバーサイドで Supabase にアクセスするための `user-server.ts` が追加されました。

```typescript
// app/services/api/user-server.ts（新規追加）
// サーバーサイドで Supabase からユーザー情報を取得
import { createServerSupabaseClient } from "./supabase";

export async function fetchUserStatusById({ authId }: { authId: string }) {
  const supabase = await createServerSupabaseClient();
  const { data, error } = await supabase
    .from("users")
    .select("status")
    .eq("auth_id", authId)
    .maybeSingle();

  if (error) {
    return { status: null, error };
  }

  return { status: data?.status ?? null, error: null };
}
```

### カテゴリーショートカットリンクの追加（PR #152）

資料一覧・動画一覧ページの上部に、各カテゴリーへのショートカットリンクを表示する機能を実装しました。リンクをクリックすると、該当カテゴリーのセクションまでスクロールします。

```typescript
// app/(authenticated)/documents/components/Template.tsx（抜粋）
export function DocumentsPageTemplate({ documents, categories }) {
  const documentCategoryNames = new Set(documents.map((d) => d.category?.name));
  const existingCategories = categories.filter(
    (c) => documentCategoryNames.has(c.name)
  );

  return (
    <Paper m="0 2rem">
      <PageTitle>資料一覧</PageTitle>

      {/* カテゴリーショートカットリンク */}
      <Paper mb="md" p="md">
        <div className="flex flex-wrap items-center">
          {existingCategories.map((category, index) => (
            <div key={category.id}>
              {index > 0 && <span className="text-gray-500 mx-2">|</span>}
              <a href={`#category-${category.id}`} className="text-blue-600">
                {category.name}
              </a>
            </div>
          ))}
        </div>
      </Paper>

      {/* カテゴリー別コンテンツ */}
      <Paper>
        {existingCategories.map((category) => (
          <div key={category.id}>
            {/* id 属性でアンカーリンクのターゲットを設定 */}
            <h2 id={`category-${category.id}`}>{category.name}</h2>
            <Grid>
              {documents
                .filter((d) => d.category?.name === category.name)
                .map((doc) => (
                  <Grid.Col span={{ base: 12, md: 6, lg: 4 }} key={doc.id}>
                    <DocumentCard document={doc} />
                  </Grid.Col>
                ))}
            </Grid>
          </div>
        ))}
      </Paper>
    </Paper>
  );
}
```

## 会議の様子

### Clerk 削除と RLS 簡素化の解説

Supabase Auth への移行後、コード中に残っていた Clerk 関連の記述を完全に削除しました。具体的には、Clerk の npm パッケージの削除、設定ファイルの修正、Clerk を前提としたコードの除去などを16ファイルにわたって実施しました。

RLS ポリシーの改善点についても解説がありました。以前は `is_registered_user()` という独自関数を通じて認証チェックを行っていましたが、Supabase Auth の `auth.uid()` を使うことで、ポリシーの条件式が非常にシンプルになりました。

**Next.js のクライアント・サーバー分離の重要性**についても改めて解説がありました。`middleware.ts` でユーザーデータを取得する際にクライアント側の API 呼び出し関数を使っていたことが原因でエラーが発生していました。サーバーサイドの処理ではサーバー用の Supabase クライアントを使う必要があります。

```typescript
// クライアント用（ブラウザで実行）
import { createClientSupabaseClient } from "./supabase-client";
const supabase = createClientSupabaseClient();

// サーバー用（Node.js で実行）
import { createServerSupabaseClient } from "./supabase";
const supabase = await createServerSupabaseClient();
```

一般的な原則として、サーバー側で処理できるものはサーバー側に寄せた方がパフォーマンスが向上します。

### カテゴリーショートカットの実装レビュー

担当メンバーが実装したカテゴリーショートカットリンクのコードレビューを行いました。HTML のアンカーリンク（`#category-{id}` 形式）を活用したページ内遷移で、URL にアンカーを含めることで特定のカテゴリーへ直接アクセスすることも可能です。

動画・資料の両一覧ページで同様のコードを実装した点について「コンポーネント化すべきか」という疑問が出ましたが、コード量が少なく、両ページで共通コンポーネント化することで逆に見通しが悪くなる可能性があるとして、現状維持の判断となりました。

今後の課題として、スマートフォン表示でのレスポンシブ対応（カテゴリー名の横並びを縦並びに変更する等）が Issue に登録されました。

## 活用した技術

### HTML アンカーリンクによるページ内遷移

`id` 属性と `#` を使ったアンカーリンクは、同一ページ内の特定の要素にジャンプする HTML の基本機能です。

```html
<!-- ジャンプ先の要素に id を設定 -->
<h2 id="category-1">GAS講座</h2>

<!-- そのidに向けたリンク -->
<a href="#category-1">GAS講座へ移動</a>

<!-- URL でも指定可能（直接アクセス） -->
<!-- https://example.com/videos#category-1 -->
```

React コンポーネントでは、`id` を動的に生成することで複数カテゴリーを統一的に扱えます。

### Supabase RLS の簡素化

Supabase Auth の組み込み関数 `auth.uid()` を使うことで、RLS ポリシーをシンプルに記述できます。

```sql
-- 認証済みユーザーのみ SELECT を許可
CREATE POLICY "authenticated_users_can_read" ON videos
  FOR SELECT USING (auth.uid() IS NOT NULL);

-- 管理者のみ INSERT を許可
CREATE POLICY "admins_can_insert" ON videos
  FOR INSERT WITH CHECK (
    EXISTS (
      SELECT 1 FROM users
      WHERE auth_id = auth.uid()
      AND role = 'admin'
    )
  );
```

`auth.uid()` は現在ログインしているユーザーの UUID を返し、未ログインの場合は `NULL` を返します。この関数が使えるようになったことで、Clerk 時代に必要だった複雑なカスタム関数が不要になりました。

### 論理削除パターン

データを物理的に削除する代わりに、`is_deleted` フラグを `true` に変更する論理削除を採用しています。

```sql
-- 物理削除（データが完全に消える）
DELETE FROM documents WHERE id = 1;

-- 論理削除（フラグを立てるだけ）
UPDATE documents SET is_deleted = true WHERE id = 1;
```

論理削除のメリットは、誤操作のデータを復元できること、削除履歴を追跡できることです。アプリケーション側では `is_deleted = false` を条件に追加することで、削除済みデータを一覧から除外します。
