### 管理者向け資料削除機能（PR #153）

資料カード上に **削除ボタン**を追加し、Admin ロールを持つユーザーだけが削除できる構成にしました。削除はモーダルで確認したうえで論理削除（`is_deleted` を `true` に更新）を実行します。

ユーザーのロールはサーバーサイドで取得し、`currentUserRole` として子コンポーネントに渡しています。

```typescript
// app/(authenticated)/documents/page.tsx
import { getServerCurrentUser } from '@/app/services/api/supabase-server';
import { fetchUserRoleByAuthId } from '@/app/services/api/user-server';

export default async function DocumentsPage() {
  const { authId, error: currentUserError } = await getServerCurrentUser();
  if (currentUserError) {
    return <p>認証情報が取得できませんでした。</p>;
  }

  const { data, error } = await fetchDocuments();
  const { data: dataCategory, error: errorCategory } = await fetchCategoriesByType("documents");
  const { role, error: roleError } = await fetchUserRoleByAuthId({ authId });

  if (error || errorCategory || roleError) {
    return <p>データを取得できませんでした。</p>;
  }

  return (
    <DocumentsPageTemplate
      documents={data}
      categories={dataCategory}
      currentUserRole={role}
    />
  );
}
```

`getServerCurrentUser` はサーバー側で認証ユーザーの `authId` を取り出すヘルパーで、Supabase Auth の `auth.getUser()` をラップしたものです。

```typescript
// app/services/api/supabase-server.ts
export async function getServerCurrentUser(): Promise<{
  authId: string;
  error: AuthError | null;
}> {
  const supabase = await createServerSupabaseClient();
  const { data, error } = await supabase.auth.getUser();

  if (error || !data?.user) {
    return { authId: "", error };
  }
  return { authId: data.user.id, error: null };
}
```

カード側では `isAdmin` を一度だけ評価し、`true` のときだけ削除ボタンと確認モーダルを描画します。

```typescript
// app/(authenticated)/documents/components/DocumentCard.tsx（抜粋）
export function DocumentCard({ document, currentUserRole }: DocumentCardProps) {
  const [deleteModalOpened, setDeleteModalOpened] = useState(false);
  const router = useRouter();
  const isAdmin = currentUserRole === 'admin';

  const handleDelete = async (id: number) => {
    try {
      const result = await deleteDocument(id);
      setDeleteModalOpened(false);
      if (result?.success) {
        notifications.show({ title: '削除完了', message: '資料を削除しました。', color: 'green' });
        router.refresh();
      } else {
        notifications.show({ title: '削除失敗', message: String(result?.error) || '不明なエラー', color: 'red' });
      }
    } catch (e) {
      setDeleteModalOpened(false);
      notifications.show({ title: 'エラー', message: '削除処理で予期しないエラーが発生しました', color: 'red' });
    }
  };

  return (
    <Card>
      {/* ...資料の表示 */}
      {isAdmin && (
        <Group m="0 1rem 1rem" gap="xs">
          <Button color="red" onClick={() => setDeleteModalOpened(true)}>削除</Button>
        </Group>
      )}
      <Modal opened={deleteModalOpened} onClose={() => setDeleteModalOpened(false)} title="削除の確認" centered>
        <Text mb="md">本当にこの資料を削除しますか？</Text>
        <Group justify="flex-end">
          <Button variant="default" onClick={() => setDeleteModalOpened(false)}>キャンセル</Button>
          <Button color="red" onClick={() => handleDelete(document.id)}>削除</Button>
        </Group>
      </Modal>
    </Card>
  );
}
```

実際の DB 操作は `documents-client.ts` に集約しました。CRUD だけを担う薄い関数として保ち、バリデーションや認可はページ側に寄せる方針です。

```typescript
// app/services/api/documents-client.ts
import { createClientSupabaseClient } from "./supabase-client";

export async function deleteDocument(id: number) {
  const supabase = createClientSupabaseClient();
  const { error } = await supabase
    .from("documents")
    .update({ is_deleted: true })
    .eq("id", id);

  if (error) {
    return { success: false, error };
  }
  return { success: true, error: null };
}
```

通知 UI には Mantine の `notifications` を採用しました。`app/layout.tsx` の最上位に `<Notifications position="top-right" />` を配置することで、認証済みエリア全体で `notifications.show(...)` を呼び出すだけでトーストが表示される構成です。

```typescript

            <Notifications position="top-right" />
            <div className="min-h-screen">{children}</div>
          </MantineProvider>
        </SupabaseAuthProvider>
      </body>
    </html>
  );
}
```

### 資料新規登録機能（PR #157）

削除機能と同じ `documents-client.ts` 内に `registerDocument` を追加し、新規登録用の汎用モーダル `DocumentFormModal` を実装しました。今後の編集機能でも同じモーダルを使い回す前提です。

```typescript
// app/(authenticated)/documents/components/DocumentFormModal.tsx（抜粋）
export function DocumentFormModal({ opened, onClose, categories, userId }: DocumentFormModalProps) {
  const [form, setForm] = useState({
    name: '', caegory_id: 0, description: '', url: '', assignee: '',
  });

  const handleSubmit = async () => {
    if (!form.name || !form.url || form.caegory_id === 0 || form.url.trim() === "") {
      notifications.show({ title: '入力エラー', message: '資料名とURL及びカテゴリーは必須です', color: 'red' });
      return;
    }
    try {
      new URL(form.url);
    } catch {
      notifications.show({ title: '入力エラー', message: '正しいURLを入力してください', color: 'red' });
      return;
    }

    const result = await registerDocument({
      name: form.name,
      category_id: form.caegory_id,
      description: form.description,
      url: form.url,
      assignee: form.assignee,
      created_by: userId,
    });

    if (result?.success) {
      notifications.show({ title: '登録完了', message: '資料が正常に登録されました。', color: 'green' });
      onClose();
    } else {
      notifications.show({ title: '登録失敗', message: String(result?.error) || '不明なエラー', color: 'red' });
    }
  };

  return (
    <Modal opened={opened} onClose={onClose} title="資料新規登録" centered>
      {/* TextInput / Select / Textarea ... */}
      <Group mt="md" justify="flex-end">
        <Button variant="default" onClick={onClose}>キャンセル</Button>
        <Button color="blue" onClick={handleSubmit}>登録</Button>
      </Group>
    </Modal>
  );
}
```

入力フォームに対応する型は、DB のテーブル定義から **`Omit` で派生**させました。`id` や `created_at` などの自動採番カラムを除外することで、テーブルスキーマが拡張されても登録フォーム側の型が自動的に追従します。

```typescript
// app/types.ts（抜粋）
type DocumentsTable = Database["public"]["Tables"]["documents"];

export type DocumentInsertFormType = Omit<
  DocumentsTable["Row"],
  "id" | "created_at" | "updated_at" | "updated_by" | "is_deleted"
>;
```

`registerDocument` 側でこの型をそのまま受け取り、`insert` に流し込みます。

```typescript
// app/services/api/documents-client.ts
export async function registerDocument({
  name, category_id, description, url, assignee, created_by,
}: DocumentInsertFormType) {
  const supabase = await createClientSupabaseClient();
  const { error } = await supabase.from("documents").insert([
    { name, category_id, description, url, assignee, is_deleted: false, created_by },
  ]);

  if (error) {
    return { success: false, error };
  }
  return { success: true, error: null };
}
```

## 会議の様子

### イシューテンプレートの「実装内容」項目の見直し

プルリク作成者が記載することを期待して用意していた「実装内容」項目について、誰も埋めていない状況が続いていることが議論の起点となりました。

- 設計書を更新する運用にしたため、**設計書と実装内容が重複**してしまう
- 「実装内容」という言葉がコーディング寄りに読めて、**書くタイミングが伝わりづらい**
- プルリク本文に詳細を書く方が、コードと連動した時系列で残しやすい

結論として、テンプレートから「実装内容」項目を一旦削除し、必要に応じて概要欄に補足情報（例：モーダルで実装するなど）を書く運用に切り替えることになりました。テンプレート更新はプルリクで反映する方針です。

### 削除機能のコードレビュー

担当メンバーから削除機能の解説があり、レビューを通して以下の論点が共有されました。

- **`isAdmin` の判定位置**：現状は子コンポーネントでロール文字列を比較しているが、より上位の層で `isAdmin` を判定し `boolean` だけを渡す方が、下層に余計な情報を伝えずに済むのではないか
- **`fetchUserRoleByAuthId` の責務**：ロール文字列を返すだけにとどめるか、ユーザー情報を一括で返すかで議論。サービスAPI層（CRUD相当）に「Admin かどうか」という判定ロジックを持ち込むのは違和感があるため、判定はページ側に置く方針で合意
- **エラー戻り値の活用**：`deleteDocument` は `{ success, error }` を返すが、呼び出し側ではエラー文字列を通知メッセージに利用しているため意図通り機能している
- **メンテナー権限の導入**：Admin はユーザー管理まで含む強い権限なので、データ追加・編集だけができる **Maintainer ロール** を別途用意した方がよさそう、という方向性が共有された

### 新規登録機能のコードレビュー

新規登録のコードレビューでは、設計を整理するための具体的な助言が複数共有されました。

- **コンポーネントへの Props は最小限に**：当初はフォーム情報やサブミット処理を親から渡していたが、新規登録モーダルでしか使わない関数はモーダル内に閉じ込めた方が、責務が明確になる
- **型は派生で作る**：フォーム用に新しい型を定義するより、テーブル定義の型から `Pick` / `Omit` で派生させると、スキーマ変更への追従が容易
- **インサート/アップデートの戻り値**：Supabase の `insert` / `update` から返ってくる `data` は通常不要なため、明示的に取得対象から外しておく方がシンプル
- **`new URL()` を使ったURLバリデーション**：簡易な妥当性チェックとしては有効だが、本格的なバリデーションには **Zod** のような専用ライブラリを使うのが一般的。編集機能の実装と合わせて導入を検討予定
- **オブジェクト分割代入の省略記法**：プロパティ名と変数名が一致するときは `{ name: name }` を `{ name }` と書ける（JavaScript 標準の機能）

### 今後の進め方

- **資料の編集機能**：削除・新規登録のパターンを横展開して実装
- **動画への展開**：資料側で確立したパターンを動画一覧にも適用
- **GitHub Actions によるテスト環境の整備**：CI/CD パイプラインの構築を開始

- **作ったサービスの紹介ページ構想**：AI 事業創出チーム等が作成したアプリを紹介する場としての活用案

## 活用した技術

### Mantine Notifications

トースト通知用のコンポーネント。`<Notifications position="top-right" />` をルートに1度だけ配置すれば、任意の場所で `notifications.show({ title, message, color })` を呼ぶだけで通知が表示されます。表示位置を変えたい場合は `position` だけ書き換えれば全体に反映されるため、レイアウト変更にも強い構成です。

### TypeScript の `Omit` / `Pick` ユーティリティ型

既存の型から特定プロパティを除外（`Omit`）／抽出（`Pick`）して新しい型を作るための組み込み機能です。

```typescript
type DocumentRow = DocumentsTable["Row"];

// 自動採番カラムを除外して登録フォーム用の型を作る
type DocumentInsertFormType = Omit<DocumentRow, "id" | "created_at" | "updated_at" | "updated_by" | "is_deleted">;

// 表示用に最小限のフィールドだけ抜き出す
type DocumentSummaryType = Pick<DocumentRow, "id" | "name" | "category_id">;
```

テーブルスキーマの変更が型に自動で反映されるため、別途フォーム用の型を手書きするより安全です。

### `new URL()` による軽量なURLチェック

URL 文字列の妥当性は、ライブラリを追加しなくても JavaScript の組み込みコンストラクタ `URL` で簡易に検証できます。不正な文字列を渡すと例外を投げるため、`try / catch` で結果を判定できます。

```typescript
try {
  new URL(form.url);
} catch {
  // 不正なURL
}
```

ただし「`http://aaa` のような最低限のフォーマットしか満たさない文字列も通る」など、ビジネスルールには合わないケースもあります。本格的なフォームバリデーションが必要になったら、**Zod** などのスキーマバリデーションライブラリへの置き換えを検討する想定です。

### Next.js App Router の Server / Client 分離

データ取得や認証情報の参照は、可能な限りサーバーコンポーネント側で完結させ、必要な値だけを `props` でクライアントコンポーネントに渡す構成にしています。サーバー用クライアントとクライアント用クライアントを別ファイル（`supabase-server.ts` / `supabase-client.ts`）で管理することで、誤って混在させるリスクを減らしました。

## 総括

ver3.0 のリリースを区切りに、コードレビューの観点が「動くものを作る」から「設計を整える」段階に移ってきました。コンポーネントの責務分離、型の派生、CRUDレイヤーと判定ロジックの分離など、メンテナンス性を高めるための議論が自然と立ち上がるようになっています。
