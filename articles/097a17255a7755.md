## 開発したもの

### セキュリティ多層防御の強化

「セキュリティヘッダーの未設定の解消」「依存関係の既知脆弱性への対応」「認証コールバックの不要なログ削除」の3点をまとめて対応したPRがマージされました。いずれも致命的な問題ではないものの、設定次第で防御をすり抜けられる余地を潰す、いわゆる多層防御（Defense in Depth）と衛生管理の観点での改善です。

#### 1. セキュリティヘッダーの追加

`next.config.ts` の `headers()` に、全ルート共通のセキュリティヘッダーを追加しました。Strict-Transport-Security、X-Frame-Options、X-Content-Type-Options、Referrer-Policy、Content-Security-Policy（CSP）を設定しています。

```typescript
async headers() {
  return [
    {
      source: "/:path*",
      headers: [
        {
          key: "Strict-Transport-Security",
          value: "max-age=63072000; includeSubDomains; preload",
        },
        {
          key: "X-Frame-Options",
          value: "DENY",
        },
        {
          key: "X-Content-Type-Options",
          value: "nosniff",
        },
        {
          key: "Referrer-Policy",
          value: "strict-origin-when-cross-origin",
        },
        {
          key: "Content-Security-Policy",
          value: contentSecurityPolicy,
        },
      ],
    },
  ];
},
```

CSPの許可ドメインは、コードを調査したうえで設定しています。Supabase、YouTube埋め込み、Googleプロフィール画像のホスト名は定数として切り出し、`images.remotePatterns` とCSPの両方から参照することで二重管理を避けています。Supabaseの許可先は環境変数のプロジェクトURLから導出しており、URLが未設定・不正な場合は許可を広げず空にする設計です。

```typescript
// app/constants/media.ts
// next.config.ts (images.remotePatterns / CSP) と VideoCard.tsx の双方から参照し、
// YouTubeサムネイルの許可ホストを一元管理する
export const YOUTUBE_HOSTNAME = "www.youtube.com";
export const YOUTUBE_THUMBNAIL_HOSTNAME = "img.youtube.com";
```

#### 2. 依存関係の既知脆弱性への対応

`next` や `postcss` など、バージョンが古く既知の脆弱性を含んでいたパッケージにパッチを当てました（Next.js は 15.5.19 → 15.5.25 など）。

#### 3. 認証コールバックの不要なログ削除

`app/(auth)/callback/route.ts` から、認証成功時にメールアドレスを出力する `console.log` などの不要なデバッグログを削除しました。一方で `console.error` は障害の見落とし防止のため維持し、認証コードが存在しない分岐にも新たに追加しています。出力するエラー識別子は、英数字などの安全な文字列だけに制限しています。

```typescript
function getSafeErrorIdentifier(value: string | null): string | null {
  if (!value) return null;
  return /^[A-Za-z0-9_.-]{1,64}$/.test(value) ? value : "invalid_error_identifier";
}
```

### 新規Issueの追加

* **ビルド時の警告の解消**: Vercelのビルドログに出ていた警告を解消するIssueです。画像の最適化とインポートまわりの問題が影響しているとのことで、放置しても問題はないものの、消せる警告は消しておく方針です。
* **ログイン画面の注意書きの削除**: ログイン画面に記載していた「ログイン時のご連絡」を削除するIssueです。Googleアカウント選択画面にサービス名ではなくSupabaseのドメイン文字列が表示されていた問題は、Google側の認証設定が完了して解消しました。そのため注意書きは不要になっており、作業は簡単ですが早めに対応する予定です。

### デプロイ環境の統合

ポータルサイトのデプロイ先を、別アカウントで管理していたVercelプロジェクトから、有料プランを契約しているアカウントへ統合しました。パフォーマンスが良いためで、これに伴いURLが変わります。

* 開発環境のURLは後日共有し、mainブランチへのマージで新環境にデプロイされる
* 本番環境は、次回リリース時などに切り替える
* しばらくは旧URLでもアクセスでき、同じデータベースを参照するため、どちらから操作しても同じデータが見える

## 会議の様子

### 進行中タスクの確認

* **ローカルSupabase環境の構築**: 担当者はまだ調査の途中です。Dockerは動作が重いため、Dockerなしでローカル環境を構築できる方法があるとの情報があり、見つかり次第共有してそちらへシフトする可能性も検討されました。
* **レビュー指摘への対応が続くタスク**: 削除したカテゴリーのコンテンツをゴミ箱から復活させると到達不能になる問題はレビュー待ちの状態です。Supabase関数でポジションタグの更新をトランザクション化するタスクは、レビュー対応中です。更新処理が途中で失敗した場合にデータ不整合が起きる問題を解消するもので、担当者は学習も兼ねて進めています。
* **マスター管理の参照機能**: レビュー指摘の修正は完了済みです。型定義の修正が入った別PRのマージを待つ必要はなく、先にレビューを依頼して構わないと確認しました。
* **ネットワーク設計の追記**: 設計段階のため、設計書へのレビュー依頼を出してレビューしてもらう段階であることを確認し、ステータスを進行中に移しました。
* **調査系のタスク**: 条件やリスクの調査が中心のタスクは、進行中ではなく調査（サーベイ）の列に移しました。

### セキュリティ強化PRの共有

マージされたPRの内容を共有しました。個々のヘッダーの意味までは把握しきれていないメンバーも多いものの、セキュリティヘッダーはHTTPのメタ情報として非常に重要であり、覚えておくべきだと強調されました。依存関係は自動で脆弱性を検知する仕組みを導入済みです。ただし、通知が数十件溜まっているため、パッチレベルの更新は定期的に取り込む方針です。メジャーアップデートはバグの原因になりやすく、慎重な対応が必要です。

### デプロイ先変更と独自ドメイン

デプロイ先の変更に伴い、Slackへ動画追加などを通知している仕組みのURLを新しい環境に合わせて直す必要がある、という指摘がありました。これを受けて、通知のURLをVercelのドメインではなく、団体の独自ドメインに揃える案が出ました。

* VercelのURLを独自ドメインに差し替えるには、DNS設定とVercel側のドメイン設定が必要
* SSL証明書はVercel側で自動発行されるため、基本的に問題はない
* 旧URLからのアクセスもしばらくは維持する

DNSの仕組みは、アプリ開発やサイト運営でも使うため、理解しておくことが大切だと共有されました。

* 入力内容の分類（問い合わせがクレームかどうかの判定など）
* 学生のレポートが人間によるものかAIによるものかの判定

世間でもまだ使いどころを模索している段階で、今後はAI技術交流会などで共有する予定です。

## 活用した技術

### セキュリティヘッダーとCSP

HTTPレスポンスヘッダーでブラウザの挙動を制限し、攻撃を防ぐ仕組みです。

| ヘッダー | 役割 |
|---|---|
| Strict-Transport-Security | HTTPS接続を強制する |
| X-Frame-Options | 他サイトのiframeへの埋め込みを禁止し、クリックジャッキングを防ぐ |
| X-Content-Type-Options | ブラウザによるMIMEタイプの推測を禁止する |
| Referrer-Policy | 他サイトへ送るリファラー情報を制限する |
| Content-Security-Policy | 読み込めるスクリプト・画像・通信先などを制限する |

Next.jsでは `next.config.ts` の `headers()` でまとめて設定できるため、すべてのルートへのアクセスで自動的に適用されます。

### 依存関係の脆弱性管理

自動検知の仕組みを使い、パッチレベルの更新を定期的に取り込みます。メジャーバージョンの更新は破壊的変更を含みやすく、慎重な検証が必要です。

### Vercelとドメイン・DNS

Vercelのプロジェクトを統合し、独自ドメインを割り当てることで、URLの見栄えを整え、通知などの連携先を一本化できます。DNSの設定を変えると、ユーザーには独自ドメインのURLが表示され、実際の接続先はVercelに向けることができます。

### 判断特化型AI

文章生成を行うLLMとは異なり、判断だけを返す高速・低コストなAIです。LLMとの併用により、速度とコストを重視する判定処理を任せる使い方が想定されています。

## 総括

今回の定例では、セキュリティヘッダーの導入や依存関係の更新といった多層防御の強化と、デプロイ環境の統合という、運用面の重要な変更を共有しました。セキュリティは目立たない一方で欠かせない領域であり、設定一つひとつの意味を学びながら取り組んでいく姿勢が大切だと再確認しました。

次回以降は、進行中のタスクのレビュー対応を進めつつ、Dockerなしでのローカル環境構築の調査や、新環境でのURL・ドメインの切り替えを進めていきます。
