## 開発したもの

### コンテンツ操作のコンポーネント化（サーバー/クライアント分離）

動画・資料ページの「新規作成・編集・削除」ボタンや、YouTube動画の表示処理を、専用のコンポーネントとして切り出しました。Next.jsはサーバー側とクライアント側の処理を明確に切り分けることでパフォーマンスを最適化できるフレームワークであり、その強みを活かすためのリファクタリングです。

ポイントは「ユーザーの操作（クリックなど）が必要な部分だけをクライアントコンポーネントにする」という考え方です。ボタンやモーダルの開閉といったインタラクティブな処理は `"use client"` を付けたクライアントコンポーネントに集約し、それ以外の表示部分はサーバーコンポーネントとして扱います。

たとえば、これまでテンプレート内に直書きしていたYouTube表示を、独立したクライアントコンポーネント `Youtube.tsx` に切り出しました。

```tsx
// app/(authenticated)/videos/[id]/components/Youtube.tsx
"use client";

import YouTube from "react-youtube";
import { getYouTubeVideoId } from "../../utils";

type YoutubeProps = {
  name: string;
  url: string;
};

function Youtube({ name, url }: YoutubeProps) {
  const videoId = getYouTubeVideoId(url);
  if (!videoId) {
    return <div className="flex items-center justify-center h-full">無効なYouTube URLです</div>;
  }

  return (
    <div>
      <YouTube
        videoId={videoId}
        title={name}
        opts={{
          width: "100%",
          height: "100%",
        }}
        className="absolute inset-0 w-full h-full"
        iframeClassName="w-full h-full"
      />
    </div>
  );
}

export default Youtube;
```

これにより、動画詳細ページの `Template.tsx` からは `"use client"` を外すことができ、ページ本体をサーバーコンポーネントとして動かせるようになりました。あわせて、特に使う理由のなかった `Paper` コンポーネントを素の `div` に置き換える整理も行っています。

```tsx
// 動画詳細ページの Template.tsx（抜粋・変更後）
// "use client" を外し、YouTube表示は Youtube コンポーネントに委譲
import Youtube from "./Youtube";

// ...
<div className="p-4 overflow-x-hidden">
  <PageTitle>{video.name}</PageTitle>
  <div className="mt-4">
    {/* ... */}
    <Youtube name={video.name} url={video.url} />
  </div>
</div>
```

新規作成・編集・削除メニューについては、動画と資料の両方に対応する必要があります。両者はデータの型が異なるため、TypeScriptのジェネリクスを使って「どちらの型でも受け取れる」コンポーネントとして実装しました。

```tsx
// app/(authenticated)/components/ContentMgrMenu.tsx（抜粋）
interface ContentMgrMenuProps<T extends DocumentWithCategoryType | VideoWithCategoryType> {
  type: ContentType;
  content: T;
  categories: SelectCategoryType[];
  userId: number;
}

export default function ContentMgrMenu<T extends DocumentWithCategoryType | VideoWithCategoryType>({
  type,
  content,
  categories,
  userId,
}: ContentMgrMenuProps<T>) {
  // 動画・資料それぞれの編集／削除モーダルの表示状態を管理し、
  // type に応じて開くモーダルを切り替える
}
```

これらをコンポーネントに集約した結果、各カードやテンプレート側に散らばっていた状態管理やボタン処理が整理され、見通しが良くなりました。

### 共通レイアウトの集約とエラーハンドリングの改善

各ページのレイアウトは、これまでページ単位で個別に書かれていました。しかし大枠は共通しているため、認証済みエリアの `layout.tsx` に余白などの共通スタイルをまとめました。一例として、全ページ共通だった `p-4`（パディング）をレイアウト側に集約しています。

```tsx
// app/(authenticated)/layout.tsx（抜粋）
<div className="flex-1 sm:ml-64 p-4">{children}</div>
```

こうしておくと、今後新しいページやテンプレートを追加したときに、何も設定しなくても同じレイアウトが自動的に適用されます。「設定しなくても揃う」状態をつくることが狙いです。

もう一つの改善がエラーハンドリングです。これまでは「ユーザー認証」「資料データ取得」「カテゴリー取得」など複数の取得処理を、まとめて一つのエラーとして扱っていました。これだと実際にどこで失敗したのかが分かりにくくなります。そこで、取得処理ごとにエラーを切り分けるように修正しました。

```tsx
// app/(authenticated)/documents/page.tsx（抜粋・変更後）
const { data: documents, error: documentError } = await fetchDocuments();
if (documentError || !documents) {
  console.error("資料データの取得に失敗:", documentError);
  return (
    <div className="text-center py-8">
      <p className="text-red-600 text-xl">資料データを取得できませんでした。</p>
    </div>
  );
}

const { data: categories, error: categoryError } = await fetchCategoriesByType("documents");
if (categoryError || !categories) {
  console.error("カテゴリーデータの取得に失敗:", categoryError);
  return (
    <div className="text-center py-8">
      <p className="text-red-600 text-xl">カテゴリーデータを取得できませんでした。</p>
    </div>
  );
}
```

このほか、各ページの変数宣言フォーマットを統一し、Supabaseからデータを取得する関数のうち戻り値の型が宣言されていなかったものに型を追加するなど、細かな整備も行いました。

### 一覧の並び順対応（display_order）

動画・資料・カテゴリーの一覧について、任意の表示順を指定できるようにしました。まず、表示順を表すカラム名を `order_by` から `display_order` へ統一して変更しています。

```sql
-- NULL 許容でカラムを追加（旧 order_by から display_order へ改名）
ALTER TABLE videos
ADD COLUMN display_order INTEGER;
```

データ取得側では、クエリに `.order("display_order")` を追加するだけで対応できました。値が `NULL` のレコードはデフォルトで末尾に並ぶため、特別なオプションを付けなくても想定どおりの挙動になります。

```typescript
// app/services/api/videos-server.ts（抜粋・変更後）
export async function fetchVideos() {
  const { data, error } = await supabase
    .from("videos")
    .select(`*, category:categories (name)`)
    .eq("is_deleted", false)
    .order("display_order");

  if (error) {
    console.error("Supabase 動画一覧データ取得エラー:", error.message);
  }
  // ...
}
```

事前に「分類のソートで苦労するかもしれない」と身構えていたものの、実際には1行追加するだけで済み、想定以上にシンプルに実装できました。

## 会議の様子

### 命名規則をめぐる議論 ― 略語は使うべきか

今回のコンポーネント名は `ContentMgrMenu`・`ContentMgrNewButton` のように、Manager を「Mgr」と略していました。これに対してあるメンバーから「変数名やコンポーネント名で独自の略し方はなるべく避けたほうがよいのでは」という指摘がありました。

「Mgr という略は実務でも見かけるが、略語を許容し始めると Document を Doc に、というように基準が曖昧になり、命名の一貫性が崩れていく」という趣旨です。一方で「エンジニア界隈である程度共通認識のある略語も存在する」という意見もあり、最終的には**基本的には略さない方針とし、機会があれば既存の名前も直していく**ことで落ち着きました。命名は小さなことのようでいて、コードの読みやすさと一貫性に直結する論点であり、率直に議論できたのは良い時間でした。

### ver4リリースの範囲とスコープ判断

ver4のリリースを9月末〜10月頭に予定しており、リリース作業日を10月5日とする方針を確認しました。あわせて「リリースに『動画・資料データ取得の効率化』を盛り込むかどうか」が議題に上がりました。

これについては「リリース日（お尻）を決めている状況で不確定要素を増やすのは避けるべき」「実装方針が担当者間で共有でき、その通りに実装される見込みがあるなら入れてよいが、そうでないなら外したほうがよい」という慎重な意見が出ました。結果として、対応する場合は方針を明確にできる担当者が短時間で仕上げる、という整理に。締め切りが決まっているときほど、やることを増やしすぎないというスコープ管理の感覚が共有された場面でした。

### ナレッジ管理をリポジトリからWikiへ

開発のノウハウをまとめた `Knowledge.md` などのドキュメントを、GitHubリポジトリからGitHub Wikiへ移動する方針を決めました。リポジトリ管理のままだと、ちょっとした追記でも毎回プルリクエストを出してレビューを通す必要があり、手間が大きいためです。気軽に書ける場所に置くことで、ナレッジの更新ハードルを下げる狙いです。あわせて、あまり管理されていなかったユースケースのドキュメントも切り離す方向で検討しました。

### 新着情報のリンク集ページというアイデア

「ポータルサイトに来れば、コミュニティの各種情報にひと通りアクセスできる」状態を目指して、新着情報やサービスへのリンクをまとめたページを作るアイデアも挙がりました。カレンダー表示など、専用ページとして用意したほうがよさそうなものも出てきており、今後のタスクとして起票されました。

なお、ミーティングの最後には「このZenn記事自体、テック記事なのにコードがほとんど載っていないので、『活用した技術』にコードブロックを入れて解説を充実させたい」という振り返りもありました。記事づくりも開発活動の一部として、よりよくしていこうとしています。

## 活用した技術

### Next.js のサーバーコンポーネントとクライアントコンポーネント

Next.js（App Router）では、コンポーネントはデフォルトでサーバーコンポーネントとして扱われ、`"use client"` を宣言したものだけがクライアントコンポーネントになります。サーバーコンポーネントはサーバー側でレンダリングされるためクライアントに送るJavaScriptを減らせますが、`useState` やイベントハンドラといったインタラクティブな処理は使えません。

今回のように「ボタンやモーダルなど操作が必要な部分だけをクライアントコンポーネントに切り出し、残りはサーバーコンポーネントのままにする」という分割は、この特性を活かす王道のリファクタリングです。どこまでをクライアントに渡すかを意識する習慣をつけることが、Next.jsをうまく使ううえで重要になります。

### TypeScript のジェネリクス

ジェネリクスは、型を「あとから差し込めるパラメータ」として扱う仕組みです。`<T extends DocumentWithCategoryType | VideoWithCategoryType>` のように書くと、「`T` には資料か動画のどちらかの型が入る」という制約を付けたうえで、両方に対応する1つのコンポーネントを定義できます。動画用・資料用に重複したコンポーネントを書かずに済み、型安全性も保てるのが利点です。

### 共通レイアウトによるDRY化

各ページに散らばっていた共通スタイルを `layout.tsx` に集約することで、「同じことを何度も書かない（DRY: Don't Repeat Yourself）」を実現しています。新規ページでも共通レイアウトが自動適用されるため、見た目の一貫性が保たれ、変更時の修正箇所も1か所で済みます。

### エラーハンドリングの個別化

複数のデータ取得をまとめて1つのエラーで処理すると、障害発生時に原因の切り分けが難しくなります。取得処理ごとにエラーを判定し、ログとユーザー向けメッセージを分けることで、運用時のデバッグ性が大きく向上します。

### Supabase の order と NULL の扱い

Supabaseのクエリビルダーでは `.order("カラム名")` で並び替えができます。PostgreSQLでは昇順（`ASC`）の場合に `NULL` が末尾に並ぶのがデフォルトの挙動のため、表示順が未設定（`NULL`）のレコードを自然と後ろに回せます。`NULLS LAST` などのオプションを明示しなくても期待どおりに動くため、実装はごくシンプルになりました。

## 総括

今回は機能追加こそ少なかったものの、コンポーネント化によるサーバー/クライアントの責務分離、共通レイアウトの集約、エラーハンドリングの整理、並び順対応と、メンテナンス性を底上げするリファクタリングが詰まった回となりました。こうした地道な土台固めは、ver4リリースとその先の開発を支える重要な作業です。

また、命名規則やリリースのスコープ管理、ナレッジの置き場所といった「開発の進め方そのもの」についても率直に議論できました。コードの書き方だけでなく、チームで開発を続けるための運用の工夫を学べるのも、チーム開発ならではの醍醐味です。
