### CSPのnonce化（#488）

CSPは、ページがどこから読み込んだスクリプトやスタイルを実行してよいかをブラウザに伝えるHTTPヘッダーです。これまでのポータルサイトでは `next.config.ts` で固定のCSPを設定しており、`script-src` に `'unsafe-inline'` を含めていました。これは「ページ内に埋め込まれたスクリプトはすべて実行してよい」という指定で、Mantineなど一部のライブラリが出力するインラインスクリプトを動かすために緩めていたものです。その結果、万が一悪意のあるスクリプトが埋め込まれた場合にも実行を防げない、XSS（クロスサイトスクリプティング）に対して弱い状態になっていました。

今回の変更では、ミドルウェアがリクエストのたびにランダムな **nonce**（一度きりの値）を発行し、その値を付けたスクリプトだけを実行可能にしました。CSPの組み立ては `app/utils/csp.ts` に切り出されています。

```typescript
export function buildContentSecurityPolicy(nonce: string): string {
  // 環境依存の値は呼び出し時に評価する(テストで本番/Preview/開発を切り替えられるようにするため)
  const isDev = process.env.NODE_ENV !== "production";
  // Vercel Previewデプロイのフィードバックツールバー用(本番には影響しない)
  const isPreview = process.env.VERCEL_ENV === "preview";
  const previewSources = isPreview ? "https://vercel.live" : "";
  const { httpOrigin: supabaseHttpOrigin, wsOrigin: supabaseWsOrigin } = getSupabaseCsp();
  // 開発(next-devtools)とPreview(vercel.live)は nonce の付かない <style> を注入するため、
  // この2環境に限り style 要素の nonce を使わず 'unsafe-inline' を許可する(本番は nonce のみ)。
  // nonce が指定されていると 'unsafe-inline' は無視されるため、nonce は付けない。
  const styleElemSources =
    isDev || isPreview ? "'self' 'unsafe-inline'" : `'self' 'nonce-${nonce}'`;
  return [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? ` 'unsafe-eval' http://${YOUTUBE_HOSTNAME}` : ""} https://${YOUTUBE_HOSTNAME} ${previewSources}`,
    `style-src ${styleElemSources} ${previewSources}`,
    `style-src-elem ${styleElemSources} ${previewSources}`,
    "style-src-attr 'unsafe-inline'",
    // ...（img-src / connect-src / frame-src などは従来どおり）
    "object-src 'none'",
    "base-uri 'self'",
    "form-action 'self'",
    "frame-ancestors 'none'",
  ]
    .map(directive => directive.replace(/\s+/g, " ").trim())
    .join("; ");
}
```

ミドルウェアでは、発行したnonceをリクエストヘッダーに積んでServer Componentから参照できるようにし、レスポンスにはCSPヘッダーを付与します。認証エラー時のリダイレクトや401レスポンスなど、すべての返却パスで漏れなくCSPが付くよう `withCsp` という小さな関数にまとめています。

```typescript
// レスポンスに CSP を設定する。nonce はここでしか使わないため、返却直前に一箇所で付与する。
function withCsp<T extends NextResponse>(response: T, nonce: string): T {
  response.headers.set("Content-Security-Policy", buildContentSecurityPolicy(nonce));
  return response;
}

export async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;

  // Server Component 側 (next/headers) から参照できるよう、リクエストヘッダーに nonce を積む。
  // 以降の NextResponse.next({ request: { headers: request.headers } }) はこの参照を共有する。
  const nonce = Buffer.from(crypto.randomUUID()).toString("base64");
  request.headers.set("x-nonce", nonce);
  // Next.js は「リクエスト側」の CSP ヘッダーから nonce を検出し、自身が生成するインラインスクリプトに付与する
  request.headers.set("Content-Security-Policy", buildContentSecurityPolicy(nonce));

  // 静的ファイルなどはスキップ
  if (shouldSkipMiddleware(pathname)) {
    return withCsp(NextResponse.next({ request: { headers: request.headers } }), nonce);
  }
```

以前nonce化を見送っていた原因は、UIライブラリのMantineが実行時に挿入する `<style>` 要素でした。Mantineには `getStyleNonce` というnonceを渡すための仕組みがありますが、関数のpropなのでServer Componentからは直接渡せません。そこで、nonceの文字列だけを受け取るClient Componentのラッパーを用意しています。

```tsx
"use client";

import { useState } from "react";
import { MantineProvider as CoreMantineProvider } from "@mantine/core";

interface AppMantineProviderProps {
  nonce: string;
  children: React.ReactNode;
}

// MantineProvider の getStyleNonce は関数 prop のため Server Component からは渡せない。
// nonce (文字列) だけを RSC 境界越しに受け取り、クロージャはこの Client Component 内で生成する。
// ...
// ブラウザの CSP は最初の HTML レスポンスの nonce のままなので、nonce はドキュメントの存続中は固定する。
// router.refresh() などで RootLayout が再実行されると nonce prop は新しい値になるが、
// そのまま使うと Mantine が後から挿入する style 要素が CSP に拒否される。初回の値を state に保持して使う。
export function AppMantineProvider({ nonce, children }: AppMantineProviderProps) {
  const [initialNonce] = useState(nonce);
  return (
    <CoreMantineProvider
      getStyleNonce={process.env.NODE_ENV === "production" ? () => initialNonce : undefined}
    >
      {children}
    </CoreMantineProvider>
  );
}
```

ルートレイアウトでは、ミドルウェアが積んだ `x-nonce` を `headers()` から読み取り、`ColorSchemeScript` と上記のプロバイダーに渡しています。

```tsx
export default async function RootLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
  // middleware.ts が発行した nonce (CSP の script-src/style-src と一致させる)
  const nonce = (await headers()).get("x-nonce") ?? "";

  return (
    <html lang="ja" {...mantineHtmlProps}>
      <head>
        {/* ブラウザが nonce 属性を隠すため client 側で nonce が空になり、ハイドレーション警告になるため suppressHydrationWarning で抑止する */}
        <ColorSchemeScript nonce={nonce} suppressHydrationWarning />
      </head>
      <body>
        <SupabaseAuthProvider>
          <AppMantineProvider nonce={nonce}>
```

なお、ルートレイアウトが `headers()` を読むようになったため、全ルートが動的レンダリングになる点も仕様書に明記されています。

### GitHub ActionsとclaspでGASを管理する

最後に司会者から、GAS（Google Apps Script）の管理方法の紹介がありました。以前の勉強会で、GASをコマンドラインから操作できる **clasp** を紹介していましたが、現在はこれをGitHub Actionsのワークフロー上で実行しているそうです。

* コードはGitHubのリポジトリだけで管理し、ローカルでは管理しない
* `main` にプッシュするたびにGitHub Actionsが動き、clasp経由でGASのスクリプトに反映される
* AIにコードを修正させてGitHubに反映すれば、そのままGAS側にも反映されるため、手動でのプッシュ／プルが不要になる

メンバーから「プライベートリポジトリにする必要があるのか」「claspのキーを公開しなくても動くのか」という質問がありました。認証情報はGitHubの **Secrets and variables** に登録すれば公開されないため、内容が公開して問題ないものならパブリックリポジトリでも構わない、とのことです。

むしろ、公開できる内容ならパブリックの方がおすすめだという話もありました。GitHub Actionsはプライベートリポジトリだと無料枠（月2,000分、全リポジトリの合計）を超えると課金されるためです。AIの登場以降、コードを修正してプッシュする頻度が上がり、この無料枠をすぐに使い切ってしまうという声がSNSなどでも増えているそうです。

## 活用した技術

### CSPのnonceと `'strict-dynamic'`

CSPの `script-src` に `'unsafe-inline'` を指定すると、HTMLに直接書かれた `<script>` がすべて実行可能になります。攻撃者が何らかの方法でスクリプトをページに注入できた場合、それも実行されてしまうため、XSSへの防御としてはほとんど意味がなくなります。

nonceベースのCSPでは、サーバーがリクエストごとに推測できないランダムな値を生成し、CSPヘッダーと正規の `<script>` タグの両方に同じ値を付けます。

```text
Content-Security-Policy: script-src 'nonce-abc123' 'strict-dynamic'
<script nonce="abc123">...</script>
```

ブラウザは、ヘッダーのnonceと一致する `nonce` 属性を持つスクリプトだけを実行します。nonceはリクエストごとに変わるため、攻撃者は事前に正しい値を知ることができません。

`'strict-dynamic'` は、「nonceで信頼されたスクリプトが動的に読み込んだスクリプトも信頼する」という指定です。これを指定すると、`'self'` やホスト名による許可は無視されます（`'strict-dynamic'` に対応していない古いブラウザ向けのフォールバックとしてのみ働きます）。そのため、新しい外部スクリプトを追加する場合は、ホストをCSPに書き足すのではなく、nonce付きのスクリプトから読み込む必要があります。

### `style-src-elem` と `style-src-attr` の分離

CSPでは、スタイルについても `<style>` 要素（`style-src-elem`）と `style="..."` 属性（`style-src-attr`）を分けて制御できます。nonceは要素に付ける属性なので、`style` 属性には適用できません。

今回の実装では、Mantineが挿入する `<style>` 要素には `getStyleNonce` でnonceを付けて本番では `'unsafe-inline'` を排除し、アプリ内で多用している `style={{...}}` によるインライン属性だけは `'unsafe-inline'` を許可しています。属性の値はすべて静的なため、実害は限定的という判断です。

### Next.jsのミドルウェアとnonce

Next.jsは、リクエストヘッダーの `Content-Security-Policy` からnonceを読み取り、自身が生成するインラインスクリプト（ストリーミング用のスクリプトなど）に自動でnonceを付与します。今回のミドルウェアがレスポンスだけでなくリクエスト側にもCSPヘッダーを積んでいるのはこのためです。

一方で、nonceを読むために `headers()` を呼び出すと、そのルートは静的に事前生成できず、リクエストごとのレンダリング（動的レンダリング）になります。セキュリティと引き換えにキャッシュの効きが変わる点は、nonce化を検討する際のトレードオフとして押さえておきたいところです。

### GitHub ActionsのSecrets

GitHub Actionsでは、リポジトリの「Settings → Secrets and variables → Actions」に登録した値を、ワークフローから `${{ secrets.NAME }}` の形で参照できます。登録した値はログ上でもマスクされるため、claspの認証情報のような秘密情報をリポジトリに含めずに自動デプロイを組めます。今回のGAS管理の例のように、コードはパブリックにしつつ認証情報だけを隠す、という運用が可能になります。

## 総括

今回は、CSPのnonce化によってポータルサイトのブラウザ側のセキュリティを一段引き上げた回となりました。`'unsafe-inline'` は「とりあえず動かす」ために使われがちな設定ですが、UIライブラリの事情を一つずつ解消していけば外すことができる、という実例になったと思います。

会議では、新しく着手するIssueのレビュアーに「理解の練習を兼ねて」立候補するメンバーがいたり、AIにPRを解説させながらレビューする進め方が話題になったりと、AIを使った学び方も広がっています。ブラウザで完結するコード実行環境や、GitHub ActionsによるGASの自動反映など、日々の開発を楽にする工夫も共有されました。

シンギュラリティ・ラボでは、こうしたチーム開発に一緒に取り組む仲間を募集しています。興味のある方はぜひご参加ください。
