## 概要

本記事は、[チーム開発記録47：ver7リリースと課題の棚卸し](https://zenn.dev/singularitylabs/articles/1703a20f0b254a)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。ver7のリリースを終えてver8の開発期間に入った今回は、**VS CodeとPrettierの設定競合を解消し、コードフォーマットをリポジトリ全体で統一するPR**がマージされました。

会議では、レビュー対応を重ねるうちに肥大化したイシューをどう分割するかという運用面の議論が中心になりました。また、サイトを使い込んでいるメンバーから報告された**4件のバグをその場でトリアージ**し、「新しいイシューには会議の場で優先度タグを付けて合意する」という新しいプロセスが始まっています。メンテナー向け管理画面の必要性や、CopilotとClaude Codeを組み合わせたAIレビューの活用法まで、イシュー管理を軸に運用改善の話題が続いた回でした。

## 開発したもの

### コードフォーマッター設定の整理とPrettierの全体適用

前回の定例後にマージされたPRでは、開発メンバーごとの環境でVS Codeのフォーマット機能とPrettierの設定が競合していた問題を解消しました。変更ファイル数は30個と多く見えますが、大半はPrettierを全ファイルに適用した際の整形差分で、実質的な変更はエディタ設定と除外設定、npmスクリプトの3点です。

まず `.vscode/settings.json` に、JSON系ファイルのフォーマッター指定とMarkdown編集時のインデント設定を追加しました。

```json
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "[json]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[jsonc]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[markdown]": {
    "editor.tabSize": 2,
    "editor.insertSpaces": true
  },
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}
```

あわせて、フォーマット対象から外すファイルを指定する `.prettierignore` を新規追加しました。`.gitignore` と同じ書式で「ここに書いたものは整形しない」と宣言するファイルです。

```text
# Dependencies
node_modules/

# Build artifacts
.next/
out/
coverage/

# Local/temporary artifacts
playwright-local/artifacts/
playwright-local/playwright-local/artifacts/

# Supabase SQL migrations are outside current prettier parser targets
supabase/**/*.sql

# Supabase型自動生成ファイル（全体formatから除外、db:types後に個別整形）
app/types/lib/database.types.ts
```

さらに `package.json` には、フォーマットの確認・適用を行うコマンドが追加されました。Supabaseの型定義を自動生成する `db:types` コマンドも、生成後にPrettierで整形するよう変更されています（抜粋・変更後）。

```json
"scripts": {
  "start": "next start",
  "lint": "next lint",
  "type-check": "tsc --noEmit",
  "format:check": "prettier --check . --ignore-unknown",
  "format": "prettier --write . --ignore-unknown",
  "db:types": "source .env.local && npx supabase gen types --lang=typescript --project-id ${SUPABASE_PROJECT_ID} --schema public > app/types/lib/database.types.ts && prettier --write app/types/lib/database.types.ts",
  "lint:logs": "node scripts/lint-logs.cjs",
  "test": "jest --verbose --coverage"
}
```

これで、最新のmainブランチを取り込めば `npm run format:check` でフォーマット違反を確認できるようになりました。CIへの組み込みは今後の課題として残されています。

このほか、テスト用GitHub Actionsの構築、本番環境リリース自動化の設計書、共通化イシューの設計書修正など、複数のプルリクエストがレビュー中の状態で進行しています。

## 会議の様子

### 肥大化するイシューをどう分割するか

進行中の「カテゴリー管理APIのコード品質改善」イシューについて、担当メンバーから「レビュー指摘への対応が続いている」との報告があったのをきっかけに、**イシューの粒度**の議論が始まりました。このイシューは元々、機能追加のプルリクエストをマージする際に「すぐ直さなくてもよいが、直しておいたほうがよい」点をまとめて起票したものでした。細かい修正を1件ずつイシューにするとイシューが多すぎて管理しづらくなり、まとめると今度は中身が膨らんで「結局何をやっているんだっけ」となる——というジレンマです。

これに対して、メンバーからは2つの提案が出ました。1つは、細かな修正・改善はバージョン開発とは**別のプロジェクト（ボード）に分けて、どんなに細かくてもチケットを切れるようにする**案。もう1つは、大がかりな修正のついでに思いついた改善はそのチケットには入れず、**着手前に「ここまでしかやらない」という線を引き、膨らんだら子・孫と何段でも冷静に切り出す**という考え方です。

リードの判断は「ボードを分けると管理の手間が増えるだけになりそうなので、**対応すべきことが1つのボードで一覧できる現状を維持する**。ただし作業の中で問題が細分化されて追加イシューが切られるのは自然な流れとして歓迎する」というものでした。実際、今回のイシューも複雑化した部分はすでに別イシューへ切り離し済みであることが確認され、経緯を追えるようにイシューのディスクリプションをきちんと埋めておくことも申し合わせました。

### バグ4件の報告と、その場での優先度付け

サイトを日常的にメンテナンスしているメンバーから、実際に使い込んで見つけた4件のバグが報告されました。

1. コンテンツの並べ替えを連続で行うと、2回目以降の選択肢の順番が変更前のまま（キャッシュが原因の可能性）
2. 資料・動画の編集メニューに「表示順」の項目が2つ表示される（本番環境のみで発生する環境差異）
3. カテゴリーの新規作成ができない（報告者の環境では失敗し、管理者権限のリードは成功したため、権限まわりが原因の可能性）
4. 動画一覧の3点メニューがスクロール時に他の要素を突き抜けて最前面に表示される（CSSのz-indexが原因と推定）

以前から「イシューに優先度を付けるべき」という話は出ていたものの、具体的な運用は決まっていませんでした。今回は**会議の場で新規イシューにHigh / Mediumの優先度タグを付けていく**ことをその場で実践。判断基準になったのは「誰がどれだけ困るか」です。カテゴリー新規作成不可は実作業に支障が出ているため**High**。表示順メニューの重複や3点メニューの最前面表示は「メンテナーや管理者にしか見えない＝困るのは自分たちだけ」なので**Medium**、並べ替えの選択肢の問題も画面更新で回避できるため**Medium**としました。Highのバグはリードが自ら担当し、レビューは別のメンバーが引き受けることになりました。

関連して、リリース間隔の議論もありました。あるメンバーの「本番にバグが残り続けるならリリース間隔を狭めては」という提案に対し、リードからは「2ヶ月というのはメジャーアップデートのスパンで、『ここまでにこれを直す』ではなく**できたものからリリースするスタンス**。バージョンをメジャー・マイナー・パッチで分けているので、緊急性の高い修正はパッチリリースでいつでも反映できる」という整理が示されました。必要なのはリリース頻度そのものより、どのバグがクリティカルかを会議で合意しておくこと——今回の優先度付けの運用は、まさにその答えというわけです。

### メンテナー向け管理画面と「DBを直接触らない」原則

バグ報告と合わせて、メンテナンス作業のつらさも共有されました。動画の並べ替えや責任者の変更が「1件ずつ画面を開いて変更するしかない」現状に対し、**全レコードをテーブル形式で編集できるマスターメンテナンス画面**の必要性が改めて確認されました。ドラッグ＆ドロップによる並べ替えや、CSVを読み込ませての一括編集といったアイデアも挙がり、メンテナー側のユーザビリティ改善はバグ修正と並んで優先的に進める方針になりました。

一方、あるメンバーからは「Supabaseの本番環境の管理画面にアクセスできるようにしてほしい。本番と検証でデータや構造の差異があったとき、見えない部分は対処のしようがない」という要望が出ました。これに対しリードは「**テーブルを直接触るのは基本的にご法度**。何でもできてしまうからこそ、アプリの制約の中で編集できる仕組みを作るのが一般的な流れ」という原則を示しつつ、障害調査のための参照ニーズには理解を示し、ユーザーテーブルなど公開すべきでない情報を除いた参照権限を設定できるか調査することになりました。

### AIレビューの使いこなし — CopilotとClaude Codeの分業

プロフィール画像機能を進めているメンバーから「Copilotのレビューコメントが数日遅れで付くのはなぜか」という質問があり、GitHub Copilotによるコードレビューの流れを全員で確認しました。プルリクエスト作成後に**レビュアーとしてCopilotを追加すると自動でレビューが始まり**、修正後の再レビューはボタンから依頼できること（ただし再レビューの依頼には課金プランの設定が必要なこと）、Copilotの指摘はあくまで提案であり、採用するかどうかは担当者が判断することが共有されました。

さらにリードから、実践的なTipsとして「Copilotのレビューが出たら、Claude Codeに『この指摘を修正できているかチェックして』と依頼し、修正の要否をまず精査させてから自分で最終判断する」という使い方が紹介されました。単体のAIではどうしても見落としがあるため、**別のAIからレビューを受けるクロスチェック**は品質面でも効率面でも有効だといいます。共通化イシューの設計書修正でも、担当メンバーがClaude Codeに追加の改善点を尋ねたところ「これ以上やるとかえって複雑になる」とAI自身が線を引いた例が共有され、「生成AIは優秀だが万能ではない。人間の確認はまだ必要」という認識で一致しました。Draw.ioで作成した機能設計書のメンテナンス方法についても、HTML化や公式MCPサーバーの活用などAIに検討させた案をもとに、メンテナンス性重視で調査を続けることになっています。

このほか、ポータルサイトに加えて学習支援サービス「sinlab-study」のリポジトリも今後チームで管理していく方針が共有され、進め方は連休明けに相談することになりました。

## 活用した技術

### Prettierとエディタ設定によるフォーマットの一元化

**Prettier**は、JavaScript/TypeScriptを中心に広く使われるコードフォーマッターです。セミコロンの有無、クォートの種類、末尾カンマなどのルールを `.prettierrc` に定義しておくと、コードを機械的に整形してくれます。一方でVS Code自体にもフォーマット機能があるため、両者の設定がずれていると「保存するたびに人によって違う整形がかかる」という競合が起きます。今回のPRは、`.vscode` フォルダの `settings.json` でPrettierをデフォルトフォーマッターに固定し、この競合を解消するものでした。ワークスペース設定はリポジトリごとに共有されるため、チーム全員のエディタ挙動を揃えられます。なお、会議中の質疑では「Cursorは中身がVS Codeなので、同じ設定がそのまま反映される」という補足もありました。

もう1つのポイントが、自動生成ファイルの扱いです。Supabaseの型定義ファイルのような自動生成物は全体フォーマットの対象から除外しつつ、生成コマンドの直後に個別整形をかけることで、「生成のたびに巨大な整形差分が出る」事態を防いでいます。

### GitHub Copilotコードレビューと多段AIレビュー

GitHub Copilotのコードレビュー機能は、プルリクエストのレビュアーにCopilotを指定するだけで、変更内容の要約と行単位の指摘コメントを自動生成してくれます。ただしCopilotは完全に「レビュアー」の立ち位置であり、指摘を修正するかどうかの判断は人間に委ねられます。今回チームで共有されたのは、この判断の一次スクリーニングをClaude Codeに任せるという運用です。AIレビューをAIに精査させ、最後に人間が判断する多段構成にすることで、単一のAIによる見落としを補いながら、人間の確認コストを下げられます。

### Supabase RLSポリシーと権限起因のバグ

今回報告された「カテゴリーの新規作成ができない」バグは、**RLS（Row Level Security）ポリシー**が原因である可能性が高いと推測されています。RLSはSupabase（PostgreSQL）でテーブルの行単位にアクセス制御をかける仕組みで、「管理者ロールのみINSERTを許可する」といったルールをデータベース側で強制できます。裏を返せば、ポリシーの設定を誤ると**特定のロールのユーザーだけが操作に失敗する**というバグになり、管理者が試すと再現しないため発見が遅れがちです。今回も「誰が・どの環境で・どのロールで試したか」によって結果が変わったことが切り分けの手がかりになっており、権限起因のバグでは再現条件の記録が重要だとわかる事例です。

なお、こうした調査のためでも本番データベースを直接操作しないのが原則です。アプリの制約を通して安全に編集できるマスターメンテナンス画面の整備は、この原則とメンテナンス性を両立させるための投資といえます。

## 総括

今回マージされたPRはコードフォーマッター整理の1件でしたが、会議ではイシューの分割基準、優先度タグの運用開始、リリース間隔の考え方の整理と、**開発を支える運用の土台**を固める議論が続きました。「イシューが膨らんだら線を引いて切り出す」「新しいイシューは会議で優先度を合意する」というシンプルなルールは、少人数の副業的なチーム開発だからこそ効いてくるはずです。

また、サイトを使い込んだメンバーからのバグ報告は、テストでは見つけにくい実運用の課題を浮かび上がらせました。メンテナー向け管理画面のような「使う人の声から生まれるイシュー」を優先度高く扱う方針と、CopilotとClaude Codeを組み合わせた多段AIレビューの定着で、ver8に向けた開発のリズムが整ってきています。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
