## 開発したもの

### カテゴリー管理APIのコード品質改善

前回のバージョンで実装したカテゴリー管理機能について、コード品質を改善するリファクタリングPRがマージされました。ポイントの1つは、カテゴリーの表示順（`display_order`）を振り直す処理を、`Promise.all` による並行更新から `for...of` による**順次更新**に変更したことです。

```typescript
// app/services/api/categories-client.ts（抜粋・変更後）
for (const category of affectedCategories) {
  const { error } = await supabase
    .from("categories")
    .update({ display_order: category.display_order + 1 })
    .eq("id", category.id);

  if (error) {
    throw new Error(`表示順更新に失敗しました(id: ${category.id}): ${error.message}`);
  }
}
```

また、これまでエラーチェックが漏れていた箇所にハンドリングを追加し、再採番の対象を未削除のアイテムに限定する修正も入りました。

```typescript
// app/services/api/utils/display-order.ts（抜粋・変更後）
// カテゴリー内の未削除アイテムを display_order の昇順で取得する。
const { data: items, error: selectError } = await supabase
  .from(table)
  .select("id")
  .eq("category_id", categoryId)
  .eq("is_deleted", false)
  .order("display_order", { ascending: true });

if (selectError) {
  throw new Error(`${table} の並び順再採番対象取得に失敗しました: ${selectError.message}`);
}
```

このPRのレビューでは「重複検証は原則行わない、というテスト方針に違反していないか」といった指摘のやり取りが定例の時点でも続いており、元のIssueから派生した改善Issueも複数作られています。

### CI/CD設計書 — 本番リリース自動化の設計

本番環境のリリース操作を自動化する取り組みは、**設計フェーズが完了**し、CI/CD設計書とリリース手順Wikiのドラフトがマージされました。設計書には、自動化の判断基準（定型的でリカバリー可能なものは自動化、本番データの変更を伴うものは手動継続、確認を挟むべきものは承認ゲート付きの半自動）や、`GITHUB_TOKEN` の権限を各ワークフローで最小限に絞る方針が明文化されています。

タグとGitHub Releaseを作成するワークフローには、誤実行を防ぐガード条件（マージ済みチェック、PRタイトルチェック、バージョン形式チェック、タグ重複チェック、承認ゲート）に加えて、同時実行制御も設計されています。

```yaml
# docs/ci-cd-design.md より（抜粋）
concurrency:
  group: create-release
  cancel-in-progress: false
```

定例では「設計までは終わったが、ワークフローの構築はこれから。早急に対応してプルリクエストを出す」という進捗が共有されました。

### プロフィール画像機能の設計ドキュメント

開発中のプロフィール画像アップロード機能について、READMEやAPI仕様書、データベース設計書などのドキュメントを更新するPRがマージされました。アップロード（`POST /api/profile/image`）と削除（`DELETE /api/profile/image`）のエンドポイントを設け、許可する拡張子はjpg/jpeg/png/gif、ファイルサイズ上限は1MBという仕様です。

```json
{
  "success": true,
  "profile_image_path": "abc123/profile-image"
}
```

実装本体については、担当メンバーから「一度プルリクエストを出したが、テスト漏れに気づいたので取り下げた。修正してテストを終えたので、改めて提出する」という進捗が共有されました。取り下げの判断も含めて状況がチームに共有されているのが健全なところです。

このほか、RLSポリシー定義を共通化する関数のリファクタリングPRもこの期間にマージされています。

## 会議の様子

### Issueのディスクリプション、何をどこに書くか

今回の中心議題は、Issueの「更新方法」でした。きっかけは、リードメンバーが3月に作られたIssueを2ヶ月ぶりに見返したときの体験です。担当メンバーが進捗状況をディスクリプション（Issue本文）に追記し続けてくれていたのですが、その結果、**冒頭を読んでも「そもそも問題って何だっけ？」が分からない**状態になっていました。

そこから「進捗はどこに書くべきか」の議論に発展しました。

* リードメンバーは「時系列の進捗はコメント欄に書き、ディスクリプションはパッと見て内容が分かる状態を保つべき」という立場
* 更新していた担当メンバーは「整理された対応状況の概要はディスクリプションにあるべき。コメントはやり取りが増えるほど流れて長くなる」という立場
* 別のメンバーからは「ディスクリプションは更新履歴が残らないので、問題だけを書いて進捗はコメントで積む方がよい」という意見
* 折衷案として「**最新の進捗だけ**をディスクリプションに書くならあり」という案

最終的な結論は次のとおりです。**背景と問題点はディスクリプションの冒頭に書くことをルール化**し、最初に目に入るようにする。時系列の進捗は原則コメントに書く。整理した最新状況をディスクリプションに載せるかどうかは、厳密にルール化せず担当者とレビュアーの判断に任せる——「こういう場合はどうするのか」という例外問題を生まないよう、あえて縛りすぎない着地です。また「自分用のメモを書くのは全然あり。ただしみんなが見る場所なので、できればコメント欄に」という運用や、「進捗を書き続けるほど伸びるIssueはタスクが大きすぎるサイン。分割すべき」という指摘も共有されました。

関連して、タスク管理では「In Progressは着手中という意味なので、同時進行できないタスクはTo Doに戻してもらえるとチームとして状況が分かってありがたい」という確認もありました。

### Resolve conversationは誰が押すか — Copilot指摘の扱い

プルリクエストのレビュー運用についても、全体向けの提案がありました。GitHubのレビューコメントに付いている**Resolve conversation**ボタンは誰でも押せますが、担当者側で先にResolveされてしまうと、**レビュアーが指摘の修正を確認しないままスルーしてしまう**恐れがあります。そこで「基本は指摘した人（レビュアー）が押す」という運用が提案されました。

議論になったのはGitHub Copilotによる自動レビュー指摘の扱いです。当初は「Copilotの指摘は、担当者が対応済みと判断したらResolveしてよい」という案でしたが、別のメンバーから「**Copilotの指摘もレビュアーがResolveする方が、間違って閉じられることがない**」という対案が出ました。Copilotは指摘の数が多く、レビュアーの負担増が懸念されましたが、「担当者が各指摘に対して、直すなら対応内容を、直さないなら理由をコメントする。レビュアーはそのコメントを見て判断すればよい」という補完案で負担を軽減できる見通しが立ちました。

結論として、**人の指摘もCopilotの指摘もResolveはレビュアーが行い、担当者はすべての指摘に何らかのアクション（修正またはコメント）を返す**という運用を試験的に始めることになりました。負担が大きければその時に再調整します。この際「面倒だからやめる、と感覚でルールを変えるとルールメイキングがぐちゃぐちゃになる。変えるときは協議の上で」という釘刺しもありました。

派生タスクとして、Copilotに与えるレビュー観点をプルリクエストのディスクリプションに明記し、的外れな指摘を減らす改善Issueも作成されました。リファクタリングや機能追加といった開発目的別に観点をテンプレートに列挙しておき、PRを出す人が不要な観点を消して提出するスタイルが最終形ではないか、という案が出ています。

### Markdownの表記揺れと「npm run format」のルール化

ドキュメント整備では、Markdownの**表記揺れ問題**への対応が共有されました。ドキュメント内に余分な半角スペースやハイフンが大量に混入していたり、テーブルのパイプ（`|`）位置が「一番長いセル」に合わせて表全体で動いてしまったりして、プルリクエストに本題と関係のないフォーマット差分が現れていたのです。

担当メンバーは、テーブル部分だけを正しい形に整形する**専用フォーマッターツール**をscripts配下に追加し、既存ドキュメントも一括修正しました。Mermaidで描いた構成図などは整形の対象外にしています。あわせてWikiのナレッジ共有ページにも情報を追記しました。

議論の中でリードメンバーから「そもそも表記揺れが起きているのは、`npm run format` を実行してからPRを出すというルールを作っていなかったからでは」という指摘があり、確認するとGitHub Actionsにもフォーマットチェックが組み込まれていないことが分かりました。結論として、**PRを出す前に `npm run format` を実行して余計な差分がないか確認し、レビュアー側も同じコマンドを実行してチェックする**運用にし、必要ならActionsへのチェック組み込みも検討することになりました。VS CodeのPrettierプラグインや保存時フォーマットは個人の設定に依存するため、「人に依存しない仕組み」を優先する判断です。

### 画面設計はdraw.ioか、HTMLモックか

継続検討中の画面設計ツールについては、担当メンバーから「**AIに描かせるならHTMLモックの方がやりやすい**」という方向性が示されました。機能設計書のための画面をHTMLで作り、その描画結果をPNGやSVGにして掲載するイメージです。

ただし課題もあります。GitHubはMarkdown内のHTMLをレンダリングしないため（Mermaidは描画対応しているのに対し）、リポジトリ上で綺麗に見せるには画像化の一手間が必要です。SVGならテキスト形式なのでAIが直接編集しやすいという利点も紹介されました。リードメンバーは「一番重視したいのは管理・メンテナンスのしやすさ。draw.ioを使うと難易度が一番高くなりそう」との考えを示し、もう少し検討したうえで改めて全員で議論することになりました。

このほか、前回決めたSupabase共有クエリの削除は「SQLエディタのクエリは作った本人しか消せないため各自で削除し、全員の確認が済んだことをミーティングで確認できたらIssueを閉じる」という進め方を確認しました。また、新しく立ち上げ準備中の学習支援アプリ（sinlab-study）チームの進め方についても「ポータルサイトと同じIssue・プルリクエストベースの運用にする」ことを確認しています。

## 活用した技術

### 並行更新の落とし穴 — Promise.allから順次更新へ

JavaScriptの `Promise.all` は複数の非同期処理を並行実行できる便利な仕組みですが、**同じデータ群の順序（今回なら `display_order`）を振り直すような処理**では注意が必要です。並行して複数のUPDATEが走ると、実行順序が保証されず、値の衝突や中途半端な状態が生まれる可能性があります。今回のリファクタリングでは `for...of` による順次更新に変更し、1件ずつ確実に更新してからエラーを検査する形にしました。

もう1つの学びはエラーハンドリングです。Supabaseのクライアントは失敗時に例外を投げるのではなく、戻り値の `error` プロパティにエラーを格納します。つまり**チェックを書き忘れると失敗が静かに握りつぶされる**ため、すべてのクエリで `error` を確認して例外に変換する徹底が品質改善につながります。

### GitHub Actionsのconcurrencyと承認ゲート

リリース自動化のように「二重に実行されると困る」ワークフローには、GitHub Actionsの `concurrency` 設定が有効です。同じグループ名のジョブは同時に走らず、`cancel-in-progress: false` を指定すれば実行中のジョブを止めることなく後続をキュー待ちにできます。

また、GitHub Environmentsの**承認ゲート**を使うと、指定した承認者がOKするまでジョブの実行を保留できます。タグ作成やリリース公開のような影響の大きい操作を「自動化はするが、実行直前に人間が確認する」半自動の形にできるのがポイントです。あわせて `permissions` でワークフローごとに `GITHUB_TOKEN` の権限を最小限に絞れば、万一の誤動作や漏洩時の影響範囲を限定できます。

### PrettierとMarkdownテーブルの整形差分

Prettierなどのフォーマッターは、Markdownのテーブルを整形するとき**列内で一番長いセルに合わせてパイプ位置を揃える**動きをします。このため、1つのセルに長い文字列を足しただけで表全体の行に差分が発生し、レビューで「どこが本質的な変更なのか」が分かりにくくなります。

こうした差分ノイズを防ぐ基本は、**全員が同じフォーマッターを同じ設定で必ず通す**ことです。誰かが通し忘れると、次に実行した人のPRに未整形分の差分がまとめて紛れ込みます。今回のチームの結論——PR前の `npm run format` 実行をルール化し、ゆくゆくはCIでチェックする——は、フォーマットを個人の設定や習慣に依存させず、仕組みで揃えるための定石といえます。

## 総括

節目の記録50回目となる今回は、コードそのものよりも「チームで開発を回すためのルール」に時間を使った回でした。Issueのディスクリプションは背景・問題点を冒頭に、進捗は原則コメントに。Resolve conversationはレビュアーが押し、担当者はすべての指摘にアクションを返す。PRの前には `npm run format`。どれも小さな取り決めですが、「2ヶ月後に見返しても分かるか」「レビューの確認漏れが起きないか」という実体験に根ざしたルールばかりです。

一方で、進捗のまとめ方やCopilot指摘の扱いをあえて厳密にルール化しすぎず、担当者とレビュアーの判断や試験運用に委ねたのもこのチームらしいバランス感覚です。開発面でもカテゴリー管理APIの品質改善やリリース自動化の設計完了など、ver8に向けた足場が着実に固まってきました。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
