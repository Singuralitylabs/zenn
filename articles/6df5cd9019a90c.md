## 概要

本記事は、[チーム開発記録25：アプリ設計とGitHub操作](https://zenn.dev/singularitylabs/articles/58c4b44d06da61)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回の1週間はマージされたプルリクエストこそなかったものの、**アプリ紹介ページの実装が大詰め**を迎え、**会員の役割別表示のデータベース設計**も前進、さらに**2件のUI改善がレビュー段階**に入るなど、複数のタスクが着実に進んでいます。

### 会員の役割別表示：roles・role_tagsテーブルの設計

担当メンバーが進めている「会員の役割別表示」機能では、役割のマスターとなる `roles` テーブルと、役割とユーザーを紐づける `role_tags` テーブルを新設するため、データベース設計書の更新が進んでいます。テーブル定義自体は書き上がっており、残るはRLS（Row Level Security：行単位のアクセス制御）ポリシーの記述です。

その執筆過程で、既存の設計書のRLSポリシー節が「ほぼコピペの繰り返し」になっているという課題が見つかりました。実際、資料（documents）や動画（videos）などコンテンツ系テーブルのポリシー説明には、次のような同じ条件式が何度も登場します。

```sql
-- docs/database.md より抜粋：多くのポリシー説明で繰り返し登場する条件式
EXISTS (
    SELECT 1 FROM users
    WHERE
    auth_id = auth.uid()
    AND role IN ('admin', 'maintainer')
    AND status = 'active'
    AND is_deleted = FALSE
)
```

この記述方針の整理は別イシューに切り出すことになり、今回追加するテーブルのポリシーは既存の記述を参照する形で書き進めることになりました（詳細は「会議の様子」参照）。

## 会議の様子

### 共有データベースに直接テーブルを作ってよいか？

アプリ紹介ページに必要な `applications` テーブルを「どこに作るか」が最初の論点になりました。開発用データベースは他のメンバーの開発でも使われる共有環境です。テーブルの中身や設計を変更すると、他のメンバーがテスト中にアクセスしたとき「思った挙動と違う動きをする」リスクがあるため、これまでは気を使う作業とされ、以前は検証用に別のデータベースを用意したこともありました。しかしその別データベースは運用が止まっており、使い勝手にも課題がありました。

そこでリードから「今回は既存テーブルの修正ではなく、新しいテーブルを追加するだけ。他の人に影響することはほぼないはずなので、直接作ってよいか」という相談がありました。データベースに馴染みの薄いメンバーには「なぜデータベース変更は気を使うのか」から噛み砕いて説明した上で意見を募り、**既存テーブルに手を入れない「追加のみ」の変更であれば、周知した上で共有データベースに直接作成してよい**という結論に落ち着きました。

### 設計書は「コピペの繰り返し」でいいのか — 記述方針とタスク分割

役割別表示の設計を進める担当メンバーからは、設計書に対する率直な問題提起がありました。「各テーブルごとのRLSポリシーがほとんどコピペに見える。デフォルトの定義をどこかに書いて、それに準ずるものは差分だけ書く形にできないか」「テーブルが増えるたびにこの記述が丸ごと増えていくのかと思うと、作業の手が止まってしまう」というものです。カテゴリーテーブルだけ書き方が違う点も、どういう意図なのか分からないと指摘されました。

リードも「意図はおそらくなく、最初に書かれた記述を後続の人がコピーして継ぎ足してきた結果だろう」と認め、**記述フォーマットの整理は別イシューとして切り出し、今回追加するテーブルのポリシーは「4.3 videosの内容に準ずる」のように既存記述を参照する一文で表現する**方針が決まりました。実装時の認識違いを防ぐため、完全に省略するのではなく参照先を明記するのがポイントです。

タスクの切り方も議論になりました。当初は「テーブル追加＋役割ごとの分類表示」までがひとつのタスクでしたが、分類表示は「管理人や代表理事といった役割をどの順番で並べるかを1人では決めにくく、定例で議論しないと煮詰まらない」という担当メンバーの見立てから、**まずテーブル追加と会員詳細画面への役割表示までをプルリクエストとして出し、分類表示は別タスクに分割する**ことになりました。スコープを広げすぎず、ブレなく進めるための判断です。

### プルリクエストの作り方を画面共有でレクチャー

後半は、この日のメインテーマであるプルリクエスト作成方法の共有です。リードが実際にVS CodeとGitHubの画面を操作しながら、ブランチ作成からプルリクエスト作成までの一連の流れをデモしました。運用ルールとして共有されたのは次のような点です。

* **タイトルは日本語で**、どんな修正かがパッと見て分かる文章にする（作成後もEditボタンで修正できる）
* **概要**には、ざっくりどんな修正を行ったかを書く
* **関連Issue**には `#` に続けてイシュー番号を書くと自動的に紐づく（入力補完も効く）
* **技術的変更点・レビュー特記事項**は、技術的な変更点や特に見てほしい箇所があれば書く。細かく書きすぎて時間をかける場所ではない
* **動作確認内容**には、画面を変えた場合に期待どおり表示されたかを一言添える（スクリーンショットの添付も歓迎）
* **レビュアー**にはイシューでレビュー担当になったメンバーとGitHub Copilotを、**アサイニー**には自分自身を設定する
* レビュー依頼・レビュー完了などの連絡は、見逃し防止のため**GitHubのコメントではなくSlackで行う**

あわせて、Markdownでは「ハイフンの後にスペースを入れると箇条書きに変換される」という小ネタや、テンプレート内の `<!-- -->` で囲まれたコメントは画面に表示されないので消さなくてよいこと、**テンプレートファイルをローカルで直接編集するのではなく、プルリクエスト作成時に自動で展開される本文に入力する**ことも、経験者のメンバーから補足されました。

Git操作の基本フローも改めてデモしました。mainブランチから新しいブランチを切り、ファイルを修正し、ステージング → コミットメッセージの入力 → コミット → 「ブランチの発行」でリモートに反映、という流れを画面で確認。**一度プルリクエストを出したブランチは、追加修正をコミットして同期するだけで自動的にプルリクエストへ反映される**（作り直しは不要）ことも、新メンバーの疑問に答える形で共有され、「すごくクリアになりました」という声が上がりました。

### Copilotレビュアーは「有料契約者しか追加できない」

プルリクエストのレビュアーにGitHub Copilotを追加する運用について、契約中のメンバーから重要な指摘がありました。**CopilotをレビュアーとしてPRに追加できるのは、GitHub Copilotの有料プランを契約しているユーザーだけ**ではないか、というものです。再レビューを依頼する更新ボタンも同様に、有料契約者しか押せません。

リード自身もこの制約を把握しておらず、「じゃあ僕だけができるの？」と驚く一幕も。チーム内で契約しているのは2名のみと分かり、**契約しているメンバーが気づいたタイミングでCopilotをレビュアーに追加する**という運用に落ち着きました。なお、高額なプランでなくても**個人向けのCopilot Proの契約でこの操作は可能**とのことです。会議中には「契約していないはずのメンバーがCopilotを追加できたように見えた」という謎の現象もあり、こちらは次回のプルリクエストで確認することになりました。

このほか、GitHub Actionsの構築は担当メンバーのスケジュール上12月以降に着手予定であること、**Supabaseの有料プランを契約し、データベースの移行方法や設定の調査を今月中をめどに整理する**こと、そして**ver5は12月上旬の本番環境リリースを目標**とすることが共有されました。

## 活用した技術

### プルリクエストテンプレート — 記述の質を仕組みで揃える

GitHubでは、リポジトリの `.github/pull_request_template.md` にテンプレートを置いておくと、プルリクエスト作成時に本文へ自動的に展開されます。ポータルサイト開発チームで運用しているテンプレートは次のようなものです。

```markdown
## 概要

<!-- 変更の背景・理由と、変更の概要を記載してください -->

-

### 関連Issue

<!-- 関連するIssue番号を記載してください -->

- #

## 技術的変更点

<!-- レビュワーに変更の流れが分かるように、どの処理をどう変更したか、どう動くのか、などを記載してください -->

-

### レビュー特記事項

<!-- レビュワーに重点的に確認してもらいたい観点や、レビュワーに伝えたい実装意図（本当はこうしようと思ったけど悩みがあってこうした、など）があれば記載してください -->

-

## 動作確認内容

<!-- 動作確認した内容（環境、ケース）を記載してください。UI変更の場合は、必要に応じて該当箇所のスクリーンショットをドラッグ&ドロップで添付してください -->

-
```

*（`.github/pull_request_template.md` より抜粋）*

HTMLコメント（`<!-- -->`）で書き方のガイドを埋め込んでおけば、PR画面には表示されないため消す手間もありません。テンプレートは「何を書くべきか」を毎回思い出させてくれるチェックリストとして機能し、書き手の経験値に左右されずレビューに必要な情報を揃えられます。今回のレクチャーのように口頭で伝えた運用ルールを、仕組みとして定着させる役割を担っています。

### VS CodeのGit統合 — GUIで学ぶブランチ・コミット・プッシュ

Gitはコマンドライン操作の印象が強いツールですが、VS Codeには標準でGit操作のGUIが搭載されています。今回のレクチャーで使った流れは次のとおりです。

1. 画面左下のブランチ名をクリック →「新しいブランチの作成」でmainから作業ブランチを切る
2. ファイルを修正すると、ソース管理ビューに変更ファイル数が表示され、クリックで差分を視覚的に確認できる
3. 「＋」ボタンで変更をステージング（コミット準備ができた状態にする操作）
4. コミットメッセージを入力してコミット（ローカルのリポジトリに記録される）
5. 「ブランチの発行」でリモート（GitHub）にブランチを反映。以降の修正は「変更の同期」を押すだけでリモートに反映される

コミットメッセージは「どんな修正や機能追加を行ったか」を記録するメモであり、空欄は基本的に認められていません。実際、今回レビュー中の修正でも、コミットメッセージを省略したことがプルリク作成のつまずきの一因になっていたようです。操作とGitの概念の対応が画面上で見えるため、Git初心者のオンボーディングにはGUIから入るのが有効だと感じられたレクチャーでした。

### GitHub Copilotによるコードレビュー

GitHub Copilotは、エディタ上でのコード補完だけでなく、**プルリクエストのレビュアー**としても利用できます。レビュアーに追加すると、変更内容のサマリーを自動生成し、直した方がよい箇所には指摘コメントを付けてくれます。チームのテンプレート末尾には「レビューコメントは日本語で書いてください」という指示をHTMLコメントで埋め込む工夫もしています。

ただし今回の会議で判明したとおり、Copilotをレビュアーに追加したり再レビューを依頼したりできるのは**有料プランの契約ユーザーのみ**です。個人向けのCopilot Proの契約でも操作できるため、チームでは契約者が気づいたタイミングで追加する運用にしています。AIのレビューは絶対ではありませんが、人間のレビュー前に指摘を受けて追加修正しておく「一次チェック」として活用しています。

## 総括

今回はマージされたプルリクエストがゼロの週でしたが、振り返ってみると「開発の土台を固めた回」でした。アプリ紹介ページと役割別表示という2つの機能開発が設計・実装の山場を越えつつあり、新メンバーによる2件のUI改善もレビュー段階へ。共有データベースへのテーブル追加の是非や、設計書の「コピペ問題」への率直な問題提起など、遠慮なく疑問を出し合ってその場で運用を決めていくチームの文化がよく表れた回だったと思います。

プルリクエスト作成方法のレクチャーは、一見遠回りに見えて、チームの暗黙知を言語化し新メンバーの立ち上がりを早める確実な投資です。「1人で考えても分からないことは、ミーティングでももくもく会でもSlackでも遠慮なく聞いてほしい」というリードの言葉どおり、質問しやすい空気づくりも含めてオンボーディングを進めています。ver5の本番リリース目標は12月上旬。進行中のタスクを一通り反映できるよう、引き続き開発を進めていきます。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
