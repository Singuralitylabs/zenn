## 開発したもの

今回紹介する実装は、いずれも定例時点でレビュー中またはレビュー依頼前のプルリクエストです。コードは実際のプルリクエストからの抜粋です。

### AIレビュー機能のトークン消費削減

sinlab-studyには、受講生が提出した演習課題のコードをGemini API（gemini-2.5-flash）でレビューするAIレビュー機能があります。無料枠の範囲で運用するため、**システムプロンプトの圧縮・出力トークン上限の短縮・月次利用上限チェック**の3点でトークン消費を削減するプルリクエストを、担当メンバーがClaudeと協働で実装しました。

1つ目の柱は出力トークンの削減です。レビュー生成時の `maxOutputTokens` を1500から800に短縮し、出力トークンを最大で半分近く削減します。

```typescript
// app/services/api/gemini.ts（抜粋・変更後）
    model: MODEL_NAME,
    systemInstruction: SYSTEM_PROMPT,
    generationConfig: {
      maxOutputTokens: 800, // 変更前は 1500
      // gemini-2.5-flash は思考モデルのため、thinking tokens が出力トークン枠を消費する。
      // レビュータスクには思考不要なので無効化してレスポンス出力に全トークンを確保する。
```

2つ目の柱は月次の利用上限です。当月に完了したAIレビューの件数をユーザーごとに集計し、上限の20回に達している場合はGemini APIを呼び出す前にHTTPステータス429でエラーを返します。

```typescript
// app/api/ai-review/route.ts（抜粋）
const MONTHLY_LIMIT = 20;

      const { count: monthlyCount, error: reviewCountError } = await supabase
        .from("ai_reviews")
        .select("id", { count: "exact", head: true })
        .in("submission_id", allUserSubmissionIds)
        .eq("status", "completed")
        .gte("reviewed_at", startOfMonth);

      if ((monthlyCount ?? 0) >= MONTHLY_LIMIT) {
        return NextResponse.json(
          {
            error: `今月のAIレビュー上限（${MONTHLY_LIMIT}回）に達しました。来月以降にご利用ください。`,
          },
          { status: 429 }
        );
      }
```

このプルリクエストには、上限チェックの動作を検証するVitestのテストコード（約200行）も含まれています。「月次20件に達したら429を返す」「19件なら通過してレビュー生成に進む」「提出が0件の新規ユーザーはカウント自体をスキップする」といった境界条件をモックで検証する構成です。

### AIトークン使用量モニタリングの設計書

リードが担当する使用量モニタリング・アラート通知機能は、まず**AIに設計書の叩き台を書かせてプルリクエストとして共有する**ところまで進みました。月次のトークン累計を保持する集計テーブル `ai_token_monthly_usages` の追加や、Slack Webhookによるアラート通知が設計に盛り込まれています。上限や警告の閾値は環境変数で調整できる想定です。

```text
# .env.local.example（抜粋・設計先行で追記）
# AIトークン使用量モニタリング
AI_REVIEW_MONTHLY_TOKEN_LIMIT=100000
AI_REVIEW_MONTHLY_WARNING_THRESHOLD_PERCENT=80

# Slack通知（初回ログイン時の承認依頼通知 / AIトークン使用量アラート）
SLACK_NOTIFICATION_WEBHOOK_URL=https://hooks.slack.com/services/xxxx/xxxx/xxxx
```

設計書では、リクエスト単位の生データ（各レビューの `prompt_tokens` / `completion_tokens`）は既存の `ai_reviews` テーブルに保持し、月次判定を高速に行うための集計値を新テーブルに持たせる方針が整理されています。

### 演習課題のヒント入力・編集機能

管理画面のコンテンツフォームから、演習課題の**ヒント**を入力・編集できるようにする対応がレビュー中です。ヒントは課題提出フォームの上部にアコーディオン形式で表示され、未入力（NULL）の場合はヒントUI自体を表示しません。

```tsx
// app/(authenticated)/manage/contents/ContentForm.tsx（抜粋）
<div className="space-y-2">
  <Label htmlFor="hint">ヒント（受講生に公開）</Label>
  <Textarea
    id="hint"
    value={hint}
    onChange={(e) => setHint(e.target.value)}
    placeholder="課題提出フォームの上部にアコーディオン形式で表示されます。..."
    className="min-h-[200px] font-mono"
  />
</div>
```

模範回答（AIレビューの採点基準・非公開）と対になる「受講生に公開」の項目として、ラベルで公開範囲を明示しているのがポイントです。このほか、コンテンツの一括アップロード機能の追加も別メンバーが進めています。

## 会議の様子

### 実装は終わった。では「削減できた」をどう確かめる？

トークン消費削減を担当したメンバーからは、「Claudeと一緒に一通り実装は終えたが、**そもそも何をもって消費削減と言えるのか**、どういう形でテストすればよいのかが分からなくなった」という率直な相談がありました。コードのテスト自体はAIが自動で書いてくれるものの、機能追加と違って「削減」は正しさの基準が自明ではない、という問題提起です。

リードからは、以前に別のメンバーがコンテキストやプロンプトの短縮を進めてきた経緯の説明とともに、「プルリクエストの内容とテスト方法をAIにそのまま尋ねた回答を共有しているが、**自分もまだ精査できていない**」という状況が共有されました。AIの回答にはベースライン検証（変更前後のトークン数を実測して比較する）やテストコードの実装が含まれていましたが、「このやり方が適切かどうかはちゃんと検討した方がよい」として、担当メンバーとリードの双方が内容を読み込んでから改めて回答することになりました。

実装はAIに任せられても、**検証方針の妥当性は人間が判断する**——AIとの協働が当たり前になったからこそ浮かび上がる論点であり、担当メンバーからも「興味があるので読んでおきます」と前向きな反応がありました。

### 使用量モニタリングは「ユーザーごと・呼び出しごと」

リードが進める使用量モニタリング機能については、課題背景から共有されました。現在のAIレビュー機能は**1つの課題につき1回だけ**レビューを依頼できる仕様ですが、今後は複数回のレビュー依頼を可能にしたい。そのためには、トークン使用量を実際にモニタリングしながら調整できる仕組みが先に必要になる、という順序立てです。

Gemini APIは月ごとの無料枠の範囲で利用している認識のため、「**API呼び出し1回ごとにデータを取り、月の上限を超えたらアラートを出す**」方針が示されました。メンバーから「これはユーザーごとに出すという発想か？」という質問があり、リードは「ユーザーごとに追い、呼び出しごとに個人の呼び出し数を記録するイメージ」と回答。ただし、どの粒度で集計するのが最適かは引き続き精査するとしています。

なお、この機能はまず設計書をAIに書かせてプルリクエストを発行し、Copilotのレビューにかけるという進め方を取っています。トークン削減のタスクと関連が深いため、両者の担当が互いのプルリクエストを確認し合う体制になりました。

### バックログの棚卸しと、初レビュアーへの挑戦

バックログに追加されたissueの読み合わせも行われました。スライド・動画ページへの概要欄カードの追加（#66）、編集時に画像URLやスライドURLを指定できないバグの修正（#67）、非公開コンテンツを管理者・コンテンツ管理者がプレビューできるようにする対応（#68）、テキストコンテンツのコードブロックへのシンタックスハイライト適用（#69）の4件です。

その場で「この対応をやりたい」と手を挙げたメンバーに新しいタスクがアサインされ、レビューは**レビュアー未経験のメンバー**が担当することになりました。「レビュアーまでできるか分からない」という不安に対して、リードがサポートに入る二段構えとし、「**練習だと思ってどんどん使ってください**」と背中を押す形でチーム全体のレビュー経験を広げていきます。

また、ポータルサイト側のテスト実装を進めるメンバーからは「テストの書き方やお作法がリードの考えと違っていたら申し訳ない」という確認がありました。これに対しリードは「**私の思想ではなく、このプロジェクトとタスクの目的に合っているかどうかで見る。目的に外れていなければ基本的にOKにする方針**」と回答し、レビューの判断基準を属人的な好みではなくプロジェクトの目的に置くことが明確に共有されました。

## 活用した技術

### LLM APIのトークン消費削減 — プロンプト圧縮と出力上限

LLM APIの利用料金や無料枠は、入力（プロンプト）と出力（生成テキスト）の**トークン数**で決まります。削減の基本は、毎回送るシステムプロンプトを短く圧縮することと、`maxOutputTokens` のような出力上限を実用最小限に絞ることです。今回のプルリクエストでは出力上限を1500→800トークンに短縮しました。

もうひとつ注意が必要なのが**思考モデル（thinking model）**の存在です。gemini-2.5-flashは応答前に内部的な思考トークンを消費し、これが出力トークン枠に含まれます。コードレビューのような定型タスクでは思考をオフにする設定（thinkingConfig）にすることで、限られた出力枠をレスポンス本文に充てられます。モデルの特性を理解した設定が、そのままコスト削減につながる好例です。

### HTTP 429と利用上限のサーバーサイド実装

利用回数の上限超過を表すHTTPステータスコードが**429 Too Many Requests**です。今回の月次上限チェックは、外部APIを呼び出す**前**にサーバーサイドで件数を集計して判定するのがポイントで、上限に達したリクエストはGemini APIに一切課金・消費を発生させずに拒否できます。また、エラーメッセージを「今月の上限に達しました。来月以降にご利用ください」と具体的に返すことで、ユーザーが状況と復帰時期を理解できるようにしています。

### モックを使ったAPIルートの自動テスト

「上限20件で拒否、19件なら通過」のような境界条件は、実際にAPIを20回叩いて確かめるわけにはいきません。今回のテストコードでは、Vitestの `vi.mock` で認証・Gemini呼び出し・DBアクセスを差し替え、Supabaseのクエリビルダー（`select().eq().gte()` のようなメソッドチェーンと `await` の両方に応答するthenableオブジェクト）を再現することで、**外部サービスに依存せず**上限判定のロジックだけを検証しています。「どうテストするか」という今回の会議の問いに対する、ひとつの実践的な答えになっています。

## 総括

今回は、sinlab-studyのAIレビュー機能をめぐって「作る」から一歩進み、**運用コストの削減とその検証方法**に向き合った回でした。出力上限の短縮や月次利用上限といった実装が形になる一方で、「何をもって削減できたと言えるのか」という問いには即答せず、AIが提案した検証方針を人間が精査してから進めるという慎重な進め方が選ばれました。

使用量モニタリングの設計もAIに叩き台を書かせつつ、集計の粒度や方式はチームで議論して決めていく——実装をAIに任せられる時代だからこそ、**判断の質**がチーム開発の中心になっていることを実感させる定例でした。初レビュアーへの挑戦やレビュー基準の言語化など、人を育てる仕組みづくりも着実に進んでいます。
