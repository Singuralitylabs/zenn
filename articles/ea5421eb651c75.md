## 概要

本記事は、[チーム開発記録38：ver6リリースと表示順バグ](https://zenn.dev/singularitylabs/articles/104e2b0e872245)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。ver6のリリースを終え、ver7に向けた開発期間に入った今回は、**テスト設計書（`docs/testing.md`）の全面的な見直し**がメインブランチにマージされたほか、コンテンツの**表示順がnullになるバグへの対応**が進みました。

会議では、Supabaseから毎週届くセキュリティ警告をきっかけに、テスト環境の**RLSポリシー適用漏れ**がその場で発覚。マイグレーション運用のダブルチェック体制が決まりました。さらに「ステージング環境は必要か」という設計思想に踏み込んだ議論や、Claude Codeをはじめとする**AIコーディングツールのチーム運用方針**の検討も行われ、テストと品質を軸にした濃い回となりました。

## 開発したもの

### テスト設計書（docs/testing.md）の全面改訂

これまでのテスト設計書は「テスト項目を優先度順に11個列挙する」という構成で、書かれた当時から実態と離れつつありました。今回の改訂では、担当メンバーが**テスト方針・テスト対象と観点・CI/ツール構成・テスト規約**という4部構成に再編し、すでに導入済みのGitHub Actionsワークフローとの対応関係も整理しました。

ポイントは、テストの実行タイミングを「プルリクエスト時」と「リリース前」の2つに絞ったことです。

```markdown
### 2.2 実行タイミング（PR / リリース前）

PR では短時間で完了するチェックを必須とし、リリース前は範囲を絞った確認を追加する。

- **PR（原則）**: 変更内容に応じて CI が自動実行される（型チェック、Lint、ビルド、ユニットテスト、デバッグ出力検知）。
- **リリース前**: 影響範囲が広い変更（例: 認証/認可、データ参照、主要画面の動線）に対して、主要フローの手動確認（または最小限のE2E）を追加する。
```

プルリクエスト時のチェックはすべてCI（Build Test / TypeScript Type Check / Jest Unit Tests / console.log検知の4ワークフロー）で自動実行されるため、**メンバーが何かを作るたびに手動でテストを行う必要はない**設計です。一方、認証まわりなど自動化が難しい確認はリリース前に手動で行います。

テストコードの置き場所と命名についての規約も、今回初めて明文化されました。

```markdown
## 5. テスト規約

### テストファイルの配置

- 原則としてテストコードは `tests/` 配下に配置する。
- ディレクトリ構成は、対象コード（例: `app/` 配下）の構造に寄せて配置する。

### ファイル名の命名

- Jest は `*.test.ts` / `*.spec.ts` をテストとして実行できるが、本プロジェクトでは `*.test.ts` に統一する。
- テストファイル名は「対象 + 期待する振る舞い」が想像できる名前にする。
```

（いずれも `docs/testing.md` より抜粋）

### 表示順ナンバリングのnullバグ修正

コンテンツ編集画面で、表示順（`display_order`）のナンバリングがnullになってしまうバグに対応しました。方針は「nullが入ってしまったら直す」ではなく、**そもそもnullを禁止する**という根本対応です。データベースの `display_order` カラムを `DEFAULT 0, NOT NULL` に変更し、TypeScriptの型定義も `number | null` から `number` に改めました。

既存データにnullや0が残っているケースに備えて、一覧取得時にはそれらを末尾に回したうえで連番を振り直すようにしています。

```typescript
// app/services/api/utils/display-order.ts（抜粋・変更後）
// display_order が 0 または null のアイテムを末尾に移動し、連番を振り直す
const sorted = (data || []).sort((a, b) => {
  const aIsUnset = !a.display_order;
  const bIsUnset = !b.display_order;
  if (aIsUnset && !bIsUnset) return 1;
  if (!aIsUnset && bIsUnset) return -1;
  return a.display_order - b.display_order;
});

return sorted.map((item, index) => ({
  ...item,
  display_order: index + 1,
}));
```

レビューは一度OKをもらったものの、データベース設計書（`docs/database.md`）へのNOT NULL追記が漏れていたことに担当メンバー自身が気づき、追加修正のうえ再確認を依頼。各テーブルの定義にも制約が反映されました。

```diff
-| `display_order` | `INTEGER`      |                     | 表示順 |
+| `display_order` | `INTEGER`      | DEFAULT 0, NOT NULL | 表示順 |
```

なお、GitHub Copilotの自動レビューからは「0で登録された場合の例外処理」について指摘がありましたが、通常の操作では発生しないケースであるため対応不要と判断しています。

## 会議の様子

### テスト設計書のポイント共有 — Copilotと100回のコメント往復

マージされたテスト設計書について、担当メンバーからは「テスト設計書を直しました。以上です」と控えめな共有がありましたが、実際にはGitHub Copilotとのコメントのやり取りが**合計100回近く**繰り返された力作です。基本的にCopilotの指摘を上から下まで踏まえて書き直したとのことでした。

リードからは内容の補足解説がありました。テストは開発において最重要と言ってもよいほど重要であるにもかかわらず、元の設計書はかなりざっくりとしか書かれていなかったため、「最低限必要な要素」を整理してもらったのが今回の更新です。テストの分類はE2E（統合）・結合・単体の3層構成とし、テスト対象としてはサービス層のCRUD・入力バリデーション・戻り値・エラーハンドリングをコンテンツ単位で確認すること、セキュリティテストは単体テスト化できる部分は自動化しつつ、**RLSの検証など自動化が難しい部分は手動で行う**ことが説明されました。E2Eテストはログインからコンテンツへのアクセス、主要画面のリンク確認までを、リリース前のみ実施する予定です。

### Supabaseのセキュリティ警告 — テスト環境のRLS適用漏れが発覚

「毎回Slackに流れてくるSupabaseのエラー通知、あれは何ですか」というメンバーからの質問をきっかけに、その場で通知の中身を確認することになりました。Supabaseが定期的に送ってくるメールをSlackに転送する仕組みになっていたのですが、よく読むと「**認証なしでアクセスできる状態のテーブルがある**」というセキュリティ警告が含まれていました。

全員で画面を見ながら調査したところ、テスト環境の `categories` テーブルにRLSポリシーが適用されていないことが判明。本番環境には適用済みだったため、**テスト環境と本番環境でアクセスルールに差異が生まれていた**ことになります。原因はデータベースへのマイグレーション適用が手作業であること。会議中にポリシーのマイグレーションファイルを実行して差異は解消されました。

この経験を踏まえ、**マイグレーションファイルの更新を含むプルリクエストでは、担当者だけでなくレビュアーもデータベース側にマイグレーションが実行されているかを確認する**というダブルチェック運用が決まりました。本番環境への反映はリードがチェックする役割分担です。

### ステージング環境は必要か — 「早く出す」を優先する判断

環境差異の話は、さらに大きな議論に発展しました。あるメンバーから「検証環境と本番環境で差が出るのは、本番リリース前に同じ手順で検証環境へのリリースを行っていないからでは。ステージング環境を作るべきではないか」という提案が出たのです。

リードの見解は「きっちりやる現場では確かにそこまでやるが、**このプロダクトにその手間をかける価値があるか**」というものでした。チーム内だけで使っており売上を立てているわけでもないプロダクトのために、デプロイ先をもう1つ用意してリリースのリハーサルを行うのはコストに見合わない。本番相当のダミーデータを維持し続ける管理コストも重く、Supabaseの無料プランではブランチ機能も使えません。

提案したメンバーの「極力バグを出さないように」という発想に対し、「バグは出るものという前提で、完璧を目指すより**とにかく早く出すことを優先する**のがこのチームの大前提」というアジャイルの方針が改めて確認され、提案メンバーも「なければ作れないわけではないので、当面はいらないという結論で納得です」と合意。データベースは開発用と本番用の2つで運用を続け、不便が出てきたら再検討することになりました。結論は「作らない」でしたが、リードからは「認識合わせとして大事な議論だった」というコメントがありました。

### AIコーディングツールの棚卸しとClaude Code運用ルール

進捗確認が早めに終わったため、メンバー各自のAIツール利用状況を棚卸ししました。Claude Codeを従量課金で試し始めプランモードで設計から進めているメンバー、ブラウザ版のClaudeやChatGPTを軽微な修正に使うメンバー、**GitHub CopilotからCodexなどのモデルを呼び出す**使い方をしているメンバーと、三者三様の状況です。Copilotの自動レビューについては「見逃しを拾ってくれるのはありがたいが、不要な指摘も混ざるので半分疑った目で見たほうがいい」という経験則も共有されました。

チームとしてClaude Codeを使っていく場合に備えて、**CLAUDE.md**（プロジェクトのルールをAIに伝えるファイル）や**Skills**（定型処理を名前で呼び出せる機能）、settings.jsonの設定をチーム内で統一する運用ルール案をリードが作成することになりました。ただし強制はせず、Claude Codeを使わないメンバーはルールをスルーして構わないという緩やかな方針です。

このほか、mainマージ時のブランチ自動削除を導入する前の古いブランチが溜まっていたため、オープン中のプルリクエストに紐づくもの以外は削除することになりました。

## 活用した技術

### テストピラミッドとテスト設計書

**テストピラミッド**は、単体テスト（Unit）を多数、結合テスト（Integration）を中程度、E2Eテストを少数という比率でテストを構成する考え方です。下層のテストほど高速で安定しており、上層ほど実環境に近い代わりに遅く壊れやすいため、この比率が保守コストと検出力のバランスを取りやすいとされています。

今回のテスト設計書はこのピラミッドを土台に、「変更頻度が高く壊れやすい領域はUnit・静的検査で早期検知し、統合・E2Eは本数を絞る」という優先度を明文化しました。さらに実行タイミングを「PR時＝CIで全自動」「リリース前＝手動確認を追加」の2つに限定したことで、開発者の負担を増やさずに品質チェックを回せる仕組みになっています。

### Jest — JavaScript/TypeScriptの定番テストフレームワーク

**Jest**は、JavaScript/TypeScriptアプリ開発で広く使われている定番のテストフレームワークです。テストランナー・アサーション・モックが一体になっており、インストールすれば `*.test.ts` という命名のファイルを自動的に検出して網羅的に実行してくれます。

近年はより新しいテストツールも台頭していますが、本プロジェクトでは情報の多さと実績を重視してまずJestを採用し、将来的な乗り換えの可能性は残す方針です。テストコードを `tests/` ディレクトリに集約し、`app/` 配下はアプリ本体のコードのみとする配置ルールも、テスト規約として合わせて定められました。

### NOT NULL制約 — 「nullを生まない」データベース設計

表示順バグの対応で採ったのは、nullが入るたびに直すのではなく、カラムに `DEFAULT 0, NOT NULL` を設定して**データベースのレベルでnullの発生を禁止する**アプローチです。nullを許容するカラムは、アプリ側のあらゆる参照箇所で「nullだったらどうするか」の分岐を強いられ、今回のようにチェック漏れがバグとして表面化します。

制約を加えたことで、Supabaseから生成されるTypeScriptの型定義も `number | null` から `number` に変わり、`maxOrder !== null && maxOrder !== undefined` のような防御的なコードを `?? 0` だけのシンプルな記述に整理できました。データベース制約・型定義・アプリコードの3層を一貫させることで、同種のバグの再発を仕組みで防いでいます。

## 総括

今回は、テスト設計書の全面改訂という「開発の土台」を固める成果がマージされ、表示順のnullバグにはデータベース制約と型定義から見直す根本対応が入りました。どちらも画面上の見た目は変わらない地味な変更ですが、今後のver7開発で予定されているテストコードの整備に直結する重要な一歩です。

会議では、セキュリティ警告の調査からRLS適用漏れの発見、マイグレーション運用の見直しへとその場で改善がつながる場面がありました。一方でステージング環境の提案は「今のチームには過剰」と判断して見送るなど、品質への投資と「早く出す」というアジャイルの原則を天秤にかける議論が印象的な回でした。AIツールの運用ルールづくりも始まり、開発プロセス自体の進化が続いています。
