### 会員情報の露出対策（member_profilesビュー）

ポータルサイトには会員一覧ページがあり、会員どうしがお互いのプロフィールを見られる仕様になっています。そのため、`users` テーブルには「承認済みの会員なら全会員の行を読める」というRLSポリシーを設定していました。

しかし、`users` テーブルには表示名や自己紹介だけでなく、他の会員に見せるべきではないメールアドレス、認証ID、権限（role）、承認状態（status）といった列も含まれています。行単位で読み取りを許可していたため、画面には表示していなくても、APIを直接呼べばこれらの列まで取得できる状態でした。セキュリティチェックで見つかった問題の一つです。

そこで、公開してよい列だけを集めた `member_profiles` ビューを作成し、会員一覧などはこのビュー経由で取得するように変更しました。

```sql
CREATE OR REPLACE VIEW member_profiles
WITH (security_invoker = false)
AS
SELECT
  id,
  display_name,
  bio,
  avatar_url,
  profile_image_path,
  x_url,
  facebook_url,
  instagram_url,
  github_url,
  portfolio_url
FROM users
WHERE status = 'active'
  AND is_deleted = FALSE
  AND (SELECT is_active_user());

REVOKE ALL ON member_profiles FROM PUBLIC;
REVOKE ALL ON member_profiles FROM anon;
REVOKE ALL ON member_profiles FROM authenticated;
GRANT SELECT ON member_profiles TO authenticated;
```

あわせて、`users` テーブル本体の読み取りは「本人の行」と「管理者」だけに絞りました。

```sql
DROP POLICY IF EXISTS "active_users_can_read_all" ON "users";
DROP POLICY IF EXISTS "admins_can_read_all_users" ON "users";
CREATE POLICY "admins_can_read_all_users" ON "users"
  FOR SELECT
  TO authenticated
  USING (
    (SELECT is_active_user())
    AND (SELECT is_admin())
    AND is_deleted = FALSE
  );
```

アプリ側では、会員一覧を取得するクエリの参照先を `users` から `member_profiles` に切り替えています。承認済み・未削除の会員に絞り込む条件はビューの定義に含まれているため、アプリ側のフィルタは不要になりました。

```typescript
const { data, error } = await supabase
  .from("member_profiles")
  .select(
    "id, display_name, bio, avatar_url, profile_image_path, x_url, facebook_url, instagram_url, github_url, portfolio_url, position_tags(positions(id, name, is_deleted))"
  )
  .eq("position_tags.positions.is_deleted", false);
```

### マスター管理画面の参照機能

データベースの「マスター」と呼ばれる登録データを画面から参照・編集できるようにする機能のうち、まずは参照部分を実装しました。サイドメニューに「マスター管理」が追加され、資料・動画・カテゴリー・アプリ・役職の5つのテーブルを選んでレコードを一覧・詳細表示できます。一般会員には表示されず、コンテンツ管理権限（maintainer以上）を持つメンバーだけが利用できます。

```typescript
const MASTER_NAV_ITEM: NavItem = {
  title: "マスター管理",
  href: "/master",
  icon: <Database className="h-5 w-5" />,
};

// ...
...(isContentMgr ? [CATEGORY_ADMIN_NAV_ITEM, MASTER_NAV_ITEM, TRASH_NAV_ITEM] : []),
```

各テーブルの表示内容は `app/constants/master.ts` に定義しています。特徴は、Supabaseから自動生成した `database.types.ts` の型を使い、**テーブルの全カラムに対して表示ラベルを必須にしている**点です。

```typescript
// 対象テーブルの Row に存在するカラム名だけを許容する型。
export type MasterTableColumn<T extends MasterTableName> = Extract<
  keyof Database["public"]["Tables"][T]["Row"],
  string
>;

// 各テーブルの全カラムに対して表示ラベルを必須化し、追従漏れを型で検知する。
export type MasterLabels<T extends MasterTableName> = Record<MasterTableColumn<T>, string>;
```

```typescript
const DOCUMENTS_MASTER_TABLE = defineMasterTable({
  tableName: "documents",
  label: "資料",
  labels: {
    id: "ID",
    name: "資料名",
    description: "説明",
    category_id: "カテゴリー",
    url: "URL",
    display_order: "表示順",
    created_by: "作成者",
    updated_by: "更新者",
    assignee: "担当者名",
    assignee_id: "担当者",
    is_deleted: "削除状態",
    created_at: "作成日時",
    updated_at: "更新日時",
  },
  listColumnKeys: ["id", "name", "category_id", "is_deleted", "updated_at"],
  references: [
    { columnKey: "assignee_id", type: "user" },
    { columnKey: "category_id", type: "category" },
    { columnKey: "created_by", type: "user" },
    { columnKey: "updated_by", type: "user" },
  ],
});
```

この仕組みにより、今後テーブルにカラムを追加すると、`master.ts` にラベルを追加しない限り型チェックでエラーになります。担当者からは「データベースのカラムを変更したときは `master.ts` のメンテナンスが必要になる」という点を全員に認識してほしい、と共有がありました。

### 役職タグの変更権限の見直し

前回までに進めていた役職（代表・副代表など）セクションの追加対応です。これまでは各メンバーが自分の役職タグを登録・更新できましたが、役職は運営側が管理するものなので、変更できるのをadminとmaintainerだけに制限しました。一般メンバーには表示はされますが、変更はできません。

```sql
-- 役職タグの変更をadmin・maintainerのみに制限する
-- memberは役職タグの登録・更新ができなくする
DROP POLICY IF EXISTS "users_can_insert_own_data" ON "position_tags";
DROP POLICY IF EXISTS "users_can_update_own_data" ON "position_tags";

-- DELETE: admin・maintainerのみが削除可能（memberは削除不可）
DROP POLICY IF EXISTS "self_user_or_admins_can_physical_delete" ON "position_tags";
CREATE POLICY "admins_can_delete_position_tags" ON "position_tags"
  FOR DELETE
  TO authenticated
  USING (
    is_active_user() AND is_content_manager()
  );
```

なお、`is_content_manager()` はadminとmaintainerの両方を許可するのに、ポリシー名が `admins_can_...` となっていて実態と合っていない、という指摘が会議中にありました。動作には影響しないため、別のIssueとして切り出して修正することになりました。

### Supabase Keep Aliveワークフローの設計

Supabaseの無料プランでは、一定期間データベースへのアクセスが少ないとプロジェクトが自動的に一時停止（Pause）され、手動で復旧するまでポータルサイトが使えなくなります。これを防ぐため、GitHub Actionsから定期的にデータベースへ軽いクエリを送るワークフローを設計し、CI/CD設計書に追記しました。今回は設計のみで、実装は別のPRで行います。

設計書では、方式の比較も整理しています。

| 方式 | 採否 | 理由 |
|---|---|---|
| GitHub Actions の `schedule` | 採用 | アプリ改修が不要。既存CIの規約とSecrets管理にそのまま乗る |
| Vercel Cron + 公開APIルート | 不採用 | アプリ改修が必要。開発用プロジェクトを対象にできない |
| Supabase `pg_cron` による自己アクセス | 不採用 | ユーザー由来のアクティビティとして計上される保証がない |
| 外部監視SaaS | 不採用 | APIキーを第三者に預けることになる |

リクエストには、データベースを経由するPostgRESTのエンドポイントを使います。

```bash
curl --fail --silent --show-error --retry 3 --retry-delay 10 \
  -H "apikey: $SUPABASE_PUBLISHABLE_KEY" \
  "$SUPABASE_URL/rest/v1/categories?select=id&limit=1" > /dev/null
```

### 依存パッケージの脆弱性解消

外部パッケージの一部で、依存関係の更新が追いついておらず既知の脆弱性が残っていたため、本番環境で使うパッケージ（next、sharp、qs、dompurifyなど）をアップデートしました。大きな変更ではなく、`package.json` の `overrides` で間接的な依存パッケージのバージョンを上書きしている程度です。開発環境でのみ使うパッケージの対応は残っており、別途対応する予定です。

```json
"overrides": {
  "@tailwindcss/typography": {
    "postcss-selector-parser": "^6.1.5"
  },
  "next": {
    "postcss": "^8.5.23"
  }
}
```

### データ補正SQLとトランザクション

削除済みカテゴリーに属するコンテンツをゴミ箱から復活させると、どの画面からも到達できない状態になるという不具合の修正PRでは、すでに発生している不整合データを補正するSQLの手順が添えられていました。対象件数を `SELECT` で確認し、問題がなければカテゴリーを「未分類」に付け替える、という手順です。

この手順は `BEGIN` / `COMMIT` / `ROLLBACK` によるトランザクションで囲む形でAIが作成していましたが、SupabaseのSQLエディタでは各文が即時実行されるため、期待どおりにロールバックできないのではないか、という懸念が出ました。検証環境では補正の動作自体は確認済みだったため、SQLエディタでの挙動を確認したうえで、マージのタイミングで補正を実行することになりました。補正はマージの前後どちらでも問題ない（復活操作をしない限り壊れたデータは発生しない）ことも確認しています。

### Zインデックスの不具合から考えるレビュー

3点メニューの修正を紹介した際、あるメンバーから「数値の意味を覚えておかないと、また同じ事故が起こるのではないか」という問いかけがありました。

議論の中で出た意見は次のとおりです。

* Zインデックスは0の次を10にするなど、慣習的に決めることが多い。厳密にやるなら設計書で管理するが、実際の現場ではあまり見かけない
* コードを見れば値はすぐに分かるので、重なりが問題になったときに関係者で話し合って決めることが多い
* このチーム開発は「すべてを完璧につぶしてからリリースする」運用ではないため、何もかも管理しようとしなくてよい

最終的には、Zインデックスを個別に管理するルールは設けず、「Zインデックスを意識しながら開発する」という知見の共有にとどめることになりました。

当時のレビューでなぜ見落とされたのかという疑問も出ましたが、司会者からは「完璧にチェックするスタンスでレビューしていなかった」という説明がありました。GitHubには誰が実装し誰がレビューしたかの記録が残りますが、大事なのは原因の追及よりも直すことと、そこから学ぶことだ、という話で締めくくられました。

### レビューの観点とAIレビューの信頼性

会議の後半では、レビューの進め方について議論が広がりました。

あるメンバーは、レビュー依頼の際に「この画面を確認してほしい」「この動作確認をした」といった確認観点を書く文化にすれば、短時間でも画面確認ができ、見落としを防げるのではないかと提案しました。別のメンバーからは、PRテンプレートに共通の確認項目を入れ、PRごとに追加する案が出ました。GitHubのPRテンプレートは複数作成できることも調べて共有されています。

一方、司会者は、PRの作成をAIに任せている立場から、次のように述べました。

> 今のモデルには、こちらから余計な制約や指示を出さない方がよいと言われている。目的を伝えて、考えることはAIに任せた方がよい成果が出る。レビュアーに確認観点を書いてもらうことのルール化はありだが、こちらでレビュー項目を作り込むのは、今のAI時代には悪手ではないか。

さらに、「AIがOKと言ったコードを、本当にOKとしてよいのか。他の人に説明できない」という悩みも共有されました。これについては次のような意見が出ています。

* 人間が責任を持ってしっかり確認すべき派と、AIの方が優秀なので人間の確認に時間を割くべきではない派で、エンジニアの間でも意見が分かれている
* コードレビューはAIに任せ、人間はローカルで起動して動作確認をする。気になる点があったときにコードを見てAIと議論する
* 変更範囲に合わせたテストをAIにその場で生成させて担保する。AIのレビュー結果がコードのどこに対応するかをAIに説明させる
* E2Eテストを自動化するサービスも出てきており、導入を検討する余地がある

結論として、コードをすべて人が読むことは現実的ではないため、レビューの方法は各レビュアーに任せつつ、**どういう修正を行ったかを把握し、動作確認を行ったうえで責任を持ってレビューする**ことを改めて確認しました。PRテンプレートを複数作るかどうかは、検討用のIssueとして残しています。

## 活用した技術

### PostgreSQLのビューによる列レベルのアクセス制御

SupabaseのRLS（Row Level Security）は、その名のとおり**行単位**でアクセスを制御する仕組みです。ある行を読めるユーザーは、その行のすべての列を読めてしまいます。「他の会員の名前は見せたいが、メールアドレスは見せたくない」といった**列単位**の制御は、RLSだけでは表現できません。

そこで使うのがビューです。ビューは、テーブルに対する `SELECT` 文に名前をつけて、仮想的なテーブルとして扱えるようにしたものです。ユーザーとテーブルの間に窓口を作り、必要な列だけを見せられます。

| 項目 | テーブルに直接アクセス | ビュー経由 |
|---|---|---|
| 公開される列 | すべての列 | ビューで選んだ列のみ |
| 絞り込み条件 | 呼び出し側で指定 | ビューの定義に組み込める |
| 権限の付与 | テーブル単位 | ビュー単位で `GRANT` / `REVOKE` |

今回のビューでは `security_invoker = false` を指定しています。これは「ビューを呼び出したユーザーではなく、ビューの所有者の権限でクエリを実行する」という意味です。一般会員は `users` テーブルの自分の行しか読めないため、呼び出したユーザーの権限で実行すると会員一覧が本人1行しか返りません。所有者権限で実行してRLSを迂回する代わりに、次の対策を組み合わせています。

* `WHERE` 句と `is_active_user()` で、承認済み会員だけが承認済み会員の情報を見られるように限定する
* `anon`（未ログイン）からのアクセスを `REVOKE` で禁止する
* 1つのテーブルから作ったビューは更新可能なため、`authenticated` にも `SELECT` 以外の権限を残さず、ビュー経由で他の会員の行を書き換えられないようにする

Supabaseのセキュリティチェック（lint）はこの構成を `security_definer_view` として警告しますが、上記のガードにより実質的な迂回は発生しないことを設計書に記録しています。

### TypeScriptの型によるカラム追従漏れの検知

マスター管理画面では、`keyof` と `Record` を組み合わせて「テーブルの全カラムにラベルが定義されていること」を型で保証しました。

```typescript
export type MasterLabels<T extends MasterTableName> = Record<MasterTableColumn<T>, string>;
```

`Record<K, V>` はキー `K` をすべて必須とするオブジェクト型です。キーにテーブルのカラム名のユニオン型を渡すことで、ラベルが1つでも欠けているとコンパイルエラーになります。データベースのスキーマ変更に画面の定義が追従していないことを、実行前に検知できる仕組みです。

### Zインデックスと重なり順

Webページは要素を層のように重ねて構成されています。Zインデックスは、そのうち何番目の層に表示するかを指定するCSSのプロパティで、X・Y・Z軸のZ方向（画面の手前・奥）の位置を表します。値が大きいほど手前に表示されます。

今回の不具合は、カード内のメニューに `zIndex: 10` が指定されていたため、`position` が固定されたヘッダーよりも手前に表示されてしまったことが原因でした。値を小さくしてヘッダーの背面に回すことで解消しています。

### GitHub Actionsの定期実行（schedule）

GitHub Actionsでは、`schedule` トリガーにcron形式で実行時刻を指定すると、ワークフローを定期実行できます。Keep Aliveワークフローの設計では、次の点も考慮しています。

* `schedule` は遅延や実行漏れが起こりうるため、1日2回の実行にして数回欠けても影響が出にくくする
* `schedule` はデフォルトブランチ上の定義だけが実行される
* 公開リポジトリでは60日間活動がないと `schedule` が自動で無効化される

### Turborepo

Turborepoは、Vercelが提供するモノレポ向けのビルドシステムです。複数のアプリや共通パッケージを1つのリポジトリで管理する際に、ビルド・テスト・リントなどのタスクをキャッシュや並列実行によって高速化します。

## 総括

今回は、セキュリティチェックで見つかった会員情報の露出問題を、PostgreSQLのビューで解決した回でした。RLSは行単位の制御であり、列単位で隠したい情報がある場合はビューを窓口として切り出す、という設計は、Supabaseを使う多くのプロジェクトで参考になるはずです。

また、Zインデックスの小さな不具合をきっかけに、レビューで何を確認すべきか、AIのレビュー結果をどう信頼するかという、AI時代の開発ならではの議論ができました。正解が一つに決まる話ではありませんが、「何を修正したかを把握し、動作確認をしたうえで責任を持ってレビューする」という基本を全員で確認できたのは大きな収穫です。
