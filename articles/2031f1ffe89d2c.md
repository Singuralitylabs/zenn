## 開発したもの

### プロフィール画面の役割タグ編集UI

ユーザーのプロフィールに役割タグを紐づけられるようにする機能が完成しました。プロフィール編集フォームに、UIライブラリMantineの**MultiSelect（複数選択コンポーネント）**を追加し、「活動チーム、役割など」を複数まとめて選べるようにしています。登録ボタンを押すと、チェックした役割が一括で保存されます。

### 役割タグの更新API — 「削除してから挿入」方式

サーバー側には、役割の取得・登録処理を追加しました。更新処理は、そのユーザーの既存タグを**いったんすべて削除してから、選択されたタグを挿入し直す**という実装になっています。

```typescript
// app/services/api/users-server.ts（抜粋）
/**
 * ユーザーの position_tags を更新する（既存削除 → 新規挿入）
 */
export async function updateUserPositionTagsInServer(
  userId: number,
  positionIds: number[]
): Promise<PostgrestError | null> {
  const supabase = await createServerSupabaseClient();

  const { error: deleteError } = await supabase
    .from("position_tags")
    .delete()
    .eq("user_id", userId);

  if (deleteError) {
    console.error("Supabase position_tags削除エラー:", deleteError.message);
    return deleteError;
  }

  const uniquePositionIds = [...new Set(positionIds)];

  if (uniquePositionIds.length === 0) {
    return null;
  }

  const { error: insertError } = await supabase.from("position_tags").insert(
    uniquePositionIds.map(positionId => ({
      user_id: userId,
      position_id: positionId,
    }))
  );

  if (insertError) {
    console.error("Supabase position_tags挿入エラー:", insertError.message);
    return insertError;
  }

  return null;
}
```

機能としては基本的に問題ないためマージされましたが、この「削除→挿入」という作りが、後述するUpsert談義のきっかけになりました。指摘事項はマージとは切り分けて、別のIssueとして残しています。

## 会議の様子

### 「Upsertって一般的なんですか？」— 削除→挿入への指摘から

マージ済みの役割タグ編集機能について、リードから「気になる点は別Issueとして残した」という共有がありました。その1つが上記の更新処理で、**削除だけ成功して挿入が失敗した場合、ユーザーのタグが消えただけで終わってしまう**というリスクです。「こういう処理はUpsertを使えばもっとシンプルに書けるはず」という提案でした。

ここで、あるメンバーから「**アップサートという表現は、もう一般的なんですか？**」という率直な質問が出ました。リードの説明は次のとおりです。

* SQL界隈では割と当たり前の単語になっている
* **UPDATE（更新）とINSERT（挿入）を合体させた処理**で、更新対象があれば更新し、なければ新規追加する
* 少なくとも5〜10年ほど前から使われている
* PostgreSQLにもMySQLにもあり、Salesforceには `upsert` というクラスも存在する

長くDBを扱ってきた別のメンバーからも「INSERTとUPDATEを分けて考えるイメージだった」という声があり、経験者でも意外と言葉として意識していなかったことが分かりました。「ちょいちょい使う場面があるので、ぜひ覚えておくといい」という共有で締めくくられています。

### データ整合性をどこで守るか — DB関数という選択肢

Upsertの話は、さらに一歩踏み込んだ設計論に発展しました。あるメンバーから「タグ管理に限らず、**1つのトランザクションの中で複数のDELETEやINSERTをまとめて行う場面はよくある。そういう処理はDB側の関数で実装して、1回のトランザクションで完了する仕組みにした方がよいのでは**」という提案があったのです。背景には、WebサーバーであるVercelとデータベースサーバーであるSupabaseの間の**通信不具合によってデータ不整合が起きることへの懸念**がありました。

これに対してリードは、トレードオフを整理しました。**Supabase側の関数で管理すれば安全性は高くなるが、コードがGitHub管理から外れるため、管理の難易度は上がる**。どちらを優先するかは要件次第、という見立てです。

議論の中では、システム構成の共有も行われました。金融系のような大規模システムでは、Webサーバーとデータベースサーバーの間に整合性を担保するバックエンド専用サーバーが置かれます。一方、このポータルサイトは**WebサーバーとDBサーバーの2つだけ**の構成で、Next.jsがWebサーバー内でフロントエンド（クライアント）とバックエンド（サーバー）を分けており、データ整合性の処理はWebサーバー内のバックエンド側で行う設計です。「現状のシステムには金融系のようなクリティカルな要件はない」という認識も共有され、DB関数化は今後の要件検討事項となりました。

### AIレビューは「別のチャット」にやらせる

役割タグ機能の担当メンバーからは「AIと一緒に実装したが、AIはUpsertを提案してくれなかった」という振り返りがありました。これを受けてリードから、AIレビューの実践的なコツが共有されました。

* **開発に使ったチャットとは別のチャットを立ち上げて、そちらにレビューさせる**。過去の履歴がない状態でレビューさせることで、客観的な指摘が出やすくなる
* Cursorを使っているなら、New Agentやデバッグモードといった標準のレビュー機能も評判がよい
* 複数のAIを立ち上げて「戦わせる」ように多角的にレビューさせるのがおすすめ

開発を伴走したAIは、自分が書いたコードに甘くなりがちです。人間のレビューと同じように「第三者の目」を意図的に作るという発想は、AI活用のノウハウとしてチームに定着しつつあります。

## 活用した技術

### Upsert — 「あれば更新、なければ挿入」

Upsert（アップサート）は、**UPDATE（更新）とINSERT（挿入）を組み合わせた造語**で、「対象データが存在すれば更新し、存在しなければ新規挿入する」処理を1回で行う仕組みです。PostgreSQLでは `INSERT ... ON CONFLICT DO UPDATE`、MySQLでは `INSERT ... ON DUPLICATE KEY UPDATE` という構文で実現でき、SupabaseのクライアントライブラリにもUpsert用のメソッドが用意されています。

今回の「削除してから挿入」方式は、実装としては素直で分かりやすい一方、削除と挿入が別々のリクエストになるため、**途中で失敗するとデータが消えたままになる**という弱点があります。Upsertを使えば処理を1つにまとめられ、こうした中途半端な状態が生まれる余地を減らせます。定番でありながら知らないと出てこないイディオムであり、レビューを通じてチームの共通語彙になった好例です。

### トランザクションとDB関数によるデータ整合性

トランザクションは、**複数のDB操作を「すべて成功」か「すべて失敗」のどちらかにまとめる仕組み**です。今回のような「削除→挿入」を1つのトランザクションで包めば、挿入に失敗したとき削除も自動的に取り消され（ロールバック）、データが消えただけの状態を防げます。

アプリ側から複数のリクエストを順に投げる構成では、リクエストの合間に通信断が起きるとトランザクションの恩恵を受けられません。そこで議論に出たのが、**PostgreSQLの関数（Supabaseではデータベース関数として作成し、RPCとして呼び出せる）に処理をまとめて、DB側で1トランザクションとして実行する**方法です。安全性は高まりますが、ロジックがアプリのリポジトリの外に出るためGitHubでのバージョン管理やレビューが効きにくくなるという運用上のコストもあり、「クリティカルな要件があるか」で採否を決めるのが現実的な判断軸になります。

### MantineのMultiSelectコンポーネント

Mantineは、このポータルサイトで採用しているReact用UIコンポーネントライブラリです。今回使ったMultiSelectは、**ドロップダウンから複数の項目をタグ形式で選択できる**コンポーネントで、選択済み項目の表示・解除やクリアボタン（`clearable`）まで標準で備えています。

1点注意が必要なのは、MultiSelectの値が**文字列の配列**として扱われることです。今回の実装でも、数値のID（`position_id`）を `String()` で文字列化してコンポーネントに渡し、選択結果を `Number()` で数値に戻すという変換を挟んでいます。UIライブラリの型の都合とDBの型の都合をどこで吸収するかは、フォーム実装でよく登場する小さな設計ポイントです。
