シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回の定例では、テストツール**Jestによる単体テスト環境の導入**が完了し、プルリクエストやプッシュのタイミングでGitHub Actionsがテストを自動実行する体制が整いました。あわせて、AIコーディングツール**Claude Codeのチーム運用ルール**（`CLAUDE.md` と共通設定ファイル）の整備も完了しています。

## 開発したもの

### Jestによる単体テスト環境の構築

テスト担当メンバーが進めていた、Jestによる単体テスト環境の導入がメインブランチにマージされました。権限判定・認証・表示順ロジック・Slack通知・Googleカレンダー連携・SupabaseのCRUD処理といった、**主にサーバーサイドの関数を対象とした数十個のテスト**を、ルート直下の `tests/` ディレクトリに集約しています。

テストコードの大半はAIに書いてもらったものですが、最初に出てきた約4000行をそのまま採用したわけではありません。レビューの中で「**内部実装の呼び出し手順ではなく、入出力と副作用の結果を検証する**」という方針に沿って重複ケースや実装依存のテストを削り、最終的に**約1900行**まで整理しました。この検証方針はテスト設計書（`docs/testing.md`）にも明文化しています。

実際のテストコードは、たとえば権限判定であれば次のように、ロールごとの入力に対して期待どおりの判定が返ることを確認するシンプルな形です。

```typescript
// tests/services/auth/permissions.test.ts（抜粋）
describe("checkAdminPermissions", () => {
  it.each([
    [USER_ROLE.ADMIN, true],
    [USER_ROLE.MAINTAINER, false],
    [USER_ROLE.MEMBER, false],
    ["unknown", false],
  ])("role=%s は %s", (role, expected) => {
    // 管理者権限の判定結果が期待どおりであることを確認
    expect(checkAdminPermissions(role)).toBe(expected);
  });
});
```

テストの実行コマンドは `package.json` の `scripts` に定義されており、ローカルでは `npm run test` で誰でも同じテストを実行できます。

```json
"scripts": {
  "lint": "next lint",
  "type-check": "tsc --noEmit",
  "lint:logs": "node scripts/lint-logs.cjs",
  "test": "jest --verbose --coverage"
}
```

（`package.json` 抜粋・変更後。デバッグ用の `console.log` 検査もCIのインライン実装からスクリプト `lint:logs` に一元化しました）

また、GitHub Actionsのテストワークフローは、これまでアプリ本体（`app/**`）の変更時のみ起動していましたが、テストコードや設定ファイルの変更でも起動するようトリガーを拡張しています。

```yaml
# .github/workflows/test.yml（抜粋・変更後）
on:
  push:
    paths:
      - "app/**"
      - "tests/**"
      - "jest.config.js"
      - "package.json"
      - "package-lock.json"
```

### Claude Codeのチーム開発設定

前回から進めていた「Claude Codeの運用ルールを作る」イシューが完了しました。追加したファイルは大きく2つ、プロジェクト指示書の **`CLAUDE.md`** とチーム共通設定の **`.claude/settings.json`** です。

`settings.json` では、AIによる破壊的な操作を防ぐため、次の3つのコマンドを禁止（deny）に設定しました。

```json
"deny": [
  "Bash(rm -rf:*)",
  "Bash(git push --force:*)",
  "Bash(git reset --hard:*)"
]
```

（`.claude/settings.json` 抜粋・変更後）

強制削除・強制プッシュ・コミットの取り消しという「強制的に何かを消す・上書きする」操作をチーム設定として一律で禁止する形です。ローカルでどうしても必要な場合は、優先して読み込まれる `settings.local.json` を各自が作成して許可に移せる、という逃げ道も用意しています。

`CLAUDE.md` には、ディレクトリ構造・コンポーネント設計パターン・実装後に実行するチェック（lint → 型チェック → ビルド）・禁止事項などを記載しました。ただし詳細なコーディング規約はあえて書かず、**Wikiへのリンクを貼るにとどめています**。`CLAUDE.md` とWikiの両方を更新する二重管理を避けるためです。あわせて、リポジトリ内にあったClaude Code初心者向けガイドはWikiの「Claude Code ガイド」ページに移設し、ドキュメントの置き場所を整理しました。

## 会議の様子

### E2Eテストの自動化はどこまでやるか

テスト用GitHub Actionsのイシューの進捗確認では、残タスクの整理から議論が広がりました。DBのデータ型をチェックするワークフローは、GitHub Actions用の**Supabaseのキー設定が未対応のためコメントアウトされたまま**マージされていたことが共有され、キー設定と有効化を別プルリクで対応してからイシューを閉じる方針になりました。ただし必要なキーが強力な権限を持つシークレットキーだとリスクが大きいため、「本当にそのキーが必要なのか中身を確認し直す」と担当メンバーが持ち帰っています。

より大きな論点になったのは**E2Eテストの自動化**です。テスト設計の段階では「E2Eは当面手動でよい」と決めていましたが、担当メンバーから「GitHub Actions上でもブラウザは動かせる。**Chromeのヘッドレスモード**を使えば画面を表示せずにブラウザの動作を実行でき、実務でも普通に使われている方式」という補足がありました。これに対して別のメンバーからは「テストはあくまで品質の担保。ブラウザで動くことの確認が自動でできるなら、裏で勝手にやってくれていてもいいのでは」と自動化に前向きな意見も出ました。

一方でリードメンバーは「テストを増やすと管理コストや処理時間の増加といった弊害もある。実際の環境を作ってみないと判断できないことも多い」として、**E2Eの自動化はGitHub Actions構築のイシューとは切り離し、別イシューとして検討する**ことで合意しました。やる・やらないを今決めるのではなく、論点を分割して前に進める判断です。

### イシューの「アクション」チェックはいつ入れる？

イシューテンプレートの運用について、「アクション欄のチェックボックスはどのタイミングでチェックすべきか」という素朴な疑問からすり合わせが行われました。あるメンバーは「このイシューで更新したものが後から分かるように印を付けるもの」と解釈していましたが、リードメンバーの意図は**進捗管理**であり、「担当者自身が『この作業は終わった』と判断したらチェックし、他の人からも進捗が見えるようにするためのもの」という認識で統一されました。

あわせて、テンプレートの各項目の役割も整理されました。「背景」は**なぜやるのか（Why）**、「更新箇所」は**何をするのか（What）**、「アクション」は**それを実現する具体的な作業（How）**という位置づけです。テンプレートには本来これらの説明コメントが埋め込まれているものの、編集モードを開かないと見えないため意図が伝わっていなかった、という原因も判明しました。説明を常時表示する案も出ましたが、テンプレート修正にはプルリクとマージが必要なため、いったん現状の運用を続け、不便が続くようなら改めて見直すことになりました。

### SupabaseとFirebase — データベースの基礎知識を共有

Supabaseのアクセストークンの話題から、新メンバー向けにSupabaseそのものの解説が行われる一幕もありました。管理画面で主に使うのは**テーブルエディター**（テーブルの閲覧・編集）、**SQLエディター**（クエリの実行）、**オーセンティケーション**（認証管理）の3つ、という実践的な整理です。

新メンバーからの「Supabaseはリレーショナルデータベースか」という質問には、その通りであると回答があり、比較対象としてよく挙がる**FirebaseはNoSQL**という違いも共有されました。開発の中でデータベースを触る機会がなければ馴染みが薄いのは当然で、「必要になったときに学べばよいし、分からないことがあれば聞いてほしい」というスタンスが確認されています。なお、GitHub Actions用のパーソナルアクセストークンを誰が発行できるのかという権限まわりの確認は、時間の都合で会議と並行して進めることになりました。

このほか、カテゴリー管理機能・役割の編集・カレンダーイベント表示・URLバリデーションなどの各イシューはそれぞれレビュー・実装が進行中であることが確認され、新たにマークダウンの**Mermaid記法対応**とGitHub Copilot向けのレビュー観点ルール作成のイシューが起票・アサインされました。

## 活用した技術

### Jestとカバレッジ

**Jest**は、JavaScript/TypeScript界隈で古くから広く使われているテストライブラリーです。`*.test.ts` という命名のファイルを自動的にテストとして認識して実行し、結果を `PASS` / `FAIL` で報告してくれます。モック（外部サービスの代わりに用意する偽物の部品）の仕組みも標準で備えており、今回のようにSlackやSupabaseなど外部依存の多いサーバーサイド関数のテストに向いています。

実行時に `--coverage` オプションを付けると、**カバレッジ**（アプリのコードがどれだけテストでカバーされているかの割合）も一覧表示されます。カバレッジは100%を目指すのが理想とされる一方、細かいテストが増えるほどメンテナンスコストも増大します。今回のチームでも「ここは100%でなくてよい」という判断を議論しながら削っており、**カバレッジは目的ではなく指標**として付き合うという現実的な運用に落ち着いています。

### ヘッドレスブラウザによるE2Eテスト

E2E（End-to-End）テストは、ユーザーの操作を模してアプリを画面から動かす統合的なテストです。GitHub Actionsのようなサーバー環境には表示する画面がありませんが、**ヘッドレスモード**を使えば画面描画なしでブラウザ内部の動作だけを実行できるため、CI上でのE2Eテスト自動化が可能になります。

会議で名前の挙がった**Playwright**は、ブラウザに命令を出して制御するための仕組みで、E2Eテストの自動化はもちろん、AIエージェントとブラウザの中間層としても使われます。「ローカルでは動かしたことがあるが、サーバー上のヘッドレス実行は知らなかった」というメンバーの声もあり、知見の共有がそのまま次の技術検討（E2E自動化の別イシュー）につながりました。

### npmとnode_modules

テストのローカル実行の説明から、npmの基礎知識の共有にも話が及びました。**npm（Node Package Manager）** はJavaScriptのパッケージ管理ツールで、`package.json` の `scripts` に定義された処理を `npm run test` のように実行できます。`npm install` は「npm自体の更新」ではなく、**プロジェクトが依存するパッケージ群を `node_modules` ディレクトリにインストール・更新するコマンド**です。

このため、環境がうまく動かないときは `node_modules` を丸ごと削除して `npm install` し直すと直ることがよくある、という実践的なトラブルシューティングも共有されました。また、npmは信頼性が高い一方で歴史の長いツールであり、最近は**pnpm**や**bun**といった新しいパッケージマネージャーも広く使われている、という周辺動向にも触れられました。

## 総括

今回は、Jestによる単体テスト環境とClaude Codeのチーム運用ルールという、機能そのものではなく**開発を支える基盤**が2つ完成した回でした。特にテスト導入では、AIが生成した約4000行をそのまま受け入れるのではなく、「何を検証すべきで、何を検証すべきでないか」を議論しながら約1900行まで磨き込んだプロセスに、AI時代のコードレビューのあり方が表れています。

会議でも、E2E自動化を別イシューに切り出す判断や、イシューテンプレートの運用のすり合わせなど、プロセス面の改善が着実に進みました。次回以降は、テスト基準の明文化やMermaid記法対応、GitHub Copilot向けルールの整備が控えており、テストとAI活用の両輪がさらに強化されていく予定です。
