## 開発したもの

今回は、立ち上げ期間中にsinlab-studyリポジトリへマージされたPRを紹介します。

### GAS応用編コンテンツの追加

学習コンテンツとして、新しく**「GAS応用編」**が追加されました。GAS（Google Apps Script）を使って実際にWebアプリを作ってみるという内容で、動画とスライドに加えて**課題機能**がついています。受講者が自分でコードを書いて提出すると、**AIが自動でレビューしてフィードバックを返す**仕様になっており、完了チェックを入れると学習記録も残ります。

あわせて、mainブランチへの直接コミットを禁止するブランチ運用ルールの明文化や、ドキュメントを実装・実DBに整合させてMermaid図で刷新する対応もマージされ、チームで開発を進めるための土台が整いつつあります。

### 演習課題の複数ファイル提出対応

GAS応用編の課題には、`コード.gs`（GAS側）と `index.html`（HTML側）の**2ファイルの提出が必要な課題**が含まれています。ところが従来の提出フォームはコード入力欄が1つだけで、データも `code_content` という単一の文字列カラムに保存する仕組みでした。

そこで、後方互換性を最優先しながら複数ファイル提出に対応するため、`submissions` テーブルにJSONB型の `code_files` カラムを追加しました。

```sql
-- supabase/migrations/01_schema/002_add_submission_code_files.sql（抜粋）
ALTER TABLE submissions
  ADD COLUMN IF NOT EXISTS code_files JSONB;

COMMENT ON COLUMN submissions.code_files IS
  '複数ファイル提出 [{filename, language, content}]。NULL の場合は code_content（単一ファイル）にフォールバック';
```

単一ファイル提出は従来どおり `code_content` に、複数ファイル提出は `code_files` に保存する方式のため、**既存の提出データはそのまま有効**です。表示やAIレビューの際は、どちらの形式でも扱えるように正規化する純粋関数を用意しました。

```typescript
// app/lib/submission-files.ts（抜粋）
export function getSubmissionCodeFiles(submission: {
  code_content: string | null;
  code_files: Json | null;
}): CodeFile[] {
  const raw = submission.code_files;

  if (Array.isArray(raw)) {
    const files = raw
      .filter((f): f is { [key: string]: Json | undefined } => typeof f === "object" && f !== null)
      .map((f) => ({
        filename: typeof f.filename === "string" ? f.filename : "",
        language: typeof f.language === "string" ? f.language : "",
        content: typeof f.content === "string" ? f.content : "",
      }))
      .filter((f) => f.content.length > 0);

    if (files.length > 0) {
      return files;
    }
  }

  if (submission.code_content) {
    return [{ filename: "", language: "", content: submission.code_content }];
  }

  return [];
}
```

さらに後続のPRでは、複数ファイル化するとファイル名が必須になり「提出する」ボタンが押せなくなる不具合の修正、言語に応じたデフォルトファイル名（`code.gs` / `index.html` など）の自動補完、言語選択肢「JavaScript / GAS」を拡張子の異なる「JavaScript」（.js）と「GAS」（.gs）に分離する改善も行われました。

### スライドアップロードのフォルダ指定・連番ファイル名対応

管理画面からPDFスライドをアップロードすると、保存先が `<タイムスタンプ>_<ファイル名>` に固定されており、命名規約 `slides/<コース>/slide-NN.pdf` に沿わせるには**アップロード後の手動リネームが必要**という課題がありました。GAS応用編のスライド5件では、実際にStorageのAPIで手動対応が発生していました。

恒久対応として、アップロードAPIに保存先フォルダの指定と連番ファイル名の自動採番機能を追加しました。

```typescript
// app/api/upload-pdf/route.ts（抜粋）
// 命名規約に沿ったスライドファイル名（slide-NN.pdf）
const SLIDE_FILE_PATTERN = /^slide-(\d+)\.pdf$/;

async function getNextSlideNumber(
  supabase: Awaited<ReturnType<typeof createAdminSupabaseClient>>,
  folder: string
): Promise<number> {
  const { data, error } = await supabase.storage.from(BUCKET_NAME).list(folder, { limit: 1000 });

  if (error || !data) {
    throw new Error(`スライド一覧の取得に失敗しました: ${error?.message ?? "unknown error"}`);
  }

  let maxNumber = 0;
  for (const item of data) {
    const match = item.name.match(SLIDE_FILE_PATTERN);
    if (match) {
      maxNumber = Math.max(maxNumber, Number.parseInt(match[1], 10));
    }
  }

  return maxNumber + 1;
}
```

番号を指定しなければフォルダ内の既存ファイルを走査して**最大値+1で自動採番**し、番号を指定した場合は**その番号で上書き保存**します。一覧取得に失敗した場合は自動採番を中断して例外を投げることで、誤った番号で既存ファイルを上書きしてしまう事故を防いでいます。

## 会議の様子

### 隔週交互の新体制とレビュー滞留の課題

今回から、定例はポータルサイトとsinlab-studyを**隔週で交互に扱うスタイル**になりました。冒頭にポータルサイトの確認事項を短く取り、残りの時間をsinlab-studyに充てる進行です。

ポータルサイト側では、ver8のリリースが約2週間後に迫る中、「レビュー待ちのまま1週間ほど止まっているPRがあり、間に合わないかもしれない」という声が上がりました。全体的にレビューが遅れがちという認識が共有され、実際に「レビューは済んでいたのに、Slackでの連絡を忘れていて依頼側が止まっていた」というすれ違いも発覚。**レビューのチェックや依頼が終わったら必ずSlackで連絡を取り合う**というコミュニケーション重視の運用を改めて確認しました。

### sinlab-studyとは — AIレビュー付きの学習サービス

sinlab-studyは、ポータルサイトとは別の**学習用サービス**です。現在はGASの学習コンテンツが公開されており、基礎編では文法やスプレッドシート・フォーム・カレンダーの自動化を、新しく追加された応用編ではGASによるWebアプリ開発を学べます。課題を提出するとAIが自動レビューしてくれる点が特徴で、すでに新会員への共有も始まっています。

メンバーからは「学習で作るアプリのプラットフォームはどうなっているのか」という質問があり、「完全にGASだけで完結しており、GASのデプロイ機能でWebアプリとして公開し、スプレッドシートと連動したアプリを作れる」ことが説明されました。コンテンツの追加はメンテナンス権限を持つメンバーが行え、現在は講師を務めるメンバーがコンテンツ追加を担当しています。開発チームとしてはこのサービスを**もっと使いやすくする機能追加・改良**を担っていきます。

技術面では、リポジトリはNext.jsの比較的新しいバージョンを採用し、UIコンポーネントには**Tailwind CSSと相性の良いshadcn/ui**を使用。パッケージ管理・実行環境はnpmではなく**Bun**（`bun dev` で起動）、リンターは**Biome**、テストは**Vitest**という構成です。ポータルサイトのJestとは異なるトレンド技術を学ぶチャンスだという紹介がありました。一方で「Bunを最新バージョンにし続けると動作に影響が出ないか」という懸念も出され、「常に最新が良いとは考えず、1ヶ月ほど様子を見てセキュリティホールなどの情報をチェックした上でコントロールする」「開発環境で動作を確認してから本番に反映し、バージョン管理をしっかり行う」という方針を確認しました。Wikiや開発フローは基本的にポータルサイトの内容を踏襲します。

### 機能アイデア出しと担当決め

sinlab-studyで今後取り組みたい機能について、活発なアイデア出しが行われました。明確な優先度計画はまだ設けていないものの、**AIレビューのトークン消費量削減を優先的に考えたい**という方向性が示されています。挙がったアイデアは次のとおりです。

* 初心者向けのガイド機能
* AIレビューの利用頻度制限の改善（現在は1コンテンツにつき1回のみ。「1ヶ月後に復帰する」月次リセット案が出てバックログ入り）
* 動画やスライドをまとめて登録できる**コンテンツの一括アップロード機能**
* コース単位のコンテンツ管理・アクセス制限
* コースごとにポイントを付与し、難しい課題には高得点の「重み」をつける**ゲーム要素**
* ユーザーごとの**トークン使用量モニタリング**（使用制限や閾値を設けて管理者に通知する仕組み）
* 課題のヒントを入力・編集できる機能、ORMの導入
* スライドのマークダウン化（AIレビュー時のトークン数削減につながる）

プロジェクトボードの運用も整理され、**バックログは検討中のテーマ、実際に取り組むものはReadyに移す**というルールを確認。そのうえで、コンテンツの一括アップロード（設計から着手）、トークン使用量のモニタリング、AIレビューのトークン消費削減をそれぞれ別のメンバーが担当し、レビュアーも同時に決めるところまで進みました。モニタリングを担当するメンバーからは「特定のユーザーが使い切ってしまうとサービス維持ができないため、個人ごとの把握が必要」という問題意識が共有され、履歴を記録して分析に使う方向で、アプリが重くならない範囲で作ってみることになりました。

### 設計書とCopilotレビューの運用ルール

ポータルサイト側では、進行中のマスターテーブル更新設計についての議論もありました。設計書に「ver8、9、10」のような**バージョン番号を特定して書くと後の修正が大変になるため外す**、機能は日本語で記載し既存機能には触れない、という提案が合意されています。また、代表・副代表・管理人は兼任しない前提で、兼任を想定した仕組みは作らないことも確認されました。修正規模については「修正箇所が多すぎると判断が難しくなるので、機能ごとに分けて進める。**開発の基本として修正行数は少ない方が良い**」という方針のもと、マスターテーブル更新はコミット内容を分割して進めることになりました。

GitHub Copilotの自動レビューコメントについては、「担当者が対応したら自分でResolve（解決済みに）してよい」という方針が提案されました。「レビュワーにも見てもらった方がいい部分もあるのでは」という意見もありましたが、「気になる場合は開いて読める。レビュワーが自分の指摘でないものまですべて確認するのは非効率」という理由から、**担当者が解決したら閉じる運用**で決着しています。

## 活用した技術

### Bun と Biome — 新世代のJavaScriptツールチェーン

**Bun**は、Node.js＋npmの代替を目指すオールインワンのJavaScriptランタイム／パッケージマネージャーです。インストールやスクリプト実行が高速で、sinlab-studyでは `bun dev` のようにnpmコマンドの代わりに使います。**Biome**はESLint＋Prettierの領域を1ツールでカバーするリンター／フォーマッターで、Rust製の高速さと設定のシンプルさが特徴です。テストにはJestより高速でVite系エコシステムと親和性の高い**Vitest**を採用しており、Jest＋npmで構成されたポータルサイトとの違いを体感しながら、最新のツールチェーンを学べる環境になっています。ただし新しいツールほど更新も頻繁なため、会議で確認したとおり「最新情報を1ヶ月ほど見極めてから追従する」といったバージョン管理の規律が重要になります。

### shadcn/ui — コピーして育てるUIコンポーネント

**shadcn/ui**は、Tailwind CSSをベースにしたUIコンポーネント集です。一般的なUIライブラリのようにnpmパッケージとして依存に加えるのではなく、**コンポーネントのソースコードを自分のプロジェクトにコピーして使う**というユニークな方式を採っています。このため、デザインの微調整やロジックの変更を自由に行うことができ、Tailwind CSSのユーティリティクラスとの相性も抜群です。会議でも「Tailwind CSSとの相性が抜群に良いライブラリ」として紹介されており、学習サービスのUIを素早く、かつ柔軟に組み立てる基盤になっています。

### JSONBカラムによる後方互換なスキーマ拡張

演習課題の複数ファイル対応では、PostgreSQL（Supabase）の**JSONB型**を活用しました。`[{filename, language, content}]` のような可変長の構造化データを1カラムに格納できるため、「ファイル数が課題によって異なる」という要件に対して、提出ファイル用の別テーブルを増やさずに対応できます。

ポイントは後方互換性の設計です。既存の `code_content`（単一ファイル）カラムはそのまま残し、複数ファイルのときだけ `code_files` を使う。読み出し側は両形式を吸収する正規化関数を1つ用意して、画面表示もAIレビューも同じ関数を通す。マイグレーションも `ADD COLUMN IF NOT EXISTS` による**冪等なSQL**にすることで、稼働中のDBにも新規セットアップにも同じファイルを安全に適用できます。稼働中のサービスにスキーマ変更を加える際の、実践的なお手本といえる構成です。

今回は、学習支援アプリsinlab-studyの開発キックオフ回でした。サービスの全体像と技術スタックの共有から始まり、AIレビューのトークン消費削減・トークン使用量モニタリング・コンテンツ一括アップロードという初期テーマの担当決めまで、新プロジェクトの立ち上げに必要な要素が一通り揃った回だったといえます。

Bun・Biome・Vitest・shadcn/uiといったポータルサイトとは異なる技術構成は、メンバーにとって新しい学びの機会である一方、「最新に追従しすぎない」バージョン管理の規律もセットで確認されました。また、レビュー連絡のSlack徹底やCopilotレビューのResolve運用、設計書からバージョン番号を外す判断など、2つのプロジェクトを並行して回すためのプロセス改善も着実に積み上がっています。隔週交互という新しいリズムで、ポータルサイトとsinlab-studyがどう育っていくのか、今後の記録もお楽しみに。
