### ホーム画面の「本日のイベント」ウィジェット

ver7の目玉のひとつが、ホーム画面に当日のカレンダーイベントを表示するウィジェットです。日をまたぐイベントや終日イベントも考慮して、開始・終了時刻の表示を出し分けています。

```tsx
// app/(authenticated)/components/TodayEventsWidget.tsx（抜粋）
function formatEventTime(event: CalendarEvent, todayStart: Date, todayEnd: Date): string {
  if (!event.start?.dateTime) return "終日";

  const start = new Date(event.start.dateTime);
  const end = new Date(event.end?.dateTime ?? event.start.dateTime);

  const startIsToday = start >= todayStart && start < todayEnd;
  const endIsToday = end > todayStart && end < todayEnd;

  if (startIsToday && endIsToday) {
    return `${toHHmm(start)}〜${toHHmm(end)}`;
  } else if (startIsToday && !endIsToday) {
    return `${toHHmm(start)}〜`;
  } else if (!startIsToday && endIsToday) {
    return `〜${toHHmm(end)}`;
  } else {
    return "終日";
  }
}
```

### URL登録のバリデーション — フロントとDBの二段構え

動画・資料・アプリの登録フォームには、Zodを使ったURLバリデーションを追加しました。`https://` で始まる正しい形式のURLのみを受け付け、未入力は許容する仕様です。

```typescript
// app/utils/url-validation.ts（抜粋）
const httpsOnlySchema = z.string().refine(
  val => {
    try {
      const parsed = new URL(val);
      return parsed.protocol === "https:";
    } catch {
      return false;
    }
  },
  {
    message: "URLは https:// から始まる正しい形式で入力してください",
  }
);

export function isValidUrl(url: string | null): boolean {
  if (!url || url.trim() === "") return true;
  return httpsOnlySchema.safeParse(url).success;
}
```

さらに、アプリ側のチェックをすり抜けたデータが入らないよう、データベース側にもCHECK制約を追加しています。

```sql
-- supabase/migrations/01_tables/applications/02_add_url_check_constraint_to_applications.sql（抜粋）
-- applicationsテーブルのurlカラムにhttpsのみ許可するCHECK制約を追加
-- NULLは許容（未入力可）、入力がある場合はhttps://から始まること
ALTER TABLE applications
  ADD CONSTRAINT applications_url_https_check
  CHECK (url IS NULL OR url ~ '^https://');
```

## 会議の様子

### リリース後の課題整理 — 重複イシューはAIで洗い出す

リリース作業の際に、**セキュリティ的なリスクとデータ不整合に関する指摘**が見つかっていました。リリースを優先したため対応は後回しになっていましたが、リードメンバーがこれらをイシュー化し、早めに対応する方針を共有しました。

ここで議論になったのが、既存イシューとの重複です。リリース時の指摘をまとめたイシューは前バージョンからのバグを網羅的に拾い上げているため、個別の機能開発から生まれた既存イシューと内容が被っている可能性がありました。重複したまま作業を進めると、**別々のイシューで同じ問題に二重に取り組んでしまう**恐れがあります。

対応方針としては、重複が見つかった場合はリリース指摘側のイシューから項目を削り、「この項目は〇〇番と重複しているため、ここでは対応しない」と一筆残す形に整理しました。あわせて、「オープン中のイシューをAIに網羅的にチェックさせれば、重複の洗い出しはすぐできるのではないか」という見立てから、**AIによる重複チェックが済むまで、To Doにあるバグ修正・改善系のイシューには着手しない**ことを決めています。手を動かす前に課題の全体像を整えるという、リリース直後ならではの判断でした。

### Wikiと設計書、どう住み分ける？

現在リードメンバーが進めている「本番環境リリース操作の自動化」では、実装に入る前にイシュー上でベテランメンバーとすり合わせを行い、専用の設計書を作ってから自動化のGitHub Actionsを作る段取りを確認しました。その中で「この設計はどのドキュメントに書くべきか」という話題から、**Wikiと設計書の住み分け**について質問が挙がりました。

チームとしての整理は次のようなものです。厳密なルールは決めていない前提としつつ、

* **Wiki**: 手順やノウハウなど、一般論も含む知見。技術スタックの概要、Claude Codeの使い方、コーディング規約など
* **設計書**: どういう思想・方針で動いているかという、**このアプリにのみ適用されるルール**。ユーザーテーブルなどアプリ固有の構造

という考え方が共有されました。本番リリースの「手順」は引き続きWikiに置き、GitHub Actionsのワークフローとして実現する要件や権限設計の基準は設計書に書く、という役割分担です。

また、進行中のRLSポリシー共通化のタスクでは、担当メンバーから「そもそも設計書をどう書き始めればよいか、お手本が見たい」という率直な相談があり、データベース設計書に「共通RLSポリシー」の節を新設して各テーブルで重複しているポリシーを拾い上げる、という具体的な書き方の方針をその場で確認しました。**AIとも相談しながら、まずは書いてみる**ことになっています。

### 設計書の画面イメージ — Draw.ioかHTMLモックか

長らく手つかずになっていた「Draw.ioによる画面イメージ作成」のイシューについて、方向性を議論しました。発端は「機能設計書を読んでもUIのイメージが湧きにくい」という過去の指摘です。一方で、使おうとしていたツールには非推奨の記載があり、このまま進めてよいかが論点になりました。

議論の軸は**見栄えとメンテナンス性のトレードオフ**です。ベテランメンバーからは「HTML/CSSだけの静的なモック画面を作り、ブラウザ自動操作でスクリーンショットを撮ってPNG化すれば、AIで簡単に修正・再生成できる」という**HTMLモック案**が提案されました。Draw.ioの図を手作業でメンテナンスするより、AIとの相性が良いという狙いです。

これに対して別のメンバーからは、「ちょっとした項目追加のたびにAIに書かせないと直せないのは嫌だ。**自分でコピペして直せるくらいのメンテナンス性が欲しい**」という現場感のある懸念も出ました。受託開発などの実務でも、依頼元が求める見栄えと開発側が重視するメンテナンス性の天秤はよくあるテーマです。最終的に、イシューの目的を「Draw.ioを使うこと」ではなく「描画を今より良くすること」と捉え直し、**ツールを限定せずAIと相性の良い描画サービスを含めて調査したうえで、方針はあらためて定例で決める**ことになりました。

### 新サービス「Sin-Lab Study」のメンテナンス体制へ

定例の最後に、新しくリリースした学習支援サービス**「Sin-Lab Study」**のメンテナンスを、今後このチーム開発で担っていく構想が共有され、参加メンバー全員をリポジトリにメンテナー権限で招待しました。すぐにタスクを割り振る段階ではなく、まずは時間のあるときにコードを眺めてもらい、欲しい機能があればイシューに追加してもらう緩やかなスタートです。

ここでは2つの議論がありました。1つ目はリポジトリの公開方針です。「サービスは会員向けなのだから、リポジトリはプライベートの方がよいのでは」という意見に対し、リードメンバーは「コンテンツ自体はリポジトリに載せないので、プラットフォームの仕組みは公開してよい。むしろ**活動のアピールのためにできるだけパブリックにしたい**」という考えを示し、合意に至りました。

2つ目はデータベースの**バックアップ**です。「万一に備えてDB全体のエクスポートデータを別で保管すべき」という提案に対し、「スライドはGoogleドライブ、動画はYouTubeにあるためコンテンツは復元できる」「パスワードは保存しておらずGoogleログインのみ」「個人情報を管理する場所はむしろ増やしたくない。下手なバックアップは漏えいリスクにもなる」という反論があり、結論としては**ユーザー規模やサービスの展開状況を見ながら、将来あらためて検討する**こととしました。守りたいものと増やしたくないリスクを天秤にかけた、セキュリティ設計らしい議論でした。

## 活用した技術

### Zodによるバリデーションと多層防御

**Zod**はTypeScript向けのスキーマバリデーションライブラリで、「文字列であること」「特定の条件を満たすこと」といった検証ルールを宣言的に記述できます。今回のURL検証では `refine` を使い、`new URL()` でパースできて、かつプロトコルが `https:` であることをチェックしました。

ポイントは、同じルールを**データベースのCHECK制約としても定義している**ことです。フロントエンドの検証はユーザー体験のためには必須ですが、APIを直接叩かれたり、別の経路でデータが書き込まれたりすればすり抜けられます。アプリ層とDB層の両方で守る「多層防御」にしておくことで、不正な形式のURLがテーブルに混入する事態を構造的に防げます。

### セマンティックバージョニングとリリースブランチ運用

今回のリリースは `v7.0.0` というタグで公開されています。これは**セマンティックバージョニング**（メジャー.マイナー.パッチ）に沿った番号づけで、このチームでは機能追加をまとめたメジャーリリースを定期的に行い、緊急性の高い修正はパッチバージョンとして別途リリースする運用を取っています。

ブランチ運用としては、開発の成果を集約したブランチからリリース用ブランチへのプルリクエストを作り、それをマージすることで本番反映する形です。現在は手作業が残っているこのリリース操作をGitHub Actionsで自動化する取り組みが進んでおり、「どこまで自動化し、どこは人間の判断を残すか」をイシュー上ですり合わせてから設計書を書くという、**実装前の合意形成を重視した進め方**をしています。

### HTMLモックとブラウザ自動化による画面イメージ生成

会議で提案されたHTMLモック案は、API呼び出しなどのロジックを持たないHTML/CSSだけの静的な画面を作り、**Playwrightのようなブラウザ自動操作ツールでスクリーンショットを撮ってPNGやSVGにする**という手法です。

作図ツールで描いた画面イメージは、UIの変更のたびに人間が図形を並べ直す必要があります。一方HTMLモックなら、修正はコードの編集なのでAIに任せやすく、スクリーンショットの再生成も自動化できます。生成AIの普及で「ドキュメント用の図をどう作り、どう保守するか」の最適解は変わりつつあり、今回の「ツールを限定せずに調査する」という判断は、その変化を織り込んだものと言えます。

## 総括

今回は、ver7.0.0のリリースという大きな節目を越え、次のバージョンに向けて課題を棚卸しする回となりました。リリースで見つかった指摘を勢いのまま潰しにいくのではなく、AIで重複を洗い出してから着手するという「急がば回れ」の判断は、限られた稼働時間で開発するコミュニティチームだからこそ効いてくる進め方です。

また、Wikiと設計書の住み分けや、画面イメージの作り方をめぐる見栄えとメンテナンス性のトレードオフなど、ドキュメントに関する議論が多かったのも今回の特徴でした。新サービス「Sin-Lab Study」のメンテナンス体制づくりも始まり、チームの活動範囲はポータルサイトの外へ広がりつつあります。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
