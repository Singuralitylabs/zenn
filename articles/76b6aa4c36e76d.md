### 新規に追加した改善Issue

バージョン8.1のリリース作業の中で、細かな不具合や改善点が見つかったため、優先度を低めにして新たにIssue化しました。

* 会員一覧の並び順の指定が消えている
* 会員一覧に不要なテンプレートが残っている
* カレンダーAPIで変数名が重複している
* ゴミ箱からの復活処理の問題（更新件数が0件でも成功扱いになる、復活ボタンを連打できる、ローディング中でもボタンが押せる、日時が誤っている場合がある）
* 承認待ちユーザーの操作によって、Slackへ承認依頼の通知を繰り返し送れてしまう問題

いずれも大きな問題ではないため、優先度は低く設定されています。

## 会議の様子

### 進捗確認

進行中のIssueを上から順に確認しました。

Supabase無料プランの自動停止防止では、担当者が指摘に回答済みで、レビュアー側の確認待ちの状態でした。設定の変更内容そのものは問題ないとの判断で、設定した理由をコメントとして残しておく程度の修正で進められることになりました。また、GitHub Actionsのワークフローを変更する場合のレビューについて質問があり、ワークフローの変更もコードと同様にプルリクエストで確認できるため、通常のレビューフローで問題ないと整理されました。

なお、進捗共有の中で、Issueの一部が別プロジェクトの名称になっていたことに気づき、その場で修正する流れもありました。AIが固有名詞の綴りを誤ることがあるという話から、「固有名詞は人間が最終確認する」ことの重要性を再確認しました。

ローカルSupabaseの調査では、MacとLinuxでは追加の準備が不要で、Windowsでは必要になることが分かりました。コードの修正ではなく手順の整理が目的のため、手順をまとめたドキュメントをWikiに書き出し、司会者がチェックする形で進めることになりました。

usersテーブルの会員情報の露出問題では、開発環境のDBに検証用にマイグレーションを適用したところ、周囲に影響が出てしまい元に戻した経緯が共有されました。レビューAIの指摘については、次のような進め方が共有されました。

* AIレビューは指摘を出し続けられるため、どこかで打ち切る必要がある
* 「マージを止めるべき問題があるか」という聞き方をすると、軽微な指摘は省かれやすい
* マージを阻害しないが直したほうがよい指摘は、別Issueとして切り出す
* 判断に迷う場合は、AIの指摘内容をそのままPRに書いてもらい、レビュアーが切り出しを提案する

削除済みカテゴリーのコンテンツ復活の問題では、担当者が複数のPRを出しており、そのうち重いものがレビュー待ちとなっていました。そこで、軽いPRを先にレビューしてマージし、重いPRは後続で対応する進め方になりました。

### 設計書にどこまで書くか

今回のメインテーマは、Supabase関数の設計書に追加された記述量が、既存の資料と比べて多すぎるのではないかという相談です。

当初は「docs」全体の話なのか、仕様書のみの話なのかで認識がずれていましたが、議論の結果、対象は仕様書（機能仕様書・データベース仕様書）であると整理されました。

#### 設計書に残すもの・外すもの

議論の結果、次のように振り分けることになりました。

* **残す**: タイトル、概要、定義ファイルの説明。概要はテーブルの前に置く
* **外す**: 処理手順、入力値の扱い、実行モードや権限の詳細
* **Issueのコメントへ移す**: 設計上の判断、不整合リスクとその対応（検討した選択肢や判断の経緯）
* **エラー**: 他の箇所に書かれていないため、この関数だけ詳細に書くのではなく、全体でエラーコードの一覧を作る場合に追加する

仕様書は機能面の説明が中心であるべきで、「なぜそうしたか」という背景や検討過程は、Issueのコメントに残しておくか、Wikiのナレッジとして残す、という考え方です。

#### 議論のポイント

* 既存のヘルパー関数の記述は、関数の一覧と戻り値の型を並べるだけの粒度であり、今回の記述はそれよりかなり詳細だった
* 処理手順は数ステップなら書いてもよいが、「コードを見ればわかる情報」は設計書に書かない、という方針になった
* 粒度を揃えるなら、他の関数にも同様に書く必要があり、メンテナンスの負担が増える
* 不整合リスクの一覧には、画面操作の制約によって実際には発生しえないものも含まれていた。そうした検討内容は、判断の過程として価値があるので、Issueに残すのが適切
* 定義ファイルをドキュメントの先頭に置くと「必ず読むべき重要な資料」という印象を与えるため、ブロックの最後に置くほうがよい
* Issue番号などの変更理由は、設計書ではなくコミットメッセージに書けば、変更の経緯を追える

細部の調整は担当者とレビュアーの判断に任せ、大まかな分量の方針だけをここで決めました。設計段階のタスクは、レビュー前でも「In Progress」に移してよいことも確認されました。

### Supabase CLIのアクセストークン

定例の最後に、ローカル環境でSupabase CLIを使った型生成コマンドが失敗する、という相談が画面共有付きで行われました。

#### 原因の切り分け

* 当初は `.env.local` を直していたが、実行されるコマンドは `.env.development` を参照していた
* 環境変数を暗号化して管理しているため、暗号化された値のままではプロジェクトIDなどが正しく読み取れない
* スクリプトを直接実行しようとすると構文エラーになり、直接実行を想定したものではないと判明
* 最終的に「Invalid access token」と表示され、アクセストークンの有効期限切れが原因だった

#### 対応

Supabaseの管理画面のアカウント設定から、アクセストークンを再発行しました。

* 有効期限は無期限にもできるが、推奨はしない
* 今回の用途はローカルでのデータベースの読み取り（型生成）が中心のため、権限は最小限に絞る。最初はすべて「アクセスなし」にし、必要なものだけ（データベース、マイグレーションなど）を読み取り専用にするのが基本
* `supabase login` 後にブラウザでログインしたアカウントの権限でローカルのコマンドは動くため、アクセストークンの権限が更新系の処理に影響するわけではない

#### GitHub Actionsでの型の差分エラー

別件として、CI（GitHub Actions）で型定義ファイルの差分エラーが出ている件も確認しました。ワークフローは、開発用Supabaseプロジェクトから取得した型と、PRに含まれる型定義ファイルを比較しており、差分があるとエラーになります。差分が実際に出ているので、ローカルで型を再生成してコミット・プッシュすれば解消するはず、という結論になりました。

あわせて、`git diff` の `a/` と `b/` は比較対象に自動で割り振られるラベルであり、特別な意味はないことも補足されました。

## 活用した技術

### 設計書・仕様書の役割分担

ドキュメントの種類ごとに、書く内容を分けて考えると運用しやすくなります。

| 置き場所 | 書く内容 |
|---|---|
| 仕様書（機能・DB） | 機能面の説明、定義、概要レベルの処理内容 |
| Issueのコメント | 検討した選択肢、設計上の判断、リスクとその対応 |
| Wiki（ナレッジ） | 手順書、ノウハウ、検証結果 |
| コミットメッセージ | 変更理由、関連Issue番号 |
| コード | 具体的な処理手順（コードを見ればわかる情報） |

「コードを見ればわかる情報は書かない」「背景や経緯は履歴の残る場所に書く」と決めておくと、設計書が膨れ上がるのを防げます。

### Supabase CLIとアクセストークン

アクセストークンは、Supabase CLIがAPI経由で操作するための認証情報です。

* 発行は、管理画面のアカウント設定にあるアクセストークンの画面から行う。GitHubなど多くのサービスも、アカウント設定から同様に発行できる
* 有効期限が切れると `Invalid access token` となる
* 権限は必要最小限（最初は「アクセスなし」、必要なものだけ読み取り専用）にするのが基本

### GitHub Actionsによる型定義の整合チェック

開発用Supabaseプロジェクトから取得した型定義と、リポジトリにコミットされた型定義ファイルを比較するチェックを、CIで実行しています。DBのスキーマ変更とコード側の型定義のずれを、PRの段階で検出できる仕組みです。

### AIレビューとの付き合い方

AIによるコードレビューは指摘をいくらでも出せるため、運用ルールを決めておくことが重要です。

* 「マージを止めるべき問題があるか」と聞いて、軽微な指摘を除外する
* 今回のPRで対応しない改善点は、別Issueとして切り出す
* 固有名詞やURLなどはAIが誤ることがあるため、人間が最終確認する

## 総括

今回は、設計書の粒度という「正解のない問い」に対して、書く内容を置き場所ごとに振り分けるという方針でチームの認識を揃えました。ドキュメントは書くことよりも、何を書かないかを決めることが、長期的なメンテナンス性につながります。

また、アクセストークンのトラブルを通じて、原因を一つずつ切り分けていく過程と、権限を最小限に絞る基本姿勢を共有できました。環境まわりのトラブルは個人環境の問題になりがちですが、画面共有で一緒に確認することで、チーム全体の知見になります。
