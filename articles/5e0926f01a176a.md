## 開発したもの

### プロフィール画像のアップロード機能

プロフィール画面から自分の画像をアップロード・変更・削除できる機能を実装し、mainブランチにマージされました。これまでGoogleアカウントのアバター画像のみを表示していましたが、ユーザーが任意の画像を設定できるようになります。

画像の保存先にはSupabase Storageを採用し、専用の非公開バケットを作成しました。バケット自体にファイルサイズ上限とMIMEタイプの制約を持たせています。

```sql
-- profile-images バケットの作成（非公開、最大1MB、jpg/jpeg/png/gifのみ）
INSERT INTO storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
VALUES (
  'profile-images',
  'profile-images',
  false,
  1048576,
  ARRAY['image/jpeg', 'image/jpg', 'image/png', 'image/gif']
) ON CONFLICT (id) DO NOTHING;
```

アクセス制御はRLS（Row Level Security）ポリシーで実現しています。アップロードは自身の `auth_id` フォルダ配下にのみ許可し、かつ承認済み（active）ユーザーであることを条件にしています。

```sql
-- active なユーザーは自身の auth_id フォルダにのみアップロード可能
CREATE POLICY "Users can upload their own profile image"
ON storage.objects FOR INSERT
TO authenticated
WITH CHECK (
  bucket_id = 'profile-images'
  AND (storage.foldername(name))[1] = auth.uid()::text
  AND EXISTS (
    SELECT 1
    FROM public.users
    WHERE users.auth_id = auth.uid()
      AND users.status = 'active'
      AND users.is_deleted = false
  )
);
```

アップロード処理はNext.jsのAPI Routeで実装しました。バリデーション後にStorageへアップロードし、DBの `profile_image_path` カラムを更新します。DB更新に失敗した場合はアップロード済みファイルを削除するロールバック処理も入れています。

```typescript
const filePath = `${authId}/profile-image`;
const fileBuffer = await file.arrayBuffer();

const { error: uploadError } = await supabase.storage
  .from(BUCKET_NAME)
  .upload(filePath, fileBuffer, { contentType: file.type, upsert: true });

if (uploadError) {
  console.error("Storage アップロードエラー:", uploadError.message);
  return NextResponse.json(
    { success: false, error: "画像のアップロードに失敗しました" },
    { status: 500 }
  );
}

const { error: updateError } = await supabase
  .from("users")
  .update({ profile_image_path: filePath })
  .eq("auth_id", authId)
  .eq("is_deleted", false);

if (updateError) {
  console.error("profile_image_path 更新エラー:", updateError.message);
  const { error: rollbackError } = await supabase.storage.from(BUCKET_NAME).remove([filePath]);
  if (rollbackError) {
    console.error("Storage ロールバック失敗:", rollbackError.message);
  }
  return NextResponse.json(
    { success: false, error: "プロフィール情報の更新に失敗しました" },
    { status: 500 }
  );
}
```

また、画面右上のアバターとプロフィール編集画面で同じ画像状態を共有するため、React Contextによるプロバイダーを新設しました。どちらか一方で画像を更新すると、リロードなしでもう一方にも即時反映されます。

```typescript
// 指定パスの署名付きURLを取得して state に反映する。
// &t=... を末尾に付与することで、同一パスへの再アップロード後もブラウザキャッシュを回避する。
const fetchSignedUrl = useCallback(async (path: string) => {
  const supabase = createClientSupabaseClient();
  const { data, error } = await supabase.storage
    .from("profile-images")
    .createSignedUrl(path, 3600);
  if (error || !data?.signedUrl) {
    setProfileImageUrl(null);
    return;
  }
  setProfileImageUrl(`${data.signedUrl}&t=${Date.now()}`);
}, []);
```

なお、マージ後のレビューで「キャッシュバスティング処理が非効率」という指摘があり、改善Issueとして引き続き対応することになりました。

### Wiki更新のSlack通知（設計）

GitHub Wikiが更新された際にSlackへ自動通知する仕組みの設計書がマージされました。Wikiの更新（`gollum` イベント）をトリガーにGitHub ActionsでWikiリポジトリの差分を取得し、ページ名・操作種別・更新者・差分抜粋を1件の通知にまとめてSlackのIncoming Webhookへ送信する方式です。

```text
Wiki が更新されました

- ページ: <ページ名とリンク>
- 操作: <created / edited / deleted>
- 更新者: <GitHub ユーザー名>
- 差分抜粋:
   <ページ単位の見出しまたは差分先頭 5 行 / 100 字以内>
- Compare: https://github.com/Singuralitylabs/portal-site/wiki/_compare/<revision>
```

Webhook URLは既存のアプリ通知と同じSecretを共通利用し、専用トークンは発行しない最小権限の方針です。実装は次回リリースに向けて進めていきます。

### クイックリンクページの設計

新着情報からシンラボの各種サービスへ遷移できるクイックリンクページの設計が完了し、機能仕様書に追加されました。リンクは「直リンク」と「詳細モーダル」の2種類を用意し、説明が必要なサービスにはモーダルを挟む構成です。

リンク情報はデータベースではなく定数ファイルで管理する方針としました。更新頻度が低く、アプリ内で完結させたほうが表示速度の面でも有利という判断です。

## 会議の様子

### マスターテーブル管理とYAGNIの法則

今回の定例で最も議論が白熱したのは、マスターテーブル管理機能の設計です。専用画面からマスター系テーブルを参照・編集できるようにする機能で、担当メンバーからは操作権限を制御するための「管理用テーブル（アドミンテーブル）」を新設する案が提示されました。

これに対して司会のメンバーから「そのテーブルが必要な理由は何か。既存のTypeScriptの型定義から取得できるのではないか」という指摘がありました。スキーマ名や表示名を保持する案について、**「あっても困らない」という考え方は「YAGNI（You Aren't Gonna Need It）の法則：必要になるまで追加しない」に反する**という議論です。

カラムごとの制約情報を管理したいという意図に対しても、「それはSupabaseの機能で備わっており、バリデーションはアプリ側で実装するのが一般的」という整理がなされ、既存の型定義ファイルから読み出す最小限の構成で設計をやり直すことになりました。

また、この機能はもともと盛り込みすぎでレビュー負荷が高いという課題があり、Issueを分割して進める方針が再確認されました。1つのIssueに機能を詰め込みすぎないこと、承認前に実装を先行させないことなど、チーム開発ならではの進め方についても率直な意見交換が行われました。

### 設計書へのモックアップ画像

設計書にモック画面のキャプチャを載せる試みも共有されました。Playwrightでスクリプトを動かし、実際に動くTSXのモックからPNG画像を自動生成する仕組みです。

一方で「設計書は実装前に書くものなのに、その段階では画面がない。鶏と卵の問題にならないか」「アプリ配下にモックアップを置くとビルドや開発環境に影響する。ドキュメント配下に置くべきでは」といった指摘もあり、何のために画像を載せるのかという目的に立ち返って引き続き検討することになりました。

### Node.jsアップデートとセキュリティ対応

現在使用しているNode.js v20のサポートが2026年9月に終了予定のため、v24へのアップデートを新しいIssueとして起票しました。GitHub Actionsのワークフローのバージョン更新に加え、依存関係の確認も必要になります。あわせてDependabotの導入などセキュリティ対応もまとめて検討する方針です。

### レビュー運用の学び

プルリクエストのレビューで「コメントを書いたのに相手に見えない」という事象があり、原因はGitHubの **「Submit review」ボタンを押していなかった**こと（Pending状態のまま）と判明しました。レビューコメントはまとめてサブミットすることで初めて他のメンバーに公開されます。こうした実践的なGitHub操作を学べるのもチーム開発の良いところです。

## 活用した技術

### Supabase StorageとRLSによるファイル管理

Supabase Storageは、バケット単位で公開/非公開・ファイルサイズ上限・許可MIMEタイプを設定でき、さらに `storage.objects` テーブルへのRLSポリシーでオブジェクト単位のアクセス制御が可能です。今回は `(storage.foldername(name))[1] = auth.uid()::text` という条件で「自分のフォルダにしか書き込めない」制約をDB層で強制しています。アプリ側のバリデーションと多層で防御することで、APIを迂回した不正操作も防げます。

非公開バケットの画像は `createSignedUrl()` で有効期限付きの署名付きURLを発行して表示します。同一パスに上書きアップロードした場合はブラウザキャッシュが残るため、URL末尾にタイムスタンプを付与するキャッシュバスティングで対処しています。

### React Contextによる状態共有

ヘッダーのアバターとプロフィール編集画面のように、離れたコンポーネント間で同じ状態を参照したい場合、React Contextが有効です。プロバイダーを認証済みレイアウトに配置することで、配下のどのコンポーネントからも `useProfileImage()` フックで画像URLと更新関数にアクセスできます。

```tsx
// 認証済みかつactiveな場合のみコンテンツを表示
if (user && userStatus === USER_STATUS.ACTIVE) {
  return <ProfileImageProvider>{children}</ProfileImageProvider>;
}
```

### GitHub Actionsのgollumイベント

GitHub ActionsはWikiページの作成・更新・削除を `gollum` イベントとして受け取れます。今回の設計ではこれをトリガーにWikiリポジトリ（`portal-site.wiki.git`）から差分を取得し、Slackへ通知します。`GITHUB_TOKEN` に `contents: read` のみを明示する最小権限の構成です。

### YAGNIの法則

YAGNI（You Aren't Gonna Need It）は「実際に必要になるまで機能を追加しない」という原則です。「将来使うかもしれない」「あっても困らない」という理由で追加されたテーブルやカラムは、メンテナンスコストとレビュー負荷を増やし続けます。今回のマスターテーブル設計の議論は、既存の仕組み（TypeScriptの型定義、Supabaseの制約機能）で代替できないかをまず確認するという、設計レビューの好例になりました。
