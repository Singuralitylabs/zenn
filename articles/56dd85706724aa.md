## 開発したもの

### URLバリデーションの共通化 — フロントとDBの二段構え

動画・資料・アプリの登録フォーム、そしてプロフィールのSNSリンクには、それぞれURLを入力する欄があります。これまでのバリデーションはページごとに実装がバラバラで、Zodをその場で使うフォームもあれば、素の正規表現でチェックするフォームもあり、`http://` を許容するかどうかも揃っていませんでした。

今回のPRでは、バリデーションロジックを共通関数 `url-validation.ts` に集約し、**HTTPSのURLのみを許可する**方針に統一しました。

```typescript
// app/services/api/utils/url-validation.ts（抜粋）
import { z } from "zod";

/**
 * zodを用いたバリデーション
 * 1. 文字列であること
 * 2. 有効なURL形式であること (new URLでパースして確認)
 * 3. https:// で始まることのみを許可
 */
const httpsOnlySchema = z.string().refine(
  val => {
    try {
      const parsed = new URL(val);
      return parsed.protocol === "https:";
    } catch {
      return false;
    }
  },
  {
    message: "URLは https:// から始まる正しい形式で入力してください",
  }
);

export function isValidUrl(url: string | null): boolean {
  if (!url || url.trim() === "") return true;
  return httpsOnlySchema.safeParse(url).success;
}
```

各フォームは `isValidUrl()` を呼び出すだけになり、プロフィール画面のように複数のURL欄がある場合は、まとめてチェックして無効なフィールド名の一覧を返す `validateUrls()` を使います。エラーメッセージも全画面で統一されました。

さらに、フロントエンドだけでなく**Supabase（PostgreSQL）側にもCHECK制約**を追加しました。

```sql
-- supabase/migrations/01_tables/documents/06_add_url_check_constraint_to_documents.sql
-- documentsテーブルのurlカラムにhttpsのみ許可するCHECK制約を追加
ALTER TABLE documents
  ADD CONSTRAINT documents_url_https_check
  CHECK (url ~ '^https://');
```

```sql
-- supabase/migrations/01_tables/users/05_add_url_check_constraint_to_users.sql（抜粋）
-- usersテーブルの各SNS URLカラムにhttpsのみ許可するCHECK制約を追加
-- NULLは許容（未入力可）、入力がある場合はhttps://から始まること
ALTER TABLE users
  ADD CONSTRAINT users_x_url_https_check
  CHECK (x_url IS NULL OR x_url ~ '^https://'),
  ADD CONSTRAINT users_github_url_https_check
  CHECK (github_url IS NULL OR github_url ~ '^https://');
```

会議では、この**マイグレーションファイルはリポジトリに追加しただけではSupabaseに反映されない**ことが共有され、Supabase管理画面のSQLエディターでSQLを1つずつ実行する手順が実演されました。実演の途中、テスト環境の既存データに `http://` のURLが残っていたため制約の追加がエラーになる場面もあり、「制約を適用する前に既存データを直す必要がある」という実践的な学びも得られました。

### テスト用カレンダーの色定義とドキュメント修正

カレンダー表示機能の動作確認用に「テスト用カレンダー」を整備しました。カレンダーの色定義に、テスト用カレンダーを紫色で表示する設定を追加しています。

```typescript
// app/constants/calendar.ts（抜粋）
  // テスト用カレンダー
  "test-calendar": {
    backgroundColor: colors.purple[300],
    borderColor: colors.purple[400],
  },
```

あわせてAPIドキュメントの色分けの記述を実態に合わせて修正しました（シンラボMTGカレンダー：緑、シンラボイベントカレンダー：青、日本の祝日：赤、テスト用：紫、それ以外：グレー）。

ローカル環境では、Gitにコミットしない `.env.local` ファイル内のGoogleカレンダーIDをテスト用カレンダーのIDに差し替えることで、`npm run dev` で起動した画面にテスト用カレンダーが表示されます。会議では、**テストイベントは本番のイベントカレンダーではなくチーム開発用カレンダーに登録する**という運用ルールと、各自のGoogleカレンダーにチーム開発用カレンダーを追加する手順を周知することも確認されました。

## 会議の様子

### 「スルーした指摘」を負債にしない — issue化の運用開始

今回の中心的な話題は**技術的負債**への向き合い方でした。このチームでは「完璧さよりスピード優先」を方針として、リードは自分がレビュアーでないPRについては、致命的な問題以外の指摘をスルーしてきました。しかし、そうして見逃してきた改善点が蓄積すると、後から「なぜこれを放置したのか」というコードが増え、やがてどこから手をつけていいか分からない状態に陥る——これがエンジニアの恐れる技術的負債だ、という説明がリードからありました。

そこで、**マージ時に見送った改善点はissueとして記録に残す**運用を始めることになりました。現時点で3件ほどのissueが作られており、専用ラベルの新設も検討中です。重要なのは、これらが「絶対に直さなければならないリスト」ではないという点です。担当になったメンバーが「この修正は不要では」と感じたら、レビュアーと相談のうえで見送ってよいという柔軟な運用にしています。「担当者がつかないと永遠に放置されるのでは」という懸念も出ましたが、「リソースが限られている以上、無理やり割り振ることはできない。運用で回していくしかない」という現実的な結論になりました。

この文脈で進行中なのが、カテゴリー管理APIのコード品質改善です。主に異常系処理（処理が途中で失敗したときの扱い）の改善を進めており、担当メンバーからは**Playwright**という画面操作を自動化するツールでテストの自動化も始めているとの共有がありました。

### 削除ボタンが効かない — 論理削除とRLSポリシーの衝突

新たに発覚したバグとして、コンテンツの**削除ボタンが機能しない**問題が共有されました。本番環境でも同じ事象が起きています。

原因の分析（AIにも相談）によると、このアプリの「削除」は実際にはDELETE文ではなく、`is_deleted` フラグを `true` にする**UPDATE文による論理削除**です。一方、Supabase側のRLSポリシーには「論理削除されていないレコードのみ更新できる」という条件が含まれており、論理削除を行うUPDATE自体がこの条件に引っかかって失敗する、という構図でした。興味深いことに、会議中の再現デモではなぜか削除に成功してしまう場面もあり、完全な原因特定には至っていません。分析内容をissueにコメントとして残し、担当メンバーが引き取って対応することになりました。

### AIレビューコメントの洪水にどう対処するか

役割タグ機能のPRレビューでは、担当メンバーから率直な相談がありました。「実装の指摘に対応したのに、今更設計の指摘が追加される」「対応不要と返信した指摘がまた来る」「大量のAIコメントを貼られても読む時間が取れず、会話になっていない感じがする」——GitHub CopilotをはじめとするAIレビューの出力を、そのままPRに貼り付けることによる混乱です。

議論の結果、チームとしての方針が整理されました。開発者もレビュアーもAIを使うこと自体は問題ない。しかし**AIの出力を理解せずにそのまま貼るのはまずい**。レビュアーは指摘の要否を吟味して取捨選択したうえで出すこと。出された側もすべて修正する義務はなく、「これは不要では」とどんどん返してよいこと。そして何より大事なのは、**レビュアーと担当者がすり合わせをして「これで良し」と合意すること**です。リードからは、MCP機能でPRの内容を直接AIに読み込ませ、レビューコメントの要否をAIに判断させながら自分の意見をぶつけていく、というAI同士を対話させるようなレビュースタイルも紹介されました。

### コードフォーマッターの競合 — 「考えなくていい」状態を作る

コードフォーマッターの挙動がおかしいというissueについても方針が決まりました。このプロジェクトでは**Prettier**を導入しており、リポジトリの `.prettierrc` にルールを定義しているため、フォーマットルールはメンバー全員で共通のはずです。ところが、VS Code自体にも標準のフォーマット機能があり、この2つが別々にフォーマットを行おうとして**競合**し、人によって保存結果にばらつきが出ている疑いがあります。

「issueを単純に取り下げると、また誰かが同じ違和感に遭遇する」という理由から取り下げはせず、調査内容をまとめたメンバーがオーナーとなって、設定の整備とWikiへのナレッジ化を行うことになりました。アプリケーションの主題ではないため、READMEではなくWikiのナレッジとして残すという整理です。CIでのフォーマットチェックまで入れるかは意見が分かれ、「ローカルでチェックできれば十分」という声と「プッシュ時に余計な差分が出るならCIに入れた方がいい」という声の両方が出て、設定検討の中で判断することになりました。「フォーマッターは設定で全部解決して、何も考えなくていいようにしておきたい」という感覚は全員に共通していました。

このほか、リリース後のメンテナンスをこのチームで担っていく予定の新しいWebスキルアップサービスの紹介もありました。Next.jsとSupabaseはポータルサイトと共通ですが、コードフォーマッターにBiome、JavaScriptランタイムにBun、UIコンポーネントにshadcn/uiと、あえて異なる技術スタックを採用しており、新しい技術を学ぶ場としても期待されています。

## 活用した技術

### Zodによるバリデーションの共通化

**Zod**はTypeScript向けのスキーマバリデーションライブラリです。`z.string().refine()` のように標準のチェックにカスタム条件を重ねられ、`safeParse()` を使えば例外を投げずに成功/失敗を判定できます。

今回のポイントはライブラリそのものより「共通化」です。同じ「URLチェック」でも、ページごとに実装すると許可プロトコルやエラーメッセージが少しずつ食い違い、それ自体が小さな技術的負債になります。1つの関数に集約すれば、仕様変更（今回なら「HTTPSのみ許可」への統一）も1箇所の修正で全画面に行き渡ります。

### PostgreSQLのCHECK制約 — 最後の砦はデータベースで

`CHECK (url ~ '^https://')` の `~` は、PostgreSQLの正規表現マッチ演算子です。フロントエンドのバリデーションは、実装漏れやAPIの直接呼び出しですり抜けられる可能性がありますが、データベースのCHECK制約は**どの経路から来たデータにも必ず適用される**最後の砦になります。

注意点は、制約を追加する `ALTER TABLE` の実行時に**既存データもチェックされる**ことです。今回の実演でも、テスト環境に残っていた `http://` のURLが原因でエラーになりました。制約の追加は既存データのクレンジングとセットで計画する必要があります。また、マイグレーションファイルをリポジトリで管理していても、実際のデータベースへの適用は別途必要という運用面の理解も、チームで共有できた収穫でした。

### 論理削除とRLSポリシーの落とし穴

**論理削除**は、レコードをDELETEで物理的に消すのではなく、`is_deleted` のようなフラグで「削除済み」とみなす設計です。誤操作からの復元やデータの追跡が可能になる一方、システムから見れば削除処理は「ただのUPDATE」になります。

Supabaseの**RLS（Row Level Security）ポリシー**は、行単位でどんな操作を許可するかをデータベース側で制御する仕組みで、UPDATEにも「どの行なら更新してよいか」の条件を課せます。今回のバグは、「論理削除済みの行は更新させない」という編集保護のためのポリシーが、論理削除を行うUPDATEそのものまでブロックしてしまったという構図でした。論理削除を採用するシステムでは、「削除もUPDATEである」ことを前提に、ポリシーの条件と業務操作の組み合わせを洗い出しておくことの大切さを示す事例です。

## 総括

今回は、URLバリデーションの共通化という「フロントエンドとデータベースの二段構え」の実装が完了するとともに、技術的負債との向き合い方というチーム運営の根幹に関わるテーマを正面から議論した回でした。スピード優先でスルーしてきた指摘をissueとして可視化し、直すかどうかは担当者とレビュアーのすり合わせに委ねる——負債を「なくす」のではなく「見える化して管理する」という現実的な落とし所は、リソースの限られたコミュニティ開発ならではの知恵といえます。

また、AIレビューコメントの取捨選択をめぐる議論は、AI時代のチーム開発が直面する新しい課題そのものでした。AIの出力を理解せずに貼らない、人間同士のすり合わせを最後に残す、というチームの結論は、AIを活用しながら開発する多くの現場の参考になるはずです。論理削除とRLSポリシーの衝突バグやコードフォーマッターの競合など、宿題も見つかりましたが、いずれも原因の分析と担当の割り当てまで進んでいます。
