## 概要

本記事は、[チーム開発記録56：ver8リリースと脆弱性対応](https://zenn.dev/singularitylabs/articles/d5da071308d06b)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、ポータルサイトの開発と並行して、2026年6月から学習支援アプリ「sinlab-study」を隔週交互で開発しています。今回はsinlab-studyの回で、**管理画面から演習課題のヒントを入力・編集できる機能**がマージされました。これまでヒントはSQLでしか投入できなかったため、講師が管理画面だけでコンテンツを完結して作成できるようになる改善です。

会議では、AIレビュー機能のトークン消費を抑えるために「講座資料を渡すか、既存のヒントを渡すか」という議論が行われ、イシューを分割して優先順位を付け直しました。また、ポータルサイト側で設計中の**マスター管理画面**をめぐっては、「統合的な管理画面」と「CSVダウンロード＋バルク入稿」というシンプル案が正面からぶつかる白熱の議論に。曖昧なイシューをそのままアサインしないという運用ルールの見直しにまで発展した、プロセス改善の濃い回となりました。

## 開発したもの

### 演習課題のヒントを管理画面から入力・編集できる機能

sinlab-studyの課題提出ページには、受講生が行き詰まったときに開ける「ヒント」の表示機能があります。ところが、このヒントの中身はこれまでseed SQL（`UPDATE ... SET hint` 形式）でしか投入できず、講師が管理画面から課題を作成してもヒントだけは設定できないという片手落ちの状態でした。今回、コンテンツ管理画面（`/manage/contents`）のフォームと管理APIをヒントに対応させました。

フォーム側では、`useState` でヒント用の状態を1つ追加し、保存時のペイロードに `hint` を含めるようにしました。あわせて、各項目の空文字をトリムして `null` として保存するように整理しています。

```tsx
// app/(authenticated)/manage/contents/ContentForm.tsx（抜粋・変更後）
const [hint, setHint] = useState(initialData?.hint ?? "");

// 保存ペイロード（演習のときのみヒントを送信、未入力はnull）
video_url: contentType === "video" ? videoUrl.trim() || null : null,
text_content: contentType === "text" ? textContent.trim() || null : null,
exercise_instructions:
  contentType === "exercise" ? exerciseInstructions.trim() || null : null,
hint: contentType === "exercise" ? hint.trim() || null : null,
reference_answer: contentType === "exercise" ? referenceAnswer.trim() || null : null,
```

入力欄は、演習コンテンツの編集フォームで「演習指示」と「模範回答」の間に配置しました。プレースホルダーで表示位置や公開範囲まで説明しているのがポイントです。

```tsx
// app/(authenticated)/manage/contents/ContentForm.tsx（抜粋・追加箇所）
<div className="space-y-2">
  <Label htmlFor="hint">ヒント（受講生に公開）</Label>
  <Textarea
    id="hint"
    value={hint}
    onChange={(e) => setHint(e.target.value)}
    placeholder="課題提出フォームの上部にアコーディオン形式で表示されます。受講生向けのヒントを記述してください（Markdown記法は使えますが、レンダリングされずプレーンテキストとして表示されます）。未入力の場合はヒントUIを表示しません。"
    className="min-h-[200px] font-mono"
  />
</div>
```

サーバー側は、作成・更新の管理APIでリクエストボディから `hint` を受け取ってINSERT/UPDATE対象に含め、Supabaseアクセス層の関数の引数型にも項目を追加しました。

```typescript
// app/services/api/admin-server.ts（抜粋・変更後）
export async function createContent(content: {
  video_url?: string;
  text_content?: string;
  exercise_instructions?: string;
  hint?: string;
  reference_answer?: string;
  allowed_submission_types?: "code" | "url" | "both";
  code_language?: "javascript" | "typescript" | "html" | "css";
```

データベースには `hint` カラムが既に存在していたため、スキーマ変更は不要でした。担当したリードいわく「修正量は実はそんなに多くない」とのことで、状態管理の変数を1つ足し、フォームにラベル付きの入力欄を追加し、サーバー側に項目を通すという素直な実装です。設計書（`docs/specification.md`）にも、ヒントが管理画面で設定される演習専用項目であることを追記しました。

## 会議の様子

### AIレビューに何を渡すか — 講座資料よりまず「ヒント」

sinlab-studyには、提出された課題をAIがレビューする機能があります。以前からの懸念は**トークン消費量**で、今回は「生徒が課題を提出したら講座資料を自動的にAIへ渡す」というイシューの進め方が議題になりました。

あるメンバーからは、「PDFの講座資料をそのまま渡すのではなく、講座を登録する時点であらかじめAIに要約・整形させたものをデータベースに登録しておき、課題ごとに最適化した資料を渡すべきでは」という前処理案が出ました。リードも「PDFをそのまま渡すよりは断然よい」と同意しつつ、別の視点を提示します。**課題ページにはすでに「ヒント」というテキストデータがデータベースに存在している**ので、まずはそれをプロンプトに含めてAIに渡すのが、実装も簡単で理屈にも合うのではないか、という提案です。

議論の結果、「ヒントを渡す」対応と「講座資料を渡す」対応は目的が異なるため、**イシューを分割**することになりました。ヒント連携を優先度高として先に進め、講座資料の連携は「余計なデータを渡してかえってトークンを無駄にしないか」を比較検証するところから着手します。リードの言葉を借りれば、これは**「正確さとスピードとトークン消費量のバランス」**の問題です。なお、新しいイシューにはメインのレビュアーとサポート役の2人体制でレビューに入ることも確認されました。

### マスター管理画面の設計 — 統合管理画面かCSV入出力か

後半は、ポータルサイト側で設計を進めている**マスター管理画面**のレビューで大きく盛り上がりました。これは、管理画面を持たないテーブルのデータを一覧で確認・編集できるようにする画面で、前回の指摘を受けて、データベース上に専用の管理テーブルを設ける方式から、**型定義ファイルのカラム情報を参照する方式**へ設計書が見直されていました。

設計を担当したメンバーの課題意識は明確です。「表示順のような情報が画面に直接出てこないため、1件ずつ編集画面を開かないと確認できない。エクスポートもインポートもできないので、一覧を作るには全レコードを手作業でスプレッドシートに転記するしかない」。実際にコンテンツを最も多く登録しているメンバーだけに、実感のこもった問題提起でした。

これに対して別のメンバーからは、**「その目的ならCSVダウンロードとバルク入稿の機能を既存の編集画面に付ける方がシンプルではないか」「課題に対して手段が大きすぎる。要件定義の合意を取らずに詳細設計まで進んでいる」**という率直な指摘が入ります。統合的なマスター管理画面を作ろうとすると、どのカラムを編集可能にするかという設定ファイルがテーブルごとに必要になり、テーブルやカラムが増えるたびにメンテナンスが発生する、という設計上の重さも懸念されました。

リードのスタンスは「アプリが重くなるなどユーザーの不利益がなければ、作ること自体に反対はしない」というもの。ただし、更新日時のような人が触るべきでないカラムは参照のみに制限すること、個人情報を含むユーザーテーブルは対象外とすることを確認したうえで、**本質的な課題は「一覧で確認・編集したい」であり、フィルターやインポート・エクスポートなど必須でない機能は切り分けるべき**と整理しました。結論として、イシューを分割し、機能を絞る方向で設計書をアップデートすることになりました。

### 「1行のイシュー」をアサインしない — 要件確認のルール化

この議論は、開発プロセスの振り返りにも発展しました。そもそもの発端は、**「マスターテーブルの更新」というたった1行のお題目だけのイシュー**だったのです。担当メンバーが具体的に検討を始めたところ、膨大なタスクが見えてきて、設計がどんどん膨らんでいったという経緯でした。

そこで今後は、**曖昧なイシューをアサインする際は、ミーティングの場で「このイシューの要件は何か」を確認してから担当を決める。話しても曖昧さが解消できなければ、いったんアサインを見送る**というルールで運用することになりました。要件定義の合意を取ってから詳細な設計に進む、という順序をチームの進め方として定着させる狙いです。

一方でリードからは、「設計書としてまとめて出してくれたからこそ、これだけ多くの意見が出た。たたき台を作ったこと自体は良かった」というフォローもありました。実装コーディングだけでなく、**何を作り何を作らないかの取捨選択**も実務レベルのスキルアップとして磨いていこう、という前向きな締めくくりです。

### 今後の開発計画 — サムネイル管理・リリース自動化・dotenvx

このほか、sinlab-studyの今後の開発として3つのテーマが共有されました。1つ目は**学習テーマのサムネイル画像を管理画面からアップロードできる機能**です。現状、トップページに表示されるテーマのアイコン画像はリポジトリを更新しないと差し替えられず、新しいテーマを2つ追加したのに画像を設定できないという不便が実際に起きています。Supabase Storageに画像をアップロードする方式で、リードが実装を担当します。

2つ目は**本番環境へのリリース**です。反映のタイミングはまだ確定していないものの今月中を目標とし、あわせて「ポータルサイトで構築したリリース自動化の仕組みをsinlab-studyにも展開してはどうか」という話になりました。手作業によるミスの防止や属人化の解消という観点から、メンバーの賛同も得られています。

3つ目は**AI駆動開発におけるセキュリティ強化**として、dotenvxの導入を検討することになりました。ローカル開発で使っている環境変数ファイルからAIにAPIキーをうっかり漏洩させてしまうリスクへの対策で、こちらもリードが担当し、興味を示したメンバーがレビューに入ります。

## 活用した技術

### LLMに渡すコンテキストとトークン消費

ChatGPTやClaudeのようなLLM（大規模言語モデル）のAPIは、入力・出力の**トークン数**（テキストを細かく分割した単位）に応じて課金されます。AIレビューの精度を上げようとして講座資料のような大きなデータを毎回プロンプトに含めると、トークン消費が跳ね上がり、応答速度も低下します。

今回の議論で出た2つのアプローチは、この問題への典型的な対処法です。1つは**前処理**で、元資料を事前にAIで要約・整形しておき、実行時には軽量なテキストだけを渡す方法。もう1つは**既存の構造化データの再利用**で、すでにデータベースにある「ヒント」のような小さく的を絞ったテキストをそのまま渡す方法です。後者は追加の変換処理が不要でシンプルに実装できるため、「まずヒントから」という今回の判断は、コスト・精度・実装スピードのバランスを取った現実的な選択といえます。

### Supabase Storage — 画像をリポジトリの外で管理する

サムネイル画像をリポジトリ内の静的ファイルとして持つと、画像を1枚差し替えるだけでもコミットとデプロイが必要になります。コンテンツ運用のたびに開発フローが走るのは非効率で、まさに今回「テーマを追加したのに画像が置けない」という形で表面化しました。

**Supabase Storage**は、Supabaseが提供するオブジェクトストレージで、画像などのファイルをバケット単位で管理し、URLで配信できます。データベースと同じプラットフォーム上でアクセス制御（ポリシー）を設定でき、アプリからはSDK経由でアップロード・取得が可能です。管理画面からStorageに画像をアップロードする構成にすれば、**コンテンツの更新とコードのリリースを分離**でき、任意のタイミングで画像を差し替えられるようになります。

### dotenvxによる環境変数の保護

Node.js開発では、APIキーなどの秘密情報を `.env` ファイルに書いて `dotenv` で読み込むのが定番です。しかし `.env` は平文のテキストファイルであるため、AIコーディングツールにプロジェクトを読ませた際に中身がそのままAIへ送信されてしまうリスクがあります。

**dotenvx**は `dotenv` の後継にあたるツールで、`.env` ファイルの値を**暗号化した状態で保存**できるのが特徴です。復号用の秘密鍵さえ別管理しておけば、暗号化済みの `.env` ファイルはリポジトリに含めても値を読み取られません。AIにワークスペースを広く読ませるAI駆動開発が当たり前になりつつある今、「AIの目に触れても安全な形で秘密情報を置く」という観点でのセキュリティ強化は、多くのチームにとって参考になるテーマではないでしょうか。

## 総括

今回は、演習課題のヒントを管理画面から入力・編集できる機能がマージされ、講師が管理画面だけでコンテンツを完成させられる状態に一歩近づきました。SQLでしか触れなかったデータに画面を用意するという地道な改善ですが、運用のしやすさに直結する変更です。

会議では、マスター管理画面の設計をめぐって「統合的な管理画面」と「CSV入出力」という2つの案が正面からぶつかり、最終的に「本質的な課題は一覧での確認・編集」という共通認識に着地しました。さらに、1行だけの曖昧なイシューが設計の膨張を招いたという反省から、アサイン前に要件をミーティングで確認するというルールも生まれました。機能そのものより、**要件の合意形成という開発プロセスの根っこ**を鍛えた回だったといえます。

サムネイル管理やリリース自動化、dotenvxによるセキュリティ強化と、次回に向けたテーマも揃いました。sinlab-studyの本番リリースも近づいており、今後の展開が楽しみです。
