## 開発したもの

### 資料・動画の「責任者」をユーザー選択式に変更

これまで資料（documents）と動画（videos）の担当者欄は自由入力のテキストフィールドで、表記ゆれや実在しない名前の入力が起こり得る状態でした。今回の改修で、`users` テーブルを参照する**ID紐付けの選択式**に変更しました。フォームを開くとユーザー一覧を取得し、`Select` コンポーネントで選ぶだけになっています。

```tsx
// app/(authenticated)/documents/components/DocumentFormModal.tsx（抜粋・変更後）
useEffect(() => {
  const fetchUsers = async () => {
    const { data } = await supabase
      .from("users")
      .select("id, display_name")
      .order("display_name");

    if (data) setUsers(data);
  };

  fetchUsers();
}, []);
```

```tsx
// 同ファイル（抜粋・変更後）: TextInputからSelectへ
<Select
  label="責任者"
  data={
    users.map(user => ({
      value: String(user.id),
      label: user.display_name
    })) ?? []
  }
  value={form.assignee_id ? String(form.assignee_id) : ""}
  onChange={(value) => setForm(f => ({ ...f, assignee_id: value ? Number(value) : null }))}
  mb="sm"
/>
```

データ側も文字列の `assignee` カラムから `assignee_id` によるID参照に変わり、表示側では紐づくユーザーの `display_name` を表示するようになりました。定例の時点でレビュー・Approveまで完了しており、リードが最終確認のうえマージする段取りが確認されました。

## 会議の様子

### テストは「むやみに増やさない」— 要否判断基準を策定

今回の中心議題は、テスト仕様書に新設した「テストの要否判断」の節のレビューでした。前提となる考え方は、**テストをむやみに増やさない**こと。テストが増えるほどメンテナンスは大変になり、コードを修正するたびにテストも書き換える手間が発生するため、「やった方がいいところ」に絞って追加していくという方針です。

具体的にテスト対象とするのは、次の3つに該当するコードです。

* **認証・認可のロジック** — ここが崩れるとセキュリティリスクに直結するため
* **複数箇所から呼ばれる共通ユーティリティ** — 影響範囲が広く、壊れたときのリスクが高いため
* **外部APIとの連携**（Slack通知やカレンダー連携など） — 障害の原因になりやすいため

一方、見た目やDBアクセス、データの型定義などは、型チェック・Lint・ビルドチェックで担保されているため**原則テスト不要**とし、迷ったらチームで相談する運用としました。この基準に照らすと既存のテストにも「実は不要」なものが結構あることが分かりましたが、今すぐ消すことはせず、運用しながら判断していくことになりました。

レビュアーからは「テストコードの修正は難しく、そのためにプルリクエストのレビューが滞って開発スピードが落ちることはすでに起きている。**難しい場合はテスト部分だけ別の担当者に移して、一人で抱え込まない対応も必要**」という運用面の指摘があり、方針に盛り込まれました。実際に、DBのカラム定義変更でテストの型チェックがNGになり、別のメンバーがテストコード側を修正して解消した事例も共有され、「カラムが増えるたびにテストを直すのは不便この上ない。モックが細かすぎないかは今後見直す」という反省も出ています。

議論が最も割れたのは**Supabaseの位置づけ**です。「この基準だと `users-server.ts` のようなDBアクセス関数はテスト対象ですか？」という質問に対し、Supabaseを外部APIとみなせば対象になる一方、「データベース関連を全部対象にすると、コードの8割がテスト対象になってしまう」という問題があります。最終的に、**SupabaseへのアクセスはRLSポリシーで既にチェックされているため原則テスト対象外とし、認証系のテーブルアクセスのみ対象とする**旨をコメントとして明記することになりました。あわせて、プルリクエストのテンプレートにも「テストの更新が必要か確認する」という項目を追記する予定です。

### マイグレーションの初期データは残すか、消すか

次のタスクを探していたメンバーが見つけたのは、「マイグレーションファイル内のデータ追加コマンドを削除する」という古いissueでした。カテゴリーテーブルの作成SQLに初期データのINSERTが含まれており、これを消すべきかという論点です。

議論では「未分類カテゴリーは必須ルールになっているので最低限残すべき」「現状の初期値は実データと不整合を起こしている」という整理が行われた一方、「これはあくまで**初期構築時のパラメーター**であって、その後のデータ管理はマイグレーションではなく通常の運用で行うもの。初期値として残しておき、後からのメンテナンスはしない、で良いのでは」という意見が出ました。設計書に初期データの説明を書くかどうかも話題になりましたが、「設計仕様書はアプリ自体がどんなものかを説明するもので、入っているデータの説明までは不要」と**目的ベース**で判断し、現状維持のままissueをクローズする結論になりました。

### コンフリクト地獄からの脱出 — git rebaseライブ解説

URLバリデーション機能を担当しているメンバーから、「実装は終わったが、マージ時にコンフリクトが発生し、リベースに失敗して止まっている」という報告がありました。AIに聞きながら進めたものの、どんどんドツボにはまってしまったとのことです。これを受けて、定例の最後に画面共有をつなぎながら**リベースのライブ解説**が行われました。

解説では、まず「今、リポジトリがどういう状態で、これから何をしようとしているのかを自分の頭でイメージできることが大事」という心構えから始まり、mainブランチの最新化 → 作業ブランチで `git rebase main` → コンフリクト箇所を目視で判断して修正 → `git add` でステージング → `git rebase --continue`、という一連の流れを実際のコンフリクトを解消しながら確認しました。別のメンバーからは「リベースがややこしくなりすぎたら、無理に最後までやり切らず、**新しくブランチを切り直して変更を持っていく方がコミット履歴が綺麗になる**」という実戦的な代替策も共有されました。

また、この機能に関連して「クライアント側だけでなく、Supabase側でもSQL制約によるバリデーションは必要ないのか」という質問も挙がりました。リードからは「非常に大事な指摘。今回のクライアント側バリデーションはこれで大事なのでこのままマージし、**サーバー側のバリデーションは別タスクとして追加で対応してほしい**」という回答があり、多層防御の考え方が共有されました。

### AI活用の裾野が広がる

今回はAIに関する話題も多く出ました。役割タグの編集機能では**AI駆動開発**でプルリクエスト作成まで進めたメンバーがいた一方、別のメンバーからは「VS Codeで勝手に修正候補が提示されてダブルクリックすると直る機能は何なのか」という素朴な疑問も。「GitHub Copilotなど何かしらのAIが裏で動いているはず。VS Code自体がAIエディターに寄っていて、勝手に直してくれる機能は今後も増えていくだろう」「みんな結構手探りでやっている」というやり取りがあり、AIツールとの付き合い方をチーム全体で模索している様子がうかがえました。

また、論理削除したレコードの復活機能を新たに担当するメンバーは、Claude Codeの従量課金プランを契約してAI活用で実装に挑戦する方針を表明。Wikiの導入ガイドを参照しながらセットアップから始めることになりました。リード自身も、シンラボ会員向けに開発中のWeb学習サービスをポータルサイトのログイン機能とJWT（JSON Web Token）で連携させる実装を優先して進めると共有しています。

## 活用した技術

### リスクベースのテスト戦略 — 「全部書く」より「どこに書くか」

ユニットテストは多ければ多いほど良いと思われがちですが、テストコードもプロダクトコードと同じく保守対象です。仕様変更のたびに大量のテストを書き換える状態になると、開発スピードが落ち、テストが形骸化する原因になります。今回チームが策定した基準は、**壊れたときの被害が大きい箇所（認証・認可）、影響範囲が広い箇所（共通ユーティリティ）、壊れやすい箇所（外部API連携）に絞る**という、いわゆるリスクベースのアプローチです。

型チェックやLint、ビルドチェックといった静的検査で担保できる領域はそちらに任せ、ユニットテストは静的検査で捉えられないロジックの検証に集中させる。テストの手段ごとに役割分担を決めることで、少ないテストで高い安心感を得るのが狙いです。

### copilot-instructions.md — AIエージェントへの「プロジェクト説明書」

`.github/copilot-instructions.md` は、GitHub Copilotにとって特別な意味を持つファイル名で、リポジトリに置いておくとCopilotのコードレビューやAgent機能が自動的に読み込んでくれます。Claude Codeにおける `CLAUDE.md` と同じ役割で、プロジェクトの技術スタック、コーディング規約、参照すべき設計書などを記述しておくことで、AIの出力をプロジェクトの文脈に沿ったものにできます。

今回の整備では、レビュー指摘をP0（セキュリティ・認可）からP3（任意の改善提案）まで重要度で分類させるルールを入れているのがポイントです。AIレビューは指摘の量が多くなりがちなので、優先度を付けさせることで「どれから直すべきか」が判断しやすくなります。なお、AIが常にWikiを参照できるとは限らないため、必須ルールはこのファイルに要約転記し、差分が出たらWikiを正として更新するという二重管理対策も明文化されています。

### git rebase — ブランチの付け根を付け替える

`git rebase main` は、自分の作業ブランチのコミット群を、最新のmainブランチの先端に「付け替える」操作です。自分がブランチを切った後にmainが進んでいる場合、両者が同じファイルの同じ行を変更しているとGitはどちらが正しいか判断できず、**コンフリクト**が発生します。

リベース中にコンフリクトが起きたら、（1）該当箇所を人間が判断して修正、（2）`git add` でステージング、（3）`git rebase --continue` で再開、という手順を繰り返します。途中でやめたくなったら `git rebase --abort` でリベース前の状態に戻せます。今回の解説でも強調されたように、コンフリクトが多発して収拾がつかなくなったときは、綺麗なブランチを切り直して変更を移し替える方が結果的に履歴も作業も綺麗になることがあり、状況に応じた使い分けが重要です。

## 総括

今回は、テストの要否判断基準という「書くコード」ではなく「書き方のルール」を固める回となりました。テストをむやみに増やさず、リスクの高い箇所に集中させるという基準は、テスト導入初期のチームが陥りがちな「テスト疲れ」を予防する現実的な落とし所だと言えます。Supabaseの位置づけをめぐる議論のように、原則を作ったうえで例外を明文化していくプロセスも、チームの共通認識を育てる良い機会になりました。

また、責任者入力のID参照化やCopilot指示書の整備といった着実な改善に加え、リベースのライブ解説では、つまずいたメンバーの疑問をその場で全員の学びに変えるこのチームらしい光景が見られました。AI駆動開発に挑むメンバーも増えており、次回以降のカテゴリー管理機能の実装が楽しみです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
