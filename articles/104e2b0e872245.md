## 概要

本記事は、[チーム開発記録37：テスト設計とSNSリンク機能](https://zenn.dev/singularitylabs/articles/fc8471a3086898)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回はいよいよ**ver6.0.0の本番リリース**が完了しました。カレンダー機能、メンバー役職タグ、SNSアカウント連携、コンテンツ表示順管理、説明文のMarkdown対応と、これまで数ヶ月かけて開発してきた機能がまとめて本番環境に反映されています。あわせて、資料一覧ページへの**詳細モーダルの追加**もマージされました。

## 開発したもの

### ver6.0.0を本番リリース

ポータルサイトの第6弾リリースが完了しました。今回のリリースに含まれる主な新機能は次のとおりです。

* **カレンダー機能** — Google Calendar API連携によるイベント表示、前後3ヶ月の先読み取得、色分け表示
* **メンバー役職タグ表示** — positions / position_tags テーブルを新設し、メンバー一覧・詳細モーダルに役職タグを表示
* **SNSアカウント連携** — usersテーブルにSNS URLカラムを追加し、プロフィール画面での入力とメンバー詳細への表示に対応
* **コンテンツ表示順管理** — 資料・動画・アプリの表示順操作機能と処理の共通化
* **説明文のMarkdown対応** — コンテンツ説明文をMarkdownで表示

このほか、サイドバー構成の見直しやRLSポリシーの追加、セキュリティパッケージの更新などの改善・バグ修正も含まれています。機能一覧はGitHubのリリースタグ（v6.0.0）に整理し、リリース手順自体もWikiの「本番環境リリース手順」ページに文書化されています。

### 資料カードに詳細モーダルを追加

資料一覧ページの各カードにあった「資料を開く」ボタンを「詳細」ボタンに変更し、クリックすると資料の詳細情報を表示するモーダルが開くようにしました。すでに実装済みだったアプリ紹介ページの詳細モーダルを参照しながら、担当メンバーが実装したものです。

ポイントは、どの資料が選択されているか・モーダルが開いているかという**状態（ステート）を、一覧ページのテンプレートコンポーネントで一元管理**している点です。

```tsx
// app/(authenticated)/documents/components/Template.tsx（抜粋）
const [selectedDocument, setSelectedDocument] = useState<DocumentWithCategoryType | null>(null);
const [modalOpened, setModalOpened] = useState(false);

const handleDetailClick = (document: DocumentWithCategoryType) => {
  setSelectedDocument(document);
  setModalOpened(true);
};

const handleModalClose = () => {
  setModalOpened(false);
  setSelectedDocument(null);
};
```

カードコンポーネントには `onDetailClick` というコールバックを渡し、詳細ボタンのクリックでモーダルが開く仕組みです。モーダル本体では資料名・詳細説明（Markdown対応）・カテゴリーを表示し、そこから元の資料をGoogleドライブで開けます。

```tsx
// app/(authenticated)/documents/components/DocumentDetailModal.tsx（抜粋）
export function DocumentDetailModal({ document, opened, onClose }: DocumentDetailModalProps) {
  if (!document) return null;

  return (
    <Modal opened={opened} onClose={onClose} title="資料詳細" size="lg" centered>
      <Stack gap="md">
        <h2 className="text-2xl font-bold">{document.name}</h2>
        {/* 詳細説明（Markdown表示）とカテゴリーバッジは省略 */}
        <Button
          color="#000"
          fullWidth
          component="a"
          href={document.url}
          target="_blank"
          rel="noopener noreferrer"
          rightSection={<ExternalLink size={16} />}
        >
          資料を開く
        </Button>
      </Stack>
    </Modal>
  );
}
```

あわせて機能設計書（`docs/specification.md`）も更新し、資料カードとモーダルの表示項目・画面レイアウトを明文化しました。

### 新規登録フォームの説明文欄を5行に拡張

動画・資料・アプリの新規登録／編集フォームで、説明文の入力欄が狭くて書きにくいという課題に対応しました。3つのフォームコンポーネントに `rows={5}` を追加するだけの小さな修正ですが、Markdown対応で説明文が長くなりがちな今、入力体験に効く改善です。

```diff
// app/(authenticated)/documents/components/DocumentFormModal.tsx（抜粋・動画/アプリも同様）
         value={form.description}
         placeholder="文字数は70文字以内にしてください。"
         onChange={e => setForm(f => ({ ...f, description: e.target.value }))}
+        rows={5}
         mb="sm"
```

## 会議の様子

### カテゴリー削除は「未分類」への移動で対応

進行中のカテゴリー追加・編集・削除機能の設計では、**削除時に既存コンテンツをどう扱うか**が論点になりました。カテゴリーは論理削除ですが、そのまま削除すると紐づくコンテンツまで見えなくなってしまいます。

議論の中で「依存コンテンツがあるカテゴリーは削除できないようにする」「対象コンテンツを一覧表示する」といった案も出ましたが、最終的には**削除時にコンテンツを「未分類」カテゴリーへ移動する**方針に決まりました。実装面では、未分類カテゴリーのIDをコードに埋め込むのではなく、**カテゴリータイプと名前で検索して特定する**方法を採用します。実際にテーブル定義を確認し、カテゴリーテーブルに論理削除用のカラムが存在することもその場で確かめました。「設計書は実態ではないので、実際のテーブルを確認すべき」という指摘も、このチームらしい進め方です。

### 表示順が「null」になる問題 — バグかデータ不備か

リードから、コンテンツ編集画面の表示順の番号が途中から「null」になっているという報告がありました。原因はすぐに判明します。**表示順の登録機能がなかった時期に追加されたコンテンツは、表示順カラムが未設定（null）のまま**だったのです。アプリのコードの問題ではなく、データ側の問題でした。

ここから「そもそもnullは悪なのか」という設計論に発展します。表示順の設計を担当したメンバーからは「カテゴリー内で順不同ならnullを許容する設計だった。データを直す必要はなく、表示側でnullなら非表示やハイフンにすれば十分では」という意見が出ました。一方で、現在の実装では表示順を操作すると**同じカテゴリー内の番号が自動的に振り直され、nullも含めて再定義される**仕組みがすでに入っていることも確認されました。

「1回編集したらカテゴリー内のnullを全部自動で埋める機能を追加する」という案も出ましたが、「それが必要なのは今だけ。**1回実行したら二度と使わない機能を実装するのは良くない**」という指摘で見送りに。最終的には、既存の編集機能を使って手作業でnullを埋めたうえで、**表示順カラムにNOT NULL制約を追加する**方針で合意しました。新規登録時には表示順が自動付与されるため、今後nullが入り込む余地はなくなります。

### エビデンスはどこまで残すべきか

このデータ修正を誰がどう記録するかをめぐって、今回いちばん白熱した議論が起きました。「メンテナンス後のエクスポートデータや画面キャプチャを証拠として残すべき」という意見に対し、「メンテナー権限があれば誰でもアプリを見に行けば分かる。**意味のないことはしたくない**」という反対意見が真っ向からぶつかったのです。

議論の中では「イシューはパブリックなので、動画や資料のURLが見える形で貼るのは正会員限定コンテンツの流出になる」というセキュリティ観点の指摘もありました。SELECTクエリで「nullが0件」という結果だけを見せる案も出ましたが、突き詰めれば**記録をどこまで残すかは各人の開発スタイルの好みの問題**であり、チームとしてどこに統一するかという話だと整理されます。

最終的な着地点は、「画面キャプチャなどの証拠は必須にしないが、**原因・対応方針・対応結果は後から検索できるようにイシューへ明記する**」というものでした。今後同じような事象が起きたときにすぐ解決策へたどり着けるようにする、という記録の目的に立ち返った判断です。

### リリース作業のCI/CD化を見据えて

ver6のリリース報告に関連して、「本番リリースの前に、同じ手順で検証リリースをやるべきでは」という問題提起がありました。現在の本番リリース手順はテスト環境で作ったものを本番に再現する形のため、そのまま検証環境でもう一度やる意味は薄いという意見もありましたが、根本的な解決策として**本番リリースをGitHub ActionsによるCI/CDで自動化すべき**という方向で一致しました。

マイグレーションの実行やVercelへの環境変数設定、承認ステップの組み込みなど課題は多く、「いきなり全部を作るのではなく、1個1個のステップをボタンで自動実行できるものを徐々に作り、最後に連結させる」という段階的なアプローチでイシュー化されました。テスト仕様書がまとまれば、プルリク前のE2Eテスト実施も視野に入ってくる長期テーマです。

このほか、詳細モーダルを資料とアプリで共通化する案は「画像の有無など構造が違い、無理に共通化すると変な条件分岐が必要になる」として見送り、新しいタスクとして**ホーム画面に本日のカレンダーイベントを表示する機能**を割り当てました。プルリク作成時にはアサイニーに自分を設定する、という運用ルールの確認も行われています。

## 活用した技術

### Reactのステートリフトアップによるモーダル制御

今回の詳細モーダルでは、「どの資料が選ばれたか」「モーダルが開いているか」という状態を、カードやモーダル自身ではなく親のテンプレートコンポーネントで `useState` により管理しています。子のカードコンポーネントには `onDetailClick` というコールバック関数をpropsとして渡し、クリックイベントを親へ通知する——これはReactの定番パターンである**ステートの巻き上げ（リフトアップ）**です。

状態を1箇所に集約することで、「一覧のどのカードから開いてもモーダルは1つだけ」「閉じたら選択状態もリセットする」といった制御がシンプルに書けます。既存のアプリ紹介ページと同じ構造を踏襲したことで、コードベース全体の一貫性も保たれました。

### NOT NULL制約と多層バリデーション

表示順問題の再発防止策として採用したのが、データベースの**NOT NULL制約**です。アプリ側で自動付与の仕組みが入っていても、過去のデータ移行や手作業のメンテナンスでnullが混入する可能性はゼロにできません。「仕組み上入らないことが確定しているなら、制約としても明示する」——フロントエンドとバックエンド（データベース）の両方でバリデーションをかける多層防御の考え方は、今回の議論でも「そのほうが安全」と支持されました。

一方でカテゴリー削除の設計では、物理削除ではなく**論理削除**（削除フラグによる非表示化）を基本とし、依存コンテンツは「未分類」へ退避させます。制約で守るデータと、運用でカバーするデータの線引きを考えるよい題材になりました。

### GitHub ActionsによるリリースのCI/CD化

CI/CD（継続的インテグレーション／継続的デリバリー）は、ビルド・テスト・デプロイといった一連の作業を自動化する仕組みです。現在のポータルサイトのリリースは、Wikiに文書化された手順を人間が実行していますが、マイグレーション適用や環境変数設定などステップが多く、ミスの入り込む余地があります。

会議で確認されたとおり、GitHub ActionsからSupabaseのAPIを叩く構成にすれば多くのステップは自動化可能です。ただし一気に作り込むのではなく、個々のステップを独立して自動実行できる部品として整備し、最後にパイプラインとして連結する——という段階的な戦略を採りました。手動手順の文書化 → 部分自動化 → 完全自動化という進化の途中経過として、今後の記録でも追いかけていきます。

## 総括

今回は、数ヶ月にわたる開発の成果をver6.0.0として本番リリースできた節目の回でした。カレンダー、役職タグ、SNS連携、表示順管理、Markdown対応と、ポータルサイトの使い勝手を大きく変える機能が一気に利用者へ届いています。

一方で会議では、表示順のnull問題を入口に「使わない機能は作らない」「エビデンスは目的に立ち返って必要な分だけ残す」「制約はデータベースにも明示する」といった、開発チームとしての価値観をすり合わせる議論が続きました。意見が対立しても、好みの問題と設計の問題を切り分けて着地点を探るプロセスこそ、チーム開発の醍醐味といえます。次はver7に向けて、カテゴリー管理機能やリリース自動化が動き出します。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
