## 開発したもの

### 会員一覧ページへの役職固定表示

会員一覧ページの上部に、代表・副代表・シンラボ管理人の3役を専用セクションとして固定表示し、それ以外のメンバーは従来通り名前順のカード一覧として下部に表示するようにしました（[PR #386](https://github.com/Singuralitylabs/portal-site/pull/386)）。

対象となる役職IDは定数として切り出されています。

```typescript
// app/constants/positions.ts
// 「会員」ページ上部の役職者セクションで、データベースから抽出表示する position_id
// 8は代表, 9は副代表, 10はシンラボ管理人に該当
export const LEADERSHIP_POSITIONS_IDS = [8, 9, 10] as const;
```

この定数を使って、役職者セクションと一般メンバーセクションを描き分けています。

```tsx
// app/(authenticated)/members/components/Template.tsx
const isLeadershipMember = (member: MemberType) =>
  member.position_tags.some(
    tag => tag.positions != null && LEADERSHIP_POSITIONS_IDS.some(id => id === tag.positions?.id)
  );

export function MembersPageTemplate({ members, positions }: MembersPageTemplateProps) {
  const sortedMembers = members.sort((a, b) => a.display_name.localeCompare(b.display_name, "ja"));
  const generalMembers = sortedMembers.filter(member => !isLeadershipMember(member));

  return (
    <>
      <div className="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 2xl:grid-cols-4 gap-6 mb-16 px-4">
        {LEADERSHIP_POSITIONS_IDS.map(id => {
          const positionMembers = members.filter(member =>
            member.position_tags.some(tag => tag.positions?.id === id)
          );
          const label = positions.find(position => position.id === id)?.name ?? "";

          return (
            <div key={id}>
              <Title order={3}>{label}</Title>
              <div className="flex flex-col gap-4 mt-4">
                {positionMembers.map(member => (
                  <MemberCard key={member.id} member={member} />
                ))}
              </div>
            </div>
          );
        })}
      </div>
      {/* 以下、一般メンバー向けのグリッド表示が続く */}
    </>
  );
}
```

三役に相当する `positions` レコードもマイグレーションで新規追加されましたが、IDを明示指定してINSERTしたことでシーケンスがずれてしまう落とし穴があり、追って修正マイグレーションが必要になりました。

```sql
-- supabase/migrations/01_tables/positions/02_insert_leadership_positions.sql
-- 会員一覧の役職者セクション（代表・副代表・シンラボ管理人）用データ追加
-- id 8, 9, 10 はアプリケーションコードで参照する予約済みID（docs/database.md §2.6 参照）
INSERT INTO positions (id, name, display_order, is_deleted)
VALUES
  (8,  '代表',           8,  FALSE),
  (9,  '副代表',         9,  FALSE),
  (10, 'シンラボ管理人', 10, FALSE);
```

```sql
-- supabase/migrations/01_tables/positions/03_fix_positions_id_seq.sql
-- 02_insert_leadership_positions.sql で id を明示指定して INSERT したため、
-- positions_id_seq が実データ（最大id=10）に追従しておらず、次の自動採番insertが
-- 既存の予約済みID（8, 9, 10）と重複しうる状態になっている。
-- シーケンスの現在値を実データの最大idに同期させる。
SELECT setval('positions_id_seq', (SELECT MAX(id) FROM positions));
```

### プロフィール画像アップロードのセキュリティ強化

拡張子やHTTPリクエストの `Content-Type` は容易に偽装できるため、ファイル実体の先頭バイト列（マジックバイト）を検証してからアップロードする対応が行われました（[PR #403](https://github.com/Singuralitylabs/portal-site/pull/403)）。

```typescript
// app/api/profile/image/route.ts
function detectMimeFromBuffer(buf: Buffer): string | null {
  if (buf.length >= 3 && buf[0] === 0xff && buf[1] === 0xd8 && buf[2] === 0xff) return "image/jpeg";
  if (
    buf.length >= 8 &&
    buf[0] === 0x89 &&
    buf[1] === 0x50 &&
    buf[2] === 0x4e &&
    buf[3] === 0x47 &&
    buf[4] === 0x0d &&
    buf[5] === 0x0a &&
    buf[6] === 0x1a &&
    buf[7] === 0x0a
  )
    return "image/png";
  if (
    buf.length >= 6 &&
    buf[0] === 0x47 &&
    buf[1] === 0x49 &&
    buf[2] === 0x46 &&
    buf[3] === 0x38 &&
    (buf[4] === 0x37 || buf[4] === 0x39) &&
    buf[5] === 0x61
  )
    return "image/gif";
  return null;
}
```

申告された `Content-Type` ではなく、この関数が検出したMIMEタイプでホワイトリスト判定・アップロードを行うことで、拡張子偽装によるファイルアップロードを防いでいます。あわせて、これまで手動でクエリパラメータにタイムスタンプを付与していたキャッシュ回避策も廃止し、Storageアップロード時に `cacheControl: "0"` を指定する方式へ整理されました。

### CIを不安定にしていた型定義の差分を分離

`database.types.ts` に含まれる `PostgrestVersion` の値が環境差で意図せず更新され、CIが赤くなる問題が発生していました。原因を切り分けるため、この1行だけを戻す専用のプルリクエストで緊急対応されました（[PR #437](https://github.com/Singuralitylabs/portal-site/pull/437)）。

```diff
  export type Database = {
    __InternalSupabase: {
-     PostgrestVersion: "14.17";
+     PostgrestVersion: "14.5";
    };
```

## 会議の様子

### レビュー運用をめぐる議論

今回の定例では、プルリクエストのレビュー運用について活発な議論がありました。きっかけは、レビュアーが一度承認したプルリクエストに対して、司会がその場で軽微な修正を依頼し、修正後にレビュアーの再承認を経ずにマージしてしまったケースが複数件あったことです。

これに対し、あるメンバーから「レビュアーが未解決のまま議論を続けている状態でマージされると困る」「修正内容が些細であっても、レビュアーが最終確認する機会は必要」といった懸念が示されました。議論の結果、承認後に修正が入った場合は、内容の大小にかかわらずレビュアーの再確認を経てからマージする、という運用に統一することになりました。

あわせて、プルリクエストの粒度についても意見が交わされました。1つのIssueに複数の修正が混在すると衝突が起きやすいため、プルリクエストはできる限り分割すべきという意見に対し、コミット単位であれば十分という意見もあり、最終的には「プルリクエストは分けた方がよいが、コミット単位まで分けるかは担当者とレビュアーの判断に委ねる」という緩やかな指針でまとまりました。あわせて、AIエージェントがレビューする際にはコミットが分かれている方が理解しやすいのではないか、という論点も挙がりました。

### 役職固定表示のデータ設計をめぐるやり取り

役職固定表示の実装過程では、役職マスタにid番号を直接指定してINSERTしたことについて懸念が示されました。Supabase（PostgreSQL）は自動採番用のシーケンスを内部に持っており、id番号を明示的に指定してレコードを追加すると、テーブル上のid自体は登録できてもシーケンスの現在値が追従しないため、次に自動採番でレコードを追加しようとした際にid重複エラーが発生しうる、という指摘です。この点は、シーケンスの現在値を実データの最大idに同期させる追加マイグレーションで解消されました。

なお、この機能は実装・マージ後の動作確認で、役職を変更して保存しても会員一覧ページの表示に反映されないという不具合が見つかり、原因調査が持ち越しとなりました。

### その他の共有

マスター管理画面の参照機能追加や、会員テーブルの情報が露出しやすい設計になっていた点のセキュリティ修正など、複数のタスクが並行して進行中であることが共有されました。また、サブプロジェクトのシンラボスタディについては、溜まっていたIssueを担当者がまとめて巻き取り、短期間での完了を目指して進めている状況が報告されました。終盤には、メンバーが個人開発で新しい技術スタック（TanStack StartやCloudflare、Drizzle ORMなど）を試している話も共有され、和やかな雰囲気で会が締めくくられました。

## 活用した技術

### Supabase（PostgreSQL）のシーケンスと自動採番

INSERT文でid列に値を明示指定すると、そのテーブルに紐づくシーケンス（例: `positions_id_seq`）の現在値には影響しません。そのため、明示指定でid=10まで登録した直後に自動採番のINSERTを行うと、シーケンスはid=10未満の値を返し続け、既存レコードとのid重複エラーが発生します。今回のように「あらかじめ決まったIDでマスタデータを投入する」場合は、`setval` 関数でシーケンスの現在値を実データの最大idに同期させる後続マイグレーションが必須になります。

### マジックバイトによるファイル形式検証

HTTPリクエストの `Content-Type` ヘッダーやファイルの拡張子は、クライアント側で自由に書き換え可能なため、これらだけを根拠にアップロードを許可すると、偽装された不正なファイルを受け入れてしまうリスクがあります。マジックバイト検証は、ファイル実体の先頭数バイトに含まれる固有のシグネチャ（JPEGなら `FF D8 FF`、PNGなら `89 50 4E 47 0D 0A 1A 0A` など）を直接読み取って形式を判定する方式で、申告情報に頼らずファイルの実体を確認できます。

### Next.jsのServer Componentsでの並列データ取得

会員一覧ページでは、会員データと役職マスタという2つの独立したデータ取得を `Promise.all` でまとめて実行しています。

```typescript
// app/(authenticated)/members/page.tsx
const [{ data, error }, { data: positions }] = await Promise.all([
  fetchActiveUsers(),
  fetchActivePositions(),
]);
```

依存関係のないリクエストを直列に `await` するのではなく並列化することで、ページの初期表示までの待ち時間を短縮できます。
