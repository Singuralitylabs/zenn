## 開発したもの

### RLSポリシーの共通ヘルパー関数化

各テーブルのRLS（Row Level Security）ポリシーで何度も繰り返されていたユーザー条件判定の `EXISTS (SELECT 1 FROM users ...)` を、2つの共通関数に集約するリファクタリングがマージされました。

```sql
-- supabase/migrations/03_functions/rls_helper_functions.sql（抜粋）
-- 現在のユーザーがアクティブかつ未削除のユーザーかを判定する
CREATE OR REPLACE FUNCTION is_active_user()
RETURNS BOOLEAN
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = public, pg_catalog
AS $$
BEGIN
  RETURN EXISTS (
    SELECT 1 FROM users
    WHERE
      auth_id = auth.uid()
      AND status = 'active'
      AND is_deleted = FALSE
  );
END;
$$;
```

これにより、各テーブルのポリシー定義は大幅にシンプルになりました。たとえばアプリ紹介（applications）テーブルのINSERTポリシーは次のように変わっています。

```sql
-- supabase/migrations/04_policies/applications_policies.sql（抜粋・変更前）
  WITH CHECK (
    EXISTS (
      SELECT 1 FROM users
      WHERE
        auth_id = auth.uid()
        AND role IN ('admin', 'maintainer')
        AND status = 'active'
        AND is_deleted = FALSE
    )
  );
```

```sql
-- supabase/migrations/04_policies/applications_policies.sql（抜粋・変更後）
  WITH CHECK (
    is_active_user() AND is_content_manager()
  );
```

条件の意味が関数名で読み取れるようになり、今後ポリシーを追加・修正する際も同じ条件を書き間違えるリスクがなくなりました。

### Supabase DB Types整合性チェックの有効化

以前は環境設定が未完了でコメントアウトされていた「Supabase DB Types Consistency」ワークフローが、正式に有効化されました。CI上でSupabase CLIによる型生成を実行し、コミット済みの型定義ファイルと差分（ドリフト）があればエラーにする仕組みです。

```yaml
# .github/workflows/db-types.yml（抜粋）
      # Supabase CLIで public スキーマから TypeScript 型を生成し、型定義ファイルへ出力
      - name: Generate Supabase database types
        env:
          # Supabase CLI認証に使用するトークン（GitHub Secrets）
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
        run: |
          npm run db:types

      # 生成結果とコミット済みファイルとの差分を確認し、ズレがあればCIを失敗させる
      - name: Check for drift in generated types
        run: |
          if ! git diff --quiet app/types/lib/database.types.ts; then
            echo "::error::database.types.ts がsupabaseスキーマの型定義と一致していません。"
            echo "::error::npm run db:types を実行後、再度コミット・プッシュしてください。"
            git diff -- app/types/lib/database.types.ts
            exit 1
          fi
        shell: bash
```

SecretsやVariablesが未設定の場合には「どこで値を確認し、どこに設定するか」を案内するエラーメッセージを出す親切設計になっているほか、fork由来のプルリクエストではSecretsが使えないためジョブをスキップする条件も入っています。

### カテゴリー管理APIのコード品質改善

前バージョンで実装したカテゴリー管理機能について、コード品質を改善するリファクタリングがマージされました。カテゴリーの表示順（display_order）を付け替える処理が `Promise.all` による並列更新になっていたのを、順次更新に改めています。

```typescript
// app/services/api/categories-client.ts（抜粋・変更後）
  for (const category of affectedCategories) {
    const { error } = await supabase
      .from("categories")
      .update({ display_order: category.display_order + 1 })
      .eq("id", category.id);

    if (error) {
      throw new Error(`表示順更新に失敗しました(id: ${category.id}): ${error.message}`);
    }
  }
```

表示順の付け替えは順番どおりに実行されることに意味がある処理のため、並列実行による衝突を避けて1件ずつ更新し、失敗時には対象IDつきの例外を投げるようにしました。あわせて、取得系クエリのエラーハンドリング追加と、登録・更新処理のJestユニットテストの拡充も行われています。

## 会議の様子

### Wikiは「レビューなしで書ける」からこそルールを決める

今回の中心議題はGitHub Wikiの運用でした。発端は本番リリース自動化のドキュメントに関する「Wikiはリポジトリには入らないのか？」という質問です。Wikiにはページごとのコミットログ（リビジョン）が残るものの、普段開発しているコードのリポジトリとは独立して管理されている、という基本が全員で確認されました。

その後、RLSポリシー共通化の完了報告の中で「この作業のナレッジをWikiのナレッジ共有ページに追加すべきか」という質問が出たことから、議論はWiki全体の運用ルールへと発展します。リファクタリング自体にナレッジは不要だろうという結論になった一方で、**そもそもナレッジ共有ページの運用ルールを決めていなかった**ことが浮き彫りになりました。

ナレッジ共有については、「残そうと思ったら自由に書いてよい」スタイルで合意しました。「統一したRLSポリシーのナレッジをAIが読めば、ポリシーに反するコードを書いたときに指摘してくれるのでは」という活用への期待も挙がっています。ただし、パブリックリポジトリのWikiは**世界中に公開されている**ことを意識して書くこと、追加したらSlackで共有することが確認されました。

一方、ガイド・規約系のページをめぐっては意見が分かれました。リードの「無断更新はせず、ミーティングやSlackで確認を取ってから反映したい」という提案に対し、別のメンバーからは「ドキュメント管理のような運用を持ち込むと、会議体で確認しなくても更新できるというWikiのメリットが失われる」「更新を誰かが確認するなら、それは結局レビューと同じではないか」という反論が出ます。リード側は「求めているのはレビューではなく、**知らない間にルールが変わることを防ぐための連絡**」と整理し、「コード管理との違いはレビューが必要かどうか。Wikiにレビューは求めない」という線引きを示しました。

最終的な結論は「**Wikiを更新したら必ず連絡する（ナレッジ共有を除く）**」というシンプルなルールです。作業を止めないよう先に更新してから連絡して構わない、問題があれば後から戻せばよい、という運用に落ち着きました。さらに「更新通知が自動で飛ぶ仕組みがあれば漏れがない」という提案もあり、通知の自動化を検討していくことになりました。

### Copilotの指摘をCopilotに直させるべきか

プロフィール画像追加機能のプルリクエストでは、GitHub Copilotの自動レビューから多数の指摘を受けた担当メンバーが「『Fix with Copilot』ボタンで直すのと、ローカルで直してプッシュするのと、どちらがいいのか」と相談しました。

GitHubには、Copilotが自動で修正ブランチを作って作業ブランチに反映するボタンや、チャットしながら修正を進めるエージェント機能があります。ただしこれらは有料プランの機能で、プレミアムリクエスト1回あたり6円ほどの課金が発生するとのこと。プランによってボタンが表示されたりされなかったりすることも、画面を見比べながら確認されました。

議論の核心は課金よりも品質面でした。**レビューしたAIと同じAIに修正させると、その修正が正しいかをチェックする仕組みが働かない**という指摘です。Copilotの指摘をClaude Codeなど別のAIに渡せば、「CopilotのレビューをClaude Codeがレビューする」形になり、AI同士のクロスチェックが機能します。この観点から、チームとしてはローカル環境で別のAIとともに修正を進める方法が推奨されました。

実践的なテクニックとして、「指摘コメントのリンクをコピーしてAIに読み込ませれば内容を確認して修正できる」「MCP接続でプルリクエストの指摘を丸ごとチェックさせる仕組みをツール化している」という2つの方法も共有されました。あわせて、AIサービスの料金プランは値上がり傾向にあるため、トークン消費や料金はよく確認しておこうという注意喚起もありました。

### 100行超の自作フォーマッターは「過剰」か

設計書のMarkdownで、テーブルの区切り線（ハイフン）の数が書く人によって違うという「整形揺れ」問題も議題になりました。担当メンバーは専用のフォーマッタースクリプトを自作して対応しましたが、リードからは「そのために100行以上のコードを管理するのはやりすぎではないか」というコメントがつきます。

担当メンバーには「表に余計なスペースが大量に入っていること自体が気持ち悪い、排除したい」という動機があり、標準のPrettierではテーブルのハイフンの数までは制御できないため自作した、という経緯も説明されました。一方でリードからは、修正のたびにフォーマッターと手動修正のいたちごっこになる懸念や、「最近はBiomeのような選択肢もあり、ライブラリを試す方が保守性は高い」という代替案が示されます。

結論として、自作フォーマッターのプルリクエストは**ドラフトのまま一旦保留**とし、まずは既存の `npm run format-check` を全員がプルリクエスト時に実行する運用を導入して様子を見ることになりました。あわせてCIにフォーマットチェックを追加し、「チェックだけでは見ていない人が見落とす」という指摘から、エラー時にはSlack通知を行う方向で進めることも決まりました。

このほか、レコード復活機能はレビュー指摘への対応中で、テストの検証はClaude Codeを活用して担当メンバーが巻き取る分担を確認しました。本番環境リリースの自動化は「どこまでを自動化し、どこを手動に残すか」をWikiにまとめ、ワークフローのレビューが進行中です（デプロイ後でないと実施できないテストがあるため、mainマージ後に本番リリースの前段階までをGitHub Actionsで検証する方式）。マスターテーブル管理は「権限の許す限りすべてのテーブルを操作できる画面」という設計方針が示され、Draw.io図の画像化はPlaywrightでブラウザ描画をPNG取得する機能を実装中です。また、新しい学習支援アプリ「sinlab-study」のリポジトリ整備が完了し、来月から本格的に開発を始める予定であることも共有されました。

## 活用した技術

### SECURITY DEFINER関数によるRLSポリシーの共通化

今回のRLSリファクタリングでは、PostgreSQLのplpgsql関数を使って条件判定を共通化しました。関数定義に付いているキーワードにはそれぞれ意味があります。`STABLE` は「同じクエリの中では同じ結果を返す」ことをプランナに伝えて最適化を助ける指定、`SECURITY DEFINER` は関数を「定義したユーザーの権限」で実行する指定です。さらに `SET search_path` でスキーマの探索順を固定することで、悪意あるオブジェクトを差し込まれてもすり替えが起きないようにする、セキュリティ上の定石も守られています。

同じ条件式を何箇所にもコピーしていると、条件を変えたいときに修正漏れが起こりがちです。共通関数化は、プログラミング一般でいう**DRY（Don't Repeat Yourself）原則**をSQLのポリシー定義に適用した例といえます。

### GitHub Wikiはリポジトリとは別のバージョン管理

GitHubのWikiは、実はコード本体とは別の独立したGitリポジトリとして管理されており、ページを編集するたびにリビジョン（コミット履歴）が残ります。バージョン管理はされている一方で、コードのようなプルリクエストとレビューの仕組みはなく、**権限があれば誰でも直接編集できてしまう**のが特徴です。

この「気軽に書ける」特性は、ナレッジ共有のようにハードルを下げたい情報には長所として働きますが、開発規約のように全員の合意が前提となる情報には短所になり得ます。今回のチームの結論——ナレッジは自由更新、それ以外は更新したら必ず連絡——は、Wikiの特性を活かしつつ「知らない間にルールが変わる」リスクを抑える、レビューと放任の中間を取った運用といえます。

### スキーマと型定義の「ドリフト」をCIで検出する

Supabaseには、データベースのスキーマからTypeScriptの型定義を自動生成するCLI（`supabase gen types`）があります。便利な仕組みですが、スキーマを変更したのに型の再生成を忘れると、**実際のDBとコード上の型がズレたまま**開発が進んでしまいます。このズレは「ドリフト」と呼ばれ、コンパイルは通るのに実行時に不整合が起きる厄介なバグの温床になります。

今回有効化したワークフローは、CI上で型を再生成し、コミット済みのファイルと `git diff` で比較して、差分があればビルドを失敗させるというシンプルな仕組みでドリフトを検出します。人の注意力に頼らず機械的にチェックする、CI活用の王道パターンです。実際にこのワークフローを通すことで、直近のスキーマ変更（プロフィール画像カラムや今回のRLSヘルパー関数）が型定義ファイルへ正しく反映されました。

## 総括

今回は、RLSポリシーの共通化・型チェックCIの有効化・管理APIの品質改善と、機能追加よりも「開発を支える基盤」への投資が目立つ回でした。地味に見える作業ですが、条件式の重複や型のドリフトといった将来のバグの芽を先回りして摘む、リファクタリングの本領が発揮されています。

会議では、Wikiという「レビューのない世界」にどこまでルールを設けるかをめぐって率直な意見がぶつかり、「自由に書けるメリット」と「知らない間にルールが変わるリスク」のバランスを取った着地点を見つけました。CopilotのレビューをCopilot自身に直させず別のAIでクロスチェックする考え方や、自作ツールの保守コストを見極めて一旦保留とする判断など、AIツールが日常になった時代のチーム運営のリアルが詰まった回だったといえます。
