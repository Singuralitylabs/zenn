## 開発したもの

### ClerkからSupabase Authへの移行（PR #146）

認証基盤を Clerk から Supabase Auth に一本化しました。Google 認証のコールバック処理を新設し、ユーザーステータスに応じたリダイレクト処理を実装しています。

```typescript
// app/(auth)/callback/route.ts（新規作成）
import { CookieOptions, createServerClient } from "@supabase/ssr";
import { NextRequest, NextResponse } from "next/server";
import { cookies } from "next/headers";
import { fetchUserStatusById } from "@/app/services/api/user";
import { USER_STATUS } from "@/app/constants/user";

export async function GET(request: NextRequest) {
  const { searchParams, origin } = new URL(request.url);
  const code = searchParams.get("code");

  if (code) {
    const cookieStore = await cookies();
    const supabase = createServerClient(
      process.env.NEXT_PUBLIC_SUPABASE_URL!,
      process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
      {
        cookies: {
          getAll() { return cookieStore.getAll(); },
          setAll(cookiesToSet) {
            cookiesToSet.forEach(({ name, value, options }) => {
              cookieStore.set(name, value, options);
            });
          },
        },
      }
    );

    // Google OAuth の認証コードをセッションに交換
    const { data, error } = await supabase.auth.exchangeCodeForSession(code);

    if (!error && data.session) {
      // ユーザーステータスを取得してリダイレクト先を決定
      const { status: userStatus } = await fetchUserStatusById({
        authId: data.session.user.id,
      });

      if (userStatus === USER_STATUS.ACTIVE) {
        return NextResponse.redirect(`${origin}/`);
      } else if (userStatus === USER_STATUS.REJECTED) {
        return NextResponse.redirect(`${origin}/rejected`);
      } else {
        return NextResponse.redirect(`${origin}/pending`);
      }
    }
  }

  return NextResponse.redirect(`${origin}/login`);
}
```

Google ログインボタンも Clerk の `useSignIn` から Supabase の `signInWithOAuth` に変更されました。

```typescript
// app/(auth)/components/GoogleLoginButton.tsx（変更後）

```

### users テーブルの clerk_id を auth_id に変更（PR #133）

Supabase Auth への移行に伴い、`users` テーブルの `clerk_id` カラムを `auth_id` にリネームし、データ型を `UUID` に変更しました。

```sql
-- supabase/migrations/01_tables/03_alter_clerk_id_to_auth_id_for_users_table.sql
-- clerk_id カラムを auth_id にリネーム
ALTER TABLE users
  RENAME COLUMN clerk_id TO auth_id;

-- データ型を UUID に変更
ALTER TABLE users
  ALTER COLUMN auth_id TYPE UUID USING auth_id::UUID;

-- Supabase Auth の users テーブルへの外部キー制約を追加
ALTER TABLE users
  ADD CONSTRAINT fk_users_auth_id
  FOREIGN KEY (auth_id) REFERENCES auth.users(id);
```

これにより、RLS ポリシーで `auth.uid()` を使ってログインユーザーを識別できるようになりました。

### Supabase ポーズ通知の GAS 実装

Supabase の無料プランは一定期間（約7日間）操作がないとプロジェクトが自動的にポーズ状態になり、データベースにアクセスできなくなります。この問題に対処するため、GAS（Google Apps Script）でメール監視とスラック通知を自動化しました。

仕組みは以下の通りです。

1. Supabase がポーズ予告メールを送信（停止の数日前）
2. GAS が1時間ごとにメールを監視
3. 該当メールを検知したらスラックに通知
4. スプレッドシートに監視ログを記録

```javascript
// GAS スクリプト（概要）
function checkSupabasePauseEmail() {
  const label = 'supabase-pause-alert';
  const threads = GmailApp.search('from:no-reply@supabase.io subject:pausing');

  if (threads.length > 0) {
    sendSlackNotification('⚠️ Supabase がポーズされる予定です。アクセスして延長してください。');
    logToSpreadsheet(new Date(), 'PAUSE_ALERT_DETECTED');
  }
}

function sendSlackNotification(message) {
  const webhookUrl = PropertiesService.getScriptProperties().getProperty('SLACK_WEBHOOK_URL');
  UrlFetchApp.fetch(webhookUrl, {
    method: 'post',
    contentType: 'application/json',
    payload: JSON.stringify({ text: message })
  });
}
```

GAS のタイムトリガーで1時間ごとに自動実行する設定も追加し、開発環境と本番環境の両方を監視できるようにしました。

## 会議の様子

### Supabase Auth 移行の完了報告

認証機能の Supabase Auth 移行がメインブランチにマージされ、実機での動作確認も取れたことが報告されました。

Google Cloud のOAuth クライアントは1つだけ発行し、開発環境と本番環境で共用する設定にしました。これは Supabase の各環境から同一の Google Cloud プロジェクトを参照できるため、クライアントの発行数を最小限に抑えられます。

残作業として、コード中に残っている Clerk 関連の記述（設定ファイル・環境変数等）の削除が必要な状態ですが、認証フローの動作自体は完成しています。

### ユーザー承認機能の完成

承認機能の実装が完了し、メインブランチへのマージが完了しました。ステータスに応じた動作は以下の通りです。

- **pending（承認待ち）**：承認待ちページへリダイレクト
- **active（承認済み）**：トップページへリダイレクト
- **rejected（拒否）**：拒否ページへリダイレクト

これで、管理者が承認したメンバーのみがポータルサイトのコンテンツにアクセスできる仕組みが整いました。

### Supabase ポーズ問題の対応

Supabase の無料プランを使用しているため、操作がないとプロジェクトがポーズ状態になる問題が顕在化していました。本番環境のデータベースにアクセスできない状態になると、ポータルサイト自体が機能停止します。

根本的な解決策としては有料プランへの移行がありますが、まずは現実的な対策として GAS による自動通知を実装しました。ポーズ予告メールを検知してスラックに通知することで、定期的なアクセスの漏れを防ぎます。

本番環境のメールは別の担当者宛に届くため、その担当者にも同様の GAS 設定の依頼が必要です。

### 管理画面の実装方針

資料・動画の管理画面について、担当メンバーが設計と削除機能の実装を着手したことが報告されました。当初は別ページに遷移する設計でしたが、モーダル表示に変更する方向で設計書を修正中です。まずは削除機能から実装し、その後新規作成・編集機能を追加する予定です。

## 活用した技術

### Supabase Auth の OAuth フロー

Supabase Auth での Google 認証は、OAuth 2.0 の認証コードフローを使用します。

1. `signInWithOAuth` で Google のログイン画面へリダイレクト
2. Google 認証後、コールバック URL に `code` パラメータ付きでリダイレクト
3. `exchangeCodeForSession(code)` でセッション（アクセストークン）を取得
4. セッションからユーザー ID（`auth.uid()`）を取得してアクセス制御

```typescript
// ログインボタン（クライアント）
await supabase.auth.signInWithOAuth({
  provider: "google",
  options: { redirectTo: `${origin}/callback` },
});

// コールバック処理（サーバー）
const { data } = await supabase.auth.exchangeCodeForSession(code);
const userId = data.session?.user.id; // UUID
```

### Supabase マイグレーションファイルの管理

テーブル変更はマイグレーションファイルとして管理することで、変更履歴を追跡できます。

```
supabase/migrations/
├── 01_tables/
│   ├── 01_create_tables.sql
│   ├── 02_add_categories_table.sql
│   └── 03_alter_clerk_id_to_auth_id_for_users_table.sql  ← 今回追加
```

マイグレーションファイルをバージョン管理に含めることで、チームメンバーがデータベースの変更履歴を把握でき、環境の再構築も容易になります。

### GAS のタイムトリガーによる定期実行

GAS のタイムトリガーを使うと、指定した時間間隔でスクリプトを自動実行できます。

```javascript
// トリガーの設定（1時間ごとに実行）
function createTimeTrigger() {
  ScriptApp.newTrigger('checkSupabasePauseEmail')
    .timeBased()
    .everyHours(1)
    .create();
}
```

メール監視・スラック通知・スプレッドシートログを組み合わせることで、インフラの監視を無料で自動化できます。
