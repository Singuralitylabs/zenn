## 開発したもの

### アプリ紹介ページに新規登録・編集・削除機能を追加

先日リリースしたアプリ紹介ページには、資料一覧・動画一覧にはある「新規登録」ボタンや、カード右上の3点リーダーからの「編集」「削除」がありませんでした。今回、これらのコンテンツ管理機能をアプリ紹介ページにも追加しました。データベースを直接操作しなくても、ポータルサイトの画面からアプリを登録・編集・削除できるようになります。

進め方として、いきなり実装に入るのではなく、**先に機能仕様書へ追加機能の説明を追記するPRをマージし、作る機能を明確にしてから実装に着手する**という手順を踏みました。ボタン類はメンテナー・管理者権限を持つメンバーにのみ表示され、一般メンバーの画面には出てきません。

ページ本体（`page.tsx`）では、サーバーサイドでログインユーザーの情報を取得して権限をチェックします。アプリ独自の入力項目である「開発者」欄は `users` テーブルからの選択式のため、選択肢のデータは権限を持つユーザーのときだけ取得するようにしています。

```tsx
// app/(authenticated)/applications/page.tsx（抜粋）
// コンテンツ管理者のみ開発者データを取得
const isContentMgr = checkContentPermissions(role);
let developers: SelectDeveloperType[] = [];
if (isContentMgr) {
  const { data: developersData, error: developersError } = await fetchActiveUsers();
  if (developersError || !developersData) {
    console.error("開発者データの取得に失敗:", developersError);
    // コンテンツ管理者でも開発者データ取得失敗時は空配列で継続
  } else {
    developers = developersData.map(developer => ({
      id: developer.id,
      display_name: developer.display_name,
    }));
  }
}
```

画面側では、権限フラグ `isContentMgr` が `true` の場合のみボタンを表示する条件付きレンダリングで表示を切り替えています。新規登録ボタンや3点リーダーメニューは資料一覧・動画一覧と共通のコンポーネントを使っており、今回アプリにも対応できるよう型定義を拡張しました。

```tsx
// app/(authenticated)/applications/components/Template.tsx（抜粋）
{isContentMgr && (
  <div className="mt-4 flex justify-end">
    <ContentMgrNewButton
      type={CONTENT_TYPE.APPLICATION}
      categories={categories}
      userId={userId}
      developers={developers}
    >
      新規登録
    </ContentMgrNewButton>
  </div>
)}
```

なお、設計段階では開発者（`developer_id`）は必須項目でしたが、「開発者名を表示したくない人もいるかもしれない」という考慮から**null許容に変更**し、テーブル定義とデータベース設計書もあわせて更新しています。

### 論理削除を妨げていたRLSポリシーの修正

実装中に、Supabase側で1つ問題が見つかりました。SELECTポリシーが**管理者・メンテナーに対しても `is_deleted = true` の行を隠していた**ため、アプリの論理削除が正常に機能しなかったのです。そこで、一般ユーザーには未削除のデータのみ、管理者・メンテナーには削除済みも含めた全データを見せるようにポリシーを修正しました。

```sql
-- supabase/migrations/04_policies/applications_policies.sql（抜粋・変更後）
-- SELECT: 一般ユーザーは削除されていないもののみ、admin/maintainerは全て閲覧可能
CREATE POLICY "authenticated_users_can_read_applications" ON "applications"
  FOR SELECT
  TO authenticated
  USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE auth_id = auth.uid()
      AND status = 'active'
      AND is_deleted = FALSE
    )
    AND (
      -- 一般ユーザー: 削除されていないもののみ
      is_deleted = FALSE
      OR
      -- admin/maintainer: 削除済みも含めてすべて閲覧可能
      EXISTS (
        SELECT 1 FROM users
        WHERE auth_id = auth.uid()
        AND role IN ('admin', 'maintainer')
        AND status = 'active'
        AND is_deleted = FALSE
      )
    )
  );
```

同様の不備は資料一覧・動画一覧のポリシーにもあったため、まとめて修正しています。あわせて、UPDATEポリシーには更新後の行が満たすべき条件を示す `WITH CHECK` 句を追加し、Supabaseクライアント生成関数に付いていた不要な `await` も修正しました。

## 会議の様子

### 進捗確認 — 12月7日のver5リリースに向けて

定例の前半は、ver5に向けた各タスクの進捗確認です。テスト用GitHub Actionsの構築は担当メンバーの本業が繁忙期のため一時停止中で、「仕事優先で、落ち着いたら再開を」と確認しました。会員一覧の役割別表示機能は実装に着手済みで、週末のもくもく会で進める予定です。シンラボカレンダーの表示機能はテストまで完了し、READMEなどのドキュメント整備が残っています。リードからは「**ver5リリースは12月7日を目標に、間に合わない機能はver6へ**」という方針が示されました。

レビュー中のユーザー承認機能のPRについては、レビュアーから「承認時のメッセージがブラウザのコンソールログに出力されているが、コンソールは普段開かれていないので意味をなさない。**アラート表示にしてはどうか**」という指摘が共有されました。リベースすればマージできる状態まで来ており、最終判断は実装した担当メンバーに委ねられます。

### 論理削除したデータの「復活機能」をどう見せるか

今回新しく起票されたのが、**論理削除したレコードの復活機能**です。このポータルサイトでは資料・動画・アプリの削除はデータを完全に消す物理削除ではなく、`is_deleted` フラグを立てて非表示にする論理削除を採用しています。ところが現状、削除したデータを戻すにはデータベースを直接操作するしかありません。「論理削除はそもそも復活できることが前提の仕組みなのだから、画面から戻せる機能が必要では」という問題提起です。

議論ではまず、あるメンバーから「論理削除の仕組みは1から作るものなのか？データベースの機能を使うのではなく？」という質問がありました。これに対して、`is_deleted` カラムは最初のテーブル設計時にチーム自身が用意したものであること、論理削除を採用するかどうかはチームやプロダクトによってケースバイケースであることが説明されました。

UIの見せ方についても意見が分かれました。当初案は「一覧の下部に『削除された資料』という分類を作って並べる」というものでしたが、「管理者には常に削除済みデータが表示され続けるのは微妙」という指摘から、**画面右上にボタンを置き、押したときだけフィルターがかかって削除済みのカードだけが表示される**方式に落ち着きました。復元操作は通常のカードと同じく3点リーダーのメニューから行うイメージです。

ボタンの名前も一議論ありました。「ゴミ箱」という案にはGoogleドライブのサイドバーが引き合いに出されましたが、「ゴミ箱は削除する操作のイメージで、復元のイメージがない」という反論があり、「**非表示コンテンツ**」という表現が「しっくりくる」と好意的に受け止められました。細かい文言ひとつでも、ユーザーがどう受け取るかを議論して決めていきます。

### 手が空いたメンバーには新タスク — SNS入力欄とローディング画面

アプリ管理機能の完了で手が空いたメンバーには、新しいタスクがアサインされました。1つは**プロフィール画面へのSNSアカウント入力欄の追加**です。作業は大きく、(1) `users` テーブルにXやFacebookなどのカラムを追加するSQLの作成、(2) プロフィール画面への入力欄の追加、(3) 会員一覧での表示、の3ステップに分解して整理されました。SQLに不慣れなメンバーでも取り組めるよう、過去のマイグレーションファイルを参考にすること、生成AIも活用できること、そして**SQLは実行前に必ずレビューを依頼する**ことが確認されました。SQLはSupabaseのSQLエディター上で実行し、ファイルは `supabase/migrations` ディレクトリに追加してPRを出す運用です。

なお、当初はプロフィール画像の追加も同じイシューに含まれていましたが、こちらはストレージへのアップロード処理が必要でハードルが高いため、**イシューを分離**しました。その際「Base64エンコードして画像をデータベースに直接入れる荒技はどうか」という質問があり、「クライアントサイドの処理が多少重くなる」「ブラウザによってはうまく動かない懸念もある」「APIでアクセスできるならストレージの方が楽で、SupabaseのストレージはFirebaseとほぼ同じ感覚で使える」という技術談義に発展しました。

もう1つの空きタスクとして、リードが**ローディング画面（スケルトン）の実装**を担当することになりました。ページを開いた瞬間に表示される白いプレースホルダーのような画面で、「読み込み中である」ことをユーザーに伝わりやすくするための機能です。こちらも次回リリースへの取り込みを目指します。

### Git学習コーナー — git resetとVS CodeでのGit操作

終盤は恒例のGit学習コーナーです。先日のセッションがコンフリクト解決の途中で通信が切れてしまったこともあり、まず「コンフリクトは複数人が同じファイルの同じ箇所に異なる変更をしたときに起き、どちらを残すかを人間が選択する」という復習から始まりました。

続いて `git reset` の紹介です。`git log --oneline` でコミット履歴を1行表示で確認しながら、直前のコミットを取り消す操作を実演しました。ただし**リモートにプッシュ済みのコミットを取り消すとリモートとの差分が生じてややこしくなる**ため、「慣れないうちは下手にリセットせず、素直に修正して新しいコミットを積んだ方がよい」という実践的なアドバイスも添えられました。

また、「GitHubの画面全体がよく分かっていない」というメンバーの声を受けて、VS CodeのソースコントロールパネルによるGit操作を一通りデモしました。ファイル修正→ステージング→コミットメッセージ入力→コミット→「変更の同期」でリモートへプッシュ、という基本の流れに加え、ブランチの作成・切り替え、プルリクエストの作成までを画面共有で確認します。「ブラウザ上のソフトがGitHubで、VS Code上で操作しているのはGit。`git clone` した時点でリモートリポジトリとローカルが連携される」という**GitとGitHubの関係の整理**は、初学者のつまずきをほぐす良い問答になりました。

## 活用した技術

### RLSポリシーと論理削除の相性問題

SupabaseのRow Level Security（RLS）は、SELECT・INSERT・UPDATE・DELETEといった操作ごとに「どの行にアクセスできるか」をポリシーとして定義する仕組みです。今回見つかった問題は、SELECTポリシーで削除済みの行を全ユーザーから一律に隠していたことが原因でした。行の可視性は更新系の操作にも影響するため、削除済みの行が管理者からも「見えない」状態では、論理削除やその後の管理操作が正常に完結しなくなります。

修正後のポリシーは「一般ユーザーは未削除のみ、admin/maintainerは全件」と、**アプリ側の権限モデルをデータベース層でも表現する**形になりました。UIでボタンを出し分けるだけでなく、データベース自体が権限に応じたアクセス制御を持つことで、多層的な防御が実現できます。あわせて追加した `WITH CHECK` 句は「更新後の行が満たすべき条件」を検証するもので、`USING`（更新対象にできる行の条件）とセットで使うことでUPDATEポリシーの意図がより明確になります。

### git resetの3つのモード

`git reset` は直前のコミットを取り消すコマンドで、オプションによって「どこまで戻すか」が変わります。

* `--soft`: コミットだけを取り消し、変更内容は**ステージング済み**の状態に戻る（最も緩い）
* `--mixed`: 変更内容が**ステージング前**の状態に戻る（デフォルト）
* `--hard`: 変更内容ごと**完全に破棄**される（取り扱い注意）

戻り先の指定には `HEAD^`（1つ前）や `HEAD~3`（3つ前）といった記法を使います。ローカルだけで完結しているコミットには便利ですが、プッシュ済みのコミットに使うとリモートとの履歴のずれが生じるため、チーム開発では「新しい修正コミットを積む」方が安全な場面が多い、というのが今回の学びです。

### 画像の保存先 — Base64埋め込みかオブジェクトストレージか

会議で話題になった「画像をBase64エンコードしてデータベースに直接保存する」方法は、ストレージを用意せずに済む手軽さがある一方、エンコード・デコードがクライアントサイドの負荷になり、データサイズも元のバイナリより大きくなります。環境による動作の不安定さも懸念材料です。

一方、Supabase Storageのような**オブジェクトストレージ**にファイル本体を置き、データベースにはそのパスだけを保存する構成なら、データベースを肥大化させずに画像を扱えます。Firebase Storageなど他のBaaSとほぼ同じ感覚でAPI経由の操作ができるため、プロフィール画像機能は今後この方式を軸に設計していく見込みです。要件の小さいうちはBase64でも動きますが、スケールを考えるとストレージ分離が定石といえます。

## 総括

今回は、アプリ紹介ページのコンテンツ管理機能という「画面から完結する運用」への大きな一歩に加え、その実装過程でRLSポリシーの潜在的な不備を3テーブル分まとめて修正できた回でした。仕様書を先にマージしてから実装するという手順や、`developer_id` をnull許容に変えた判断など、作る前・作りながらの意思決定が丁寧に積み重ねられています。

会議では、論理削除の復活機能をめぐって「常に見せるか、ボタンで切り替えるか」「ゴミ箱か、非表示コンテンツか」といったUIの議論が交わされ、新しいタスクのアサインではSQL未経験のメンバーへのフォロー体制も整いました。`git reset` やVS CodeのGit操作といった学習コーナーも含め、経験の異なるメンバーがそれぞれのレベルで持ち帰りのある定例になっています。12月7日のver5リリースに向けて、ラストスパートです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
