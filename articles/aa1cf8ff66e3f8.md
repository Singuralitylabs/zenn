## 概要

本記事は、[チーム開発記録57：ヒント編集とマスター画面設計](https://zenn.dev/singularitylabs/articles/ded4d5790784cc)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、ポータルサイトと学習支援アプリ「sinlab-study」を隔週交互で開発しています。今回はポータルサイトの回で、**論理削除したコンテンツを一覧から復活できる「ゴミ箱」機能**がマージされました。誤って削除した資料・動画・アプリ・カテゴリーを、管理者が画面から元に戻せるようになります。

会議では、AIに依頼したセキュリティ・パフォーマンスの総点検で**「一般メンバーから管理者権限へ昇格できる抜け道」**を含む複数の指摘が上がり、まとめてイシュー化しました。あわせて、完了報告のたびに感じていた運用上の違和感を解消する「Check」リストの導入、そしてsinlab-studyを一般公開できるサービスへ育てるための**開発体制の二軸化**という、プロセス面の大きな決定もあった回です。

## 開発したもの

### 削除したコンテンツを元に戻す「ゴミ箱」機能

ポータルサイトでは、資料・動画・アプリ・カテゴリーの削除を**論理削除**（データを物理的に消さず、削除フラグを立てるだけ）で扱っています。しかし、これまで一度削除したコンテンツを画面から元に戻す手段はなく、復活させたい場合はデータベースを直接操作するしかありませんでした。今回、コンテンツ管理者向けに専用の**ゴミ箱ページ（`/trash`）**を追加し、削除済みアイテムの一覧表示と復活操作を画面から完結できるようにしました。

まず、サイドナビゲーションにゴミ箱への導線を追加しています。コンテンツ管理者権限を持つユーザーにだけ表示されるようにしました。

```tsx
// app/(authenticated)/components/SideNav.tsx（抜粋・変更後）
const TRASH_NAV_ITEM: NavItem = {
  title: "ゴミ箱",
  href: "/trash",
  icon: <Trash2 className="h-5 w-5" />,
};

// コンテンツ管理者のときだけゴミ箱を表示
...(isContentMgr ? [CATEGORY_ADMIN_NAV_ITEM, TRASH_NAV_ITEM] : []),
```

ゴミ箱ページはタブで「資料／動画／アプリ／カテゴリー」を切り替えられるようにし、各行の操作ボタンから復活モーダルを開く構成です。復活処理は、対象の種別ごとにサーバーアクションを呼び分け、結果に応じて通知を出したうえで画面を再取得します。

```tsx
// app/(authenticated)/trash/components/RestoreModal.tsx（抜粋・変更後）
const handleRestore = async () => {
  if (!target) return;

  let result: { success: boolean; error: Error | null };

  switch (target.type) {
    case "documents":
      result = await restoreDocument(target.item.id, userId);
      break;
    case "videos":
      result = await restoreVideo(target.item.id, userId);
      break;
    case "applications":
      result = await restoreApplication(target.item.id, userId);
      break;
    case "categories":
      result = await restoreCategory(target.item.id);
      break;
    default:
      return;
  }

  if (!result.success) {
    notifications.show({
      title: "復活失敗",
      message: getErrorMessage(result.error),
      color: "red",
    });
    return;
  }

  notifications.show({
    title: "復活完了",
    message: `${TAB_LABELS[target.type]}「${target.item.name}」を復活しました。`,
    color: "green",
  });

  onClose();
  router.refresh();
};
```

復活時の挙動はモーダル上で明示しています。コンテンツは元のカテゴリーへ戻る一方で表示順は末尾に配置されること、カテゴリーを削除した際に「未分類」へ移動したコンテンツは自動では戻らないことなど、運用者が誤解しないような注意書きを添えました。

この機能で技術的に力を入れたのは、実装そのものよりも**テスト**でした。担当者は「正常系（削除→復活が期待どおり動くこと）は問題ないことを確認済み。各ステップでどんな検証をしているかはコメントで残してある」と共有し、イレギュラーな操作でのケースは別イシューとして切り分けることになりました。

## 会議の様子

### 完了したのに「進行中」の違和感 — Checkリストの導入

会議の序盤、あるメンバーから運用上のちょっとした違和感が提起されました。**「マージまで終わったタスクが、ミーティングで確認するまでカンバンの『進行中（In Progress）』に残り続ける。完了しているのに『終わっています』と報告するのが、どうもしっくりこない」**というものです。

sinlab-studyでは以前、同じ課題に対して「In Review」というリストを追加して対応した経緯があります。今回のポータルサイトでは、リードから**DONEに移すのはこのミーティングで『終わったね』と確認した後にしたい**という考えが示され、その確認待ちを可視化する「Check」リストを新設することになりました。

新しい運用は次のとおりです。**マージまで完了したタスクは「Check」リストへ移動し、ミーティングで完了確認が取れたものだけをDONEへ動かす。** これにより「完了確認の漏れ」を防ぎつつ、報告時の違和感も解消されます。参加メンバーの合意も取れ、その場で運用開始が決まりました。小さな不満をそのままにせず運用ルールに落とし込む、チーム開発らしい改善です。

### AIによるセキュリティ・パフォーマンス総点検

今回の大きなトピックが、リードがAIに依頼して実施した**セキュリティとパフォーマンスの棚卸し**です。想像以上に多くの指摘が返ってきたとのことで、主だったものは以下のようにイシュー化されました。

セキュリティ面で最もインパクトが大きかったのが、**RLS（Row Level Security）ポリシーの不備による権限昇格の抜け道**です。テーブルを保護するはずのポリシーが緩く、「うまく操作すると一般メンバーからアドミン権限まで昇格できる経路が存在する」という指摘でした。ほかにも、セキュリティヘッダーの設定不足や、依存パッケージに含まれる既知の脆弱性が挙がっています。

パフォーマンス面では、体感として「ポータルサイトが少し重い」という声の裏にある具体的な原因が指摘されました。**認証チェックが過剰に実行されて画面描画をブロックしている**こと、Googleカレンダー APIのレスポンスをキャッシュしていないこと、複数のデータ取得が直列に走っていて並列化できること、SQLのSELECT文に改善余地があること、などです。

いずれも「動いてはいるが、放置するとリスクや遅延として効いてくる」種類の課題で、AIによる横断的なレビューが弱点の洗い出しに有効だったことを示す結果となりました。

### sinlab-studyの開発体制を二軸に分ける

会議の最後は、リードからの相談という形で**sinlab-studyの進め方**が議題に上がりました。「今後、一般に展開できるサービスへ育てたい。ただ、それをチーム開発のペースだけで進めるのは現実的に厳しい」という問題意識です。

提案されたのは、**チーム開発とリード個人による単独開発を並行させる二軸体制**でした。スピードを優先してガンガン進めたい部分はリードが単独で進め、じっくり取り組める・タスクを分担できる内容はチーム開発に残す、という切り分けです。あるメンバーからは「スピード重視の内容なら早くフローが回るやり方でよい。ゆっくり進めても問題ない、分散できるタスクこそチーム開発に向いている」と、切り分けの基準を補強する意見が出ました。

運用としては、**プロジェクトのカンバンボードを分割**し、リードが単独で進めるタスクは別ボードへ、チーム開発で扱うタスクは現行ボードに残す形で試すことになりました。学習の場としてのチーム開発と、プロダクトを前に進めるスピード、その両立を模索する現実的な一歩です。

### その他の進捗と相談

このほかにも、多くのタスクが進行しています。マスターテーブルの管理機能は、実装量が多いことから**1つのイシューを「表示」「フィルター・検索・ソート」「レコードの追加・編集・削除」など4つに分割**し、まず一覧表示から着手する方針が共有されました。

プロフィール画像の改善では、**キャッシュバスティング**（画像URLに付与した値を変えてブラウザキャッシュを更新する仕組み）にまつわる不具合が話題に。URLに付いた日付情報が原因で毎回キャッシュミスが起き、無駄な再取得でパフォーマンスが落ちているため、URLから余計な情報を外す方向で修正を進めています。あわせてStorageのRLSポリシーに関する指摘も残っており、継続対応となりました。

また、VS Code上でJestの型が解決できずエラーになる問題は、型定義を追加する設定ファイルを1つ足すことで対応。CD（継続的デリバリー）用のスクリプトがファイル名の辞書順で並んでしまう件は、明示的にナンバリングしようという方針を確認しました。マイグレーションファイルについては、これまで長く並べていたポリシー定義を**機能ごとに分割**し、見通しをよくする整理も入りました。

そして、前回から検討していた**dotenvxの導入**も方針が固まりつつあります。ローカル開発の環境変数をAIにうっかり読み取られるリスクへの対策で、設計段階のプルリクエストを出してレビューですり合わせる予定です。導入すると各自が復号用の秘密鍵を管理する運用が発生しますが、リードは「AI開発ではこうした鍵管理がスタンダードになりつつある。経験値という意味でも取り入れたい」と、スキルアップの機会として位置づけていました。

## 活用した技術

### 論理削除とゴミ箱パターン

今回のゴミ箱機能の土台にあるのが**論理削除（ソフトデリート）**です。レコードを実際にDELETEするのではなく、`deleted_at` のような削除日時カラムに値を入れることで「削除済み」と印を付け、通常の一覧では `deleted_at IS NULL` の行だけを表示します。データ自体は残っているため、印を消す（＝復活させる）だけで元に戻せるのが利点です。

この仕組みがあって初めて「ゴミ箱」が成立します。削除済みのレコードを集めて一覧化したものがゴミ箱ページであり、復活は削除フラグをクリアする操作にほかなりません。今回はさらに、復活後の表示順を末尾に回す、カテゴリー削除で「未分類」に退避したコンテンツは自動では戻さない、といった**復活時の副作用をどう扱うか**という設計判断が加わりました。誤削除からの回復手段を用意することは、運用者が安心して操作できるUXにも直結します。

### RLS（Row Level Security）と権限昇格リスク

**RLS（行レベルセキュリティ）**は、PostgreSQL／Supabaseが提供する、テーブルの行単位でアクセス可否を制御する仕組みです。「自分のデータだけ読める」「管理者だけが更新できる」といったルールをデータベース側に定義でき、アプリのコードにバグがあってもDBの層で不正アクセスを止められるのが強みです。

裏を返せば、**このポリシーが緩いと防御の最後の砦が機能しません**。今回指摘された「一般メンバーから管理者権限へ昇格できる抜け道」は、権限をチェックすべきポリシーの条件が不十分で、本来更新できないはずの行（例えば自分のロールを表す情報）を書き換えられてしまうようなケースが典型です。RLSは「有効にしてあること」と「ポリシーの条件が正しいこと」が別問題であり、AIによる横断レビューはこうした見落としを洗い出すのに向いています。設定した気になっているポリシーを、攻撃者目線で改めて棚卸しする重要性を示す指摘でした。

### dotenvxによる環境変数の暗号化

Node.js開発では、APIキーなどの秘密情報を `.env` ファイルに書き、`dotenv` で読み込むのが定番です。しかし `.env` は平文のテキストファイルであるため、AIコーディングツールにプロジェクトを読ませると、その中身がそのままAIへ送られてしまうリスクがあります。

**dotenvx**は `dotenv` の後継にあたるツールで、`.env` の値を**暗号化した状態で保存**できるのが特徴です。復号用の秘密鍵さえ別に管理しておけば、暗号化済みの `.env` はAIの目に触れても値を読み取られません。今回のように「AIにワークスペースを広く読ませる開発」が前提になると、秘密情報を平文で置かない運用は現実的なリスク対策になります。各メンバーが秘密鍵を自分で管理するという手間は増えますが、これ自体がAI駆動開発時代の実務スキルとして価値がある、というのがチームの見立てです。

## 総括

今回は、論理削除したコンテンツを画面から復活できる「ゴミ箱」機能がマージされ、誤削除からの回復手段が整いました。実装以上にテストの整備に重きが置かれた点は、安心して使える機能を届けるうえで見習いたい姿勢です。

会議では、AIによるセキュリティ・パフォーマンスの総点検が「権限昇格の抜け道」をはじめとする複数の弱点を可視化し、まとめてイシュー化されました。「動いているコード」を攻撃者や利用者の目線で棚卸しすることの価値を、あらためて実感する回だったといえます。あわせて、完了確認を可視化する「Check」リストの導入や、sinlab-studyを一般公開へ育てるための開発体制の二軸化など、プロセス面の決定も並びました。

作るものだけでなく、**どう安全に・どういう体制で作り続けるか**へと目線が広がってきています。sinlab-studyの本番リリースやdotenvx導入も近づいており、次回の展開も楽しみです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
