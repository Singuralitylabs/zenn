## 開発したもの

### 会員種別（membership_type）の導入

決済機能の前提として、まず承認済みユーザーを「コミュニティ会員（`community`）」と「一般有料会員（`general`）」に分類する軸が追加されました。シンラボ会員以外にも有料でsinlab-studyを使ってもらう、という今後の展開に備えた区別です。

仕様書には、この軸の位置づけが明確に書かれています。

> ロール（権限）とは独立した軸であり、**現時点では種別によるコンテンツ・機能のアクセス差はない**（将来の出し分けに備えた区別のみ）。承認前（`pending`）・却下（`rejected`）ユーザーは `NULL`。

管理者が承認操作を行うときにセレクトボックスで種別を選ぶ、却下すると `NULL` に戻る（そのため確認ダイアログに「設定は解除されます」を明示する）、といった運用の詳細まで固めたうえで、次のStripe連携に進んでいます。

### Stripe月額サブスク決済

今回の目玉です。お試しユーザー（`status = 'pending'`）がアプリ内のアップグレードページからStripe Checkoutに遷移し、決済が完了すると一般有料会員として自動承認される、という一連の流れが実装されました。

データベース側には2つのテーブルが追加されました。設計意図がマイグレーションのコメントにそのまま残されています。

```sql
-- stripe_subscriptions: ユーザーごとの課金状態のミラー（1ユーザー1行）。
-- アプリの認可判定は従来どおり users.status / users.membership_type が
-- 唯一の真実であり、このテーブルは Stripe 側の状態を参照可能にするための
-- ミラーに徹する

CREATE TABLE IF NOT EXISTS stripe_subscriptions (
  id SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  stripe_customer_id TEXT NOT NULL UNIQUE,
  stripe_subscription_id TEXT UNIQUE,
  -- Stripeのsubscription.statusをそのままミラーするため、CHECK制約は設けない
  status VARCHAR(30) NOT NULL,
  cancel_at_period_end BOOLEAN NOT NULL DEFAULT false,
  current_period_end TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- stripe_events: Webhookイベントの冪等性を担保するための処理権（claim）記録
CREATE TABLE IF NOT EXISTS stripe_events (
  id TEXT PRIMARY KEY, -- Stripe event.id（evt_...）
  type TEXT NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

「課金状態はミラーに徹し、認可の唯一の真実は `users` テーブル」という線引きが最初から明文化されているのがポイントです。

Checkout作成APIは、認証・ステータス・既存契約の三段チェックを通してからセッションを作ります。解約済みユーザーが再契約するケースでは、以前のStripe Customerを再利用する配慮も入っています。

```typescript
// app/api/stripe/checkout/route.ts（抜粋）
if (existing && !TERMINAL_SUBSCRIPTION_STATUSES.includes(existing.status)) {
  return NextResponse.json(
    { error: "既に決済手続き中、またはご契約済みです" },
    { status: 409 }
  );
}

// 解約済み等で終端状態の行が残っている場合、以前作成済みのCustomerを再利用する
// （毎回新規Customerを作らないことで、保存済みカード・請求履歴の孤児化を防ぐ）
const { url } = await createCheckoutSession(
  auth.userId,
  auth.user.id,
  auth.user.email,
  existing?.stripe_customer_id ?? null
);
```

決済完了・契約変更はStripeからのWebhookで受け取ります。ここで面白いのが、`stripe_events` テーブルへの**素のINSERTを「処理権のclaim」として使う**冪等性制御です。

```typescript
// app/api/stripe/webhook/route.ts（抜粋）
// event.idの処理権を原子的に確保する（素のINSERTのため、同一event.idの並行配信は
// 一意制約により片方だけがclaimに成功する）。claimできなければ「他のリクエストが
// 既に処理済み、または処理中」であり、ハンドラを実行せずスキップする
const { claimed: didClaim, processedAt, error: claimError } =
  await claimEvent(event.id, event.type);
if (!didClaim || !processedAt) {
  return NextResponse.json({ received: true, skipped: true });
}

switch (event.type) {
  case "checkout.session.completed": {
    const { error } = await activateUserFromCheckoutSession(
      event.data.object as Stripe.Checkout.Session
    );
    // 失敗時はclaimを解放してから500を返し、Stripeのリトライで再処理できるようにする
    ...
  }
  // deleted時点でsubscription.statusは既に'canceled'のため、
  // updatedと同じ同期処理で降格まで完結する
  case "customer.subscription.updated":
  case "customer.subscription.deleted": {
    ...
  }
  case "invoice.payment_failed": {
    // 初回失敗では降格せずSmart Retriesに任せる。運用者への通知のみ行う
    ...
  }
}
```

Webhookは同一イベントが複数回配信されうるため、冪等性の担保が必須です。分散ロックのような仕掛けを持ち込まず、PRIMARY KEYの一意制約だけで「並行配信のうち片方だけが処理する」を実現しているのが、シンプルで堅い設計です。解約はアプリ内からStripe Customer Portal経由で可能で、解約後もその期の終わりまでは利用できます。

### 決済日を毎月27日に固定する

続くPRで、決済日（請求サイクルのアンカー）が全ユーザー一律で**毎月27日 UTC 0:00（JST 9:00）**に固定されました。登録日ベースだとユーザーごとに請求日がバラつき、運用時の把握が難しくなるためです。

```typescript
// app/services/api/stripe-server.ts（抜粋）
subscription_data: {
  metadata: { user_id: String(userId), auth_id: authId },
  // 決済日を全ユーザー一律で毎月27日（UTC 0:00 = JST 9:00）に固定する。
  // hour/minute/secondを省略するとサブスク作成時刻がそのまま使われ、
  // ユーザーごとに請求時刻がバラつくため明示する
  billing_cycle_anchor_config: {
    day_of_month: BILLING_ANCHOR_DAY_OF_MONTH, // 27
    hour: BILLING_ANCHOR_HOUR_UTC,
    minute: 0,
    second: 0,
  },
  proration_behavior: prorationBehavior,
},
```

27日を選んだのは「すべての月に存在する日付なので、短い月の繰り上げ処理が不要」という理由。月末やうるう年の面倒はStripe側に委ねる構えです。

初回請求は日割り（`proration_behavior: "create_prorations"`）です。無償にすると「27日直前に登録して1ヶ月弱をタダで使って解約する」抜け道ができてしまうためですが、逆にアンカー直前の登録では日割り額がStripeの最低請求額（JPY ¥50）を下回って決済自体が失敗しうる、という細かい罠があります。そこで日割り額が最低請求額を下回る場合に限り無償に切り替えるガード（`isProrationBelowMinimum()`）を入れる、という二段構えになっています。エッジケースをどこまで潰すかの判断が設計書に理由つきで残っているのが読みどころです。

### 機能フラグによる一時停止

決済機能は実装・マージ済みですが、有料会員の募集開始前であることや特定商取引法に基づく表記などの準備がこれからであるため、本番環境ではまだ公開されていません。この「作ったが公開しない」を実現しているのが `STRIPE_ENABLED` フラグです。

```bash
# STRIPE_ENABLED: "true"以外（未設定含む）は決済機能を無効化する
# フィーチャーフラグ（フェイルクローズ）
STRIPE_ENABLED=true
```

`"true"` 以外はすべて無効扱い、というフェイルクローズの倒し方で、チェックアウト・ポータル・アップグレード画面の各入り口が `isStripeEnabled()` を確認します。環境変数の設定漏れが「決済が誤って開放される」方向に倒れない設計です。

### Gemini SDKの刷新とAPIキーの2ティア構成

AIレビュー機能の基盤も大きく手が入りました。従来使っていた `@google/generative-ai` SDKはすでにサポート終了がアナウンスされており、後継の `@google/genai` に移行。あわせて、有料会員には有料ティアのAPIキー、お試しユーザーには無料ティアのAPIキーを使う2構成になりました。

```typescript
// app/services/api/gemini.ts（抜粋）
/**
 * userStatus に応じて Gemini API キーを返す。
 * - active: 会員用（`GEMINI_API_KEY`）。未設定なら undefined
 * - pending: お試し用（`GEMINI_API_KEY_TRIAL`）。未設定なら会員用へフォールバック
 * - それ以外（rejected / null 等）: undefined（呼び出し側で 403 等を返す）
 */
export function resolveGeminiApiKey(userStatus: UserStatusType | null): string | undefined {
  const memberKey = process.env[GEMINI_API_KEY_ENV];
  if (userStatus === USER_STATUS.ACTIVE) {
    return memberKey || undefined;
  }
  if (userStatus === USER_STATUS.PENDING) {
    return process.env[GEMINI_API_KEY_TRIAL_ENV] || memberKey || undefined;
  }
  return undefined;
}
```

モデル自体は両ティアで共通ですが、有料ティアはレート制限や速度の面で優位があります。それでいてレビュー1回あたりのコストは1円を切る（0.3円程度）水準とのことで、「レビューにそこまでハイスペックなモデルは要らない」という割り切りと合わせて、コストを抑えた構成になっています。

このリファクタリングでは、旧SDKの型定義に `thinkingConfig` が無く `@ts-expect-error` で握りつぶしていた箇所も解消され、エラーメッセージからAPIキーを除去する `redactApiKey()` のような防御も追加されました。

### Gemini 3系への追従

会議直前には、モデルを `gemini-2.5-flash` から `gemini-3.6-flash` に更新するPRもマージされています。3系では思考（thinking）を完全には無効化できないため、思考トークンを最小に抑える指定へと切り替わりました。

```typescript
// app/constants/gemini.ts（抜粋）
/**
 * レビュー生成の最大出力トークン数。
 * Gemini 3系では思考トークンもこの枠と出力課金を消費するため、本文用に余裕を持たせる。
 */
export const GEMINI_MAX_OUTPUT_TOKENS = 4000;

/**
 * Gemini 3系の思考レベル。思考を完全には無効化できないため最小レベルを指定する。
 */
export const GEMINI_THINKING_LEVEL = "low" as ThinkingLevel;
```

2系では `thinkingBudget: 0` で思考を切っていましたが、3系では `thinkingLevel: "low"` を指定しつつ、思考トークンが出力枠を食う分だけ `maxOutputTokens` を1500から4000へ増額する、という追従です。モデルの世代交代のたびにパラメータの意味が変わる領域なので、定数化してコメントに理由を残しておく効き目が大きいところです。

このほか、テーマサムネイルのStorageアップロード機能やパフォーマンス改善もこの期間にマージされています。

## 会議の様子

### 「講座資料をAIに渡す」をやめる判断

進捗確認の中で議論が白熱したのが、「AIレビューの際に講座資料をAIに渡す」というイシューの扱いです。担当メンバーは設計まで進めていましたが、司会からは「講座資料をマークダウン化してAIに渡すと、入力トークンが莫大に増える。削減どころか逆効果ではないか」という根本的な疑義が出ました。

AIレビューはユーザーごと・提出ごとに独立したセッションで実行されるため、資料を「一度だけ渡しておく」ことはできず、毎回のリクエストに載せるしかありません。「課題の情報にレビューに必要な最低限の情報をあらかじめ入れておく方向ならあり」という代案に収束し、この機能自体は中止の方向になりました。設計まで作った後の中止は担当者にとって手戻りですが、「入れるとマイナス面の方が大きい」と冷静に判断できたのは健全な着地です。

### アサインは着手承認ではない — 「調査」ステップの導入

この中止判断をきっかけに、進め方そのものの議論に発展しました。あるメンバーからは「作業が進んでからスコープの見直しが多々発生している。攻め方を考えた方がいい」という問題提起があり、別のメンバーからは「**着手していいと言われたことと、着手が肯定されたことはイコールではない**、というのはちゃんと認識した方がいい」という整理が示されました。

議論の末に決まった運用は次のとおりです。

- イシューのテンプレートにアクションとして**調査**ステップを追加する（ただし全イシューで必須にはせず、ケースバイケースで運用する）
- GitHub Projectsの **Ready列を「調査・検討段階」**、**In Progress列を「設計以降」**と位置づけ直す
- Readyの段階で議論して合意を得たものだけがIn Progressに移る。個人の判断でいつの間にか移動するのはイレギュラー扱い

「アサインされたらまず設計・開発ではなく、そのイシューが本当に必要かの検討から入る」——実際の開発現場でもよくある「調査タスク」という概念を、ボードの列運用として明文化した形です。ガチガチのゲート管理にはしない、という緩さを残したのもチームらしい判断でした。

### Stripe管理画面のデモと、決済まわりの質疑

リードエンジニアからは、Stripeのテスト環境ダッシュボードを画面共有しながらのデモがありました。商品カタログやサブスクリプションの設定、Webhookエンドポイントの発行など、「決済するためのエンドポイントを発行して、管理画面の設定とアプリ側の実装を組み合わせる」という全体像の説明です。「複雑そうに見えるが、パターンが決まっているので一度覚えれば作り方は見えてくる」というのが経験談でした。

質疑では、メンバーから運用面の確認が相次ぎました。解約はユーザー自身がアプリからできること、27日決済で初回は日割りになること、その説明が決済時のポップアップに掲載されていること。さらに「アカウント削除機能は要らないのか」という論点からは、決済履歴が絡むデータは**論理削除**が望ましく、個人情報保護の観点では**物理削除**が安全、という削除方式の使い分けの議論に広がりました。現時点で削除機能を実装する予定はないものの、論点として頭の片隅に置くことになっています。

また、有料サービスの提供には特定商取引法に基づく表記や利用規約の整備が必要という話も共有され、「対応していないサイトは最近見ない。誰が・何を売っているのかを明示するのは当たり前の水準」というコメントもありました。決済機能は技術だけでは公開できない、という実例です。

### ループエンジニアリングという開発スタイル

会議の後半では、リードエンジニアが最近実践しているAI駆動開発の手法「ループエンジニアリング」が紹介されました。ポイントは次のとおりです。

- 設計書ではなく、まず**イシューを徹底的に詰める**。背景・変更箇所・完了条件をAIと相談しながら書き切る
- イシューに**完了条件**を明記する。「CIがすべて通ること」に加え、「実装セッションとは別の検証用セッションを立ち上げてレビューし、指摘がゼロになるまで繰り返すこと（ただし最大3回）」をルール化する
- あとは「このイシューの完了条件を満たすまでやってください」とAIに投げる。プルリクエストができたら、さらに**別セッション**でレビューさせ、指摘の反映とチェックを繰り返す

「人間のレビュアーを挟まないなら、設計してから実装するというステップは必須ではない。詰めるべきはイシュー（要件）」という思想で、`CLAUDE.md` のようなプロジェクト指示書には全体共通のルールだけを書き、個別の作りたいものはイシュー内で完結させるのがコツとのこと。ここまでやると人間がレビューする余地はあまり残らないが、それでもレビューはする——余計な実装が混ざることはあるので、という現実的な補足もありました。

### チーム開発の対象をポータルサイトに寄せる

この開発スタイルの話は、チーム開発の枠組み自体の相談につながりました。結論としては次の整理です。

- **チーム開発の中心は今後もポータルサイト**。従来どおりのレビューを挟む開発スタイルを残す（初心者が開発経験を積む場としての価値を重視）
- **sinlab-studyはチーム開発から完全には外さない**が、進行中のイシューの確認程度にとどめ、レビューは基本的にリードエンジニアが担当する。一般向けに収益化を目指すサービスであることが理由
- それ以外は、**各自が作りたいものを自分で作り、この場で相談・紹介する**スタイルを推奨する。データベースやデプロイ先の準備といったインフラ経験は自分のプロダクトを作らないと積めない、という背景から

「決済機能を自分のアプリに組み込みたいので相談したい」というメンバーの声もその場で挙がっており、個人開発とチームの知見共有を組み合わせる方向性が見え始めています。

なお、共有されていた学習用のAPIキー暗号化ファイルがAIセッション上で復号・閲覧されてしまった、というヒヤリハット共有もありました。対象がテスト環境の値であり公開リポジトリに平文で出たわけではないことから、再暗号化はしない判断でしたが、「公開情報になったかどうかで切り分ける」「AIに読ませたくないデータはプロジェクトフォルダに置かない」という観点が整理されました。

## 活用した技術

### Stripe Checkout + Webhook + Customer Portal

今回の決済実装は、Stripeの標準的な構成をきれいになぞっています。決済ページ自体はStripeホストのCheckoutに任せ、アプリは「セッションを作ってリダイレクトする」「Webhookで結果を受け取って自分のDBに反映する」「解約・カード変更はCustomer Portalへ誘導する」ことに徹する構成です。カード情報がアプリのサーバーを一切通らないため、PCI DSS対応の負担を最小化できます。

その分、設計の重心はWebhookの信頼性に移ります。今回の実装では、①署名検証（生ボディ必須）、②一意制約INSERTによる冪等性claim、③失敗時のclaim解放とStripe側リトライへの委任、という3点で「同じイベントが何度来ても、並行して来ても、取りこぼしても壊れない」を担保しています。Webhook駆動のシステム全般に流用できるパターンです。

### billing_cycle_anchor_config による請求日の統一

Stripeのサブスクリプションは既定では契約日ベースで請求日が決まりますが、`billing_cycle_anchor_config` を使うと「毎月27日」のような固定アンカーを宣言的に設定できます。短い月の扱いやうるう年をStripeに任せられるのが利点です。一方で**サブスク作成時にしか適用されない**ため、既存契約者への遡及はできず、「実課金開始前に導入を終わらせる」という導入タイミングの制約が生まれます。日割りと最低請求額の相互作用も含め、決済機能は「動くコード」よりも「エッジケースの潰し込み」に工数がかかる、という好例でした。

### @google/generative-ai から @google/genai への移行

Googleの生成AI向けSDKは世代交代が進んでおり、旧 `@google/generative-ai` はすでにサポート終了しています。今回の移行は単なる置き換えにとどまらず、モデル名・トークン上限・思考設定・APIキー環境変数名を定数モジュールに集約し、プロンプト構築やスコア抽出を純粋関数として切り出してテスト可能にする、というリファクタリングを伴いました。おかげで直後のGemini 3系対応（`thinkingBudget` → `thinkingLevel`）は、定数と設定の差し替えだけの小さなPRで済んでいます。**外部SDKの都合で変わる部分を一箇所に寄せておく**ことが、モデルの世代交代が激しい時代の保守性に直結します。

### フィーチャーフラグとフェイルクローズ

`STRIPE_ENABLED` のような機能フラグは、「リリース（デプロイ）」と「公開（機能の有効化）」を分離する基本テクニックです。今回のように法務準備や移行作業（Cloudflare Workersへのカットオーバー）を待つ間、コードはマージしてテスト済みの状態で寝かせておけます。重要なのは倒し方で、「`"true"` 以外はすべて無効」というフェイルクローズにしておけば、環境変数の設定漏れ・タイポが「決済が勝手に開放される」事故につながりません。認可まわりの判定と同じ発想が、機能フラグにも一貫して適用されています。

## 総括

今回は、**個人開発のスピードとチーム開発の学びをどう両立させるか**が正面から議論された回でした。Stripe決済とGemini SDK刷新という大きな実装はリードエンジニアがループエンジニアリングで一気に仕上げ、その知見（Stripeの全体像、決済日のエッジケース、SDK移行の勘所）を会議で還元する。一方でチームとしては、調査ステップとボード運用の見直しで「作る前に立ち止まる」仕組みを整える。AIで実装が速くなるほど、**何を作るか・作らないかの判断**にチームの価値が移っていくことを実感させる内容でした。

「講座資料をAIに渡す」機能の中止は、担当者にとっては残念な結果ですが、「着手の許可と方針の肯定は別物」「イシュー（要件定義）こそ最重要」という共通認識に昇華されました。決済という「失敗できない機能」の設計と、失敗を許容するプロセス改善が同居しているのが、このチームらしいバランスです。

シンギュラリティ・ラボでは、こうしたチーム開発に一緒に取り組む仲間を募集しています。決済やAIレビューのような実践的な機能開発に興味がある方も、開発プロセスの議論に加わりたい方も、ぜひのぞいてみてください。
