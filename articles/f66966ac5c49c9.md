## 開発したもの

### 表示順ナンバリング不具合の修正 — display_order のNOT NULL化

コンテンツ編集画面で表示順のナンバリングが `NULL` になってしまう不具合を修正しました。原因は、表示順を保持する `display_order` カラムが `NULL` を許容していたことです。そこで `applications`・`categories`・`documents`・`positions`・`videos` の5テーブルに対して、既存の `NULL` データを更新したうえで `NOT NULL DEFAULT 0` 制約を追加するマイグレーションを作成しました。

```sql
-- supabase/migrations/01_tables/categories/03_set_display_order_not_null.sql
-- 既存のNULLデータを0に更新
UPDATE categories SET display_order = 0 WHERE display_order IS NULL;

-- display_order を NOT NULL DEFAULT 0 に変更
ALTER TABLE categories
ALTER COLUMN display_order SET DEFAULT 0,
ALTER COLUMN display_order SET NOT NULL;
```

同じ内容のSQLを5テーブルぶん用意し、型定義ファイル（`database.types.ts`）の `display_order` も `number | null` から `number` に変更しました。これにより、コード中に散らばっていた `?? 0` などのNULLチェックを大幅に減らせています。フロントエンド側では、表示順が未設定（`0` または `NULL`）のアイテムを末尾に回し、1始まりの連番を振り直すロジックを追加しました。

```typescript
// app/services/api/utils/display-order.ts（抜粋・変更後）
// display_order が 0 または null のアイテムを末尾に移動し、連番を振り直す
const sorted = (data || []).sort((a, b) => {
  const aIsUnset = !a.display_order;
  const bIsUnset = !b.display_order;
  if (aIsUnset && !bIsUnset) return 1;
  if (!aIsUnset && bIsUnset) return -1;
  return a.display_order - b.display_order;
});

return sorted.map((item, index) => ({
  ...item,
  display_order: index + 1,
}));
```

ただし定例では、マージ後にレビュアーから「マイグレーションで全データが採番済みになる以上、この自動採番ロジックは今後使われないので削除した方がよい」という指摘があったことが共有され、**不要コードを後追いで削除する追加対応**を行うことになりました。あわせて「イシューはいつクローズすべきか」も話題になり、削除対応のマージまで待つ案も出ましたが、イシューの要件自体はすでに満たしているため、残作業を追加対応として引き継いだうえでクローズする方針に落ち着きました。

### 進行中のドキュメント整備

コード以外のドキュメント整備も並行して進んでいます。カテゴリー管理機能の設計を進める中で、機能設計書のMarkdownにインデントの表記ルール違反の指摘が出ることが分かり、**設計書のインデント・コードスニペットを調整する対応**を、レビュアーの助言によりイシューとブランチを分けて進めています。また、READMEのプロジェクト構成に追加済みのファイルやドキュメントが反映されていなかったため、**構成の更新とコードブロックの言語指定の明記**もレビュー中です。

さらに、Claude Codeをチーム開発で使うための**運用ルールの整備**も作業中です。必ず読み込ませる指示文である `CLAUDE.md` と、コマンドの許可・禁止を設定する `settings.json` をまず整え、コーディング規約は `CLAUDE.md` に直接書くとWikiと二重管理になるため、Wiki側を更新して参照する形にする方針が共有されました。

## 会議の様子

### カテゴリー管理画面の設計レビュー — 3点リーダーか、横並びボタンか

今回の設計レビューの中心は、カテゴリーの追加・編集・削除を行う**カテゴリー管理画面**でした。設計書では、資料・動画・アプリをタブで切り替え、それぞれのカテゴリーを一覧表示して、新規登録ボタンと各行の3点リーダー（︙）から編集・削除を行う構成になっています。データベース側は管理者とコンテンツ管理者だけがカテゴリーを変更できるようRLSポリシーを設計し、対象ユーザーにのみカテゴリー管理のメニューを表示します。

議論になったのは操作ボタンの見せ方です。「一覧形式なら編集・削除を横並びに出す方が一般的では」という案に対し、「他の画面は3点リーダーを使うパターンが多いので合わせた方がよい」という意見も出ました。既存画面で3点リーダーを使っているのは、カード表示にボタンを並べると煩雑になるためで、テーブル形式の今回はどちらもあり得ます。最終的には、**操作するのが管理者・コンテンツ管理者に限られる画面なので多少硬いGUIでも許容できる**こと、デザインは実装してみると印象が変わることから、開発しながら調整し、変更したら設計書も追従させることになりました。

また、画面の配置については「管理者専用の管理画面の中に入れると、コンテンツ管理者が操作できなくなる」ため、**管理画面には含めずサイドバーに独立したメニューとして表示する**設計意図が確認されました。設計書のワイヤーフレームがテキストのアスキーアートで表現の限界があることから、XMLベースの作図ツール**draw.io**へ移行するイシューにも触れ、現在進行中のUI修正が一段落した次のタイミングで試すことになりました。

### 「ホーム」か「トップページ」か — 本日イベント表示の設計すり合わせ

トップページに本日のカレンダーイベントを表示する機能では、設計書の用語をめぐって面白い議論がありました。担当メンバーが「ホームページ＝サイト全体の総称であって、この画面はトップページと呼ぶべきでは」と設計書で「トップページ」表記を使ったのに対し、サイドバーの表記は「ホーム」。既存の利用者がいる以上UIはむやみに変えない方がよいという意見もあり、**画面・設計書ともに「ホーム」に統一**することになりました。

あわせて、サイドバーとトップページでコンテンツの並び順が違う点も指摘され、統一する順序を議論しました。「動画より資料が先では。資料は申請などの業務で必要になるが、動画は時間があるときに見るもの」という利用実態からの意見が出て、**資料を上にする並びで統一**することに。正解のない好みの世界に入りかけたところで、リードが「決めの問題として」即断したのも印象的な場面でした。

イベント表示のデザインでは、場所が未設定の場合に「未設定」と表示するのではなく**ハイフン表記にする**（場所が決まっていないことが明確に見える）こと、日をまたぐイベントの表示はGoogleカレンダーの終日イベント表示を参考に検討することが決まりました。凝った作りにするより、まず機能として実現させることを優先し、**技術的に実装しやすいかという観点もAIに相談しながら**設計を詰めていきます。

### テストコードは誰が書くのか — 運用ルールをめぐる議論

テスト用GitHub Actionsの構築が進む中で、「27個ほどあるテストを、関数やコンポーネントが追加されるたびにメンテナンスし続けなければならない」という懸念がテスト基盤の担当メンバーから提起されました。理想は開発者自身がテストコードまで書くことですが、全員がテストに慣れているわけではなく、ハードルが高いのも事実です。

「1つのプルリクエストの中で、担当者が途中で交代してもよいから開発とテストを完結させるべき」という提案に対し、リードは「開発スピードが落ち、混乱しそうなので賛同しかねる」と反対。担当メンバーが当面すべてのテストを引き受ける案にも「1人に背負わせるのは現実的ではない」と待ったがかかりました。議論の結果、**テストを必ず書くルールにはせず、必要に応じて追加していく運用**とし、開発者がテストも書くことは大歓迎、既存のテストを壊す修正をした場合はテストも一緒に直す、という整理になりました。そのうえで、**どこまでテストするかの基準を決めるイシュー**を優先度高めで作成することになりました。

さらに重要な気づきとして、「直近の開発でサーバーサイドのファイルが変わるため、このテストをマージすると既存テストがこける」ことが判明。**テストだけを先行導入するのは危険**という判断から、型チェックやDBの型チェックのような汎用的な部分だけを切り出して先にマージするなど、マージの仕方を別途相談することになりました。機能テストについては、Playwrightのようなブラウザ自動操作がAIの活用でコードを書かずに実現しつつあり、GitHub Actions上でも動かせるらしいという情報も共有されました。

### Copilotレビューの指摘が多すぎる問題

資料・動画の責任者をユーザーテーブルから選択できるようにする開発では、レビュアーが編集モーダルの文言修正（「担当者」→「責任者」）を指摘していたのに、**GitHub Copilotの大量の指摘コメントにレビューが畳まれてしまい、担当メンバーが気づいていなかった**ことが発覚しました。人間のレビューがAIの指摘に埋もれるという、AIレビュー時代ならではの問題です。

対応として、Copilotの指摘を1件ずつ解決済みにして畳む運用のほか、「何でもかんでも指摘してくるのは、レビュー観点を伝えていないから。人間のレビューでもレビュー観点を設けるのだから、**レビューしてほしくない観点も含めた指示文を整理すべき**」という意見でまとまり、Copilotへのレビュー指示文を作成するイシューが作られました。あわせて、無料プランではプルリクエスト作成後にCopilotをレビュアーとして追加できないため、**作成時に選択肢に出たら追加し、出なければリードが後から追加する**運用や、「レビュアーはApproveまでを担当し、mainへのマージはリードが行う」という役割分担も確認されました。

なお、責任者機能そのものについても、登録・表示・編集・削除（CRUD）をセットで考えると詳細画面への表示までやるべきという議論がSlackで行われ、要件を追加。要件を変えたときはイシューにも追記する運用を確認し、承認済みのプルリクエストは既知の対応漏れを認識したうえで先にマージし、文言修正と表示追加は後追いで対応することになりました。

## 活用した技術

### PostgreSQLカラムのNOT NULL化 — 既存データを先に整えるマイグレーション

稼働中のテーブルに `NOT NULL` 制約を後付けする場合、`NULL` のレコードが1件でも残っていると `ALTER TABLE` が失敗します。今回のマイグレーションのように、**先に `UPDATE` で既存の `NULL` をデフォルト値に変換してから制約を追加する**のが定石です。`DEFAULT 0` も同時に設定することで、以降のINSERTで値を省略しても `NULL` が混入しなくなります。

この変更はSupabaseが自動生成する型定義にも波及し、`display_order` が `number | null` から `number` になったことで、アプリ側のNULL合体演算子（`??`）や `nullsFirst` オプションが不要になりました。**データベースの制約を強めるとフロントエンドのコードがシンプルになる**という、型がDBからUIまでつながっているSupabase + TypeScript構成ならではの効果が見える事例です。

### CLAUDE.mdとsettings.json — AIコーディングエージェントのチーム運用

Claude Codeは、プロジェクト直下の `CLAUDE.md` に書かれた内容を必ず読み込む指示文として扱い、`settings.json` でコマンド単位の許可・禁止（例: このコマンドは実行してよい、これは禁止）を設定できます。個人で使うだけなら好みの設定で済みますが、チームで使うなら「AIにどの作業をどう任せるか」をルールとして揃える必要があります。

今回のチームの方針で参考になるのは、コーディング規約を `CLAUDE.md` に直接書かず、**すでにWikiにある開発ルールを更新して参照させる**とした点です。同じ情報を2箇所に持つと更新漏れで食い違いが生まれるため、ドキュメントの一元管理（Single Source of Truth）の考え方をAI向けの指示文にも適用した形です。

### GitHub Copilotコードレビューと「レビュー観点」

GitHub Copilotのコードレビューは、プルリクエストのレビュアーにCopilotを指定すると自動でコードを確認し、改善点をコメントしてくれる機能です。人間が見逃しがちな細かい問題を拾ってくれる一方、今回のチームが直面したように、**指摘が多すぎると本当に重要な人間のレビューコメントが埋もれる**という副作用があります。

人間のレビューでは「今回は仕様との整合性を重点的に見る」といったレビュー観点を事前に決めるのが一般的です。Copilotにもリポジトリへの指示ファイルなどでレビューの重点や「指摘不要な範囲」を伝えられるため、AIレビューを導入する際は、**レビューさせたい観点と同じくらい、レビューさせない観点を言語化する**ことが運用のポイントになります。

## 総括

今回は、表示順ナンバリング不具合の修正というデータベースの土台を固める開発が完了し、会議ではカテゴリー管理機能の設計レビューを中心に、ホーム画面の用語統一から日またぎイベントの表示方法まで、細部の設計判断を丁寧に積み重ねました。「操作する人が限られる画面はシンプルなGUIで割り切る」「正解のない並び順は決めで進める」など、議論の切り上げ方にもチームの成熟が表れています。

一方で、テストコードの運用ルールやCopilotレビューとの付き合い方は、結論を急がず「基準を決めるイシューを作って考える」という宿題になりました。テストだけを先行導入すると既存の開発を壊しかねないという気づきは、テスト自動化を進めるチームにとって示唆に富む論点です。AIレビューやAIコーディングエージェントをチーム開発にどう組み込むか、模索の過程も含めて今後の記録でお伝えしていきます。
