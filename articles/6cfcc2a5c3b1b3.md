## 概要

本記事は、[チーム開発記録23：会員タグ設計とドキュメント刷新](https://zenn.dev/singularitylabs/articles/3c07d46baa801e)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回は、**プルリクエストテンプレートの全面刷新**と**ログイン画面への注意メッセージ追加**が完了し、これらを含む**バージョン4.1.0のリリース**を実施しました。また、Jestによる単体テストをGitHub Actionsで自動実行する仕組みも、レビューを経てマージされています。

会議では、新メンバー2名のローカル環境構築が無事完了したことが報告され、初めてのタスクとして取り組みやすい修正を割り当てました。さらに、シンラボのGoogleカレンダーをポータルサイトに表示する新機能のアイデアをめぐって、アクセス権限の観点から活発な議論が交わされました。新メンバーのオンボーディングと機能開発が並走する、チームの現在地をお伝えします。

## 開発したもの

### プルリクエストテンプレートの全面刷新

担当メンバーが、GitHubでプルリクエストを作成するときに表示されるテンプレートを、レビュアーがレビューしやすい構成に書き直しました。従来は「変更内容」「関連Issue」「特記事項」「備考」というシンプルな構成でしたが、変更の背景から動作確認内容までを段階的に書ける詳細な構成になっています。

```markdown
<!-- .github/pull_request_template.md（抜粋・変更後） -->
## 概要

<!-- 変更の背景・理由と、変更の概要を記載してください -->

### 関連Issue

## 技術的変更点

<!-- レビュワーに変更の流れが分かるように、どの処理をどう変更したか、どう動くのか、などを記載してください -->

### レビュー特記事項

<!-- レビュワーに重点的に確認してもらいたい観点や、レビュワーに伝えたい実装意図（本当はこうしようと思ったけど悩みがあってこうした、など）があれば記載してください -->

### TODO事項

<!-- 修正量が多くなるのでPRを分けたい・Issueの範囲外で見つけたバグなど、今回あえて修正を保留した箇所があれば記載してください（別Issueで対応する予定の場合は番号も） -->

## 動作確認内容

<!-- 動作確認した内容（環境、ケース）を記載してください。UI変更の場合は、必要に応じて該当箇所のスクリーンショットをドラッグ&ドロップで添付してください -->
```

会議では担当メンバーから「コメント（`<!-- -->`）で書いてある補足は実際のPR画面には表示されないので、その下に内容を書いていってほしい」という使い方の補足もありました。

### ログイン画面への注意メッセージ追加

前回の定例で決まった「緊急パッチリリース」対応として、ログイン画面に注意書きを追加しました。Googleアカウントの選択画面にSupabaseのドメイン（URL）が表示されて不安になる、という新メンバーの声に応えたものです。

```tsx
{/* app/(auth)/login/page.tsx（抜粋・変更後） */}
<div className="flex justify-center">
  <div className="max-w-md bg-blue-50 border border-blue-200 rounded-lg px-4 text-sm text-gray-700">
    <p className="font-semibold text-lg text-blue-900 mb-2">ログイン時のご連絡</p>
    <p className="leading-relaxed text-base">
      Googleアカウント選択画面では、Supabaseの認証システムを利用している仕様上、下記のURLが表示されます。
      <br />
      本URLはシンラボのポータルサイトへのアクセスページなので、安心してログインしてください。
    </p>
    <p className="text-center text-base">anawnwhhsgragkcorecl.supabase.co</p>
  </div>
</div>
```

注意書きを載せたことでログインボタンが目立ちにくくなったため、あわせてボタンのサイズも少し大きくしています。レビューの中では「こうした通知メッセージの見た目に統一感を持たせるルールが必要では」という意見も出ました。現状はデザインが設計者任せになっているため、Issueとして記録し、将来的には共通の「カード」コンポーネント化も視野に入れて検討していきます。

### Jest単体テストのGitHub Actions自動実行

担当メンバーが、テストフレームワーク**Jest**の導入と、GitHub Actionsによるテスト自動実行の仕組みを構築しました。`app/` 配下のコードが変更されたpushやプルリクエストのタイミングで、自動的にテストが走ります。

```yaml
# .github/workflows/test.yml
name: Jest Unit Tests

on:
  push:
    paths:
      - "app/**"
  pull_request:
    paths:
      - "app/**"
  workflow_dispatch:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      # ソースコード取得
      - name: Checkout repository
        uses: actions/checkout@v4

      # Node.js セットアップ
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22.x
          cache: 'npm'

      # 依存関係インストール
      - name: Install dependencies
        run: npm ci

      # Jest 実行
      - name: Run Jest tests
        run: npm test
```

レビューでは「Node.jsのバージョン指定を配列形式で書くとエラーになる」という指摘があり、単一バージョン指定（`22.x`）に修正した経緯も共有されました。担当メンバーいわく「今はまだ設定した段階で、テストがちゃんと機能する状態ではない」とのことで、このPRのマージ後に実際のテストケースを作り込んでいくフェーズに進みます。

### バージョン4.1.0のリリース

これらの内容を踏まえて、**バージョン4.1.0**としてリリースを行いました。スクロール時のヘッダー固定表示、ログインページの注意事項表示、ドキュメントの修正などが含まれます。このほか、管理者によるユーザー承認機能の設計ドキュメントもレビューを経てマージされ、実装フェーズに入りました。

## 会議の様子

### 新メンバー2名の環境構築が完了 — 最初のつまずきも即解決

冒頭で、新メンバー2名のローカル環境構築が無事完了したことが報告されました。ただし1名からは「構築はできたが、そこからの操作が分からない」という率直な声が。リードが画面を共有しながら、`npm run dev` で開発サーバーを起動し、ブラウザで `localhost:3000` を開くと自分のパソコン内でポータルサイトが動くこと、コードを保存すると画面に自動反映されるので、**開発サーバーを動かしたまま編集し、期待どおりに更新されるかを確認するのが定番の開発スタイル**であることを解説しました。

もうひとつのつまずきは「ローカルで起動したサイトに自分のIDでログインできない」というもの。これはポータルサイトの承認機能によるもので、初回ログイン時はデータベース上のステータスが「ペンディング（承認待ち）」として登録される仕様です。現状はSupabaseの画面から手動で「アクティブ」に変更して解決しましたが、まさにこの手作業をなくすための「管理者によるユーザー承認画面」を別のメンバーが実装中である、という背景も共有されました。

### シンラボカレンダー表示機能 — 埋め込みは簡単、でも権限は？

新しいIssueとして、**シンラボのGoogleカレンダーをポータルサイトに表示するページ**の追加が提案されました。シンラボのスケジュールはGoogleカレンダーで管理されていますが、普段Googleカレンダーを見る習慣がないメンバーもいるため、ポータルサイトで予定を確認できるようにしたい、という狙いです。Googleカレンダーには埋め込み用リンクを発行する機能があるため、実装自体は難しくないと見込まれています。

ただし、レビュー経験の豊富なメンバーから重要な指摘がありました。「埋め込みカレンダーはURLを知っていれば誰でも見られる状態になるはず。それで問題ないか」「**カレンダーの参照権限を持っているアカウントと、ポータルサイトにアクセスしているアカウントが同じとは限らない**」という点です。ログイン必須のページに置くから大丈夫、と単純には言い切れないことが分かり、作る方向で検討しつつ、**事前にアクセス権限まわりを調査してから着手する**ことになりました。

### 初めてのタスク割り当てとGitHub入門

新メンバー2名には、最初のタスクとして取り組みやすい修正を割り当てました。1つは**会員プロフィールの自己紹介欄の縦幅を5〜6行分広げる**修正、もう1つは**スクロール時にカードの影がヘッダー付近にはみ出して見える違和感を、カードのブロックを数ピクセル内側に寄せて解消する**修正です。「設計は本来、実装の知見がある人がやるべき上流工程。まずは設計を変えずに済む小さな修正から」という経験者の助言を踏まえた采配です。このほか、経験のあるメンバーには会員一覧の**役職別表示**を担当してもらうことになりました。

あわせて、GitHubでの作業手順も解説しました。ブランチ名は `feature/` を頭に付けて修正内容が分かる英単語を続けるというルールや、ブランチを切ってVS Codeで修正しプッシュするという流れです。話題は `git checkout` と `git switch` の違いにも及び、「switchはブランチ切り替え専用で、存在しないブランチ名を指定してもエラーになるだけなので安全」という知見が共有されました。初心者のサポート体制については「経験者がガイドしないと詰まるのでは」という意見もありましたが、「今はAIに聞きながら自分で進めて、詰まったら相談する形で一度やってみよう」という方針に。**失敗したらフォルダごと消してクローンし直せばいくらでもやり直せる**、という心強い(?)アドバイスもありました。

## 活用した技術

### JestとGitHub ActionsによるCI（継続的インテグレーション）

**Jest**は、JavaScript/TypeScript向けの定番テストフレームワークです。ボタンや入力欄などが期待どおりに動くかをコードで記述し、自動で検証できます。今回はTypeScriptコードをテストするために `ts-jest` と組み合わせて導入しました。

これを**GitHub Actions**と組み合わせると、コードがpushされるたびにテストが自動実行される、いわゆるCI（継続的インテグレーション）の環境になります。今回のワークフローでは `paths: "app/**"` という指定により、アプリ本体のコードが変更されたときだけテストを走らせて、無駄な実行を減らしています。テスト自体はこれから作り込む段階ですが、「まず自動実行の土台を作り、テストケースは後から充実させる」という進め方は、CI導入の現実的なステップといえます。

### リリースブランチとGitタグによるバージョン管理

このプロジェクトでは、`main` ブランチは実は開発用で、本番用のコードは `release` ブランチに反映するという運用を取っています。リリース時には、Gitの**タグ機能**で `v4.1.0` のようなバージョン番号を付け、どの時点のコードがリリースされたかをいつでも辿れるようにしています。

会議では、GitHubの**Insights（インサイト）にあるNetwork（ネットワーク）**画面も紹介されました。ブランチが枝分かれしてmainに戻り、releaseブランチへ反映されていく流れが図で確認でき、リリースの初めてのメンバーにもブランチ運用の全体像が伝わりやすい機能です。

### Googleカレンダーの埋め込みとアクセス権限

Googleカレンダーには、Webページに貼り付けられる埋め込み用リンク（iframe）を発行する機能があり、技術的には数行のHTMLでカレンダーを表示できます。手軽な一方で、埋め込みURLは「URLを知っている人なら誰でも見られる」形式になるため、限定公開したい情報には注意が必要です。

今回の議論で浮かび上がったのは、**アプリのログイン認証とカレンダー自体の参照権限は別物**という点です。ポータルサイトにログインできるアカウントが、必ずしもカレンダーの共有設定に含まれているとは限りません。外部サービスを組み込むときは「誰が・どの権限で・何にアクセスするのか」を実装前に整理する必要がある、という好例になりました。

## 総括

今回は、プルリクエストテンプレートの刷新、ログイン画面の注意メッセージ、Jest×GitHub Actionsのテスト自動実行と、開発の土台を固める成果が揃い、バージョン4.1.0のリリースまで到達しました。前回決めたばかりの「緊急パッチリリース」運用が早速実践された形で、決めたルールをすぐ回してみるチームのフットワークが表れています。

また、新メンバー2名の環境構築が完了し、最初のタスク割り当てまで進んだのも大きな一歩です。「AIに聞きながらまず自分で進めてみる」という今の時代らしい学び方と、詰まったらすぐ相談できるチームの体制がどう機能するか、次回以降の進捗が楽しみです。シンラボカレンダーのような新機能も、権限調査というひと手間を惜しまず着実に進めていきます。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
