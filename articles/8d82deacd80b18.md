## 開発したもの

### カテゴリー管理機能（追加・編集・削除）

ポータルサイトで扱う動画・資料・アプリ紹介の「カテゴリー」を、管理画面から新規作成・編集・削除できる機能を実装しました。これまでカテゴリーの変更はデータベースを直接操作する必要がありましたが、コンテンツ管理権限を持つユーザーであれば画面から操作できるようになります。サイドナビゲーションには、権限を持つユーザーにだけ「カテゴリー管理」メニューが表示されます。

データベース側では、Supabase の RLS（Row Level Security）ポリシーを追加し、カテゴリーの作成・更新ができるのは `admin` または `maintainer` ロールのユーザーだけに制限しています。

```sql
-- supabase/migrations/04_policies/categories_policies.sql（抜粋）
-- SELECT: adminまたはmaintainerは削除済みを含むcategoriesを閲覧可能
DROP POLICY IF EXISTS "content_managers_can_read_all_categories" ON "categories";
CREATE POLICY "content_managers_can_read_all_categories" ON "categories"
  FOR SELECT
  TO authenticated
  USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE
        auth_id = auth.uid()
        AND role IN ('admin', 'maintainer')
        AND status = 'active'
        AND is_deleted = FALSE
    )
  );
```

削除は物理削除ではなく**論理削除**（`is_deleted` フラグを立てる方式）で、削除するカテゴリーに紐づいていたコンテンツは「未分類」カテゴリーに自動で付け替えられます。受け皿となる「未分類」カテゴリー自体は削除できないようガードされています。

```typescript
// app/services/api/categories-client.ts deleteCategory（抜粋）
    const tableName = getTableNameByType(categoryType);
    const { error: moveError } = await supabase
      .from(tableName)
      .update({ category_id: uncategorized.id })
      .eq("category_id", id)
      .eq("is_deleted", false);

    if (moveError) {
      return { success: false, error: moveError };
    }

    const { error: deleteError } = await supabase
      .from("categories")
      .update({ is_deleted: true })
      .eq("id", id);
```

また、カテゴリーの追加・編集では表示位置（先頭・末尾・指定カテゴリーの直後）を指定でき、操作後には表示順（`display_order`）を1から振り直す再採番処理が走ります。この再採番は `Promise.all` を使って複数レコードを一括更新する実装になっており、会議ではここが議論の的になりました（詳細は「会議の様子」で紹介します）。

```typescript
// app/services/api/categories-client.ts reorderCategoriesByType（抜粋）
  await Promise.all(
    categories.map(async (category, index) => {
      const { error } = await supabase
        .from("categories")
        .update({ display_order: index + 1 })
        .eq("id", category.id);

      if (error) {
        throw new Error(`並び順再採番に失敗しました(id: ${category.id}): ${error.message}`);
      }
    })
  );
```

### プルリクエストテンプレートに「ユニットテスト」欄を追加

前回の会議で議論した**ユニットテストの要否判断基準**がテスト設計書に追記され、マージされました。あわせて、プルリクエストのテンプレートに「ユニットテスト」のチェック欄が追加されています。

```markdown
## ユニットテスト

<!-- テストの追加・修正が必要かを確認してください（判断基準: docs/testing.md 2.5節）
     必須: 認証・認可ロジック / 共通ユーティリティ関数 / 外部API連携のエラーハンドリング
     不要: 単純なCRUDラッパー / UIの見た目 / 定数・型定義 など -->

- [ ] テストの追加・修正は不要
- [ ] テストを追加・修正した
```

会議では「基本的にテストは必須ではないが、あった方がいいとレビュアーと判断したら追加する」「判断に迷ったら一旦なしでマージし、後から追加してもよい」という運用が改めて共有されました。**テストに気を取られて開発が止まることは避ける**、というバランス感覚がこのチームらしいポイントです。

このほか、当日開催されるカレンダーイベントをポータルサイトに表示する機能の設計ドキュメントもマージ済みで、実装はレビュー段階に進んでいます。

## 会議の様子

### 承認済みのPRをあえて深掘り — Promise.allは残すべきか

今回の会議で最も学びが多かったのは、すでにレビュー承認が済んでいたカテゴリー管理機能のプルリクエストを、リードがあえて取り上げた場面です。「クリティカルな問題ではないが、勉強も兼ねて共有したい」という前置きで始まりました。

論点は、表示順を更新する処理で使われている `Promise.all` です。`Promise.all` は括弧内の処理を**同時並行で実行する**ため高速になる一方、今回のケースでは `categories` という**1つのテーブルを複数の更新処理が同時に触りに行く**ことになります。リードからは「データ数が少ない今は問題にならないが、データが増えると弊害が出る可能性がある。1つのテーブルを同時に並行操作するのは避けた方がよい」という指摘がありました。

これに対して担当メンバーは、「懸念はその通り」とした上で、**この一括更新が終わらないと後続の処理を開始できないため、完了を待ち合わせる目的で `Promise.all` と `await` を入れている**と実装意図を説明しました。リードは「個人的には `Promise.all` を外して1件ずつ順番に処理する形でもよいと思うが、`await` が必要という点はその通り」と応じ、両者の理解をすり合わせました。

最終的には、この機能は**管理者相当のユーザーしか触らず、対象データ数も限られているため実害はない**と判断し、修正なしでそのままマージすることになりました。なお、同じ箇所は GitHub Copilot の自動レビューも指摘していたとのこと。「直さなくてよいコード」を題材に設計上のリスクを言語化して共有する、レビュー文化の成熟を感じる一幕でした。

### Web学習サービスとのログイン連携を「やめる」決断

シンラボ会員向けにWeb技術を学べる**Web学習サービス**を別リポジトリで開発中であることが共有され、ポータルサイトとログイン機能を統一する計画について「一旦やめる」という結論が報告されました。

理由は、調査の結果**「ログインした状態を保持し続ける」ことが想定以上に難しい**と分かったためです。単に連携するだけなら難しくないものの、セッション維持まで考えるとシンプルに分けた方が分かりやすく、開発も楽になります。ポータルサイトのデータベースをそのまま共用すれば実現はできるものの、それはそれで開発がややこしくなるため見送りました。

会議では「いっそポータルサイトに組み込んでは？」という提案も出ましたが、リードの見解は「選択肢としてはアリだが、**アプリが複雑になりすぎるのが最大の問題**。開発が大変になり、トラブル時の原因究明も難しくなる」というもので、こちらも見送りに。代わりにポータルサイトからリンクで飛べるようにする案が検討されています。

デモでは、フェーズ単位にスライド（PDF）・動画（YouTube埋め込み）・演習をステップバイステップで学ぶ画面構成や、演習で提出したコードを**AIがレビューしてフィードバックする機能**が披露されました。一方で「会員向けにリリースするなら、トークンを使い果たしてもサービスが継続できる仕組みが必要では」という指摘があり、「AIレビューの使い放題はやめるべき。1日5回までのような回数制限や、ユーザーごとの呼び出し回数の記録・制限が必要になりそう」という議論に発展しました。ビジネス面も含めて要検討としつつ、正式リリースは4月を予定しています。

### レビューで揃える命名規則とファイルの置き場所

レビュー中のURL入力バリデーション機能では、リードから2つの修正依頼がありました。1つ目は**ファイル名の命名規則**です。新規ファイルがアンダースコアで単語をつなぐ「スネークケース」で命名されていましたが、このプロジェクトではハイフンでつなぐ**ケバブケース**に統一しているため、リネームをお願いすることに。あわせて語順も「URLバリデーション」の方が自然では、という提案がありました。

2つ目は**ファイルの置き場所**です。今回のファイルは Supabase へアクセスする処理を置くディレクトリに作られていましたが、バリデーションのようなチェック処理はユーティリティ用のディレクトリに置く決まりのため、移動を依頼しました。VS Code 上でファイルをドラッグして移動すると、インポート文をまとめて修正するか確認するポップアップが出る、という実践的なテクニックも共有されました。

さらに、このイシューはもともと**サーバーサイド**のバリデーション追加が目的でしたが、今回の実装は入力時・送信時の**フロントエンド**バリデーションであることも話題に。修正自体は重要な内容なのでこのままマージまで進め、サーバーサイド分は別イシューにするか継続対応にするか相談する、と整理されました。

### 開発環境の小さなつまずきを拾う

このほか、開発環境まわりの改善が3つ動きました。1つ目は**テスト用カレンダーの追加**です。当日イベント表示機能のテストで「日付を跨ぐケースが検証できない」という報告があり、原因は開発環境に本番と同じカレンダーしか登録されておらず、メンバーに編集権限がないことでした。そこで、開発メンバーが自由にテストデータを作れるカレンダーを新設することに決まりました。

2つ目は**Prettier と VS Code 標準フォーマッターの競合**です。あるメンバーから「両者で空白行などの設定値が異なり、保存時に競合を起こしている」という報告がSlackであり、その場でイシュー化されました。3つ目はGitHub Projectsの運用で、プルリク作成時にProjectsタブでプロジェクトを追加すると、ステータスなしのカードが自動で作られてしまうため、**PR側からのプロジェクト追加は不要**という運用が確認されました。

## 活用した技術

### Promise.all — 並行実行の速さと引き換えのリスク

JavaScript / TypeScript の `Promise.all` は、複数の非同期処理を**同時並行で実行し、すべての完了を待つ**APIです。プログラムは通常上から順番に実行されますが、`Promise.all` に処理の配列を渡すと一斉に走り出すため、待ち時間が重ならず高速になります。

ただし今回のように、並行実行される処理がすべて**同じテーブルへの更新**である場合は注意が必要です。データ数が少ないうちは問題になりませんが、件数が増えると同時更新による競合や負荷が顕在化する可能性があります。「速くなるから」と機械的に使うのではなく、処理同士が同じリソースを触らないか確認する——今回のレビュー共有は、`Promise.all` を使う際の基本的なチェックポイントを学べる好例でした。なお `for...of` などで1件ずつ `await` すれば、遅くなる代わりに更新は直列化されます。

### Supabase RLSによるロールベースのアクセス制御

Supabase（PostgreSQL）の RLS ポリシーは、テーブルへの操作を行単位で制御する仕組みです。今回のカテゴリー管理機能では、`USING` / `WITH CHECK` 句の中で `users` テーブルを参照し、ログイン中のユーザー（`auth.uid()`）のロールが `admin` または `maintainer` であることを条件にしています。

この方式の利点は、**アプリのコードを経由しないアクセスに対しても権限チェックが効く**ことです。フロントエンドの画面出し分け（権限のあるユーザーにだけメニューを表示する）はあくまでUX上の配慮であり、最後の砦はデータベース側のポリシーが担う。フロントとDBの二段構えで守るのが、Supabaseを使った開発の定石です。

### Prettier（オートフォーマッター）とエディタ設定の競合

Prettier は、コードやマークダウンの書式を保存時に自動で整える**オートフォーマッター**の代表格です。見出しの後に空白行を入れる、表の罫線の長さを揃える、箇条書きのインデント幅を統一する——といったルールを `.prettierrc` という設定ファイルに定義しておけば、メンバーごとの書き方のばらつきを自動で吸収できます。チーム開発では「人がスタイルを指摘しなくて済む」大きな効果があります。

一方で、VS Code 自体にもフォーマット機能があり、**双方が異なる設定で有効になっていると保存のたびに書式がせめぎ合う**競合が起きます。今回のケースもまさにこれで、プロジェクトのPrettier設定とエディタ側の設定が食い違っていたことが原因とみられます。フォーマッターは「プロジェクトで1つ」に揃え、エディタの既定フォーマッターをPrettierに指定するのが基本の対処法です。

## 総括

今回は、カテゴリー管理機能という比較的大きな機能がマージまで到達し、コンテンツ運用がデータベース直接操作から画面操作へと一歩前進しました。論理削除と「未分類」への付け替え、RLSによる権限制御、表示順の再採番と、地味ながら考えどころの多い実装です。

会議の見どころは「直さないコード」を巡る議論でした。承認済みのPRをあえて開き、`Promise.all` のリスクと実装意図を突き合わせた上で「今回は実害なし」と合意してマージする——正解を押し付けるのではなく、判断の根拠をチームの共有知にしていくレビュー文化が印象的です。Web学習サービスのログイン連携を「やめる」と決めた場面も含め、**作る判断と同じくらい、やめる・直さない判断に理由を尽くす**回だったといえます。
