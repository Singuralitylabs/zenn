## 開発したもの

### 役職タグを管理する2つのテーブルを追加

会員一覧ページに「チームリーダー」「広報チーム」のような役職・所属をタグ形式で表示する機能に向けて、担当メンバーが設計とマイグレーションSQLを作成し、マージされました。追加されたのは**役職マスターの `positions` テーブル**と、**ユーザーと役職を紐づける中間テーブルの `position_tags` テーブル**の2つです。

```sql
-- supabase/migrations/01_tables/positions/00_create_positions_table.sql（抜粋）
CREATE TABLE IF NOT EXISTS positions (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    description TEXT,
    display_order INTEGER,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

テーブル名は当初「ロール」を検討しましたが、既存の `users` テーブルにある `role` カラム（管理者/メンバーなどの権限）と紛らわしいため、`positions` に決めたとのことです。

```sql
-- supabase/migrations/01_tables/position_tags/00_create_position_tags_table.sql
CREATE TABLE IF NOT EXISTS position_tags (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    position_id INTEGER NOT NULL REFERENCES positions(id) ON DELETE CASCADE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(user_id, position_id)
);
```

`position_tags` は `user_id` と `position_id` のペアだけを持つシンプルな構成で、**`UNIQUE(user_id, position_id)` の制約により、同じユーザーに同じ役職タグを重複して紐づけられない**ようにしています。これにより、1人のユーザーに複数のタグを付けることができます。

RLS（Row Level Security）ポリシーは基本的に `users` テーブルと同様ですが、削除だけは扱いを変えています。`position_tags` はIDのペアしか持たず消えて困る固有情報がないため、論理削除ではなく**物理削除**を採用しました。

```sql
-- position_tagsの削除ポリシー（docs/database.mdより抜粋）
USING (
  -- ユーザー自身の役職タグを削除できる
  EXISTS (
    SELECT 1 FROM users
    WHERE
      users.id = position_tags.user_id
      AND users.auth_id = auth.uid()
      AND users.status = 'active'
      AND users.is_deleted = FALSE
  )
  OR
  -- 管理者は全ての役職タグを削除できる
  EXISTS (
    SELECT 1 FROM users
    WHERE
      auth_id = auth.uid()
      AND role = 'admin'
      AND status = 'active'
      AND is_deleted = FALSE
  )
);
```

あわせて設計書も更新し、メンバー詳細モーダルに「役職・所属チーム」の表示を追加、メンバーカードもこれまでの「役割（メンバー/管理者）」表示から役職・所属チーム表示へ書き換える方針となりました。

### 自己紹介欄の入力フォーム改善（前週マージ分の解説）

前週にマージ済みだったプロフィールページの改善についても、担当メンバーから解説がありました。自己紹介の入力欄が1行分の高さしかなく書きづらかった問題への対応です。

```tsx
// app/(authenticated)/profile/components/Template.tsx（変更後）
<Textarea
  id="bio"
  value={bio}
  onChange={e => setBio(e.target.value)}
  autosize // ← これを追加して、サイズ自動調整を有効化
  minRows={5} // ← 現実的な最小行数（例：5行）
  maxRows={10} // maxRows を設定しなければ、入力に応じて無限に伸びます
/>
```

`autosize` で入力量に応じた自動リサイズを有効にし、`minRows` で最低限の入力枠を確保、`maxRows` で無限に伸びないよう上限を設けるという3点セットの修正です。レビューを担当したリードメンバーからも「テキストエリアのサイズはこの3つでコントロールできる、と覚えておくとよい」と補足がありました。

このほか、動画・資料・会員一覧ページのカード表示の横幅を調整するUI改善もマージされています。

## 会議の様子

### 初期データはSQLに残すべきか — マスターデータ管理の議論

役職タグ設計のレビューで議論になったのが、`positions` テーブルのCREATE文に含まれていた**初期データのINSERT文**です。担当メンバーは「チームリーダーと各チーム名など、確定していそうな名前だけをとりあえず入れた」と説明しましたが、リードメンバーから「これを残すと、テーブルにデータを追加するたびにこのSQLファイルも更新しないと整合性が取れなくなるのでは」という指摘が入りました。

「他のテーブルではそこまでやっていないはず」と確認していくと、実はカテゴリーテーブルにも同様の初期データが入っていた前例が見つかります。それでも「**マスターデータとして管理するなら、SQLファイルとは別の仕組みでやったほうがいい**。もっと言えば、DBそのものをマスターとして扱えば十分では」という結論に至り、初期データは一旦削除する方向で合意。あわせてマスターデータの管理方法を検討する改善タスクをissueとして起票することになりました。ファイルに書いた情報は保守し続けるコストが発生する、という設計の基本を再確認する場面でした。

### Supabase有料版は「思ったよりお金がかかる」— 見送りの方向へ

リードメンバーが進めていたSupabase有料版の調査結果が共有されました。事前に把握していたのは「月額25ドル」という情報だけでしたが、実際に調べると、**プロジェクトを1つ増やすごとに約10ドルの追加予算が必要**で、データベースのブランチ機能も別料金（1ブランチを1ヶ月残すと約10ドル）と、想定以上に費用がかさむ料金体系だと分かりました。

有料版には「一定期間使わないとデータベースが停止する無料版の制限がなくなる」「ストレージ容量が増える」「認証画面のURL表示を改善できる」といったメリットもあります。しかし、団体の代表には「月額25ドル」で話を通していた経緯もあり、**有料版の利用は見送って無料版を使い続ける方向**に傾いています。幸い、有料版は契約済みなもののデータベース自体の移行はまだ行っていなかったため、後戻りは容易です。「別のデータベースサービスに乗り換える選択肢は？」という質問には、「ポータルサイトはSupabase前提で作られており乗り換えは大工事になる。使い勝手も一番良い」として考えていないとの回答でした。結論は今月中に出す予定です。

### カレンダー機能の相談 — 2つのカレンダーと祝日表示

開発中のカレンダー表示機能について、担当メンバーからローカル環境の画面を共有しながら複数の相談がありました。1つ目は「シンラボには**イベントとミーティングの2つのGoogleカレンダーがある**が、違いは何か。1つの画面にまとめて表示してよいか」というもの。ミーティングは各チームの定例会議、イベントは忘年会・交流会・プログラミング体験会などの行事を登録しているという使い分けが説明され、画面上は1つのカレンダーにまとめて表示する方針で合意しました。

2つ目はアクセス権限の確認です。カレンダーはユーザー登録された会員のみが閲覧できる仕様であること、そのユーザー管理はSupabaseの `users` テーブルで行い、初回ログイン時の承認は管理者が1人ずつ行っていること、Googleカレンダー自体へのアクセス権は会員のGoogleグループで管理していることが整理されました。

3つ目は「日本の祝日」カレンダーに**クリスマスや銀行休業日まで含まれてしまう**が外すべきか、という相談。担当メンバーは外す方に傾いていましたが、「個人的にはあったほうが嬉しい」「自分もあり派」と残す意見が続き、祝日以外の記念日も含めて表示する方向で決まりました。小さな仕様でも独断で決めずに合意を取るスタイルが徹底されています。

### git rebaseをライブ実演 — コンフリクトは「どこでも起きる」

カレンダー機能ではサイドナビにボタンを追加する予定ですが、直前にマージされたアプリ紹介ページも同じサイドナビにボタンを追加したばかり。このまま進めると**コンフリクト（複数人が同じ箇所を編集した際の衝突）が起きる可能性が高い**ため、リードメンバーの提案で、その場でgit rebaseを実演することになりました。mainブランチで `git pull` して最新化し、自分の開発ブランチに戻って `git rebase main` を実行、最後に `git push --force origin HEAD` で強制プッシュするという一連の流れを、画面共有しながら一緒に操作します。リベース後はコミット数の表示が増える理由や、そのままプッシュするとエラーになるため強制プッシュが必要になることも解説されました。

「コンフリクトはそういうものなのか」という質問には、「どこの開発現場でもよく起きている。リベースなどのスキルを身につけてトラブル対応できるようになるのが、エンジニアの大事な能力の1つ」との回答がありました。

また、このメンバーが生成AIを活用してコードを修正したことに関連して、リードメンバーから**「生成AIを使うことは全く問題なく、むしろ今の時代は存分に使ったほうがいい」**という方針が示されました。ただし、生成AIが修正した内容が何なのかはできるだけ理解しておくこと、そして定例でPRの内容を自分の言葉で説明するアウトプットが学習の定着に効く、という補足つきです。AIに任せる部分と自分で理解する部分のバランスを、チームとして言語化した場面でした。

## 活用した技術

### 中間テーブルとUNIQUE制約 — 多対多の実装

「1人のユーザーが複数の役職を持ち、1つの役職に複数のユーザーが就く」という関係は、データベースの典型的な**多対多（Many-to-Many）**です。前回までの設計議論を経て、今回はマスターテーブル（`positions`）と中間テーブル（`position_tags`）という構成で実際のSQLに落とし込まれました。

ポイントは中間テーブルに付けた複合ユニーク制約 `UNIQUE(user_id, position_id)` です。アプリケーション側でチェックし忘れても、データベースが重複した紐づけの登録を拒否してくれるため、データの整合性を最後の砦として守れます。また、`ON DELETE CASCADE` により、ユーザーや役職が削除された際に紐づけレコードも自動で削除されます。

### 論理削除と物理削除の使い分け

このポータルサイトでは、ユーザーや資料などのテーブルは `is_deleted` フラグを立てるだけの**論理削除**を基本としています。誤操作からの復旧や履歴の追跡ができる一方、データは残り続けます。今回の `position_tags` はIDの組み合わせしか持たず「消えて困る情報」がないため、レコードを本当に消してしまう**物理削除**を採用しました。「とにかく論理削除」ではなく、テーブルが持つ情報の性質から削除方式を選ぶという判断基準は、設計の参考になる考え方です。

### git rebase と強制プッシュ

`git rebase` は、自分のブランチの変更を、更新が進んだmainブランチの最新状態の上に積み直すコマンドです。今回の実演では次の手順が共有されました。

```text
1. mainブランチに切り替えて git pull（最新化）
2. 自分の開発ブランチに戻る
3. git rebase main（mainの更新を自分のブランチに反映）
4. git push --force origin HEAD（強制プッシュ）
```

リベースはコミットの積み方を作り替える操作のため、リモートに同じブランチをプッシュ済みの場合は履歴が食い違い、通常のプッシュはエラーになります。そこで強制プッシュが必要になりますが、**共有ブランチに対する強制プッシュは他の人の作業を壊す危険がある**ため、自分しか使っていないブランチに限定するのが原則です。同じ箇所を触る他の変更がマージされたら、着手前にリベースしておくことでコンフリクトの発生自体を減らせます。

今回は、役職タグ機能のテーブル設計がマージされ、SQLレベルの具体的なレビューが行われた回でした。テーブル名の衝突回避、ユニーク制約、削除方式の使い分け、初期データの置き場所と、小さな2テーブルの追加にも設計判断が数多く詰まっていることが分かります。特に「初期データをSQLに残すか」の議論は、目先の便利さと保守コストを天秤にかける良い教材となりました。

一方で、Supabase有料版の見送り判断や、カレンダーの祝日表示の合意形成、git rebaseのライブ実演など、技術・お金・チーム運営のバランスを取りながら進むチーム開発ならではの場面も多い回でした。12月7日を目標とするバージョン5リリースに向けて、各タスクの仕上げが続きます。
