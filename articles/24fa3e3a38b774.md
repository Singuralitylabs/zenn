## 概要

本記事は、[チーム開発記録31：メンバー承認機能とレビュー運用](https://zenn.dev/singularitylabs/articles/27cde379929679)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回は約2ヶ月分の開発の集大成として、**ポータルサイトver5を本番環境にリリース**しました。98コミット・59ファイルにおよぶ変更をエラーなく反映し、プロジェクトはver6へと移行しています。

開発面では、前回から進めていた**メンバー承認機能（管理画面ダッシュボード）**が完成したほか、React/Next.js界隈で大きな話題となった**致命的な脆弱性への緊急対応**も実施しました。会議では、権限チェックをクライアントサイドで行う実装のセキュリティリスク、AIに提案されるがまま入れた `as unknown as` という型アサーションの是非、GitHub Projectsがメンバーから見えなくなった原因の調査など、チーム開発ならではの実践的なトピックが数多く飛び交いました。

## 開発したもの

### ポータルサイトver5のリリースとタグ付け

12月14日（日）に、ポータルサイトver5を本番環境にリリースしました。この2ヶ月ほどでチームが積み上げた**98コミット・59ファイルの変更**を本番環境用ブランチにマージし、エラーなく無事に反映できました。

リリースにあわせて、Gitの**タグ付け**も行っています。今回は `v5.0.0` というタグをメインブランチに付与し、その中にどんな修正を行ったかの一覧を記載、あわせてその時点のソースコードの圧縮ファイルも作成しました。本格的なアプリ開発の現場ではほぼ必ず行われている運用で、手順はWikiの「本番環境リリースの手順」に文書化されています。

### メンバー承認機能（管理画面ダッシュボード）の完成

サイトにアクセスしたものの、まだ承認を得ていない「承認待ち」ユーザーを管理者が承認・否認できる管理画面が完成し、ver5リリースに含まれました。サイドバーの「管理画面」ボタンから `/dashboard` ページに遷移すると、承認待ちユーザーがカードで一覧表示されます。

Next.jsのルールに従い、ページの入り口となる `page.tsx` では、現在のユーザー取得 → 承認待ちユーザーの取得 → 権限チェックという流れをすべて**サーバーサイド**で行っています。

```tsx
// app/(authenticated)/dashboard/page.tsx（抜粋）
export default async function DashboardPage() {
  const { authId, error: currentUserError } = await getServerCurrentUser();
  if (currentUserError) {
    console.error("認証情報の取得に失敗:", currentUserError);
    return <p>認証情報が取得できませんでした。</p>;
  }

  const { error, data: initialData } = await fetchApprovalUsers();
  const data = initialData ?? [];

  // ...（中略）...

  const { role, error: roleError } = await fetchUserInfoByAuthId({ authId });

  if (!checkAdminPermissions(role)) {
    console.error("管理者ではありません.");
    return <p>管理者ではありません</p>;
  }

  return <DashboardPageTemplate members={data} />;
}
```

画面表示を担うテンプレートコンポーネントでは、取得した承認待ちメンバーを `map`（繰り返し処理）で1件ずつカード表示しています。カードの「承認」「否認」ボタンを押すとモーダルが開き、確定するとユーザーのステータスがアクティブまたはリジェクトに切り替わる、という流れです。

```tsx
// app/(authenticated)/dashboard/components/Template.tsx（抜粋）
{members.length > 0 ? (
  <div className="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 2xl:grid-cols-4 gap-6 lg:gap-8 mb-8">
    {members.map(member => (
      <MemberActionCard key={member.id} member={member} />
    ))}
  </div>
) : (
  <p className="text-gray-500 mt-4">承認待ちのユーザーはいません。</p>
)}
```

動画一覧や資料一覧など他のページも基本的に同じ構成なので、この実装を読み解けばサイト全体の作りが理解しやすくなっています。

### 権限チェックをサーバーサイドへ移行

この機能はもともと別のメンバーが実装したものをリードが引き取って仕上げたのですが、その過程で**セキュリティ上よろしくない実装**が見つかりました。当初はサイドバーのコンポーネント（`use client` が付いたクライアントサイドのコード）の中で「このユーザーは管理者か？」の判定を行っていたのです。

ブラウザ側で権限を判定する実装では、悪意のある人が「私は管理者です」という情報を送り出せば管理者として認識されてしまう恐れがあります。そこで、権限チェックはサーバーサイドの `layout.tsx` で行い、サイドバーには判定済みの `isAdmin` という真偽値だけを渡す形に修正しました。

```tsx
// app/(authenticated)/components/SideNav.tsx（抜粋・変更後）
export function SideNav({ isAdmin }: { isAdmin: boolean }) {
  const [open, setOpen] = useState(false);
  const router = useRouter();

  // isAdminに応じて動的にnavItemsを構築
  const navItems = useMemo<NavItem[]>(
    () => [...DEFAULT_NAV_ITEMS, ...(isAdmin ? [ADMIN_NAV_ITEM] : []), LOGOUT_NAV_ITEM],
    [isAdmin]
  );
```

これでサイドバーは「管理者なら管理画面ボタンを出す」という表示の出し分けに専念し、権限の判定そのものはサーバーサイドが担う構成になりました。

### Next.jsの脆弱性への緊急パッチ適用

2〜3週間ほど前から、Reactが致命的な脆弱性を公表し、ReactやNext.jsの利用者に早急なパッチ適用が呼びかけられていました。対応内容はシンプルで、Next.jsのバージョンを引き上げるだけです。

```diff
     "lucide-react": "^0.475.0",
-    "next": "^15.4.1",
+    "next": "^15.4.10",
     "react": "^19.0.0",
```

このパッチを当てないと他のバージョンアップができない状態になっていたため、ver5リリースに先立って対応を完了させました。

### SNSアカウントURL用カラムの追加

プロフィール画面にSNSアカウントの編集機能を追加する取り組みも進行中です。今回は担当メンバーがSupabaseのSQLエディタで `users` テーブルへのカラム追加を実行し、あわせてデータベース設計書と仕様書を更新するプルリクエストがマージされました。追加されたのは `x_url`・`facebook_url`・`instagram_url`・`github_url`・`portfolio_url` の5カラムで、今後プロフィール編集フォームからこれらのURLを入力できるようにしていきます。

## 会議の様子

### 役割タグはどこに表示する？ — 名前の右か、下か

会員一覧カードとメンバー詳細モーダルに役割タグを表示する機能は、プルリクエストの提出まで完了しました。悩ましいのはタグの表示位置です。設計書では名前の下に置く想定でしたが、タグの数によって**カードの高さが人ごとにバラバラになってしまう**ため、担当メンバーは名前の右側に出す実装を試みました。ただし今度は、英語表記など長い名前だとタグに隠れてしまう問題が発生します。

議論の結果、「クリックすればモーダルで名前は確認できる」「スマホ表示では1列に並ぶので高さの差は問題にならない」という**モバイルファーストの観点**から、名前の右に表示し、長い名前は省略記号（...）で切る現在の実装を採用することになりました。カードの高さを完全に揃える対応は、余力があれば別件として取り組みます。

また、当初のタスクに含まれていた「代表・副代表などを一覧の上部に固定表示する」件は、仕様がまだ煮詰まっていないため**別タスクに切り出し**、タグ表示の完了をもって現在のissueをクローズする方針を決めました。チーム別のフィルタ機能も、「そもそも各自が自分の所属チームを登録してくれるか怪しい」という利用実態を踏まえ、今回は見送っています。

### `as unknown as` は正解か — Claude Codeに聞いてみた

タグ表示の実装中、型エラーの解消のためにAIに提案されるがまま `as unknown as MemberType` という記述を入れたら直った、という報告がありました。リードが「素直に読むと『MemberTypeという型は無視してくれ』と書いているように見える」と疑問を呈し、その場でプログラミング特化AIの**Claude Code**に検証させてみることに。

返ってきた答えは「問題の修正ではなく、**型安全の完全な放棄**」。`as unknown as` は二重型アサーションと呼ばれる形で、コンパイラのチェックを完全にバイパスしてしまうため、実行時エラーのリスクや保守性の低下を招くという指摘でした。この結果を受けて、Claude Codeに修正案を作らせてプルリクエストにコメントすることになりました。

Claude Codeは開発中のVS Code上で動き、何も指示しなくてもプロジェクトのコードを読んだ上で回答してくれるため、一般的なチャットAIより正確で速いのが利点です。利用にはお金がかかる可能性があるため強制はしない、という前提で、チームでの活用を進めていきます。

### 「プロジェクトが見えない」— GitHub Projectsとリポジトリの紐付け

会議の途中、複数のメンバーから「GitHub Projectsでver6のプロジェクトが見つからない。ver5までしか見えない」という声が上がりました。設定を確認しても権限まわりに違いは見当たらず、一同で原因を探ることに。

判明した原因は、**新しく作ったプロジェクトがリポジトリに紐付いていなかった**ことでした。メンバーはポータルサイトのリポジトリの「Projects」タブからプロジェクトを開いていたため、紐付けされていないver6が一覧に出てこなかったのです。リードが紐付け作業を行うと、全員がver6を見られるようになりました。「プロジェクトは作った後にリポジトリとの紐付けが必要」という、意外と知られていないGitHubの仕様をチーム全員で学んだ一幕でした。

### カレンダー機能の共有とGit操作のライブサポート

Googleカレンダーで管理されているシンラボのイベント・ミーティング・祝日を、ポータルサイト内のカレンダーに表示する新機能も共有されました。シンラボ会員だけに共有されているカレンダー情報を取得するには、Google Calendar APIの導入や認証アカウントの作成・カレンダーへの追加といった手順が必要で、想定以上に複雑な実装になったとのこと。月・週・日の3単位で表示でき、当月の前後2ヶ月分は初期表示時に自動取得、それ以降の月は画面遷移時に読み込む仕様です。現在レビュー中で、Slack通知APIを含むAPI仕様書のドキュメントも追加されました。レビュー担当からは「依存パッケージの更新を自動でプルリク化してくれる**Dependabot**を導入してはどうか」という提案もあり、issueとして起票することになりました。

また、SNSカラム追加を担当したメンバーから「ブランチをたくさん作ってしまい混乱している」という相談があり、画面共有をしながらのライブサポートを実施。ローカルブランチがリモートより37コミット遅れていることを示す表示の読み方から始まり、最新化してからメインブランチで新しいブランチを切り直し、ターミナルで `git add .` → `git commit -m "..."` → `git push` と進める基本の流れを、実際に手を動かしながら確認しました。VS CodeのGUIに変更が表示されないときはターミナル操作が確実、という実践的なノウハウも共有されています。

## 活用した技術

### 依存パッケージの脆弱性対応

今回のNext.jsのバージョンアップのように、利用しているフレームワークやライブラリに脆弱性が見つかり「早急にパッチを当ててください」と呼びかけられる事態は、アプリを運用していれば時々発生します。脆弱性はある日突然公表されるため、**セキュリティ情報を日頃からウォッチしておく**ことが運用者には求められます。

趣味で作っているアプリなら影響は限定的ですが、商用サービスや、シンラボ会員のように実際のユーザーに使ってもらっているアプリでは、放置すれば利用者を危険にさらすことになります。「作って終わり」ではなく、公開後も依存パッケージの健全性に責任を持つ——これもアプリ開発の大事な一部です。

### 権限チェックはサーバーサイドで行う

Next.jsでは、コンポーネントがブラウザ側で動く（`use client`）のか、サーバー側で動くのかを意識する必要があります。ユーザーの権限確認のようなセキュリティに関わる処理をクライアントサイドに置くと、ブラウザから送られる情報は改ざんできてしまうため、認可を偽装される恐れがあります。

注意したいのは、**生成AIはこうしたセキュリティ観点を平気でスルーすることがある**という点です。今回のケースでも、AIが生成したクライアントサイドの権限チェックを人間のレビューも見逃してApproveしていました。AIに実装を任せる場面が増えるほど、「この処理はどちら側で動くべきか」を人間が見抜けるかどうかが、良いアプリを作れるかの分かれ目になります。

### Gitのタグ付けとリリース管理

Gitには、任意のタイミングでブランチの特定時点に「タグ」を付けられる機能があります。`v5.0.0` のようにバージョン番号をタグとして残しておけば、「本番で動いているのはどの時点のコードか」がいつでも特定でき、リリースノートやソースコードのアーカイブとセットで履歴を管理できます。

個人開発では知らなくても困りませんが、複数人での開発や、ユーザーに継続的にサービスを提供する開発では、リリースのたびにタグを打つ運用が標準的です。チームではこの手順をWikiに文書化し、誰でも同じ手順でリリース作業ができるようにしています。

## 総括

今回は、2ヶ月にわたる開発の成果をver5として本番環境に届け、リリースサイクルをひと回りさせた節目の回でした。98コミットという規模の変更をエラーなく反映できた背景には、タグ付けやリリース手順の文書化といった、これまで積み上げてきた運用の仕組みがあります。

一方で内容を振り返ると、クライアントサイド認可の修正、`as unknown as` の検証、脆弱性パッチと、**「動くコード」と「良いコード」の差**を考えさせられるトピックが多い回でもありました。AIがコードを書く時代だからこそ、セキュリティや型安全といった観点で人間がレビューの目を光らせる重要性を、チーム全体で確認できたのは大きな収穫です。ver6ではSNSリンク表示やカレンダー機能など、ユーザーに見える新機能が続々と控えています。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
