## 概要

本記事は、[チーム開発記録60：お試しユーザーの設計とRLS](https://zenn.dev/singularitylabs/articles/63fb23450ca0c2)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、ポータルサイトと学習支援アプリ「sinlab-study」を隔週交互で開発しています。今回はポータルサイトの回で、**`users` テーブルの権限管理に見つかった4件の脆弱性の修正**がマージされました。

指摘の中身は、ひとことで言えば「メンバー権限のユーザーが、管理者向けの情報にたどり着ける経路が存在する」というものです。原因は大きく2つに分かれていたため、2本のプルリクエストに分けて対応しました。

* 管理者判定が**改ざん可能なユーザーメタデータ**に依存していた（PR #422）
* RLSは行単位の制御であり**カラム単位の制限ができない**ため、ユーザーが自分の `role` / `status` を書き換えられた（PR #423）

後半では、リリースの運用方針についてもチーム内で意見が分かれた議論を取り上げます。

* チーム開発方針については、[こちら](https://zenn.dev/singularitylabs/articles/20123b869b7e6a)をご参考ください
* 技術スタックは[こちら](https://github.com/Singuralitylabs/portal-site/wiki)をご参考ください
* 開発しているポータルサイトのGithubリポジトリは[こちら](https://github.com/Singuralitylabs/portal-site)です

## 開発したもの

### 1. 管理者判定をユーザーメタデータからDBのロールへ

ポータルサイトのユーザー情報は、基本的に `users` テーブルで管理しています。しかしそれとは別に、Supabase Authには**ユーザーメタデータ**という情報の置き場所があります。

修正前は、このメタデータをもとに「このユーザーが管理者かどうか」を検証していました。ところがユーザーメタデータは、その気になれば**ユーザー自身が書き換えられます**。つまり、メンバー権限のユーザーが自分を管理者だと名乗ることが可能な状態でした。

そこで、メタデータでの検証をやめ、DB上の `users.role` を参照する `is_admin()` 関数を新設しました。

```sql
-- 現在のユーザーがadminロールを持つかを判定する
CREATE OR REPLACE FUNCTION is_admin()
RETURNS BOOLEAN
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = public, pg_catalog
AS $$
BEGIN
  RETURN EXISTS (
    SELECT 1 FROM users
    WHERE
      auth_id = auth.uid()
      AND role = 'admin'
  );
END;
$$;
```

そのうえで、管理者向けのポリシーの判定条件を `is_active_user() AND is_admin()` に差し替えています。

```sql
-- UPDATE: 管理者はすべてのユーザー情報を更新可能
DROP POLICY IF EXISTS "admins_can_update_all_users" ON "users";
CREATE POLICY "admins_can_update_all_users" ON "users"
  FOR UPDATE
  TO authenticated
  USING (
    (SELECT is_active_user()) AND (SELECT is_admin())
  )
  WITH CHECK (
    (SELECT is_active_user()) AND (SELECT is_admin())
  );
```

あわせて、SELECTポリシーも見直しました。従来は「認証済みユーザーは全データを閲覧可能」という1本のポリシーでしたが、これでは**承認前・否認済みのユーザーが全会員情報を列挙できてしまいます**。そこで以下の2本に分割しました。

```sql
-- SELECT: 旧ポリシー（全認証ユーザーが全データを閲覧可能）を削除
DROP POLICY IF EXISTS "authenticated_users_can_read_all" ON "users";

-- SELECT: ユーザーは自身のデータを閲覧可能
-- 承認前・否認済みユーザーが自身のステータスを確認するために必要
DROP POLICY IF EXISTS "users_can_read_own_data" ON "users";
CREATE POLICY "users_can_read_own_data" ON "users"
  FOR SELECT
  TO authenticated
  USING (
    auth_id = (SELECT auth.uid())
    AND is_deleted = FALSE
  );

-- SELECT: アクティブユーザーは削除されていない全データを閲覧可能
DROP POLICY IF EXISTS "active_users_can_read_all" ON "users";
CREATE POLICY "active_users_can_read_all" ON "users"
  FOR SELECT
  TO authenticated
  USING (
    (SELECT is_active_user())
    AND is_deleted = FALSE
  );
```

承認前のユーザーが自分のステータスだけは確認できるよう、「自身のデータ」と「全データ」を別ポリシーに切り分けているのがポイントです。

### 2. `role` / `status` をトリガーで保護する

もう1本のプルリクエストは、RLSの構造的な限界に対処するものです。

RLSは**行単位**の制御であり、カラム単位の制限はできません。`users` テーブルには「ユーザーは自身のデータのみ更新可能」というポリシーがあるため、**RLSだけでは自分の `role` / `status` の書き換えを防げない**のです。

具体的には、次のような状態でした。

* 承認前（`pending`）のユーザーが、自分を `active` に書き換えて**承認をバイパスできる**
* 初回登録時に `role: 'admin'` を指定することで、**いきなり管理者として登録できる**

これを防ぐために、`enforce_users_role_and_status()` トリガー関数を作成しました。トリガーは、条件を満たしたときに自動的に実行される関数です。

```sql
CREATE OR REPLACE FUNCTION enforce_users_role_and_status()
RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = public, pg_catalog
AS $$
BEGIN
  -- is_admin() は role のみを判定するため、承認済み・未削除の担保として
  -- is_active_user() と組み合わせる（否認済み管理者による自己復帰を防ぐ）
  IF auth.uid() IS NULL OR (is_active_user() AND is_admin()) THEN
    RETURN NEW;
  END IF;

  IF TG_OP = 'INSERT' THEN
    -- 明示指定があってもDEFAULTと同じ値に固定する（自己登録でのadmin/active指定を防止）
    NEW.role := 'member';
    NEW.status := 'pending';
  ELSE
    -- 一般ユーザーの更新では旧値を維持する（承認バイパス・権限昇格を防止）
    NEW.role := OLD.role;
    NEW.status := OLD.status;
  END IF;

  RETURN NEW;
END;
$$;
```

挙動を整理すると次のとおりです。

| 契機 | 挙動 |
| --- | --- |
| `BEFORE INSERT` | `role` を `'member'`、`status` を `'pending'` に固定する |
| `BEFORE UPDATE OF role, status` | `role` / `status` を更新前の値のまま維持する |

つまり、初回登録時に何を指定しようと強制的に「メンバー かつ 承認待ち」に上書きされ、更新時に権限を上げようとしても元の値に戻されます。

トリガーの登録は列指定（`UPDATE OF role, status`）にしています。

```sql
DROP TRIGGER IF EXISTS enforce_users_role_and_status ON users;
CREATE TRIGGER enforce_users_role_and_status
BEFORE INSERT OR UPDATE OF role, status ON users
FOR EACH ROW
EXECUTE FUNCTION enforce_users_role_and_status();
```

UPDATE文はSET句にないカラムを変更できないため、これで保護対象を取りこぼすことはありません。一方でプロフィール更新や `avatar_url` の更新では発火しないため、不要なヘルパー関数の評価を避けられます。

## 会議の様子

### AIレビューの「時差」に振り回される

プロフィール画像機能を担当しているメンバーから、思わぬ落とし穴の共有がありました。

GitHub Copilotのレビューには**タイムラグがある**、というものです。修正を反映した後にコメントが届くのですが、そのコメントは**修正前のコードに対するもの**でした。それに気づかないまま「指摘されたから直す」を繰り返していた結果、同じ内容の修正とレビュー依頼を何度も往復していたことが判明しました。

「何度も何度も同じことをやっていた」という本人の実感が、実際にそのとおりだったわけです。レビュアー側からも「一つひとつのコメントで対応を確認しているので、繰り返しが発生している状況に見えていた」という声があり、AI活用ならではの事象として共有されました。

### ローカル環境固有のエラーは追いかけない

解決できないエラーが出ていた件については、検証の結果**バージョン管理に含めていない設定をローカルに持っていたことが原因**と判明しました。担当者がクリーンな環境でセットアップし直し、他のメンバーと同じ状態で試したところ、事象は解消しています。

ローカルの環境を別フォルダに分離することで対処し、該当のプルリクエストは取り下げ、issueもクローズすることになりました。環境固有の問題をプロダクトのコードで解決しようとしない、という判断です。

### プルリクエストが勝手にプロジェクトに割り当てられる

「issueリストの一番左にある No Status は何か」という質問から、最近発生している現象の話になりました。

プルリクエストを作成すると、**自動的にプロジェクトが割り当てられてしまう**というものです。No Status に並んでいたのは、すべてプルリクエストでした。当面は各自でプロジェクトの割り当てを外して対応することになり、原因は「AIでプルリクエストまで作成すると起きるのではないか」と推測されています。

### リリース運用をめぐる議論

今回いちばん議論が深まったのが、リリースの進め方でした。

きっかけは「リリースが大がかりな作業になっているなら、承認が必要なプロセスを除いて、なるべく自動化を検討したほうがよいのでは」という提起です。ここから、開発と本番の間に**ステージング環境（検証用ブランチ）を設けるべきか**という論点に発展しました。

提案側の主張は明快でした。現状は開発環境がmainブランチ、本番環境がリリースブランチで管理されており、両者のデプロイ手順が厳密には同じではありません。本番にしかない・開発にしかないデータの差異によって、**本番リリース後に初めて問題が判明する**リスクがあります。その手前にもう一段、同じ手順で反映する検証環境を挟めば防げるのではないか、という考え方です。

これに対しては、**手間を増やすほどミスが発生しやすくなる**という反論が出ました。管理対象が増えることで、検証のために作ったものが逆に新たなミスを生む可能性のほうが高いのではないか、という指摘です。

議論の土台になったのは、開発に対する姿勢の違いでした。

> 開発はバグが出るのが前提、というスタイルのほうがよいと思っているし、おそらくそれが世界の主流。よほど銀行のようなガチガチのものでなければ。いかにバグを早く発見するかのほうが大事で、バグを絶対に起こさないようにという仕組みを作るのは避けたほうがいい。

提案側もこの前提には同意しつつ、「そうすると今度は**リリースの間隔が短いほうがよい**、という話になりますね」と切り返します。これは全面的に受け入れられました。実装が完了した機能があるなら期間を空けずにリリースしたほうが使い勝手の向上につながるし、逆に完了した機能がないなら慌てる必要もない、という整理です。

最終的に落ち着いたのは、**「この会議の中でリリース工程を開始して完了させてしまう」**という案でした。前回のリリースは初めてだったこともあり30分ほどかかりましたが、自動化を進めた今ならうまくやれば5分程度で終わるはずで、「サクッとできるように作ったのだから」ミーティング中に実施してみる価値はある、という結論に至っています。

ステージング環境の追加は見送り、代わりにリリース頻度を上げる方向で対処する、という着地でした。

## 活用した技術

### RLSは行単位、カラム単位は守れない

今回の修正の中心にあるのは、**RLS（Row Level Security）でできること・できないこと**の切り分けです。

RLSはその名のとおり「行」に対するアクセス制御です。「自分の行だけ更新できる」というポリシーは書けますが、「自分の行のうち `role` カラムだけは更新できない」とは書けません。ユーザーが自分のプロフィールを更新できる以上、同じUPDATE文で `role` を書き換える余地が残ります。

この隙間を埋めるのが `BEFORE` トリガーです。ポリシーで「その行を触ってよいか」を判定し、トリガーで「触ってよいカラムか」を強制する、という二段構えになっています。

なお、カラムに `DEFAULT` 制約を付ければよいのでは、という発想もありますが、これは機能しません。`DEFAULT` は**値が明示指定されなかった場合にのみ適用される**ため、クライアントが `insert({ role: 'admin', status: 'active' })` のように値を明示すれば素通りしてしまいます。値の明示指定を含めて固定するにはトリガーが必要です。

### `SECURITY DEFINER` とポリシーの再帰

`is_admin()` のようなヘルパー関数は `SECURITY DEFINER` で定義しています。これは `users` テーブル自身のポリシーから、内部で `users` を参照する関数を呼び出しても**無限再帰を起こさない**ようにするためです。

ただし、ドキュメントには重要な注意書きが追加されました。`SECURITY DEFINER` それ自体がRLSを無効化するわけではなく、関数の実行ユーザーが所有者に切り替わることで**結果的に**RLSを免除される仕組みです。したがって次の前提が必要になります。

* 関数の所有者が `users` の所有者と一致していること
* `users` に `FORCE ROW LEVEL SECURITY` が設定されていないこと

この前提が崩れると `42P17 infinite recursion detected in policy for relation "users"` が発生し、`users` へのSELECTが全面的に失敗します。前提の確認用に、次のクエリがドキュメントに記載されています。

```sql
SELECT p.proname,
       pg_get_userbyid(p.proowner) AS func_owner,
       pg_get_userbyid(c.relowner) AS table_owner,
       c.relforcerowsecurity
FROM pg_proc p
CROSS JOIN pg_class c
WHERE p.proname IN ('is_active_user', 'is_admin', 'is_content_manager')
  AND p.pronamespace = 'public'::regnamespace
  AND c.oid = 'public.users'::regclass;
```

### ポリシー内の関数呼び出しを `(SELECT ...)` で包む

新しいポリシーでは、関数呼び出しを `(SELECT is_active_user())` のようにサブクエリでラップしています。これはパフォーマンス上の工夫です。

相関のないスカラサブクエリは**InitPlan**として評価されるため、候補行ごとではなく**ステートメントあたり1回**の評価で済みます。判定結果は変わらないまま、行数に比例した関数呼び出しを避けられます。

### 適用順とポリシーのOR結合という落とし穴

マイグレーションの運用面でも、2つの注意点がドキュメント化されました。

1つは**適用順**です。トリガー関数は `is_active_user()` / `is_admin()` を参照するため、ディレクトリの番号順（`02_triggers` → `03_functions`）とは逆の依存関係になります。関数の作成自体は遅延解決のため成功しますが、関数が未定義のままトリガーが発火すると `function is_admin() does not exist` で失敗し、新規ユーザー登録と承認・否認が行えなくなります。

もう1つは**ポリシーのOR結合**です。旧定義が残る `00_users_policies.sql` を単独で再実行すると、permissiveポリシーはOR結合されるため、条件の緩い旧定義（全認証ユーザーへのSELECT許可・メタデータ依存の管理者判定）が復活し、**今回の修正が無効化されます**。

セキュリティ修正は「新しいポリシーを追加する」だけでは足りず、「古いポリシーを確実に消す」までがセットである、という教訓です。

## 総括

今回は、権限管理という開発の土台にあたる部分の見直しでした。

改ざん可能な場所（ユーザーメタデータ）を信頼の起点にしていた点、そしてRLSという仕組みの適用範囲を過大に見積もっていた点。どちらも「動いてはいる」がゆえに気づきにくい種類の問題で、司会からも「自分も見落としていたので勉強になった」という感想がありました。AIによる指摘がきっかけで発見できたケースでもあり、レビュー体制の一部としてAIが機能した回だったと言えます。

一方で、AIレビューのタイムラグに振り回されるという逆方向の事例もありました。ツールをどう使いこなすかは、まだ手探りの部分が残っています。

リリース運用の議論では、「検証を厚くする」か「リリース間隔を短くする」かという選択で、後者を選ぶ形になりました。次回はミーティング中にリリースを完了させる、という新しい試みが控えています。
