## 開発したもの

### SQLファイルの重複削除とポリシーのバグ修正

前回のver4リリース作業中に見つかった2つのバグを修正しました。1つ目は、まったく同じ内容のマイグレーションファイルが2箇所に存在していた問題で、重複ファイルを削除するだけのシンプルな対応です。

2つ目は、資料（documents）と動画（videos）の物理削除を禁止するRLSポリシーが、誤って `users` テーブルを対象に作成されていた問題です。

```sql
-- supabase/migrations/04_policies/documents_policies.sql（変更前）
-- documentsのポリシーなのに、対象テーブルがusersになっていた
DROP POLICY IF EXISTS "prevent_physical_delete_documents" ON "users";
CREATE POLICY "prevent_physical_delete_documents" ON "users"
  FOR DELETE
  USING (false);  -- 常にfalseを返すことで物理削除を防止
```

```sql
-- supabase/migrations/04_policies/documents_policies.sql（変更後）
-- 対象テーブルを正しくdocumentsに修正（videosも同様に修正）
DROP POLICY IF EXISTS "prevent_physical_delete_documents" ON "documents";
CREATE POLICY "prevent_physical_delete_documents" ON "documents"
  FOR DELETE
  USING (false);  -- 常にfalseを返すことで物理削除を防止
```

このクエリはどのテーブルに対しても実行できてしまうシンプルなものだったため、実行時にエラーが出ず、レビューでも見逃されていました。「エラーにならないバグ」ほど発見が難しいという、前回の振り返りを裏付ける修正となりました。

### READMEと環境構築手順書の全面刷新

新しいメンバーの参画をきっかけに、READMEと環境構築手順書（`docs/setup.md`）を全面的に書き直しました。

READMEは「シンラボ会員向けポータルサイトを、シンラボ内の希望者で開発している」というプロジェクトの位置づけを明確にし、主な機能・最新の技術スタック・ライセンス情報を整理しました。また、これまで記載のなかったディレクトリ構成を追加しています。

```text
portal-site/
├── app/                    # Next.js App Router
│   ├── (auth)/            # 認証関連ページ（ログイン、コールバックなど）
│   ├── (authenticated)/   # 認証済みユーザー向けページ
```

環境構築手順書は、もともとNext.jsプロジェクトを新規作成する一般的な手順が書かれていたため、「このチーム開発に参画するための手順」として作り直しました。事前準備（Node.js 20.x以上、Gitなどのインストール）、リポジトリのクローン、`.env.local` への環境変数設定、VS Codeの推奨設定、`npm run dev` / `npm run build` での動作確認、トラブルシューティングという流れです。

あわせて、ブランチ戦略や開発手順などWikiと重複していた記述は思い切って削除し、各ドキュメントへのリンクに差し替えました。刷新した手順書は見学中の新メンバーにも共有し、実際に環境構築を試してもらうことで実効性を検証していきます。

## 会議の様子

### 会員一覧に「タグ」を付ける — 作る機能と作らない機能

今回最も議論が盛り上がったのは、会員一覧ページの改善です。発端は「今の会員一覧では、代表や副代表といった主要メンバーが他の会員に埋もれてしまい、誰に相談すればよいのか分からない」という問題提起でした。

議論の中では、さまざまな選択肢が検討されました。

* 役割（ロール）で並び替えて上位に表示する案
* 役割を「タグ」として表示し、フィルターできるようにする案
* 「相談窓口一覧」のページやリンクを設ける案
* 体制図を掲載する案

このうち相談窓口については、「資料一覧にすでに窓口一覧の資料がある」「現状、会員の普段の居場所はSlackであり、ポータルサイトは資料を参照するときに訪れる場所。窓口機能を作っても使われないのでは」という利用実態を踏まえた意見が出て、**今回は作らない**という判断になりました。ポータルサイトのアクセス率が上がってきたら再検討します。

体制図の案に対しては、「個人名入りの体制図をオープンなリポジトリの固定コンテンツとして置くと、個人情報が公開されてしまう」というセキュリティ観点の指摘があり、こちらも見送りました。

最終的に採用されたのは**タグ機能**です。1人の会員が複数の役割を持つケースが多いことから、ユーザーテーブルにカラムを足すのではなく、**タグのマスターテーブルと、ユーザーとタグを紐づける管理テーブルを分けて持つ**設計案が有力になりました。まずは「代表」「副代表」「シンラボ管理者」「コンテンツ管理者」といった少数のタグから小さく始め、後から増減しやすい設計にする方針です。また、「設計段階で実際にクエリを投げて動くことを確認してから設計完了とする」という進め方も確認されました。

### ログイン画面の不安を「緊急パッチリリース」で解消する

前回、新メンバーから指摘のあった「Googleログイン時に `supabase.co` というドメインが表示されて不安になる」問題について、調査結果が共有されました。結論としては、**Supabaseの無料プランでは表示ドメインのカスタマイズはできない**ことが判明。そこで、ログイン画面に「アカウント選択画面にはこの表示が出ますが、シンラボポータルサイトです」という注意書きを添える対応を取ることになりました。

さらに、「実際に不安を感じている人がいる以上、次のメジャーリリースを待たずに反映すべきでは」という意見から、**緊急性の高い修正はver4.0.1のようなパッチバージョンとして通常のリリースサイクルとは別に緊急リリースする**という運用が新たに決まりました。リリース手順を文書化した直後に、その運用ルール自体が早速アップデートされた形です。

### レビュー運用の学び — Copilotの指摘とApproveの操作

進行中のユーザー承認機能の設計レビューでは、GitHub Copilotによる自動レビューとの付き合い方が話題になりました。担当メンバーの「Copilotの指摘は絶対ではないが、今後も同じ指摘が出そうな表現の揺れはこの機会に直しておく」というスタンスに対し、レビュアーからも「内容としては問題ないと判断している。細かい指摘をどこまで反映するかはお任せする」と、人間とAIのレビューを使い分ける運用が共有されました。

また、初めてレビューを担当したメンバーから「Approveのボタンが見つからない」という声があり、全員で画面を確認しながら、**Files changedタブの「Review changes」ボタンからApproveできる**ことを確認しました。あわせて、「レビュアーはApproveまでを担当し、Approve完了をSlackで共有したらリードがマージする」という役割分担も整理されました。ツールの操作ひとつでも、つまずきをその場で共有して全員の知識にしていくのがこのチームの進め方です。

このほか、開発中のJestテスト環境については「テストディレクトリは `app/` 配下ではなくルート直下に置く（`app/` はアプリ本体のコードのみにする）」という構成方針が示され、READMEのディレクトリ構成にも反映していくことになりました。

## 活用した技術

### PostgreSQLのRLSポリシーと「エラーにならないバグ」

Supabase（PostgreSQL）のRow Level Security（RLS）ポリシーは、`CREATE POLICY ... ON <テーブル名> FOR DELETE USING (false)` のように記述することで、特定テーブルへのDELETEクエリを常に拒否し、物理削除を防げます。

今回のバグは、この `ON` 句のテーブル名を誤っていたというものでした。ポリシー作成のSQL自体は「どのテーブルが対象でも」文法的に正しく実行できてしまうため、エラーは発生せず、**意図したテーブルが保護されていない**状態に気づけませんでした。DDL（テーブル定義やポリシーなどのSQL）はアプリのコードと違って動作確認で異常が表面化しにくいため、レビュー時に対象テーブル名まで目を配ることの大切さを学べる事例です。

### タグの多対多設計 — 中間テーブルによる正規化

「1人のユーザーが複数のタグを持ち、1つのタグが複数のユーザーに付く」という関係は、データベース設計における典型的な**多対多（Many-to-Many）**の関係です。ユーザーテーブルにカンマ区切りでタグを詰め込む方法もありますが、その場合は検索が `LIKE` による部分一致頼みになり、タグの追加・削除やタグ名変更にも弱くなります。

今回有力になった「タグのマスターテーブル＋ユーザーIDとタグIDを紐づける中間テーブル」という構成なら、既存のユーザーテーブルに手を入れずにタグを自由に増減でき、フィルター機能も素直なJOINで実現できます。設計段階で実際にクエリを動かして検証するというチームの合意は、この構成の実現可能性を早期に確かめるためのものです。

### ドキュメントの一元管理（Single Source of Truth）

READMEの刷新では、Wikiや他のドキュメントと重複する記述を削除し、リンクへの差し替えを徹底しました。同じ情報が複数の場所にあると、更新のたびにすべてを直す必要があり、やがて内容が食い違って「どちらが正しいのか分からない」状態に陥ります。情報の置き場所を1つに定めて他からは参照する、いわゆる**Single Source of Truth**の考え方です。

また、環境構築手順書のように「新しく参加する人が最初に読むドキュメント」は、書いた本人には正しさを検証しにくいものです。実際に新メンバーに手順どおり試してもらいフィードバックを得るのは、オンボーディングドキュメントの品質を上げる実践的な方法といえます。

## 総括

今回は、リリースで見つかったSQLバグの修正とドキュメントの全面刷新という「地味だが効く」開発に加えて、会議では会員タグ機能の設計方針を固めました。相談窓口や体制図といった案を利用実態やセキュリティの観点から「今は作らない」と判断し、タグ機能も最小構成から始める——機能を足すことよりも、何をどこまで作るかの見極めに時間を使った回だったといえます。

また、緊急パッチリリースの運用決定や、Copilotレビューとの付き合い方、Approve操作の共有など、開発を支えるプロセス面の改善も着実に積み上がっています。新メンバーの参画準備も整いつつあり、チームの新しい体制が楽しみです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
