## 概要

本記事は、[チーム開発記録51：Wiki運用ルールの整備](https://zenn.dev/singularitylabs/articles/f7dee4fdbb6e76)に続く最新の活動記録です。

シンギュラリティ・ラボのチーム開発では、コミュニティ向けポータルサイトの開発を進めています。今回は、**GitHub Actionsによる本番環境リリースの半自動化**が大きく前進しました。リリースPRの作成からタグ・GitHub Releaseの公開までを3つのワークフローで自動化し、承認ゲートや各種ガード条件で誤操作を防ぐ仕組みです。あわせて、フォークリポジトリ同期で発生した403エラーの修正や、Prettierによるフォーマットチェックの CI 追加も行われました。

会議では、マスターテーブル更新の設計を「単独のレビューで進めるか、会議体で合意を取るか」という進め方の議論や、代表・副代表を会員一覧に固定表示する機能の「テーブルを増やさない」設計判断、Supabase共有クエリの掃除、かんばんと会議スタイルの見直しなど、開発の中身と運用の両面で話し合いが行われました。次のバージョン8のリリースは**6月21日を目途**とすることも決まっています。

## 開発したもの

### 本番環境リリースを半自動化する3つのワークフロー

これまで手作業で行っていた本番環境リリース手順を、GitHub Actionsで半自動化しました。手動操作によるヒューマンエラーの削減と、誤実行を防ぐ承認ゲート・ガード条件の導入が目的です。事前に作成した設計書（`docs/ci-cd-design.md`）をベースに、次の3つのワークフローを実装しています。

1. **`release-pr.yml`** — 手動起動でバージョン番号を受け取り、mainブランチをreleaseブランチへマージするための「リリースPR」を作成する
2. **`fork-sync.yml`** — releaseへのPRマージ後、フォークリポジトリのreleaseブランチを同期する
3. **`create-release.yml`** — releaseへのPRマージ後、承認ゲートを経てGitタグとGitHub Releaseを作成する

リリースPRの作成前には、`build` / `type-check` / `lint` / `test` / `lint:logs` の5種類の品質チェックがmatrixで並列実行されます。1つが失敗しても他のチェックは止めず、**リリース前にすべての問題を一度に把握できる**構成です。

```yaml
# .github/workflows/release-pr.yml（抜粋）
  # main ブランチに対する品質ゲート。失敗時は PR を作成しない
  quality-checks:
    name: 品質チェック (${{ matrix.task }})
    runs-on: ubuntu-latest
    needs: validate-input
    strategy:
      # fail-fast: false → 1 つのチェックが失敗しても他のチェックは継続実行する
      fail-fast: false
      matrix:
        task: [build, type-check, lint, test, lint:logs]
```

さらにリリースPRの本文には、release..main間の差分から**マイグレーションファイルと新規環境変数を自動検出した結果**と、マージ前チェックリストが記載されます。「本番のSupabaseにマイグレーションを適用したか」「本番環境に環境変数を登録したか」といった、忘れると事故につながる事前作業を機械的に洗い出す仕組みです。

タグとGitHub Releaseを作成する `create-release.yml` には、5種類のガード条件（マージ済みか／PRタイトルが「リリース」で始まるか／バージョンが `X.Y.Z` 形式か／タグが重複していないか／Environmentの承認）を実装しました。

```yaml
# .github/workflows/create-release.yml（抜粋）
  validate:
    name: ガード条件チェック
    runs-on: ubuntu-latest
    # マージ済みチェック: pull_request トリガーではマージされた場合のみ実行
    if: ${{ github.event_name == 'workflow_dispatch' || github.event.pull_request.merged == true }}

  # ...（中略）...

  # 承認ゲート付きのリリースジョブ。Environment の Required reviewers で承認待ちになる
  release:
    name: タグ作成と GitHub Release 公開
    runs-on: ubuntu-latest
    needs: validate
    # GitHub Environments 側で Required reviewers を設定することで承認ゲートとして機能する
    environment:
      name: production-release
```

「自動化」ではなく「**半自動化**」なのは、この承認ゲートがあるためです。すべてのチェックを通過しても、`production-release` Environmentに登録された承認者がGitHub上で承認するまでリリースジョブは実行されません。あわせて `.env.example` を新規作成してGit管理対象に加え、環境構築手順書（`docs/setup.md`）も「`.env.example` をコピーして各値を差し替える」手順に更新しました。

定例では「プルリクエストのレビューとマージまで完了し、できる範囲での実行確認は終わった。ただし念のため、実際の本番リリースで正常に動くことを確認してからIssueをクローズする」という状況が共有されました。

### fork-syncの403エラーを`persist-credentials: false`で修正

マージ後に `fork-sync.yml` を手動実行したところ、フォークリポジトリへのpushが**403エラー（権限拒否）**で失敗する問題が見つかり、追加のPRで修正しました。

原因は `actions/checkout` の既定動作にあります。checkoutは既定で `GITHUB_TOKEN`（`github-actions[bot]`）の認証情報をgit設定に永続化し、これが後から追加したフォーク用リモートURLに埋め込んだ専用トークンよりも**優先されてしまう**ため、書き込み権限のないbotの権限でpushが実行されていました。

```yaml
# .github/workflows/fork-sync.yml（抜粋・変更後）
      - name: Checkout release branch
        uses: actions/checkout@v4
        with:
          ref: release
          fetch-depth: 0
          # 既定では checkout が GITHUB_TOKEN（github-actions[bot]）を
          # http.extraheader として全 github.com URL に永続化する。これは fork remote URL に
          # 埋め込んだ FORK_SYNC_TOKEN より優先されるため、push が github-actions[bot] 権限で
          # 実行されフォークへの書き込みが 403 で拒否される。これを防ぐため認証情報を永続化しない。
          persist-credentials: false
```

`persist-credentials: false` を1行追加するだけの修正ですが、原因調査の過程をコメントとして残すことで、同じ落とし穴を踏むメンバーが出ないよう配慮しています。

### Prettierフォーマットチェックの GitHub Actions 追加

コード整形の統一性をCIで担保するため、`npm run format:check`（Prettier）を自動実行するワークフローも追加しました。定例の時点では「指摘の修正を行って確認してもらっている段階」でしたが、その後マージされています。

```yaml
# .github/workflows/format-check.yml（抜粋）
name: Format Check

on:
  push:
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

# ...（中略）...

      - name: Run Prettier format check
        run: npm run format:check
```

導入にあたっては、CIの初回失敗を避けるため、既存のフォーマット崩れ（Markdownテーブルの整列など）を事前に `npm run format` で整形しています。あわせて、コミット前に `npm run format:check` を実行する旨をドキュメントにも追記する対応が進められました。このほか、DB型定義のチェックをGitHub Actionsに組み込む対応もマージ済みPRとして共有されています。

## 会議の様子

### レビューか、会議体での合意か — マスターテーブル更新の進め方

マスターテーブルの更新に取り組む担当メンバーから、「設計書はほぼAIに作らせたものをプルリクエストとして出している」という進捗とともに、進め方についての提案がありました。**「この件はもともと概要がふわっとしていて詳細設計の自由度が大きく、影響範囲も大きい。単独のレビューで進めるより、この会議体で話して全体の合意を取りたい」**というものです。

これに対してリードは、レビュー運用との整理を行いました。「レビュアーがいるのに他の人も細かくコメントすると非生産的すぎる。ただし**設計に関しては、誰でも関係なく意見してもらってよい**」という切り分けです。結論として、来週の定例で担当メンバーが背景とやろうとしていることを解説し、その場で方針の合意を取ることになりました。興味のあるメンバーは、それまでにIssueに上がっているやりかけの設計書に目を通しておきます。

関連して、設計図ツールdraw.ioの代替検討では、「HTMLで書いたモックをPlaywright（ブラウザ自動操作ツール）で画面キャプチャしてPNG画像にし、機能設計書に埋め込む」というアイデアが共有されました。こちらもやり方とメリット・デメリットをIssueに整理したうえで、定例で擦り合わせる方針です。

### テーブルは増やさない — 代表・副代表の固定表示設計

会員一覧に代表・副代表・管理人を固定表示する機能では、設計レビューのコメントを受けて方向性の議論が行われました。担当メンバーがAIを使って設計したところ、既存の `positions`（役職）テーブルとは別に `positions_2` という**新しいテーブルを作る案**が出てきたため、「元のテーブルと被らない方がよいと考えたが、これでよいのか」という相談です。

議論の結果、「代表や副代表も『チームリーダー』などと同じ役職であり、**既存のpositionsテーブルに同列で追加すればよい。新しいテーブルはいらない**」という結論になりました。リードからは「**基本的にテーブルは増やさないのが開発の基本方針**」であることも改めて確認されています。

担当メンバーからは「自分で代表などを選べるようになってしまうが、偉い方々の役職を自由にいじれてよいのか」という懸念も出ましたが、「副代表じゃないのにチェックしたところで誰も信じないだけ」として許容する判断に。あわせて「プルリクエストではできるだけ余計なことをしないのが正解。色々作り出すとコードのレビュー負担が増えるので、今回は固定表示というIssueのスコープに注力する」という進め方の指針も共有されました。最終的に、positionsテーブルに8・9・10番として代表・副代表・管理人を追加し、一覧の上位に表示する方針で修正を進めます。

### SQLは残さない — 共有クエリの掃除と足回りの棚卸し

Supabaseの開発用ダッシュボードに残っていた共有SQLクエリの掃除も、この場で完了しました。共有クエリは**作成した本人しか削除できない**仕様のため、作成したメンバーに会議中にその場で削除してもらい、Issueをクローズしています。今後は「**SQL文は基本的に残さず、一時的に確認したいときだけ残す**」という運用です。

インフラ・CI周りでは、新しいIssueが2件起票されました。1つはGitHub Actionsの権限を最小権限に設定する対応、もう1つは**Node.jsのバージョンアップ**です。現在使用しているNode.js 20は9月にサポートが切れる見込みのため、優先度「高」で対応することになりました。リリース自動化が整った直後に、その土台となるランタイムや権限の棚卸しにも手を付ける流れです。

### かんばん整理と会議スタイルの見直し — ver8は6月21日目途

次のバージョン8のリリースは**6月21日を目途**とすることが決まりました。また来週からは、新しく開発を始めた学習支援アプリ「sinlab-study」とポータルサイトの開発を**交互に行うスタイル**を試すことになっています。

タスク管理では、かんばんを「バックログ・レディ・進行中・レビュー中・完了」に分け、設計フェーズから細かく管理していく案が共有されました。一方でリードからは「タスクの進め方が色々同時になりすぎではないか。進んでいなければ減らすことも検討しよう」という指摘があり、担当メンバーは「1個1個、Issueを形にするのに注力する」と応えています。

会議の進め方自体も見直されました。議題ごとに毎回「何か気になることはありますか？」と確認するのはテンポを損なうため、**気になった人が横から口を挟んでよいスタイル**に変更しています。また、sinlab-studyなどのサービスへの動線となる新しいリンクページを次のリリースまでに作る計画に対し、**初めてレビューに挑戦するメンバーが立候補**しました。「本を借りて勉強してくる」という意気込みに、経験者からは「実装が揃っているか、セキュリティ上の問題がないか、設計方針に従っているかという観点で見るとよい」というアドバイスが送られています。

## 活用した技術

### GitHub Environmentsによる承認ゲート

GitHub Actionsの**Environments**は、ジョブの実行先環境を定義し、保護ルールを設定できる機能です。Environmentに**Required reviewers**（必須承認者）を設定すると、そのEnvironmentを参照するジョブは、指定された承認者がGitHub上で承認するまで実行が保留されます。

今回のリリース自動化では、タグ作成とGitHub Release公開を行うジョブに `production-release` というEnvironmentを割り当てました。これにより、品質チェックやガード条件をすべて通過しても、**最後は人間の承認がなければ本番リリースが実行されない**という「半自動化」を実現しています。なお、Required reviewersが未設定だと承認ゲートは機能せずジョブが自動で進んでしまうため、設定手順や注意点は設計書に明文化しました。全自動化ではなく要所に人の判断を残す構成は、小規模チームの本番運用における現実的な落としどころといえます。

### actions/checkoutの`persist-credentials`と認証の優先順位

`actions/checkout` は既定（`persist-credentials: true`）で、ワークフロー用の `GITHUB_TOKEN` をgitの `http.extraheader` 設定として書き込み、これが**github.comホスト全体への通信に適用**されます。便利な仕様ですが、今回のfork-syncのように「別のトークンで別リポジトリへpushしたい」場合には罠になります。リモートURLに埋め込んだ認証情報よりextraheaderのAuthorizationヘッダーが優先されるため、意図しないトークンでpushが実行されてしまうのです。

対策は、checkout時に `persist-credentials: false` を指定して認証情報を永続化しないこと。エラーメッセージは単なる「403 Permission denied」でも、原因はトークンの権限不足ではなく**どのトークンが使われているか**にある、という切り分けが学べる事例でした。

### `.env.example`による環境変数のカタログ化

`.env.example` は、アプリが必要とする環境変数のキーを**ダミー値と説明コメント付きで列挙したサンプルファイル**です。実際の秘密情報を含む `.env.local` はGit管理から除外しつつ、`.env.example` だけは例外的にコミット対象とすることで、「このプロジェクトにどんな環境変数が必要か」をリポジトリ自体がカタログとして持てます。新規メンバーは `cp .env.example .env.local` で雛形を作り、値を差し替えるだけで環境構築ができます。

今回の導入では、もう1つの狙いがあります。リリースPR作成ワークフローが**releaseブランチとmainブランチの `.env.example` を比較し、新規追加された環境変数を自動検出**する仕組みです。「コードは本番に反映されたが環境変数の登録を忘れていた」という典型的なリリース事故を、ファイル1つの運用ルールとCIの組み合わせで防いでいます。

## 総括

今回は、本番環境リリースの半自動化という大きな仕組みが完成した回でした。品質チェック・事前作業の自動検出・承認ゲート・ガード条件と、リリースにまつわる「うっかり」を何重にも防ぐ構成は、これからのリリース運用の土台になります。マージ後に見つかった403エラーも、原因をコメントとして残しながら素早く修正されました。

会議では、影響範囲の大きい設計は会議体で合意を取る、テーブルは増やさない、PRでは余計なことをしない、SQLは残さないといった、チームとしての判断基準が言葉になって積み上がっていきました。かんばんの整理や会議スタイルの変更、初レビューへの立候補など、体制面の新陳代謝も進んでいます。6月21日を目途とするver8リリースと、sinlab-studyとの交互開発という新しいリズムが楽しみです。

シンギュラリティ・ラボのチーム開発では、こうした実践的な開発経験を通じてスキルアップしたい仲間を募集しています。興味のある方はぜひご参加ください。
