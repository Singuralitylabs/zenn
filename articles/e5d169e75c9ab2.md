## 開発したもの

### メンテナー権限の追加

これまでコンテンツ（資料・動画）の新規登録・編集・削除は管理者（admin）のみに許可されていましたが、管理者だけだと制約が強すぎて権限を段階的に委譲できないため、新たに**メンテナー（maintainer）** というロールを追加しました。

権限判定はユーティリティ関数として共通化し、ページなど上位の層で一度だけ判定する設計です。

```typescript
// app/services/auth/permissions.ts
// ユーザーがコンテンツの管理対象か確認
export function checkContentPermissions(role: string): boolean {
  return role === "admin" || role === "maintainer";
}
```

ページコンポーネント側では、ロール文字列をそのまま下位に渡すのではなく、判定結果のフラグ（`isContentMgr`）だけをコンポーネントに渡すようにしました。

```typescript
// app/(authenticated)/documents/page.tsx
return (
  <DocumentsPageTemplate
    documents={data}
    categories={dataCategory}
    isContentMgr={checkContentPermissions(role)}
    userId={id}
  />
);
```

カードコンポーネントなどの末端では、フラグを見て編集・削除ボタンの表示を切り替えるだけになります。

```typescript
{isContentMgr && (
  <Group m="0 1rem 1rem" gap="xs">
    <Button color="blue" onClick={() => onEdit(document)}>
      編集
    </Button>
    <Button color="red" onClick={() => onDelete(document.id)}>
      削除
    </Button>
  </Group>
)}
```

あわせて、データベース側でもRLSポリシーを拡充しました。資料・動画テーブルの作成・更新ポリシーは、管理者またはメンテナー権限を持つアクティブなユーザーのみに許可されます。

```sql
EXISTS (
    SELECT 1 FROM users
    WHERE
    auth_id = auth.uid()
    AND role IN ('admin', 'maintainer')
    AND status = 'active'
    AND is_deleted = FALSE
)
```

usersテーブルの設計書も更新し、`role` カラムの想定値を `member, maintainer, admin` の3段階としました。

### 自動フォーマッター設定の追加

前回の定例で「メンバー間でコードフォーマットの結果が異なる」問題が挙がっていましたが、原因の1つが `.prettierrc` の設定ミスでした。`doubleQuote` という存在しないオプションが指定されていたため、正しい `singleQuote: false` に修正しました。

```json
{
  "semi": true,
  "trailingComma": "es5",
  "singleQuote": false,
  "printWidth": 100,
  "tabWidth": 2,
  "useTabs": false
}
```

さらに、エディタ設定の個人差をなくすため、VSCodeのワークスペース設定をリポジトリに追加しました。これにより、リポジトリを開くだけで保存時の自動フォーマットとESLint自動修正が全員に適用されます。

```json
// .vscode/settings.json
{
    "editor.defaultFormatter": "esbenp.prettier-vscode",
    "editor.formatOnSave": true,
    "editor.codeActionsOnSave": {
        "source.fixAll.eslint": "explicit"
    }
}
```

各メンバーには、ローカルの設定ファイルがリモートと一致しているか、VSCodeの拡張機能（Prettier・ESLint）がインストールされているかの確認を依頼しました。

### メンバー一覧ページの機能仕様策定

開発に先立ち、機能仕様書にメンバー一覧ページの仕様を追加しました。主な仕様は以下のとおりです。

- サイドバーに「メンバー一覧」メニューを追加し、`/members` に遷移
- カード形式・1行3カードのグリッドレイアウト（レスポンシブ対応）
- 表示対象は承認済み（`status='active'`）かつ論理削除されていないメンバー
- 各カードにプロフィール画像・名前・自己紹介を表示

設計書の修正と確認は完了しており、現在は実装を進めています。

### メンバー一覧ページのデザイン議論

カード形式でプロフィール画像・名前・役割・自己紹介文を載せる設計案に対し、「管理者」「コンテンツ管理者」といったロールを表示すると**新規会員が混乱するのではないか**という意見が出ました。相談の結果、まずはロールを表示せず、名前順に並べるシンプルな形から始めることになりました。

プロフィール画像については、Googleアカウントからの取得が難しいため、将来的に自分でアップロードして差し替えられる機能を検討します。画像データの保存方法としては、Base64エンコードで直接保存する案とSupabase Storageを使う案が挙がっています。

### 型定義の設計方針

メンバーから「フロントエンドとバックエンド（DB）で型を分けるべきか」という、クリーンアーキテクチャの考え方に基づく提案がありました。レイヤーごとに型を分離すれば、DB構造の変更がフロントに直接波及しなくなるメリットがあります。

一方で、本プロジェクトは規模がシンプルでSupabaseを直接利用しているため、**型を共通化した方が実装しやすい**という結論になり、DBの型をそのまま利用する方針で進めることになりました。プロジェクトの規模に応じて設計の複雑さを選ぶ、現実的な判断です。

### 新規タスク：初回ログイン時のSlack通知

ポータルサイトは初回ログイン時に管理者の承認が必要ですが、現在は通知の仕組みがなく、テーブルを直接確認しないと承認待ちユーザーに気づけません。そこで、ユーザーテーブルにインサートが走った際にWebhookを使ってSlackに通知するプログラムを作ることになりました。

「承認待ち画面に『連絡をください』と表示する」案もありましたが、ユーザーに負担をかけたくないため自動化する方向で進めます。ver4リリースに間に合わせる予定です。

### 検証環境の管理

検証用のSupabaseプロジェクトが停止していた件も話題になりました。Supabaseの無料プランは**1週間アクセスがないとプロジェクトが一時停止し、90日間放置すると削除される**仕様のため、無料枠（2プロジェクトまで）の制約とあわせて、アカウント情報をチームで共有して管理することになりました。

## 活用した技術

### SupabaseのRLS：USINGとWITH CHECKの違い

会議では、RLSポリシーで使う `USING` と `WITH CHECK` の違いについて解説がありました。

- **USING**: 操作の対象となる**既存の行**に対する条件。SELECTやUPDATE・DELETEの対象行の絞り込みに使う
- **WITH CHECK**: 操作の**結果として書き込まれる行**に対する条件。INSERTやUPDATE後のデータが条件を満たすかをチェックする

INSERT文の場合は「何もないところ」に事前チェックはできないため、追加されたデータが条件を満たしているかを検証する `WITH CHECK` を使います。SELECT文は既にあるデータを見るだけなので `USING` を使う、という使い分けです。

### ロールベースアクセス制御（RBAC）の段階設計

今回のメンテナー権限の追加は、ロールベースアクセス制御（RBAC）の実践です。ポイントは、アクセス制御を**フロントエンドとデータベースの2層で実施している**ことです。

- フロントエンド: `checkContentPermissions()` でボタンの表示・非表示を制御（UX目的）
- データベース: RLSポリシーで実際の書き込みを制御（セキュリティ目的）

フロントの制御は画面表示の利便性のためであり、本質的な防御はRLSが担います。仮にAPIを直接叩かれても、データベース層で権限のない操作は拒否されます。

### VSCodeワークスペース設定の共有

`.vscode/settings.json` をリポジトリにコミットすると、そのフォルダを開いた全員に同じエディタ設定が適用されます。個人のユーザー設定より優先されるため、「保存時の自動フォーマットが人によって効いたり効かなかったりする」というチーム開発あるあるの問題を仕組みで解決できます。フォーマッターの設定ファイル（`.prettierrc`）とエディタ設定のセットでの共有が効果的です。
